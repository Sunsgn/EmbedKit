# AI 辅助嵌入式产品开发通用指南

- 文档版本：V1.0
- 总结日期：2026-11-12
- 适用范围：MCU、无线模组、传感器、家电控制器、IoT 终端等软硬件一体化产品
- 经验来源：智能油烟机 F20/BS20 项目的固件、协议、构建、测试工具和开发记录

## 1. 文档目的

本文给出一套让 AI 真正参与嵌入式产品开发、同时保持工程可控和结果可验证的方法。它不是某一芯片或某一产品的代码规范，而是覆盖需求、硬件、固件、通信、测试、升级、生产和维护的通用工作流。

核心观点：AI 适合加速资料整理、代码检索、方案比较、样板代码、测试工具、日志分析和文档追溯；产品负责人仍须掌握需求裁决、硬件安全、实时性、资源预算、实机验证、生产参数和发布批准。

一个 AI 开发任务只有形成以下闭环，才算交付：

```text
需求与约束
    ↓
事实盘点 → 影响分析 → 最小设计 → 实现
    ↑                         ↓
历史记录 ← 故障证据 ← 分层验证 ← 构建产物
                         ↓
                  版本发布与现场反馈
```

## 2. 从本项目提炼出的关键经验

### 2.1 先建立“可恢复工程”，再追求开发速度

嵌入式工程经常只能在某台电脑编译。F20/BS20 项目把 Python、CMake、Ninja、私有编译器和构建脚本收口为统一入口，并将构建支持与测试工具分离。这说明 AI 接手项目前，第一优先级应是确认：

- 仓库根目录、SDK 根目录和默认目标；
- 唯一、可重复的构建命令；
- 工具链版本、来源、哈希和离线恢复方式；
- 构建产物目录以及哪些文件不得提交；
- 量产固件、测试固件、application-only 固件的边界。

如果构建环境不可恢复，AI 生成再多代码也不能形成稳定交付。

### 2.2 通信必须由状态机和所有权驱动

项目同时包含 Modbus、UART AT、TCP、SLE 和云端协议。实践中暴露出的半包、粘包、异步下行、断网重连、ACK 超时和多来源控制问题，不能靠增加延时或全局布尔变量根治。

通用原则是：

- 一个物理接口只能有一个明确所有者；
- ISR/回调只采集和投递，业务任务负责解析与执行；
- 同步设备协议封装在拥有该链路的任务内部；
- 跨模块调用使用有限长队列、事件或事务接口；
- 每个事务包含来源、标识、状态、超时、重试和最终结果；
- “成功入队”“已发出”“收到 ACK”“业务执行成功”是四个不同状态。

本项目形成的典型控制方向可抽象为：

```text
云端 / 无线 / 本地按键
          ↓ 解析、校验、标记来源
      业务控制器
          ↓ 有界事务
      设备总线任务
          ↓
   响应匹配 / 状态核验
          ↓
    异步结果与状态上报
```

### 2.3 编译成功只是最低等级证据

项目记录中多次清楚区分“构建通过”和“尚未下载实机”。这应成为所有 AI 项目的强制表达方式。

| 证据等级 | 名称 | 可证明的内容 | 不能证明的内容 |
| --- | --- | --- | --- |
| E0 | 静态证据 | 代码结构、引用、配置和基本边界合理 | 能编译、能运行 |
| E1 | 构建证据 | 指定目标完成编译、链接、签名或打包 | 外设、时序和业务正确 |
| E2 | 主机/模拟证据 | 解析器、算法、工具和协议样例通过 | 真实驱动、电气和射频行为 |
| E3 | 台架/实机证据 | 真实板卡关键路径和故障路径通过 | 长期稳定、批量一致性 |
| E4 | 系统/现场证据 | 云端、网络、整机和长稳场景通过 | 批量生产良率和全生命周期可靠性 |
| E5 | 生产/发布证据 | 受控版本、工装、追溯和抽检通过 | 未覆盖的新环境和未来变更 |

报告必须写明实际达到的等级，禁止用 E1 的结果宣称 E3 已完成。

### 2.4 日志要能回答问题，而不是越多越好

项目将 MC661/AT 日志和业务日志分流，并通过现场日志定位到 UART 半包间隔、I2C 时钟未开启和 OTA 内存申请失败。有效日志应包含：

- 模块、状态、事务号和错误码；
- 关键长度、偏移、剩余量、重试次数和耗时；
- 状态变化，而不是高频重复状态；
- 帧内容应脱敏、限长，并由调试开关控制；
- 生产固件中的日志量、时序影响和敏感信息必须受控。

### 2.5 资源预算是功能设计的一部分

嵌入式功能不能只看逻辑。项目曾通过把 OTA 旧镜像校验缓冲从 4 KiB 改为 256 B 分块，解决运行时内存申请失败；也持续记录 Flash、ITCM 和 DTCM 占用。

每项功能开始前应预算：

- Flash 增量和升级分区余量；
- 静态 RAM、峰值堆、DMA 缓冲和协议缓冲；
- 任务数、栈大小、队列长度和定时器；
- UART、I2C、SPI、GPIO、ADC、PWM、DMA 和中断；
- 峰值电流、平均功耗和唤醒源；
- 最坏执行时间、总线占用和看门狗窗口。

### 2.6 AI 必须保存“为什么改”的上下文

开发记录让后续 AI 能知道某个延时、开关、缓存或任务边界来自什么现场现象，避免重复试错。每次重要变更至少记录：目标、依据、涉及文件、根因、实现、验证、未验证项、风险和回退方式。

## 3. AI 与人的职责边界

| 工作 | AI 可主导 | 人必须确认或执行 |
| --- | --- | --- |
| 仓库盘点、调用链和依赖分析 | 是 | 对业务事实纠偏 |
| 协议文档转结构表、解析器和测试向量 | 是 | 确认协议版本和歧义 |
| 重复代码、边界检查、静态问题发现 | 是 | 审核实时性与安全影响 |
| 构建脚本、模拟器、日志分析工具 | 是 | 提供合法环境和真实设备 |
| GPIO、时钟、分区、功耗方案建议 | 辅助 | 审核原理图、数据手册和实测结果 |
| 烧录、复位、射频、功耗和故障注入 | 辅助自动化 | 连接设备并确认安全范围 |
| 密钥、证书、唯一标识和生产参数 | 不应接触明文 | 受控系统管理和授权 |
| 量产放行、认证结论、OTA 发布 | 不可自行批准 | 产品责任人签字批准 |

AI 不得伪造示波器、电流、射频、实机日志、认证、签名、生产良率或用户验收结论。缺少硬件时应产出“待实机验证清单”，而不是填补想象中的结果。

## 4. 项目知识底座

### 4.1 最小目录

已有 SDK 不应为了套模板而拆散。新项目可从以下最小结构开始，并按需扩展：

```text
project/
├─ README.md                 # 项目入口、构建与最小验证
├─ AGENTS.md                 # AI平台自动发现入口
├─ CLAUDE.md                 # AI平台自动发现入口
├─ .ai/
│  ├─ 项目目录框架.md        # 通用目录、安全与验证规范
│  ├─ PROJECT_PROFILE.md     # 当前项目事实与未知项
│  ├─ AGENTS.template.md     # 安全的平台入口模板
│  └─ 工程规则/              # 项目专属编码、构建和调试约束
├─ program/                  # SDK、产品源码、构建入口
├─ 开发文档/
│  ├─ 需求规格/
│  ├─ 通信协议/
│  ├─ 技术文档/
│  └─ 开发记录/
├─ 硬件原理图PCB/
└─ 测试/
   ├─ 工具/
   ├─ 测试用例/
   └─ 测试报告/
```

发布、生产、认证和归档目录只在真实进入对应阶段时创建。工作主文件保持单一权威来源，发布目录保存不可编辑的冻结快照及其哈希。

### 4.2 AI 读取顺序

每次任务按以下顺序读取，避免只盯着用户提到的单个文件：

1. 平台和项目安全规则；
2. 本次任务、授权范围和验收标准；
3. 项目档案、README、构建说明和工程约束；
4. 需求、协议、原理图网络名或芯片资料；
5. 当前实现、调用链和编译配置；
6. 同模块历史记录、提交和真实运行日志；
7. Git 工作区，识别并保护用户未完成的修改。

### 4.3 项目事实表

建议维护以下事实，未知项明确写“待确认”：

| 类别 | 必填事实 |
| --- | --- |
| 产品 | 型号、硬件版本、软件版本、当前阶段 |
| 芯片 | MCU/SoC、频率、Flash、RAM、启动方式 |
| 工具链 | OS、编译器、SDK、构建工具及版本 |
| 构建 | 默认目标、命令、产物、清理方式 |
| 硬件 | 外设分配、电平、时钟、复位和电源域 |
| 存储 | 分区、NV、校准区、唯一标识、升级区 |
| 通信 | 接口、协议版本、角色、波特率/频段 |
| 实时性 | 周期、超时、优先级、最坏响应时间 |
| 功耗 | 模式、唤醒源、禁止睡眠场景 |
| 安全 | 安全功能、密钥边界、升级和回滚策略 |
| 测试 | 主机、台架、HIL、系统和生产测试入口 |

## 5. 端到端开发流程

### 阶段 A：任务定义与基线冻结

先写一张任务卡，不直接改代码。

```markdown
## 任务卡
- 目标：
- 明确不做：
- 输入与输出：
- 协议/数据手册版本：
- 运行上下文：任务 / ISR / 回调：
- 资源所有者：
- 成功标准：
- 失败和降级策略：
- 受影响模块：
- 需要的证据等级：E0-E5
- 回退方式：
```

基线检查至少包括：工作区状态、当前可构建目标、现有测试结果、资源占用和已知问题。若基线本身失败，应先记录失败，不能把既有问题归因于新修改。

### 阶段 B：需求与风险拆解

把自然语言需求转换成可验证条目：

- 正常路径：触发、状态变化、输出和完成条件；
- 边界条件：最小/最大长度、数值、频率和并发数；
- 异常路径：超时、断电、断网、CRC 错、队列满和资源不足；
- 兼容性：旧设备、旧数据、旧协议和降级；
- 安全性：本地安全功能是否被网络、升级或日志阻塞；
- 可观测性：如何判断当前状态和最近失败原因。

对高风险功能使用简化 FMEA：

| 失效模式 | 原因 | 后果 | 检测方式 | 防护/恢复 | 风险等级 |
| --- | --- | --- | --- | --- | --- |
| 示例：通信任务永久等待 | 丢失 ACK | 控制链路阻塞 | 超时计数与看门狗 | 有界超时、释放事务 | 高 |

### 阶段 C：架构与资源设计

设计时至少画出任务、接口和数据流，明确谁拥有状态。

```text
硬件驱动层：寄存器、GPIO、UART、I2C、Flash
      ↑ 统一驱动接口
设备服务层：总线任务、无线任务、存储、升级、时间
      ↑ 队列 / 事件 / 事务
业务层：状态机、策略、联动、告警、数据模型
      ↑
外部接口层：云端协议、调试接口、生产工装
```

设计审查问题：

- 外设和共享状态是否只有一个所有者？
- 回调中是否存在阻塞、动态内存或长耗时日志？
- 队列是否有限长，满时如何处理？
- 重试是否有次数、间隔、退避和最终失败状态？
- 关闭功能开关时是否真正不占任务和外设？
- 本地安全控制是否始终高于云端、日志和升级？
- 资源预算是否包含最坏情况而非平均情况？

### 阶段 D：增量实现

实现遵循“小步、单一目的、随时可回退”：

1. 先补协议常量、数据结构和纯函数；
2. 为纯函数建立主机测试或测试向量；
3. 接入任务间接口和状态机；
4. 最后接驱动、启动入口和产品配置；
5. 每一步编译并记录资源变化；
6. 调试代码必须有开关，结束后清理临时入口。

AI 修改代码时应优先复用项目现有抽象，不因局部需求复制整套收发流程，也不在驱动层嵌入产品业务。

### 阶段 E：分层验证

测试金字塔适用于嵌入式，但需要增加硬件层：

```text
          系统/现场/E2E        少量，真实网络与整机
        HIL/台架/故障注入       关键接口和时序
      集成测试/协议模拟器        模块协作和状态机
    单元测试/静态检查/构建       大量、快速、可重复
```

推荐门禁：

| 层级 | 必测内容 | 典型证据 |
| --- | --- | --- |
| 静态 | 边界、类型、危险 API、配置和引用 | 检查输出、diff |
| 构建 | 默认/功能开关配置、链接和资源 | 构建日志、map |
| 单元 | CRC、编解码、长度、状态转换 | 用例数量和结果 |
| 集成 | 半包、粘包、超时、重试、队列满 | 模拟器日志 |
| 实机 | 外设、复位、启动、通信和升级 | 串口、仪器、版本 |
| 长稳 | 断网、反复上电、老化、内存和看门狗 | 持续时间和统计 |
| 生产 | 烧录、校准、唯一标识、抽检 | 工单和追溯记录 |

### 阶段 F：发布与反馈

正式制品至少记录：

- 产品、硬件版本、固件版本和 Git 提交；
- 构建目标、配置、工具链和构建时间；
- 文件名、类型、长度和 SHA-256；
- 分区和烧录范围；
- 升级基线、签名状态和回滚条件；
- 测试报告、已知问题和批准人；
- 生产参数与应用固件的边界。

现场问题回流时，先保存原始日志、设备版本、时间线和复现条件，再分析和修改。不得用新日志覆盖唯一的原始证据。

## 6. 重点领域方法

### 6.1 驱动与硬件联调

AI 在改驱动前必须核对原理图、芯片手册、SDK 端口层和现有板级初始化。重点检查：

- 管脚复用、电气方向、上下拉和有效电平；
- 外设时钟和电源域是否已开启；
- 初始化顺序、复位时序和稳定时间；
- 中断优先级、清标志顺序和并发访问；
- DMA 缓冲生命周期和 Cache 一致性；
- 板型差异是否通过配置表达。

F20/BS20 的 I2C 启动异常说明：寄存器地址异常不能只看崩溃函数，还应向上追到时钟门控、配置宏和 SDK 驱动条件分支。

### 6.2 串口、网络和无线协议

接收路径建议分层：

```text
ISR/DMA 收字节
  → 环形缓冲
  → 传输层拆包（静默时间/长度/帧界）
  → 帧头、长度、CRC、版本校验
  → 命令与字段解析
  → 业务队列
  → 异步结果
```

必须覆盖：0 字节、半包、粘包、拆分字段、超长帧、非法字符、CRC 错、重复包、乱序、超时和断线重连。多字节字段显式处理字节序、符号、缩放和单位，禁止直接强转结构体。

### 6.3 RTOS 任务与并发

- 任务只承担一种主要职责；
- 启动顺序依赖用事件表达，不用固定延时冒充就绪；
- 必须使用延时时，要记录硬件或协议依据和超时兜底；
- ISR 不阻塞、不打印大日志、不做协议和业务处理；
- 锁的范围尽可能小，明确锁顺序，禁止无限等待；
- 队列元素固定上限，定义拒绝、覆盖或降级策略；
- 看门狗喂狗点代表系统健康，不应掩盖死锁。

项目把烟机业务、SLE、Modbus 和甲烷检测拆成独立入口，证明“任务生命周期解耦”和“数据交接”应该分开设计。

### 6.4 低功耗

低功耗不是一个开关，而是跨外设、通信、升级和业务的状态机。设计应包含：

- 模式：WFI、Light Sleep、Deep Sleep、关机；
- 进入条件和禁止条件；
- 唤醒源、唤醒延迟和时钟恢复；
- 通信、Flash 写入、OTA 和安全控制的低功耗锁；
- 锁的引用计数、异常释放和泄漏诊断；
- 空闲、联网、发送、升级等场景的实测电流。

验证不能止于构建；至少测平均/峰值电流、唤醒可靠性、联网保持、定时误差和升级期间行为。

### 6.5 存储与配置

持久化记录应包含 magic、版本、长度、CRC/哈希和有效标志。写入策略应考虑掉电：先写数据与校验，最后提交有效状态；关键数据使用双副本、日志式或平台原子能力。

配置升级要定义：旧版本迁移、新版本回退、未知字段、默认值、损坏恢复和写寿命。唯一 MAC、校准值、密钥和生产 NV 不得被普通应用烧录或 OTA 覆盖。

### 6.6 OTA/FOTA

升级流程至少包含：

```text
IDLE → PREPARE → RECEIVE → VERIFY → PENDING
          ↘          ↘         ↘
                 FAILED/CLEANUP
PENDING → REBOOT → FIRST_BOOT_CHECK → COMMIT / ROLLBACK
```

开始帧校验产品、硬件、版本、包类型、总长度、帧数和哈希；数据帧校验会话、帧号、偏移、长度和校验值；写入前验证 `offset + length` 不溢出且不跨分区。

发布前执行：随机断电、重复帧、漏帧、乱序、错误基线、错误签名、空间不足、低内存、断网重连、首次启动失败和配置迁移测试。若平台不能自动回滚，必须提供明确的有线恢复方案。

### 6.7 安全与生产

- 不在代码、日志或 AI 对话中放密码、Token、私钥和生产密钥；
- 调试口、测试命令、连续发射和校准入口不能进入量产固件；
- 外部输入先验证，再进入 SQL、命令、文件、Flash 和协议处理；
- 发布包签名、哈希和版本策略必须由受控流程管理；
- 生产固件、产测固件和研发固件应有明显标识和独立配置；
- 产测完成后重刷量产固件并冷启动抽检。

## 7. AI 工作协议

### 7.1 开始任务时

AI 应先输出简短工作说明：目标、将检查的事实、预计修改范围和验证方法。随后执行只读盘点，发现以下情况应停止有风险的改动并询问：

- 协议版本互相冲突；
- 原理图与管脚定义不一致；
- 生产参数或分区边界未知；
- 工作区存在与本任务重叠的未提交修改；
- 需要删除、覆盖、强推、重启服务或使用全量擦除烧录。

### 7.2 实现任务时

AI 必须：

- 保持改动局部、可解释、可回退；
- 对所有外部长度、索引、偏移和枚举做验证；
- 不静默吞掉错误；
- 不以增加无限重试或超长延时掩盖状态机问题；
- 不把调试日志、临时开关和固定测试标识遗留在量产配置；
- 不修改无关文件，不覆盖用户已有变更；
- 同步维护必要的变更记录和测试用例。

### 7.3 结束任务时

最终报告统一包含：

```markdown
## 结果
- 实现内容：
- 修改文件：

## 验证结果
- 执行命令/操作：
- 实际输出：
- 证据等级：E0-E5
- 资源变化：Flash / RAM / 栈 / 功耗

## 未验证与风险
- 待实机项：
- 已知限制：
- 回退方式：
```

不得只写“应该可以”“编译没问题”或“已修复”。

## 10. 常见反模式

| 反模式 | 风险 | 正确做法 |
| --- | --- | --- |
| AI 读一个文件就改代码 | 忽略配置、硬件和历史约束 | 先做事实盘点和调用链分析 |
| 用固定延时解决所有时序 | 环境变化后失效 | 事件、就绪状态和有界超时 |
| 回调内同步等待 AT/总线 | 阻塞关键任务或死锁 | 投递给链路所有者异步处理 |
| 一个全局布尔表示所有事务 | 来源、超时和并发丢失 | 带 ID、来源和状态的事务对象 |
| 队列/重试无限 | 内存耗尽或永不恢复 | 有界容量、退避和最终失败 |
| 为省内存移除校验 | 引入安全和数据风险 | 分块、流式处理，保持算法不变 |
| 只保存最终结论 | 后续无法复现 | 保存原始证据和排除过程 |
| 构建成功即宣称完成 | 外设和真实业务未验证 | 明确证据等级和待实机项 |
| 测试固件直接用于量产 | 调试入口和生产参数风险 | 固件类型隔离、重新烧录和抽检 |
| AI 自动提交/发布 | 混入无关修改或错误制品 | 人工审查差异与发布批准 |

## 12. 结语

AI 在嵌入式开发中的最佳角色，不是替代硬件和产品责任人，而是成为一个速度快、记忆完整、能自动化重复劳动的工程协作者。真正可靠的 AI 开发体系由四部分组成：可恢复的工程、明确的所有权、有界的状态机和分级的真实证据。

只要每次变更都能回答“依据是什么、谁拥有它、失败会怎样、如何证明、如何回退”，AI 就能显著缩短嵌入式产品从需求到稳定交付的周期，而不会以速度换取不可控风险。
