# 验证与交付规范

## 1. 变更与版本控制

1. 修改前记录工作区和设计库状态，不覆盖用户已有工作。
2. 使用最小、单一目的、可解释的增量变更；不得顺手重构或重画无关模块。
3. 先保护已验证基线；不得删除失败证据、历史制品或已发布制造文件。
4. 先执行受影响的定向检查，再执行风险相称的软硬件回归。
5. 最终审计差异、生成物、制造输出、凭据和无关文件。
6. 只有获得授权且验证通过后，才能建立单一目标的版本检查点；只暂存本次文件。
7. 不得自行推送、合并、采购、打样、烧录、部署或发布。

## 2. 必测类别

- 正常、边界、非法、损坏和未知格式；
- 超时、取消、重试耗尽、断线与恢复；
- 队列、内存、磁盘、电源或带宽不足；
- 并发、反复启停、异常退出、掉电和重启；
- 旧数据、旧协议、旧硬件和迁移；
- 资源峰值、长期增长、泄漏、功耗和热；
- 回退以及受保护基线回归；
- 硬件相关任务还须覆盖额定、最坏工况、容差、故障注入和板版差异。

## 3. 故障诊断

1. 诊断请求默认只分析，不擅自实施修复。
2. 先冻结日志、波形、抓包、转储、版本、板号、配置和时间线。
3. 从最近变更及基线差异开始建立可证伪假设。
4. 每次实验只改变一个主要变量，并记录预期、实际和结论。
5. 区分“未发现问题”和“数据不足无法判断”。
6. 已排除路径无新证据不得重复。
7. 证据指向物理连接或能力缺失时，停止用应用、格式、延时及重试补偿。

## 4. 证据等级

- E0：静态审查、计算或规则检查；
- E1：软件构建/链接/打包，或 EDA ERC/DRC/制造输出检查；
- E2：主机测试、仿真、回放，或电路/SI/PI/热仿真；
- E3：台架、HIL、真实板卡或样机测量；
- E4：整机、环境、EMC/射频/安规预检、现场或长稳；
- E5：受控试产、认证、量产与正式发布。

AI 只能报告实际达到的等级。没有硬件或仪器时，必须给出待实测步骤、测点、仪器设置、预期范围、停止条件和失败定位。

## 5. 实机与样机操作

烧录、刷新、部署、重启、上电、功耗、射频和故障注入前必须确认：设备标识、板版、供电及安全条件、目标范围、当前版本、备份、恢复通道和停止条件。生产及现场设备默认不得执行破坏性实验。

## 6. AI 最终交付格式

```markdown
## 结果
- 完成内容：
- 修改的源码/配置/原理图页/PCB 区域：
- 保留能力与兼容性：

## 依据与追溯
- 需求 ID、数据手册/规范章节：
- 关键计算、源码或设计位置：
- 假设、未知项和适用边界：

## 验证
- 执行命令、EDA 检查或实测步骤：
- 实际结果：
- 证据等级：E0-E5
- 资源与裕量：Flash/RAM/栈/CPU/电源/热/时序/空间等

## 未验证、风险与恢复
- 待实机、样机、现场或认证项：
- 已知限制和失败定位：
- 软件回退、硬件返工或版本恢复方法：

## 版本控制
- 工作区/设计库差异：
- 软件、硬件、BOM 和制造版本：
- 检查点或提交：
```

AI 不得只写“应该可以”“编译没问题”“ERC/DRC 已过”或“已经修复”。
