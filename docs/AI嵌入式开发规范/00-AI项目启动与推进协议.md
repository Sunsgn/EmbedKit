# AI 项目启动与推进协议

本协议是“AI 嵌入式产品开发约束包”的固定启动入口。AI 拿到约束包、项目文档包和一句需求后，必须先执行本协议，不得直接选型、画图、编码、建完整目录或宣称进入后续阶段。

## 当前状态卡（M-STATUS-001）

AI 每次任务的第一段必须输出且只保留当前状态，不复述规则正文：

```text
[当前状态卡]
当前阶段：F? / G?
阻塞项：B?（无则写无）
当前证据：E?
下一步只允许：<一个动作>
下一步禁止：<一个动作>
需要工程师决定：<不超过3条；无则写无>
```

状态未知时用`?`并进入输入登记，不得自行补值；“下一步只允许”和“下一步禁止”都只能写一个动作。

状态卡之后只报告本轮触发的规则ID、证据位置、未关闭项和下一步；不得复制规则正文、重述门禁表或重述已完成全文。

## 1. 同时生效的约束

以下规则同时生效，任何一项都不能覆盖另一项：

1. 本约束包规定 AI 如何启动、推进、验证和交付；
2. [01-AI执行总则.md](01-AI执行总则.md) 规定权限、事实、停止和变更纪律；
3. [01A-项目输入与立项.md](01A-项目输入与立项.md) 规定输入状态、B0-B4阻塞和G0-G5门禁；
4. [02-完整项目开发流程.md](02-完整项目开发流程.md) 规定F0-F7阶段推进；
5. 《项目目录框架》规定目录模式、分支、资料归属、迁移和Git/文件授权边界；
6. 用户授权、项目事实和项目专属规则继续有效。

读取约束包或目录框架不代表获得创建、移动、覆盖、删除、Git、烧录、部署、打样或发布权限。

## 2. 固定启动动作序列

AI 必须按顺序执行，前一步输出是后一步输入。

| 顺序 | 固定动作 | 必须输出 | 禁止跳转条件 |
| --- | --- | --- | --- |
| S0 接收 | 列出收到的需求、文档包、约束包和工作区 | 启动回执 | 未确认收到什么时不得分析方案 |
| S1 识别 | 判断T0-T4任务等级及NEW/ORGANIZE/EXTEND/AUDIT目录模式 | 任务与目录模式 | 模式冲突时不得写目录 |
| S2 基线 | 只读检查Git/EDA状态、现有目录、源码边界、版本和受保护基线 | 基线摘要 | 工作区冲突或目标不明时停止 |
| S3 锁输入 | 按01A登记输入状态、假设、冲突和B0-B4阻塞 | 输入登记表 | B1-B4按影响阶段阻塞 |
| S4 定路线 | 用08选择当前G/F阶段、证据目标、目录分支和交付物 | 阶段推进计划 | 前置门禁未关闭不得进入后续阶段 |
| S5 建载体 | 按目录框架只创建当前需要的分支，按07创建实际使用的模板 | 目录/模板变更清单 | 未授权不得移动、覆盖或补齐空目录树 |
| S6 执行 | 按03/04执行当前阶段的软件或硬件工作，按06记录确定变量 | 阶段工作产物 | 不得扩大到未授权范围 |
| S7 验证 | 按05执行最小充分验证，记录E0-E5证据和未验证项 | 门禁输出 | 失败或证据不足不得标记通过 |
| S8 交接 | 更新风险、追溯、manifest和交接包，指出下一门禁 | 交接包 | 交接不等于发布批准 |

## 3. 启动回执格式

```text
[启动回执]
需求原文：<保持原意>
收到的文档包：<文件/目录及版本；无则写无>
约束入口：<00、01、01A、08及任务相关分册>
任务等级：T0-T4
目录模式：NEW / ORGANIZE / EXTEND / AUDIT / 不涉及目录
当前推定阶段：G?/F?
工作区基线：<Git/EDA/目录状态>
已知输入：<摘要>
未知/冲突：<摘要及B0-B4>
当前允许动作：<只读/模板/设计/实现/验证等>
当前禁止动作：<精确说明>
下一步：<唯一下一动作或待用户回答>
```

输入不足时，AI 仍须输出启动回执和输入问题清单，不得用一连串自由提问代替结构化登记。

## 4. F0-F7 与目录路由

下表只用于启动时确定产物归属；完整门禁、证据和关闭条件以08为准，目录是否创建仍由《项目目录框架》授权边界决定。

| F阶段 | 主要产物 | 目录框架分支 |
| --- | --- | --- |
| F0 输入立项 | 输入登记、风险和启动回执 | `.ai/`；按需`项目管理/立项与范围/`、`开发文档/需求规格/` |
| F1 需求 | 需求表和追溯矩阵 | `开发文档/需求规格/`；按需`配置与变更管理/需求追溯矩阵/` |
| F2 架构 | 接口、预算和ADR | `开发文档/系统设计/`、`开发文档/通信协议/` |
| F3 详细设计 | 软件设计、原理图和PCB评审 | `开发文档/系统设计/`、`硬件原理图PCB/当前设计/`及已有资料分支 |
| F4 实现/制板 | 源码、EDA、BOM和制造输出 | `program/{实际英文工程名}/`、`硬件原理图PCB/当前设计/`及制造资料分支 |
| F5 Bring-up | 板级记录和原始测量 | `测试/测试报告/`、`开发文档/开发记录/`、硬件版本记录分支 |
| F6 集成验证 | 测试、缺陷和证据 | `测试/`下实际使用的计划、用例、自动化、HIL或报告分支 |
| F7 发布/维护 | manifest、批准、归档和交接 | `开发文档/版本发布/`、`release/`；获批后按需进入生产、合规和售后分支 |

## 5. 阶段推进规则

1. 当前阶段只使用已接受输入和显式假设；假设不得进入冻结基线或正式发布。
2. 每次只申请进入一个下一阶段；不得从F0直接宣称F3、F4或F7完成。
3. 阶段内可以并行处理不互相依赖的工作，但每个产物仍须关联输入、规则和验证。
4. 发现前置输入错误时退回相应G/F阶段，保留历史记录，不在后续阶段打补丁掩盖。
5. 目录只承载当前真实产物；08给出的目录是归属位置，不是自动创建清单。
6. 阶段通过只表示该门禁满足，不表示项目整体完成。

## 6. 门禁输出格式

```text
[阶段门禁]
门禁：G? / F?
任务范围：<本阶段实际范围>
输入基线：<输入登记版本>
触发规则：<01A/02/03/04/05/06规则ID>
目录位置：<实际启用路径；未创建写无>
交付物：<07模板ID及实际文件>
证据：<E0-E5、对象版本、位置>
阻塞项：<B0-B4；无则写无>
未验证项：<清单或无>
关闭条件检查：<逐项通过/失败/不适用>
结论：通过 / 有条件通过 / 失败 / 阻塞
允许进入：<下一阶段或不允许>
批准需求：<责任人/用户/无>
```

“有条件通过”只能用于不影响下一阶段安全和正确性的B0项；B1-B4不得通过改写措辞绕过。

```text
[交接包]
项目/产品稳定ID：
当前G/F阶段：
本轮目标与完成范围：
输入基线与变更：
需求/接口/决策追溯：
软件、硬件、BOM、配置和工具版本：
目录及工作主文件：
交付物清单与SHA-256：
测试结果与E0-E5证据：
开放风险、阻塞和未知项：

Git/EDA状态及检查点：
```

交接包必须引用真实文件和记录，不复制虚构的批准、测试或生产数据。

## 8. 任务类型适配

| 任务类型 | 启动与推进方式 |
| --- | --- |
| 一句需求的新项目 | 完整执行S0-S8；从G0/F0开始，不直接进入设计或编码 |
| 已有项目新增功能 | S0-S4识别受影响输入和阶段；只推进受影响F阶段并完成回归 |
| 缺陷诊断 | T0启动；锁定现象、版本和证据，可停在诊断交接，不自动实施修复 |
| 局部软件/文档修改 | T1启动；保留F0范围确认和F7交接，不强制重跑无关阶段 |
| 硬件/PCB变更 | 至少T3；同时执行01A、02、04、05、06和目录框架授权边界 |
| 目录整理/迁移 | 本协议只建立任务边界；实际执行完全服从目录框架ORGANIZE两轮闭环 |
| 只读目录审核 | 目录模式AUDIT；保持只读，不因本协议创建Profile或模板 |
| 发布/试产/生产 | T4；必须满足G5/F7/B4和E级要求，AI不得自行放行 |

## 9. 停止与恢复

出现以下任一情况时停止推进，并输出当前门禁、已完成工作、原始证据、阻塞等级、恢复条件和下一步责任人：

- 01中的S-AUTH停止规则被触发；
- 01A中的B1-B4影响当前或下一阶段；
- 目录模式、源码工程边界、目标路径或权威文件无法确定；
- 目录框架要求的移动、删除、覆盖、Git或生产操作尚未获得对应授权；
- 输入冲突、测试失败、哈希不一致或证据等级不足；
- 用户改变范围导致阶段、目录或交付物映射失效。

恢复后从阻塞发生的S步骤继续，不重新自由规划，也不跳过已经记录但尚未关闭的门禁。
