# AI 嵌入式产品开发规范

- 规范版本：V2.2
- 用途：约束 AI 在嵌入式项目中分析、设计、编码、审查、测试和交付
- 适用：裸机、事件驱动、RTOS、嵌入式 Linux，以及包含原理图和 PCB 的软硬件产品
- 规则形式：规则编号 + 触发条件 + 必须动作 + 完成证据

## 1. 实际使用方法

AI 不得把全部规则机械套到每个任务。开始工作时先确定任务等级和影响域，只加载被触发的规则；涉及安全、硬件、公共接口、持久化或发布时自动提高等级。

| 等级 | 典型任务 | 最小执行要求 |
| --- | --- | --- |
| T0 只读 | 解释、盘点、诊断、评审 | 01 + 对应技术分册；不得修改或把推测写成结论 |
| T1 局部修改 | 单文件缺陷、文档、局部测试 | 01 + 对应技术分册 + 05；定向验证和差异审计 |
| T2 模块变更 | 驱动、协议、任务、存储格式、公共接口 | 01 + 02受影响阶段 + 03 + 05 + 06 |
| T3 系统/硬件 | 新项目、新板、原理图、PCB、Bring-up、跨模块联调 | 01、01A、02 至 06；先完成输入门禁 |
| T4 发布/生产 | OTA、制造文件、试产、认证、量产 | T3 要求 + 明确批准人；AI 不得自行放行 |

## 4. 规则执行约定

- `S-*`：停止规则。触发后 AI 必须暂停修改并请求确认。
- `M-*`：强制规则。满足触发条件就必须执行，不得用“时间不足”跳过。
- `C-*`：条件规则。AI 必须说明适用或不适用的理由。
- 同一任务只报告实际触发的规则，不复制整份规范充当执行记录。
- 数量、时间、容量、电压、温度和公差不得使用规范里的假设值；必须来自项目变量或实测。

## 5. 每次任务的最小输出

```text
任务等级：T0-T4
影响域：软件 / 原理图 / PCB / 固件 / 数据 / 设备 / 发布
触发规则：规则 ID 列表
未知项：缺失事实及影响
计划证据：将执行的检查或实测
完成状态：完成 / 部分完成 / 阻塞 / 仅诊断
```

发生冲突时依次服从：人员和设备安全、法规与数据完整性 → 用户明确授权 → 已验证基线与可恢复性 → 项目规则及权威资料 → 功能正确性 → 性能、成本与便利性。
