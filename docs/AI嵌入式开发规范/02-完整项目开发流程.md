# 完整嵌入式项目开发流程

AI 不得跳过前置门禁把后续产物宣称为完成。允许并行准备，但必须标明依赖、未知项和未关闭风险。

## 1. 需求与风险定义

必须形成用户场景、输入输出、性能、实时、功耗、环境、接口、电源、安全、法规、成本和可测试性要求。每项需求必须具有稳定 ID、来源、验收方法和变更记录。

门禁：关键需求、危险动作、异常安全状态、使用环境和验收人已明确；矛盾与未知项没有被默认值静默替代。

## 2. 系统架构与软硬件划分

必须形成系统框图、电源树、时钟/复位树、数据流、控制流、启动与升级链路、接口协议、资源预算、模块职责、软件层次、故障降级和恢复方案。

门禁：跨域接口具有电气与逻辑双重定义；关键资源具有正常和最坏情况预算；本地安全功能不依赖非安全链路才能工作。

## 3. 详细设计

- 硬件：器件选型、原理图、约束、BOM、封装、叠层和 PCB 设计；
- 软件：模块接口、状态机、并发模型、资源所有权、存储格式、错误模型和测试设计；
- 测试：板级 Bring-up、单元、集成、HIL、整机、环境、EMC/射频/安规和生产测试计划。

门禁：设计项能回溯到需求；关键器件和参数有权威依据；评审问题有责任人、状态及关闭证据。

## 4. 实现、制板与样机准备

AI 必须小步修改并保留可回退基线。软件构建、EDA 输出、BOM 和制造文件必须锁定版本；替代料、板版、固件和装配选项不得仅靠可变显示名称关联。

门禁：源码和设计检查通过；制造输出来自已审计设计版本；样机上电方案、限流值、测点、烧录/恢复通道及停止条件已准备。

## 5. 板级 Bring-up

顺序原则：目检与无源检查 → 限流上电 → 电源轨与功耗 → 时钟/复位/启动配置 → 调试口和最小固件 → GPIO/中断/DMA → I²C/SPI/UART/CAN 等总线 → 存储/网络/射频 → 完整业务。

AI 不得在电源、时钟、复位或物理连接未验证时，用上层延时、重试、格式转换或寄存器脚本掩盖问题。每一步必须记录板号、板版、固件、仪器、配置、原始测量和通过/失败判据。

## 6. 软件集成与系统验证

必须覆盖正常、边界、非法、损坏、未知格式、超时、取消、断线、掉电、重启、资源不足、反复启停、升级和回退；同时比较 Flash、RAM、栈、CPU、带宽、磁盘、功耗和温度的预算与实测。

门禁：需求具有测试证据或明确未验证状态；缺陷可定位到原始日志、波形、抓包、转储、源码或设计位置；受保护基线完成回归。

## 7. 试产、发布与维护

必须建立生产测试、校准和唯一数据写入边界，记录软硬件版本、BOM/替代料、制造文件哈希、固件哈希、配置、工具版本和批准记录。现场问题必须能追溯到批次、板版、固件和测试证据。

发布后变更仍须经过影响分析、回归、迁移和回退门禁。AI 不得自行批准采购、打样、试产、量产、认证或正式发布。

## 8. 跨阶段变更规则

1. 需求变化必须分析对架构、硬件、软件、测试、生产和已交付版本的影响。
2. 任何阶段发现前置事实错误时，必须退回对应门禁，不得只修补末端现象。
3. 软件、原理图、PCB、BOM、固件、装配选项和测试结果必须使用稳定标识建立关联。
4. 每个阶段都必须保留输入、操作、输出、失败原因、恢复方式和批准记录。
