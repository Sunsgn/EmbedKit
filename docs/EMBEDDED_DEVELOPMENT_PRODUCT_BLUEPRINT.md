# EmbedKit 通用嵌入式开发平台产品蓝图

更新日期：2026-10-13

最终产品目标以 [EmbedKit 最终产品目标](./PRODUCT_GOAL.md) 为最高约束；本文负责产品与系统架构。当前能力和开发路线的快速入口见 [EmbedKit 项目定位与开发方案总结](./PROJECT_SUMMARY.md)。

## 1. 产品定位

EmbedKit 的目标不是再做一个网页计算器集合，也不是替代 Keil、IAR、VS Code、编译器或芯片厂商 IDE，而是成为嵌入式开发过程中可以随时打开使用的统一工程工作台：

> 围绕板级 Bring-up、底层驱动开发、总线调试、通信与网络协议、固件诊断和自动化测试，整合高频工具，连接真实设备，保留可复现证据，减少开发者在 IDE、串口工具、脚本、计算器、数据手册和临时程序之间反复切换。

四类核心价值：

1. **看懂工程**：分析陌生源码、启动流程、驱动层次、任务/事件和构建产物。
2. **调通硬件**：调试寄存器、时钟、GPIO、中断、DMA、I²C、SPI、UART、CAN 等底层能力。
3. **验证通信**：处理字节流、总线帧、网络连接和应用层协议，连接真实设备并批量复现。
4. **沉淀证据**：把日志、抓包、测试、固件版本、源码位置和结论关联为可导出的工程记录。

AI 是可选外部增强，不是运行依赖。无 AI 时工程分析、工具、设备操作、测试、知识和报告必须完整可用；配置 AI 时只用于解释证据、生成候选和提出待验证假设，不能替代确定性计算、执行和判定。

## 2. 服务的开发阶段

```text
需求与选型
  ↓
芯片/模组资料查找
  ↓
工程导入与框架理解
  ↓
板级 Bring-up 与底层驱动
  ↓
I²C / SPI / UART / CAN 总线联调
  ↓
TCP / UDP / WebSocket / 应用协议联调
  ↓
固件、MAP、ELF 与运行异常分析
  ↓
集成测试、回归验证和发布归档
```

用户可以从任意阶段独立进入。项目工作台只用于增强关联和追溯，不得成为串口、I²C、SPI、协议或固件工具的使用前置条件。

## 3. 设计原则

### 3.1 实用性优先

每个功能必须回答：真实输入是什么、连接什么对象、执行什么操作、产生什么证据、失败如何恢复、资源上限是什么、结果如何复用。只有静态说明、单一成功样例或一次性 AI 回答不能算完成。

### 3.2 不重复成熟 IDE 和工具链

- Keil、IAR、CMake、Make、Ninja 等继续负责编译和链接；
- EmbedKit 自动识别已有工程配置、MAP、ELF、HEX、BIN、日志和构建结果；
- 构建只作为 CMake 类项目的可选便利能力，不是工程分析前提；
- 不自行实现编译器、链接器、烧录算法或任意 Shell 平台。

### 3.3 Web 优先，本地助手增强

格式转换、日志分析、协议模型、计算和报告在浏览器直接运行；串口后台会话、原始网络、CAN、I²C/SPI 适配器、调试探针和大文件由 Local Agent 提供。Agent 缺少某项能力时只禁用该能力。

### 3.4 安全操作真实硬件

- 默认只读和最小权限；
- 写寄存器、总线写入、复位、擦除和升级必须显示目标并确认；
- 所有硬件操作带超时、取消、互斥、资源释放和会话关闭；
- 不允许网页或 AI 直接执行任意系统命令；
- AI 建议必须经过参数校验和确定性执行层。

### 3.5 平台无关和适配器扩展

不假定 STM32、FreeRTOS、Keil 或某一种 USB 适配器。芯片、RTOS、IDE、调试探针、I²C/SPI/CAN 设备和协议差异放入版本化适配器，并声明能力、测试样本和降级方式。

## 5. 工程分析与驱动开发工作台

### 5.1 陌生工程分析

保留并继续增强现有源码分析：

- 自动识别 Keil、IAR、CMake、Make、Ninja 及通用源码工程；
- 区分裸机、事件驱动、多种 RTOS 和未知框架；
- 识别启动入口、初始化顺序、主循环、任务、中断、回调和状态机；
- 展示调用关系、关键数据流、共享资源和并发风险；
- 每条结论跳转到文件和行号，显示覆盖率、置信度和未知项；
- 结合 MAP/ELF 给出内存、符号和版本增长证据；
- 优化建议必须说明依据、风险、验证方法和预期收益，不能只是通用 AI 建议。

### 5.2 驱动开发助手

输入数据手册章节、SVD、寄存器头文件和板级参数后，生成的是“驱动实现草案 + 可执行验证清单”，而不是只有代码片段。

建议流程：

```text
选择外设和目标功能
→ 提取时钟/引脚/寄存器依赖
→ 生成初始化步骤与驱动接口草案
→ 静态检查寄存器位和调用顺序
→ 在真实目标上读取关键寄存器
→ 执行外设自测
→ 记录实测结果和失败位置
```

驱动能力包括：

- 初始化顺序和复位值核对；
- 时钟源、分频、门控和频率计算；
- GPIO 模式、复用、上下拉、速度和电气约束；
- 轮询、中断和 DMA 三种工作方式比较；
- 中断向量、优先级、标志清除顺序和丢中断风险；
- DMA 通道、方向、宽度、对齐、循环模式和缓存一致性；
- 超时、错误恢复、资源互斥和低功耗恢复；
- 驱动单元测试接口、Mock 边界和目标板验收步骤。

AI 生成的驱动代码必须标明芯片系列、参考手册版本、HAL/LL/裸寄存器假设和未验证项。没有真实寄存器或设备验证时不得标记为可量产。

### 5.3 寄存器与芯片资料联动

- 导入 CMSIS-SVD、芯片头文件或厂家 Pack；
- 根据地址解码寄存器和字段，显示复位值、访问权限和保留位；
- 导入寄存器转储并与期望配置比较；
- 从异常字段跳转官方资料或源码初始化位置；
- 支持多个时间点快照比较，定位哪个步骤改变了寄存器；
- 读取真实目标寄存器需要调试探针适配器，离线解码不依赖 Agent。

## 6. 板级与底层调试

### 6.1 Bring-up 检查流

建立通用但可裁剪的检查流程：

1. 供电、复位和时钟证据记录；
2. SWD/JTAG 可连接性与芯片身份；
3. 启动模式、向量表、PC/SP 和复位原因；
4. GPIO 安全状态和关键复用；
5. 系统 Tick、定时器和中断；
6. UART 日志；
7. I²C/SPI/CAN 等板级总线；
8. 外部 Flash、传感器、模组和网络；
9. 睡眠、唤醒、看门狗和异常恢复。

每项保存目标板、固件指纹、工具版本、参数、原始结果和时间，不用“正常/失败”替代证据。

### 6.2 调试探针

Local Agent 通过 Provider Registry 适配已有工具，例如 OpenOCD、pyOCD、J-Link 或厂商命令行工具。首期只提供能力检测、连接、读取寄存器/内存、复位和 RTT/SWO 会话等明确操作，不提供任意命令执行。

探针能力不能假设所有环境都存在；每个 Provider 必须报告版本、支持目标、读写能力、占用状态和缺失依赖。烧录与擦除属于高风险后续能力，必须使用显式文件、目标和二次确认。

## 7. I²C 调试工作台

### 7.1 实时能力

通过 Local Agent 的 I²C Provider 连接 Linux `i2c-dev`、USB 转换器或开发板桥接固件，支持：

- 总线和适配器枚举、能力检测、独占会话；
- 7 位/10 位地址；
- 地址扫描，显示 ACK、耗时和重复结果；
- 单次写、单次读、写后重复起始读；
- 8/16/24/32 位寄存器地址及端序；
- 批量寄存器表、字段解码、轮询和变化高亮；
- NACK、仲裁丢失、超时、忙总线和适配器错误分类；
- 可取消脚本、间隔限制和会话自动释放；
- 每笔交易记录 Start/Restart/Stop、地址、方向、数据、ACK 和时间。

总线扫描和写操作会影响真实设备，界面必须明确目标适配器、速率和地址范围。EEPROM、PMIC、Flash 等敏感写操作默认关闭。

### 7.2 离线分析

- 导入 Saleae/PulseView 等导出的 CSV、VCD 或规范化交易日志；
- 显示地址、方向、字节、ACK/NACK、重复起始和交易间隔；
- 根据寄存器表解析字段和工程值；
- 识别缺少 Stop、频繁 NACK、超时空洞和异常重试；
- 将一段真实交易保存为驱动测试向量。

### 7.3 驱动验证

将 I²C 实测交易与驱动预期比较：寄存器地址端序、Repeated Start、读取长度、写后延时、ACK 轮询和错误恢复。平台不能仅凭数字日志判断上拉电阻、波形质量或电压是否正确；需要示波器/逻辑分析仪时必须明确提示。

## 8. SPI 调试工作台

### 8.1 实时能力

通过 SPI Provider 支持：

- 控制器/USB 适配器枚举和能力检测；
- Mode 0–3、频率、位序、8/16/32 位字宽；
- CS 极性、建立/保持时间、交易间延时和手动 CS；
- 全双工 Transfer、仅写和读时填充字节；
- 多段交易与 CS 保持；
- 十六进制、文件和可重复脚本发送；
- 接收比较、掩码断言、超时和重复测试；
- 每次操作记录配置、TX、RX、耗时和错误。

### 8.2 离线波形/交易分析

- 导入逻辑分析仪 CSV/VCD 或已解码 SPI 交易；
- 按 CS 会话重组 MOSI/MISO；
- 用不同 CPOL/CPHA/位序进行离线重解释；
- 标记帧宽、CS 间隔、空闲时钟和异常长度；
- 对接 SPI Flash、传感器和显示屏等协议适配器；
- 保存真实交易为驱动回归向量。

网页不能在没有模拟波形采样证据时断言信号完整性、建立保持时间或电压满足要求。

## 9. UART、CAN 与其他接口

### 9.1 UART

保留现有通信终端、多会话、分屏、周期发送、快捷指令、文件发送和日志导出。新增价值放在：

- 连续流协议解析与原始终端同步定位；
- 波特率误差、吞吐、FIFO、突发和软超时预算；
- 接收间隔和丢帧统计；
- 通信会话直接生成协议样例和测试步骤。

### 9.2 CAN/CAN FD

- 保留 DBC 单帧及批量日志；
- 增加 Local Agent CAN Provider、过滤、实时收发和周期报文；
- 支持 CAN FD、总线负载、周期抖动、丢帧和错误帧统计；
- DBC multiplex、信号曲线、触发条件和测试断言；
- 适配 SocketCAN 及常用 USB CAN，具体硬件由 Provider 扩展。

### 9.3 后续接口

1-Wire、LIN、RS-485、USB、SDIO 等按真实需求通过相同的 Provider、会话、日志和证据模型扩展，不先创建只有表单的空工具。

## 10. 网络与协议调试

### 10.1 网络连接

保留 TCP Client/Server、UDP、WebSocket 独立调试，统一时间戳、方向、搜索、HEX、统计、周期发送和导出。Local Agent 负责浏览器不能直接建立的原始 TCP/UDP/Server，会话失败不能影响纯浏览器工具。

### 10.2 抓包与流分析

- 导入 PCAP/PCAPNG、Wireshark 导出 CSV 或应用日志；
- 按五元组筛选并重组 TCP 字节流；
- 区分重传、乱序、连接关闭和应用消息边界；
- 将重组流交给协议工程工作台；
- 保存报文偏移、时间、方向和源数据包位置；
- TLS 加密流没有会话密钥时只分析元数据，不伪装成可解析明文。

### 10.3 应用协议

HTTP、MQTT、CoAP、Modbus TCP 和厂家私有协议使用适配器扩展。详细设计由 [协议工程工作台实用化方案](./PROTOCOL_ENGINEERING_WORKSPACE.md) 负责：协议模型可手工导入、编辑或由外部 AI 生成草案，确定性引擎负责验证，最后绑定真实通信和测试。

## 11. 固件、构建产物与故障诊断

- MAP：双版本 Flash/RAM、库/对象/节区/符号增长证据；
- ELF/AXF：地址和调用栈批量符号化、DWARF 源码定位；
- HardFault：从真实日志提取寄存器、解释 SCB 状态并联动 ELF/MAP；
- HEX/SREC/BIN：统一地址段、空洞、重叠、CRC、合并和发布清单；
- SVD：寄存器转储、字段差异和真实目标快照；
- 日志：时间轴、关键事件、状态转换和通信关联；
- 性能：栈、堆、静态内存、CPU 时间和通信吞吐在有证据时逐步接入。

这些工具独立可用，也可关联同一工程、构建、设备和测试运行。分析结论必须区分确定性解析、启发式风险和 AI 建议。

## 12. 自动化测试与设备项目

### 12.1 测试编排

统一步骤模型支持：

- 串口、I²C、SPI、CAN、TCP、UDP 和 WebSocket；
- 发送、读取、等待、断言、循环、变量、条件和人工检查；
- 协议字段提取、请求响应、异步事件和超时重试；
- 多通道资源锁、通道继承、取消和清理；
- 失败步骤定位、原始数据和环境快照。

流程默认复用第一个通信步骤的通道，只有高级模式才允许逐步覆盖。测试用例必须支持删除、复制、排序、版本和导入导出。

### 12.2 设备项目

设备项目用于关联：

- 板卡、样机和硬件版本；
- 固件指纹和构建版本；
- 调试探针与通信端点；
- 协议和寄存器表版本；
- 测试运行、日志、故障和报告。

关联是可选增强。所有通信和工具必须继续支持“不创建项目直接使用”。

## 13. 资料中心与学习路径

资料中心优先官方标准、芯片/工具厂商和持续维护的专业资料，记录来源、适用范围、版本和核验时间。资料应围绕任务组织：

- 板级 Bring-up；
- GPIO、时钟、中断和 DMA；
- I²C/SPI/UART/CAN 驱动；
- 网络和协议；
- 调试探针、逻辑分析仪和示波器；
- MAP/ELF/HardFault；
- 测试、可靠性、安全和低功耗。

学习路径必须包含实际操作、工具使用、代码实践、设备实验和验收证据，不能只提供文章列表或绑定单一芯片生态。

## 14. 系统架构

### 14.1 分层

```text
Web UI
  ├─ 独立工具工作区
  ├─ 项目与设备工作区
  └─ 统一证据/报告视图
        ↓
领域引擎
  ├─ 工程/源码分析
  ├─ 寄存器与驱动规则
  ├─ 总线与协议解析
  ├─ 固件与构建产物
  └─ 测试执行模型
        ↓
会话与适配器接口
  ├─ Communication Provider
  ├─ Debug Probe Provider
  ├─ Artifact Adapter
  └─ Protocol Adapter
        ↓
Local Agent
  ├─ Serial / TCP / UDP / CAN
  ├─ I²C / SPI hardware providers
  ├─ SWD / JTAG / RTT providers
  └─ Authorized local files and tools
```

### 14.2 Provider 合同

每个硬件 Provider 至少声明：

- `id`、版本、平台和驱动依赖；
- 支持的设备与能力；
- 参数范围和默认安全模式；
- 打开、关闭、取消和超时行为；
- 结构化错误码；
- 并发/独占规则；
- 真实硬件与虚拟回环测试样本；
- 缺失驱动或设备断开时的降级行为。

前端只按能力调用，不出现某个厂商适配器的硬编码业务分支。

### 14.3 公共数据模型

稳定公共模型至少包括：

- `DeviceProfile`：设备、板卡、硬件与固件身份；
- `TransportEndpoint`：串口、网络、CAN、I²C、SPI 和探针端点；
- `HardwareSession`：配置、状态、时间和资源所有权；
- `CapturedEvent`：时间、方向、原始数据、解析层和来源位置；
- `ProtocolDefinition`：版本化协议模型；
- `BuildArtifact`：MAP、ELF、HEX、BIN、SREC 和指纹；
- `TestRun`：步骤、断言、清理和证据；
- `EvidenceReference`：文件、行、地址、字节偏移、数据包或设备操作。

模型带 Schema 版本和迁移；跨模块通过模型关联，不通过 React 组件互调。

## 15. AI 在整个平台中的作用

AI 适合：

- 阅读数据手册和陌生源码；
- 生成驱动/协议/测试草案；
- 解释寄存器和故障证据；
- 汇总版本差异和优化方向；
- 根据已有确定性结果生成易读报告。

确定性代码必须负责：

- 寄存器地址、位域、时钟、CRC、端序和时序计算；
- I²C/SPI/CAN/串口/网络实际操作；
- 文件、日志和抓包解析；
- 超时、取消、资源锁和测试判定；
- 原始证据、版本、导出和复现。

AI 生成内容必须标记来源、适用芯片/协议/版本、未确认项和验证状态；不能直接取得硬件写权限。

## 16. 界面结构

顶级导航保持稳定：

```text
工作台

通信调试
集成测试
嵌入式工具箱
AI 助手
资料中心

```

嵌入式工具箱按任务分类，只显示目录，点击后进入独立工作区：

- 板级与驱动：时钟、GPIO、寄存器、中断/DMA、SVD；
- 总线调试：I²C、SPI、UART、CAN；
- 网络协议：TCP/UDP/WebSocket、PCAP、Modbus、DBC、自定义协议；
- 固件诊断：HEX/SREC/BIN、MAP、ELF、HardFault；
- 工程计算：定时器/PWM、ADC、CRC、字节序、位域、吞吐；
- 测试辅助：日志转换、测试向量、报告和差异。

复杂工具使用互斥面板、步骤导航和证据抽屉，不同时铺开所有参数。

## 17. 分阶段路线

### P0：公共工程与证据基础

1. 定义 ProjectRevision、BuildArtifact、DeviceProfile、FirmwareIdentity、CommunicationSession、TestRun、EvidenceReference、Finding 和 KnowledgeEntry；
2. 公共模型使用稳定 ID、Schema 版本、迁移和未知版本降级；
3. 保持现有通信、设备项目、测试、工具、工作区备份和独立入口兼容；
4. 统一资源上限、取消、错误分类、脱敏和原始证据引用；
5. 区分确定性事实、推导、启发式风险、人工观察和外部 AI 建议。

验收：旧数据可迁移，损坏数据安全降级，同一构建、设备、会话、测试和报告可互相追溯，独立模式不受影响。

### P0-A：真实设备验证闭环

1. 复用现有串口、TCP、UDP 和 WebSocket 创建独立或关联测试；
2. 运行前确认目标设备和固件指纹；
3. 保存准备、执行、清理、原始收发和失败步骤；
4. 比较历史基线中的新增失败、已修复和持续失败；
5. 导出版本化 JSON、HTML、JUnit 和 CSV 证据。

验收：使用真实设备完成“确认固件 → 正常步骤 → 注入失败 → 原始证据定位 → 修复复测 → 基线比较 → 报告”。

### P0-B：故障调查闭环

1. 将 HardFault、寄存器转储、ELF/DWARF、MAP、SVD、固件和通信日志保存为一次调查；
2. 支持多个异常地址、冲突证据、未知项和结论状态；
3. 所有结论可返回原始日志、符号、源码、地址或构建产物；
4. 将修复结论关联真实测试运行；
5. 导出脱敏调查包和报告。

验收：使用真实异常日志完成“寄存器提取 → ELF 源码定位 → MAP 变化 → 调查结论 → 修复复测”。

### P0-C：陌生工程分析闭环

1. 导入真实目录、工程配置和已有构建产物；
2. 覆盖裸机、事件驱动、主流 RTOS、非 FreeRTOS 和未知格式；
3. 展示启动、任务、中断、回调、状态机和关键调用关系；
4. 显示源码位置、覆盖率、可信度、多定义和未知项；
5. 关联运行轨迹、ELF、MAP 和可验证优化结果。

验收：四类独立样本回归通过，未知工程不猜测平台，结论可跳转证据并导出。

### P1：知识、资料与协议工程

1. 分层管理官方资料、通用经验、项目私有笔记和外部 AI 内容；
2. 索引 Pack、SVD、SDK、头文件、链接脚本、官方文档和本地资料；
3. 从真实调查生成包含症状、证据、解决、回退和复测的经验条目；
4. 协议支持手工建模、导入和可选 AI 草案，确定性引擎负责验证；
5. 增加 PCAP/PCAPNG、TCP 流重组、协议版本比较和测试联动。

### P1-A：适配器生态

1. 定义芯片、RTOS、工具链、工程、MAP、协议、资料来源、设备、探针和仪器适配器合同；
2. 每个适配器声明能力、版本、依赖、限制、错误、测试样本和降级行为；
3. 单个适配器故障不影响公共模型、独立工具和其他扩展；
4. 适配器结果保留来源证据，不改变公共模型含义；
5. 建立虚拟回归与真实样本验收矩阵。

### P2：需求驱动的硬件生态

按真实用户、可获得硬件和验收样本增加 CAN/CAN FD、I²C、SPI、LIN、1-Wire、USB、SWO/RTT、功耗日志、逻辑分析仪和探针。每个扩展必须说明验证边界，带真实输入、失败路径、资源限制、测试和证据导出，不以数量为目标。

## 18. 端到端验收场景

### 场景 A：I²C 传感器驱动

```text
导入数据手册/SVD
→ 导入或编写初始化方案
→ 确定性检查寄存器和值域
→ I²C 扫描发现设备
→ 读取 ID 和复位值
→ 执行初始化
→ 轮询测量值
→ 比较驱动日志与总线交易
→ 导出报告和测试向量
```

### 场景 B：SPI Flash Bring-up

```text
配置 Mode/频率/CS
→ 读取 JEDEC ID
→ 读取状态寄存器
→ 导入逻辑分析交易
→ 对比不同 CPOL/CPHA 解码
→ 验证驱动发送序列
→ 保存回归测试
```

### 场景 C：联网模组

```text
导入 AT 手册
→ 生成并验证协议模型
→ 串口连接真实模组
→ 执行联网流程
→ TCP/UDP 建连和业务协议解析
→ 故障步骤定位
→ 归档设备/固件/日志/报告
```

### 场景 D：固件异常

```text
导入 HardFault 日志
→ 提取寄存器和原始行
→ ELF 定位源码
→ MAP 查看模块/符号变化
→ SVD 解码故障状态
→ 形成调查清单
→ 修复后执行回归并比较证据
```

只有这些跨工具流程使用真实实现并可复现，平台才算真正帮助嵌入式开发，而不是工具入口集合。

## 19. 测试与可靠性

| 层级 | 必须覆盖 |
| --- | --- |
| 领域引擎 | 边界、端序、时序、错误输入、未知格式、资源上限 |
| Provider 合同 | 能力发现、设备断开、占用、权限、超时、取消和关闭 |
| 虚拟硬件 | 正常设备、NACK/超时、错误响应、断线和恢复 |
| 真实硬件 | 每类已发布 Provider 至少一个正式验收样本 |
| 前端流程 | 独立使用、Agent 离线、错误恢复、导出和跨工具关联 |
| 长期运行 | 日志轮转、内存上限、页面卸载、会话泄漏和重复连接 |
| 发布 | Windows/Linux/macOS 能力矩阵、GitHub Pages 和 Agent 包 |

“测试通过”只能证明实现没有触发已知缺陷，不能替代真实设备验收。真实电气问题、信号质量和硬件损坏风险必须明确能力边界。

## 20. 完成判定与下一步

平台功能完成必须满足：真实输入或硬件、可控操作、失败恢复、确定性证据、导出/联动、资源边界、自动测试、真实设备验收、兼容迁移和独立 Git 检查点。

近期执行顺序：

1. 不回退现有串口、网络、工具和测试能力；
2. 建立版本化公共工程、构建、设备、会话、测试、证据、结论和知识模型；
3. 用现有串口和网络能力完成真实设备验证、基线比较和报告；
4. 将 HardFault、ELF、MAP、SVD、固件和日志连接为故障调查；
5. 将真实工程目录、构建产物和运行轨迹连接为陌生工程分析；
6. 建立官方资料、工程经验和项目笔记的分层知识库；
7. 再由真实需求增加协议、芯片、CAN、I²C、SPI、探针和仪器适配器；
8. 每个阶段通过专项、全量、构建和 Pages 验证后独立 Git 备份。

第一条应证明的产品路径是：

> 固件身份 → 真实设备连接 → 多步骤测试 → 失败原始证据 → 修复复测 → 基线比较 → 可追溯报告。

这条路径优先复用当前已经具备的通信、设备、测试、固件和报告能力，并证明独立工具能够通过公共模型形成真实闭环。后续硬件总线和探针扩展必须复用同一证据与测试基础。
