# 嵌入式 Linux 问题解决及开发规避

- 文档版本：V1.0
- 适用范围：Buildroot、Yocto 或其他嵌入式 Linux 产品
- 内容性质：从真实工程现象匿名提炼的问题解决方法，不保留板卡、SoC、传感器、项目路径或客户信息

## 1. 先建立分层事实，避免跨层试错

Linux 产品问题至少跨越硬件、Boot、Kernel/DTS/驱动、rootfs、原生服务、脚本编排和业务应用。处理前先建立以下权威关系：

```text
SDK/构建机：Kernel、DTS、驱动、rootfs 配方和镜像
    ↓ 版本、构建配置、哈希
应用仓库：源码、部署清单、模型/资源清单、测试和迁移脚本
    ↓ 受控部署与校验
目标设备：已安装版本、运行配置、设备节点、日志和资源状态
```

开发时禁止用应用层脚本长期代替 DTS、驱动或构建系统问题；临时诊断操作必须记录并能恢复。

## 2. 驱动加载成功但业务数据无效

### 典型现象

- I²C/SPI 可以识别设备，驱动 probe 成功；
- media/video/input 等节点存在，启动采集也返回成功；
- DMA 持续产生数据，但图像、采样值或协议内容明显错误；
- 更换格式、转码、网络传输或应用算法均不能恢复有效信息。

### 逐层定位

1. **控制面**：确认供电、复位、时钟和寄存器读写；
2. **同步面**：测量时钟、帧/行同步、极性和时序；
3. **物理数据面**：对照原理图、封装、SoC 引脚组和总线位宽；
4. **DMA 原始证据**：保存未转换数据，统计每一位的翻转和有效范围；
5. **格式层**：只有原始位完整后再检查字节序、stride、像素/采样格式；
6. **业务层**：最后验证编码、推流、算法或控制逻辑。

### 关键解决方法

当 DMA 只有少数位变化时，先计算“物理连接位集合”与“控制器采样位集合”的交集。若有效位数量与交集一致，根因应优先收敛到引脚复用、总线位映射或硬件连接，而不是继续改上层格式。硬件修订前保留失败证据并停止重复软件试验。

### 开发时规避

- 原理图评审必须把逻辑数据位映射到 SoC 实际采样位；
- Bring-up 按控制面、同步面、原始数据面、格式面逐级设门禁；
- “有节点”“STREAMON 成功”“DMA 有数据”和“业务数据有效”必须分级报告；
- 不允许上层转换掩盖丢位、错位或错误极性。

## 3. 设备节点编号变化导致应用失效

### 解决方式

- 从 sysfs、media graph、udev 属性或驱动标识发现目标设备；
- 发布稳定状态文件、符号链接或本地服务接口给应用；
- 探测必须有超时、最大候选数和清晰失败原因；
- 多设备冲突时停止并展示证据，不按“第一个节点”猜测；
- 重启、热插拔和驱动加载顺序变化后重复验证。

### 开发时规避

- 禁止在业务代码中固定 `/dev/videoN`、`/dev/ttyN` 等可变编号；
- 稳定标识不能依赖可变显示名称；
- 状态接口必须包含就绪、来源、更新时间和失败原因；
- 应用离线时仍可查看上次状态，但不得把历史状态当作当前就绪。

## 4. 预编译程序可运行但无法维护

### 典型风险

- 仓库只有二进制，没有对应源码、构建参数或 SDK 提交；
- 变更只能替换二进制，无法代码审查和复现；
- 动态库、模型或插件版本与程序不匹配；
- 当前设备能运行，但换系统镜像后出现 ABI 错误。

### 解决方式

1. 记录二进制 SHA-256、ELF 架构、ABI、动态依赖和运行参数；
2. 找回匹配源码、工具链、SDK/系统提交和构建命令；
3. 在隔离环境重建并比较符号、依赖、大小和行为；
4. 找不回源码时把该组件标为不可维护风险，限制变更范围；
5. 保留当前可运行版本作为回退，不把未知二进制重新包装成“已验证源码构建”。

### 开发时规避

- 发布 manifest 同时记录源码提交、工具链、sysroot、构建参数和产物哈希；
- 第三方二进制必须记录许可证、来源和兼容范围；
- 模型、插件和动态库分别版本化，启动时检查兼容性；
- 单个闭源组件故障不得破坏日志、升级和安全回退能力。

## 5. 主机依赖复制到目标机后无法运行

### 解决方式

- 对可执行文件和 `.so` 检查 ELF 架构、解释器、ABI 和依赖；
- 使用目标 sysroot 或发行版构建配方生成依赖；
- 只部署应用实际导入/链接的白名单，不复制完整开发环境；
- 检查 C 扩展、证书、时区、编码和动态加载插件；
- 在干净 rootfs 上执行冷启动、功能、升级和卸载测试。

### 开发时规避

- 禁止从开发机整体复制 `site-packages` 或系统库；
- 依赖清单必须有版本、来源、许可证、大小和哈希；
- 构建阶段检测错误架构和越界依赖；
- 磁盘、内存和启动时间都纳入依赖选择。

## 6. FIFO/Socket 流处理偶发卡死或内存增长

### 解决方式

- 协议包含明确帧头、长度或分隔规则，并限制最大帧；
- 接收循环处理短读、粘包、EOF、编码错误和空闲超时；
- 消费者慢时采用有界队列、最新值覆盖或显式背压；
- 取消时关闭描述符、停止生产者并等待任务退出；
- 断开后重新打开连接，但使用退避和最大尝试次数；
- 日志记录连接代次、丢帧数、队列高水位和关闭原因。

### 开发时规避

- 禁止假设一次 `read` 就得到完整帧；
- 禁止无限缓存和无界重连；
- 明确多消费者的生命周期和所有权；
- 覆盖生产者先退出、消费者先退出、半帧退出和重复启动。

## 7. 启动脚本误杀进程或留下失控任务

### 解决方式

- 每个服务保存 PID，并校验 `/proc/<pid>/cmdline` 或 cgroup 身份；
- stop 只终止自己创建且身份匹配的进程；
- 先发送正常退出信号，超时后再升级处理；
- 启动前检测旧实例、端口、锁文件和资源占用；
- 优先使用受支持的服务管理器，脚本只负责必要编排。

### 开发时规避

- 禁止使用宽泛 `killall` 或进程名模糊匹配；
- start/stop/restart 必须幂等并有超时；
- 失败启动清理本次创建的临时资源；
- 更新启动链路前保护当前可运行基线并做 Canary 验证。

## 8. 日志、原始帧和临时部署目录无限增长

### 解决方式

- 日志按大小/时间轮转并限制总量；
- 原始帧和抓包以调查 ID 归档，记录来源、格式和哈希；
- 临时部署采用事务目录，成功后原子切换，失败后只清理本任务目录；
- 启动时识别未完成事务，提供恢复或清理预览；
- 磁盘水位触发降级，不能挤满系统分区。

### 开发时规避

- 不把大型诊断文件平铺在源码入口；
- 不提交缓存、运行日志、密钥和临时下载；
- 清理必须有明确范围，重要证据先导出；
- 设置单文件、总容量、保留时间和并发任务上限。

## 9. 推荐验证顺序

| 阶段 | 必须证明 | 不能冒充的结论 |
| --- | --- | --- |
| 构建 | 配置、工具链、源码提交和产物哈希 | 不能证明目标机可运行 |
| 驱动 | probe、节点、拓扑和错误日志 | 不能证明数据有效 |
| 原始数据 | 位宽、同步、长度、统计和样本 | 不能证明业务功能完成 |
| 应用 | 正常/失败路径、取消和资源释放 | 不能替代长期稳定性 |
| 系统 | 冷启动、升级、回退、资源与长稳 | 不能替代现场环境验证 |

## 10. 完成判定

问题只有在以下条件同时满足时才算解决：故障层级已由原始证据确定；修复没有破坏已验证基线；失败路径、取消和资源释放可复现；部署与回退有版本和哈希；测试覆盖重启、异常输入、资源上限和长稳；未知项没有被包装成已验证结论。
