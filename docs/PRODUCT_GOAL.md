# EmbedKit 最终产品目标

状态：生效

生效日期：2026-10-13

适用范围：产品、架构、数据、界面、Local Agent、适配器、测试、文档与发布

本文档是 EmbedKit 的最高层产品约束。其他蓝图、专项方案、路线图和执行记录如果与本文冲突，以本文为准；冲突内容必须修订，不能通过局部实现改变最终目标。

## 1. 唯一目标

EmbedKit 必须建设为一个本地优先、平台无关、无需依赖 AI 的通用嵌入式工程工具与调试测试工作台，使通信调试、工程与构建产物分析、故障诊断、自动化测试、知识经验沉淀和证据报告既可独立使用，又能通过版本化公共模型形成从真实输入与设备到可复现结果的闭环。

AI 仅作为可选外部增强。未配置 AI、AI 服务不可用或用户禁止发送数据时，全部确定性工具、设备操作、测试、证据、报告、资料和知识能力必须继续工作。

## 2. 产品形态

产品由三层组成：

1. **独立工具层**：通信、协议、数据转换、固件、构建产物、故障和工程计算工具可直接进入，不要求先创建项目。
2. **公共工程层**：用稳定 ID 关联工程版本、构建产物、设备、固件、通信会话、测试运行、证据、结论和知识条目。
3. **可选工作流层**：用户按需把独立工具连接为工程分析、真实设备验证、故障调查、修复复测和报告归档流程。

GitHub Pages 承载静态前端和纯浏览器能力；Local Agent 只增强串口、原始网络、本地文件、工具链、探针和其他需要本机权限的能力。Agent 离线不得阻断无关功能。

## 3. 必须形成的六类能力

### 3.1 通信调试

- 串口、TCP Client/Server、UDP Client/Server 和 WebSocket 独立可用；
- 支持真实连接、收发、文本/HEX、时间戳、搜索、过滤、统计、日志上限、关闭和恢复；
- CAN、I²C、SPI、探针和仪器按真实需求通过适配器扩展，不在公共界面写死厂商或芯片。

### 3.2 工程与构建产物分析

- 识别裸机、事件驱动、多种 RTOS 和未知框架；
- 分析启动、初始化、主循环、任务、中断、回调、状态机和关键数据流；
- 优先消费已有工程配置、ELF、MAP、HEX、BIN、SREC、日志和运行轨迹；
- 所有结论显示来源、位置、覆盖率、可信度和未知项。

### 3.3 故障诊断

- 将 HardFault、寄存器转储、日志、地址、ELF/DWARF、MAP、SVD、通信记录和版本变化组成调查链；
- 区分已验证事实、确定性推导、启发式风险和外部 AI 建议；
- 修复结论必须能够关联复测结果，不能只输出文字建议。

### 3.4 自动化测试

- 支持发送、等待、断言、变量、条件、循环、重试、取消、超时、准备和清理；
- 测试可以独立运行，也可选关联设备、固件、工程和协议；
- 失败定位到步骤、原始数据、帧或字段，并生成 JSON、HTML、JUnit、CSV 等可带走结果；
- 虚拟设备用于自动回归，不能冒充真实设备验收。

### 3.5 知识与资料

- 资料中心管理官方标准、厂商资料、SDK、Pack、SVD 和可靠专业来源的索引、版本、适用范围与核验时间；
- 工程经验记录症状、上下文、原因、证据、解决步骤、复测方法、适用边界和失效状态；
- 官方事实、通用经验、项目私有笔记和 AI 内容必须分层，项目私有内容默认只保存在本地；
- 知识条目应能从真实工具结果和故障调查沉淀，也能反向关联相关工具和验证步骤。

### 3.6 证据与报告

- 每次正式分析或测试记录源码/工程版本、固件指纹、设备身份、配置、工具版本、输入和时间；
- 证据可引用文件、行号、地址、字节偏移、日志行、数据包、设备操作和人工观察；
- 支持脱敏导出、工作区迁移、历史比较和损坏数据降级；
- “未发现问题”与“证据不足无法判断”必须明确区分。

## 4. 通用性与扩展原则

- 公共模型不得默认 STM32、FreeRTOS、GCC、Keil、Windows 或某个通信模组；
- 芯片、RTOS、IDE、工具链、MAP 格式、协议、设备、探针和资料来源差异进入版本化适配器或规则注册表；
- 适配器声明能力、适用范围、版本、依赖、限制、错误、测试样本和安全降级；
- 无法识别的输入保留原始证据并降级为通用分析，禁止静默猜测；
- 单个适配器、设备或外部来源故障不得破坏其他模块。

## 5. AI 边界

EmbedKit 不自建通用聊天、通用代码生成、通用驱动生成或文档 RAG 作为核心竞争力。外部 AI 可以：

- 解释已经提取的证据；
- 生成代码、协议、测试或修复候选；
- 提出待验证假设；
- 汇总确定性结果。

但 AI 不负责最终协议校验、计算、设备操作、测试判定、资源限制和证据真实性。AI 输出必须标注为外部建议，并经过用户确认或确定性验证后才能进入正式结论。

## 6. 非目标

EmbedKit 不：

- 替代编译器、链接器、Keil、IAR、厂商 IDE、烧录器或成熟调试工具；
- 以页面数量、工具数量、文章数量或 AI 自动化率作为完成标准；
- 用静态入口、Mock 数据、硬编码样例或一次成功演示冒充完成；
- 强制用户创建项目后才能使用通信、工具、资料或学习能力；
- 将源码、固件、日志、密钥或本机权限迁移到公开服务；
- 在缺少证据时宣称芯片、协议、驱动或时序已经验证。

## 7. 最终验收

最终发布必须用真实实现和可核验证据通过以下流程：

1. **陌生工程**：导入工程 → 识别工程与框架 → 展示执行流程 → 跳转源码证据 → 关联构建产物 → 输出未知项和可验证建议。
2. **真实设备**：连接设备 → 确认固件身份 → 执行多步骤测试 → 定位失败步骤和原始数据 → 修复后复测 → 比较结果 → 导出报告。
3. **故障调查**：导入真实日志或异常 → 关联 ELF/MAP/SVD/通信证据 → 定位源码或地址 → 保存调查结论 → 关联修复验证。
4. **独立工具**：不创建项目即可使用通信、协议、固件、ELF、MAP、CAN、Timer/PWM、ADC 等对应工具，并处理正常、损坏和边界输入。
5. **经验沉淀**：从一次真实问题生成带证据的经验条目 → 标明适用范围和复测方法 → 在另一个工作区中检索和复用。
6. **迁移恢复**：导出版本化工作区 → 在新环境导入 → 恢复关键配置、关联关系、分析摘要和测试历史，不自动打开设备或执行危险操作。

## 8. 功能立项规则

每项新增能力必须至少提供一项通用对话或静态页面不能稳定替代的价值：真实本地数据处理、真实设备操作、严格格式校验、原始位置证据、批量重复执行、版本比较、自动化测试、失败恢复或可审计导出。

立项前必须明确真实输入、用户操作、输出、失败路径、资源上限、持久化、迁移、独立模式、关联模式、自动测试、真实验收和 Git 检查点。无法回答这些问题的功能不进入正式开发。
