## 1. 项目概述

本项目是北燃双炉头家用燃气灶控制固件，主控为 CW32L083MC，使用 FreeRTOS V10.0.1。系统负责双灶开关和档位识别、热电偶与干烧温度采集、安全保护、数据缓存、NB-IoT 平台通信，以及通过 F20 模组完成 SLE 烟机联动和 BLE 调试数据发送。

项目已经形成可工作的产品固件和较丰富的实机排障记录，但工程目录仍保留明显的研发现场形态：源码、Keil/IAR 工程、构建中间文件、调试日志、发布产物和协议资料混在同一仓库中。后续整理的首要目标不是立即改代码，而是先固定权威入口、构建基线、资料归属和验证证据。

## 4. 软件架构

### 4.1 分层结构

```text
产品业务层
├─ Function.c       双灶采样、档位识别、安全保护、联动触发
├─ monitor.c        周期采样调度、状态检查、运行资源观测
└─ UratSeting.c     业务协议组帧、下行解析、上报调度

通信与服务层
├─ NBIoT.c          MC661/F20 AT 状态机、TCP、重连、发送队列
├─ SLE.c            SLE/BLE 状态机、广播、连接、收发和烟机联动
├─ AT_24C04.c       EEPROM 访问
└─ AD7793.c         MS5193 配置、采样与温度换算

板级与基础层
├─ driver.c / uart.c / interrupts_cw32l083.c
├─ USER/inc/PortDefine.h
├─ driver/
└─ FreeRTOS/
```

### 4.2 FreeRTOS 任务

| 任务 | 栈深度 | 优先级 | 主要职责 |
| --- | ---: | ---: | --- |
| `IOT` | 320 words | Idle + 2 | NB 入网、连接、上行、下行和重连 |
| `SLE` | 384 words | Idle + 2 | SLE/BLE 初始化、广播、连接、收发和链路监控 |
| `MONITOR` | 192 words | Idle + 1 | 双灶采样、安全判断、电池和资源监控 |
| `COMM` | 256 words | Idle + 2 | 业务组帧、缓存调度、NB 上报 |
| Timer Task | 128 words | 最高配置优先级 | FreeRTOS 软件定时器服务 |

任务创建、堆申请失败和栈溢出已有 RAM 诊断变量：

- `g_rtos_boot_stage`；
- `g_task_create_*`；
- `g_malloc_failed`；
- `g_stack_overflow`；
- 各任务 stack high-water mark 和堆余量。

### 4.3 主要数据流

```text
按键/旋钮 + MS5193
        ↓
   MonitorTask / Function
        ├─ 安全判断 → 本地执行/事件位
        ├─ 状态变化 → SLE B003 烟机联动
        └─ 状态/报警 → AT24C04 缓存 → CommTask
                                      ↓
                                  NB 发送队列
                                      ↓
                                    IotTask
                                      ↓
                                  MC661 / 平台
```

烟机联动链路：

```text
炉头开关/档位变化
  → `SLE_SendHoodControl()`
  → SLE 任务拥有发送状态
  → B003 发送
  → 序列号/ACK/有限重试
  → 断线期间保存最新期望状态，重连后恢复
```

## 5. 核心功能总结

### 5.1 双灶采样与档位识别

- 左右炉头分别维护开关、档位、干烧温度和熄火保护温度；
- MS5193 负责高精度模拟采样，程序包含配置、原始码读取、热电偶毫伏换算和 K 型温度换算；
- 档位变化会驱动烟机联动状态更新；
- MonitorTask 在炉头工作期间按约 1 秒周期执行采样和安全判断。

### 5.2 安全保护

当前业务包含：

- 干烧温度判断；
- 熄火保护判断；
- 点火失败判断；
- 电池状态检查；
- 异常状态缓存和平台上报。

安全逻辑属于产品最高风险区域。任何阈值、延时、采样映射或执行输出修改，都必须核对硬件版本、产品标准、试验记录和实机故障注入结果，不能仅凭代码推断调整。

### 5.3 NB-IoT 平台通信

- 通过 AT 状态机完成上电、SIM、信号、校时、DNS/TCP 和收发；
- 使用有限长发送队列，当前最大单帧 256 B、队列 3 项、发送重试上限 3 次；
- 区分联网就绪、发送和平台 ACK；
- 连接失败和发送失败有重连路径；
- CommTask 负责业务帧生成，IotTask 负责链路和 AT 所有权。

### 5.4 SLE/BLE 与烟机联动

- 当前燃气灶按从机角色广播，由烟机发起 SLE 连接；
- 兼容 F20 V1.03 AT 返回格式和异步连接事件；
- 支持广播恢复、连接状态查询、断线检测和运行时看门狗；
- B003 控制包含档位映射、ACK、重复状态抑制、延时关机与重连恢复；
- BLE 通道用于发送档位、温度和 MS5193 原始采样调试数据；
- SLE 与 BLE 共用模组/串口状态机，必须保持命令所有权和发送序列化。

### 5.5 缓存与掉线补报

- AT24C04 保存待上报状态和报警记录；
- 写入路径包含互斥和回读校验相关实现；
- 平台 ACK 后清理已上传缓存；
- 需要继续明确缓存格式版本、掉电原子性、容量上限、写寿命和损坏恢复策略。

### 5.6 低功耗

- Idle Hook 在 NB 已关机空闲、SLE 允许休眠、按键均空闲且无业务锁时进入低功耗；
- 进入前暂停 Tick，唤醒后恢复；
- `g_lowPowerLock` 用于阻止关键业务期间休眠；
- `configUSE_TICKLESS_IDLE` 当前为 0，项目使用自己的 Idle Hook 低功耗入口。

低功耗策略需要用电流、唤醒、RTC、按键、串口和无线保持的实测证据验证，不能只依据状态函数返回值。

## 6. 关键开发演进

从 `代码修改记录.md` 和 Git 历史可归纳出以下主线：

1. 建立 NB 联网、时间获取、连接失败恢复和平台 ACK 闭环；
2. 引入 SLE/BLE，并逐步修正扫描分段接收、连接事件、广播恢复和断线重连；
3. 将 B003 烟机联动从“连接即发送”演进为带状态、序列号、ACK 和重试的异步事务；
4. 修复任务创建、全局中断恢复、MonitorTask 阻塞和 RTC 观测问题；
5. 增加堆申请失败、栈溢出、任务栈余量和堆余量诊断；
6. 通过实机 RAM、寄存器、烧录日志和平台现象反复校正假设；
7. 增加低功耗进入条件以及 SLE 运行时卡死恢复；
8. 持续修正左右灶映射、档位死区、点火阶段联动和关机竞争条件。

其中最值得复用的方法是：记录真实现象和原始证据、用状态机表达长流程、通信链路保持单一所有者、每次改动后同时检查构建资源与实机行为。

## 7. 当前工程风险与技术债

风险级别用于安排治理顺序，不代表已经确认存在产品故障。

### 7.1 阻断级：安全参数与验证资料尚未集中

干烧、熄火、点火失败和阀控属于安全功能，但当前协议、源码宏、硬件版本和实机测试证据没有形成统一索引。正式发布前应建立安全需求到代码、测试和批准记录的追踪矩阵。

### 7.2 高：工程产物大量进入 Git

盘点时共有 416 个跟踪文件，其中约 167 个位于 `MDK/output/`，另有大量 `.o`、`.d`、`.crf`、`.log`、`.bak`、`.axf` 和 `.hex`。仓库根目录未发现 `.gitignore`。

影响：

- diff 和提交容易混入生成文件；
- 仓库增长快，难以识别权威制品；
- 历史构建日志与当前结果容易混淆；
- 自动检查点提交降低有意义历史的可读性。

处理这些已跟踪文件需要单独确认和备份，不属于本次总结范围。

### 7.3 高：大文件和多职责源文件

- `SLE.c` 约 87 KB；
- `NBIoT.c` 约 63 KB；
- `Function.c` 约 26 KB。

它们同时承担 AT 解析、状态机、重试、队列、业务映射和诊断等职责，后续改动回归面较大。`NBIoT.c` 中还可检索到多组相同公开函数定义，需要确认条件编译边界和当前实际生效实现。

建议先建立行为测试，再按“传输接收、AT 解析、链路状态机、业务适配”逐层拆分，不能直接大范围重构。

### 7.4 高：中断和任务上下文边界需专项审核

工程中仍可见中断处理附近的 `Delayms(10)`，以及 ISR/任务间事件和信号量交互。需要逐项确认这些延时是否真的运行在中断上下文、是否屏蔽关键中断，以及 FreeRTOS FromISR API 和中断优先级是否完全匹配。

### 7.5 中：编码和命名一致性

部分中文注释存在乱码，说明历史文件可能混用 GBK、UTF-8 或被错误转换。`UratSeting` 命名存在拼写历史，头文件重复声明和重复 include 也较明显。

编码统一属于高风险机械变更：它会造成整文件 diff，必须独立执行、保留备份并验证 Keil/IAR 工程兼容性。

### 7.6 中：当前构建仍有 2 个警告

警告都在 NB 状态相关变量，可能是历史状态演进后的残留。应先确认变量的预期语义和条件编译路径，再决定删除、恢复使用或增加明确注释，不能为追求零警告直接删除状态逻辑。

### 7.7 中：测试自动化不足

当前证据以编译、烧录、RAM 读取和现场现象为主，尚未发现独立的主机单元测试、协议测试向量或 HIL 用例目录。协议编解码、档位映射、缓存格式和状态机非常适合先建立无硬件测试。

### 7.8 中：发布与生产边界不清晰

仓库中存在当前 `.hex/.axf`，但没有独立发布清单说明固件版本、硬件版本、Git 提交、工具链、长度、SHA-256、测试证据和烧录范围。是否存在量产固件、产测固件和校准数据隔离也待确认。

| 温度采集 | 原始码、负值、开路、越界换算 | MS5193 数据注入 | 热电偶与标准温源 |
| 安全保护 | 阈值状态转换、计时边界 | 传感器故障注入 | 点火失败、熄火、干烧 |
| NB | AT 半包、粘包、超时、重试、ACK | MC661 模拟器/服务器 | 弱网、断网、重连、长稳 |
| SLE/BLE | AT 回放、B003 编解码、ACK 序列 | F20 模组和烟机模拟器 | 绑定、断线、重连、延时关机 |
| EEPROM | 格式、CRC、容量、重复记录 | 写入中断电 | 长期写入和掉线补报 |
| RTOS | 队列满、堆不足、状态机超时 | 任务压力和故障注入 | 24/72 小时长稳、看门狗 |
| 低功耗 | 进入条件纯逻辑 | 唤醒源组合 | 电流、唤醒、联网保持 |

覆盖率目标不能只用代码行衡量。安全状态转换、外部输入边界、掉电一致性和通信恢复路径必须 100% 有明确用例。

## 11. AI 后续开发规则建议

1. 修改前先读取 `readme.txt`、协议、`代码修改记录.md` 和相关 Git 历史；
2. 明确本次修改属于安全、采集、NB、SLE、存储还是构建领域；
3. 安全阈值、左右灶映射、端口、电源时序和通信方向不得凭猜测修改；
4. ISR 只采集和投递，禁止新增阻塞延时和复杂业务；
5. NB 和 SLE 串口只能由各自任务拥有，同步等待不能扩散到业务任务；
6. 每个重试必须有上限、间隔、最终状态和可观测计数；
7. 关闭链路时，本地安全保护必须继续工作；
8. 修改后先全量构建，再按风险执行主机、实机和故障测试；
9. 报告严格区分静态检查、构建通过、烧录通过、实机功能通过和现场长稳通过；
10. 同步记录修改原因、实际证据、未验证项和回退方法。

## 12. 随系统增长需要复查的点

- 14 KiB RTOS 堆和各任务栈是否仍有足够最坏情况余量；
- NB、SLE/BLE 同时活动时的 CPU、串口和电源峰值；
- MS5193 采样阻塞时间对 RTC、无线和安全响应的影响；
- EEPROM 写寿命、缓存容量和断电一致性；
- SLE/BLE 模组固件版本变化对 AT 返回格式的兼容性；
- 平台协议、F20 AT 手册和产品通信协议的版本同步；
- 安全阈值和延时是否与硬件代次、认证标准和试验记录一致；
- 是否需要独立硬件看门狗、故障安全输出和复位原因追踪；
- 发布固件是否能从干净环境稳定复现；
- 自动检查点提交是否影响审查、回退和正式版本追溯。

## 13. 本次整理结论

该项目已经具备完整产品雏形和大量实机演进经验，尤其在 NB 恢复、SLE 烟机联动、FreeRTOS 资源诊断和双灶状态处理方面积累较深。当前最需要的不是立即重写，而是把“能运行的研发工程”转化为“可恢复、可测试、可发布、可追溯的产品工程”。

推荐顺序是：先冻结可运行基线，再补项目入口与索引，然后治理生成物，随后建立协议和安全逻辑测试，最后才进行模块化重构。任何涉及安全逻辑、目录迁移、历史产物删除或量产配置的动作，都应单独评审和确认。
