# AI 嵌入式开发 Markdown 约束包后续开发方案

## 1. 文档目的

本文档用于指导 V6.0 后续开发，将当前“专业约束库、Python 运行内核、测试工具和交付验证混合在同一包中”的形态，调整为面向真实用户的 Markdown-only AI 开发约束产品。

最终目标是：用户把约束包直接复制到一个新建或既有嵌入式工程中，Codex、Claude Code 等具备文件、终端和工具调用能力的 AI 开发工具即可按需读取约束，自主完成工程识别、任务规划、代码或设计修改、构建、测试、失败整改、证据收集、状态保存和跨会话恢复。

约束包负责规定 AI 必须做什么、禁止做什么、如何验证和何时阻止放行；实际文件编辑、命令执行、构建、测试和设备操作由用户正在使用的 AI 工具及其现有能力完成。约束包不重复实现一套与 AI 工具重叠的自动化执行平台。

## 2. 当前状态与主要问题

当前成果已经具备 17 个专业领域的详细约束、按需路由思想、项目事实模板、安全边界和证据要求，但从真实项目使用角度仍存在以下问题：

1. 当前 ZIP 同时包含用户约束、Python 运行源码、测试、示例、打包工具和研发资料，用户无法快速判断哪些文件需要复制到工程。
2. 约束主要存在于 Markdown，结构化原子规则和详细约束之间没有完整的一一映射，存在双重权威风险。
3. 任务计划仍偏通用，尚未把详细专业约束稳定转化为具体的工程步骤、检查点和完成条件。
4. 工程识别主要依赖文件统计和关键词，不能自动形成 MCU、SDK、RTOS、工具链、Pinmux、协议、构建目标等完整项目事实。
5. `PROJECT_PROFILE.md` 目前主要依赖人工填写，缺少 AI 首次进入项目时的自动调查、来源记录、冲突发现和增量更新流程。
6. 路由主要依赖任务文本关键词，缺少目标文件、工程对象、修改影响和跨专业风险传播。
7. 证据要求已经写入约束，但仍需明确每个专业领域的证据内容、版本绑定和交叉验证方法。
8. 自动状态恢复依赖运行内核的设计思路，没有完全转成可供任意 AI 工具执行的文件化工作协议。
9. 当前自动测试主要验证约束包自身结构、路由和安全函数，尚未充分验证 AI 在多个真实嵌入式工程中是否会正确遵循约束。
10. 原 54 项验收矩阵不能覆盖新增的所有详细专业规则和 Markdown-only 产品形态。

## 3. 产品边界重新定义

后续正式产品拆分为“用户约束包”和“研发维护工程”。两者不得继续混合交付。

### 3.1 用户约束包

用户约束包是正式产品，全部采用 Markdown，建议结构如下：

正式用户 ZIP 不得包含 Python、JSON、可执行程序、测试源码、合成工程、开发日志、缓存或历史证据。

### 3.2 研发维护工程

当前的 Python、测试和打包能力保留在研发侧，用于检查 Markdown 约束包，不进入用户工程：

```text
developer/
├─ validators/
├─ package-builder/
├─ tests/
├─ examples/
├─ acceptance/
└─ internal-docs/
```

研发侧负责检查规则 ID、链接、内容完整性、项目特例泄漏、路由覆盖、Token 预算和交付包内容。用户不需要安装或运行这些工具。

## 4. 统一约束条款格式

Markdown 是正式权威源。每条可执行约束必须具有稳定规则 ID，并使用统一格式：

```markdown
## SW-ISR-001：中断服务函数执行限制

触发条件：
- 新增或修改 ISR。
- 修改中断回调调用链。

适用范围：
- 裸机、事件驱动和 RTOS 中断上下文。

必须确认：
- 中断来源、优先级、清除顺序、共享对象和截止时间。

必须执行：
1. 定位 ISR 及全部调用路径。
2. 检查调用 API 的上下文安全性。
3. 检查共享数据同步。
4. 测量或计算最大执行时间。
5. 执行异常和高频中断测试。

禁止：
- 阻塞、sleep、动态内存、格式化日志、Flash 写入、复杂解析和无界循环。

必需证据：
- 源码位置、API 依据、时序结果和测试日志。

PASS 条件：
- 禁止项不存在，共享状态受保护，时序满足项目要求，异常可以恢复。

失败处理：
- 不满足时禁止合入；无目标硬件时标记 NOT_RUN。
```

所有正式规则必须回答：何时触发、需要哪些项目事实、AI 必须执行什么、禁止什么、如何证明、什么条件才允许 PASS、失败后如何处理。

## 5. 按需加载与 Token 控制

### 5.1 L0 入口

根目录 `AGENTS.md` 控制在约 2～3 KB，只保留：

1. 权威顺序。
2. 按需读取要求。
3. 项目事实不得猜测。
4. 修改、测试、证据和恢复闭环。
5. 高风险操作授权边界。
6. 状态文件位置。

`AGENTS.md` 不得复制全部专业规则。

### 5.2 三级路由

`INDEX.md` 使用三级路由选择约束：

1. 任务对象路由：源码、驱动、原理图、PCB、设备树、协议、制造等。
2. 目标文件路由：根据 `.c`、`.ld`、`.kicad_sch`、`.kicad_pcb`、`.dts`、`.map` 等目标文件补充领域。
3. 影响传播路由：例如 Pinmux 自动补充软件、硬件、集成和验证；OTA 自动补充软件、安全、构建产物和验证。

无法确定领域时只允许调查和记录未知项，不允许直接写入。

### 5.3 读取预算

- 每个任务始终读取 `AGENTS.md`、`PROJECT_PROFILE.md` 和 `INDEX.md`。
- 只读取命中领域及必要工作流。
- 典型单任务约束上下文原则上不超过约 20 KB。
- 软件等大领域按章节精确定位；必要时进一步拆分为 ISR/DMA、并发、协议、存储/OTA、构建测试等规则簇。
- 已读取且未变化的文件不得在同一任务重复读取。

## 6. 新项目首次识别与 Profile 建立

AI 第一次进入工程时必须执行：

```text
确认项目根和 Git 状态
→ 搜索工程入口和构建文件
→ 识别 MCU/SoC、SDK、RTOS 或执行模型
→ 识别正式工具链和构建目标
→ 识别启动入口、链接脚本和板级配置
→ 识别协议、存储、Bootloader/OTA
→ 识别测试、下载和设备日志入口
→ 生成项目事实候选
→ 交叉核对来源
→ 更新 PROJECT_PROFILE.md
```

每项事实记录值、状态、来源、版本和适用范围。状态统一为：

- `VERIFIED`：有直接工程或实测证据。
- `USER_PROVIDED`：用户明确提供。
- `INFERRED`：依据多个间接来源推断，尚未完全验证。
- `UNKNOWN`：没有足够信息。
- `CONFLICT`：多个权威来源互相冲突。
- `UNAVAILABLE`：需要的资料或工具不可用。

`UNKNOWN` 不得自动变成经验值；`CONFLICT` 不得由 AI 静默择一。涉及硬件损坏、安全、地址、引脚、烧录和兼容性的未知项必须阻止相应操作。

## 7. AI 自动执行工作协议

AI 工具按照以下统一闭环工作：

```text
读取约束
→ 建立项目事实
→ 解析用户需求
→ 影响分析
→ 生成任务计划
→ 检查授权和工作区
→ 实施最小修改
→ 运行定向测试
→ 保存真实证据
→ 判断 PASS/FAIL/BLOCKED
→ 针对性修复
→ 受影响回归
→ 更新状态和交接
→ 创建可回退 Git 检查点
```

约束包不提供文件编辑器、终端、编译器、EDA 或设备控制实现，这些由 AI 工具和项目现有工具提供。约束包只规定调用条件、输入、证据和安全边界。

## 8. 文件化状态恢复

AI 在目标工程运行过程中动态创建：

```text
.ai/work/
├─ STATUS.md
├─ HANDOFF.md
├─ TASK_PLAN.md
├─ INPUT_HASHES.md
└─ evidence/
```

### 8.1 STATUS.md

记录当前需求、阶段、已完成、失败、阻塞、正在执行、下一安全动作和总体状态。

### 8.2 HANDOFF.md

记录项目根、当前基线、已加载规则、修改文件、实际命令、测试结果、证据路径、未知项、禁止重复动作和恢复命令。

### 8.3 恢复流程

新会话必须：

1. 读取 `AGENTS.md` 和 `PROJECT_PROFILE.md`。
2. 读取 `STATUS.md`、`TASK_PLAN.md` 和 `HANDOFF.md`。
3. 检查 Git 状态和现有用户改动。
4. 重新校验关键输入哈希。
5. 判断上次动作是否真正完成。
6. 从最近一次具有有效证据的检查点继续。
7. 对烧录、生产写入、发布和设备控制等非幂等动作不得盲目重放。

## 9. 领域证据合同

### 9.1 软件证据

- 当前源码版本或工作区状态。
- 构建命令、工作目录、工具链版本和退出码。
- 构建日志、测试日志、新产物路径、生成时间和 SHA-256。
- 资源报告、失败路径结果和未执行的设备验证。

### 9.2 原理图证据

- 原生工程、库和 BOM 哈希。
- EDA 版本、ERC 原始报告、网络/器件/Pin 差异和 waiver。
- 未执行的仿真、样机和测量项目。

### 9.3 PCB 证据

- 原生 PCB、输入网表版本、对象计数和未布线数量。
- DRC 原始报告、规则来源、Gerber/钻孔/BOM/PnP 清单。
- 制造输出独立回读及逐文件哈希。

### 9.4 真实设备证据

- 设备 ID、板卡版本、固件哈希、连接配置和工具版本。
- 原始日志、抓包、波形或测量文件。
- 测试步骤、首次失败、恢复动作和最终结果。

### 9.5 通用验真规则

- 文件存在不等于 PASS。
- 工具退出零不等于功能正确。
- 旧日志和旧 output 不能作为本次证据。
- mock、桩和合成工程不能证明真实设备或真实 EDA。
- 报告必须引用原始证据，能够追溯到当前源码、固件、设备和配置。

## 10. 专业工作流模板

优先实现以下工作流：

1. `NEW_PROJECT_DISCOVERY.md`：新项目识别和 Profile 建立。
2. `SOFTWARE_CHANGE.md`：通用软件修改闭环。
3. `DRIVER_DEVELOPMENT.md`：GPIO/时钟/中断/DMA/总线驱动开发。
4. `PROTOCOL_CHANGE.md`：协议字段、状态机和兼容修改。
5. `BOARD_BRINGUP.md`：新板逐级上电与故障隔离。
6. `SCHEMATIC_REVIEW.md`：原理图解析、ERC 和接口影响。
7. `PCB_CHANGE.md`：规则推导、布局布线、DRC 和制造输出。
8. `DEVICE_TEST.md`：设备连接、多步骤测试、失败定位和报告。
9. `DEFECT_FIX.md`：首次失败、最小复现、根因、修复和回归。
10. `PROJECT_DELIVERY.md`：清单、哈希、净室验证、交接和 RC 判定。

工作流模板只规定过程和证据，不写死 MCU、RTOS、工具链、引脚、路径和数值。

## 11. 重新建立验收体系

### 11.1 用户包结构验收

- 用户 ZIP 只包含 Markdown。
- 没有 Python、JSON、测试工具、日志和缓存。
- 解压后能够直接复制到新工程。
- 根入口唯一，用户只需维护 `PROJECT_PROFILE.md`。

### 11.2 路由和 Token 验收

至少覆盖 UART DMA、I²C 驱动、协议解析、NVM 升级、新板上电、原理图、PCB、DTS、产测、EMC、机械热和未知任务。

每项验证：加载正确领域、不加载无关领域、缺事实时不擅自修改、上下文没有无意义全文读取。

### 11.3 AI 行为验收

验证 AI 是否在修改前检查工作区，是否实际构建和测试，是否保存首次失败，是否拒绝猜测项目参数，是否区分模拟与真实验证，是否更新状态、证据和 Git 检查点。

### 11.4 恢复验收

模拟构建中断、会话结束、输入变化、测试失败后恢复和高风险动作状态未知，验证 AI 不依赖聊天记忆、不重复危险副作用。

### 11.5 真实工程试点

至少选择：

1. 一个裸机工程。
2. 一个主流 RTOS 工程。
3. 一个非 FreeRTOS 工程。
4. 一个 Embedded Linux 工程。
5. 一个真实原理图/PCB 工程。
6. 一个虚拟设备或可安全连接的真实设备工程。

真实工具、硬件或授权不可用时必须记录 `BLOCKED/NOT_RUN/UNAVAILABLE`，不得用模拟结果替代。

## 12. 分阶段实施计划

### 阶段 A：产品拆分

1. 建立 Markdown-only 用户包目录。
2. 将运行内核、测试和工具移入研发侧。
3. 制定用户包文件白名单。
4. 生成首个 Runtime MD 候选包。

完成条件：用户 ZIP 只含 Markdown，复制后无需安装程序。

### 阶段 B：统一规则格式

1. 为全部专业条款分配稳定 ID。
2. 将条款统一为触发、输入、动作、禁止、证据、PASS 和失败处理。
3. 消除 `CONSTRAINTS.md`、`RULES.md` 和 JSON 之间的双重权威。
4. 建立规则 ID 到工作流和验收用例的追踪。

完成条件：每条正式规则都可以直接指导 AI 行为并被验收。

### 阶段 C：工程识别与路由

1. 完成首次工程识别工作流。
2. 完成 Profile 状态与来源规范。
3. 完成任务、文件、影响三级路由。
4. 建立上下文读取预算和未知任务降级。

完成条件：AI 能从陌生工程建立可靠事实，只读取实际相关规则。

### 阶段 D：执行、证据与恢复

1. 建立任务计划、状态、交接和证据模板。
2. 建立通用开发闭环和专业工作流。
3. 建立各领域证据合同。
4. 建立跨会话恢复及非幂等动作保护。

完成条件：AI 能在中断后继续，并且所有 PASS 可追溯。

### 阶段 E：真实项目验证

1. 建立代表性样本矩阵。
2. 使用真实 AI 工具执行完整任务。
3. 记录路由遗漏、规则冲突、Token、失败和恢复结果。
4. 整改并执行回归。

完成条件：至少完成软件、硬件/PCB 和设备测试三类代表性闭环，缺少条件的项目如实保持阻塞。

### 阶段 F：正式交付

1. 执行 Markdown 包白名单检查。
2. 执行全部规则、路由、行为、恢复和真实工程验收。
3. 生成 Runtime MD ZIP、SHA-256、使用说明和验证报告。
4. 未达到真实工程标准时保持 RC，不得直接标正式版。

## 15. 最终完成标准

V6.0 只有同时满足以下条件才能作为正式 Markdown 约束产品完成：

1. 用户 ZIP 只包含 Markdown。
2. 用户复制到工程后不需要安装 Python 或其他运行程序。
