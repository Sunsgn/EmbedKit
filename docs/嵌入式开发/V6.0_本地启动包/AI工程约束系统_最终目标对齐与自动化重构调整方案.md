# AI 工程约束系统最终目标对齐与自动化重构调整方案

## 1. 文档定位

本文是后续重构、测试和交付的开发基线，位于最终交付目录之外。最终交付给使用者的内容仍然只能是通用接入 Markdown 和自包含 ZIP，不得把本文、阶段报告、源码工作区或修改记录放入最终双文件。

后续实现发生冲突时，以本文定义的用户最终效果、权威来源、自动化边界、Token 硬预算和验收标准为准。不得因为现有命令、数据结构或测试已经存在，就降低最终目标。

## 2. 最终目标

最终系统是在项目后台自动工作的 AI 项目记忆、历史检索、开发约束、证据验证和任务连续性系统。

用户只负责：

- 提出和调整项目最终方向；
- 决定重大技术方案、范围变化和高风险操作；
- 判断最终成果是否符合预期。

用户不负责：

- 为每个项目重新编写约束；
- 手工创建任务、下一步、会话、锁或修订；
- 指定应该读取哪些历史文档；
- 管理证据 ID、总结 ID 或内部状态文件；
- 提醒 AI 保存失败方案、阶段总结或交接信息；
- 控制历史输出数量和 Token 分页。

每个项目只需一次接入同一套最终双文件。以后用户正常提出开发目标，AI 必须自动恢复项目、检索相关历史、保护已有成果、决定下一步、执行开发、验证结果并保存可恢复总结。

## 3. 最终用户体验

### 3.1 首次接入

用户把 Markdown 和 ZIP 放入项目后，只需告诉 AI：

```text
按照约束文档初始化，并继续完成这个项目。
```

AI 自动完成：

1. 确认唯一项目根和访问边界；
2. 校验 ZIP 身份与完整性；
3. 安全安装或升级运行系统；
4. 检查 Git、用户已有改动和项目事实；
5. 建立稳定项目身份与工作副本身份；
6. 识别已有工程、构建方式、规则和历史资料；
7. 建立项目方向基线、历史索引和统一状态；
8. 将用户目标转换为任务、验收条件和第一步；
9. 在没有真实阻断时继续实际开发。

### 3.2 后续会话

用户只需正常描述当前想完成的内容。AI 自动：

1. 运行单一高层会话入口；
2. 恢复当前任务和上次停止位置；
3. 判断用户输入是继续、补充、插入、改向、取消还是新任务；
4. 根据目标、文件、符号、模块和错误自动检索相关历史；
5. 生成受硬预算约束的当前上下文包；
6. 检查失败方案、已有决策、受保护成果和用户改动；
7. 给出简短的当前进度、风险和下一步；
8. 无需用户管理内部状态即可继续工作。

### 3.3 用户可见回执

普通情况下只向用户显示：

- 当前做到哪里；
- 本次准备做什么；
- 本次完成了什么；
- 使用了什么证据；
- 有什么风险、未知项或阻断；
- 是否需要用户决定；
- 下一步是什么以及理由。

内部会话 ID、锁 ID、实体修订、事件序号和证据 ID 默认不展示，只有诊断时才显示。

## 4. 权威来源和冲突优先级

系统不得把所有事实都归入一个状态文件。不同类型事实的权威来源如下：

1. 用户当前明确决定：项目方向和授权的最高权威；
2. 已确认的项目方向与决策：长期目标和范围权威；
3. 源码、Git、构建配置和真实设备状态：工程事实权威；
4. 测试产物、日志、设备数据和哈希：验证结果权威；
5. 结构化状态中心：任务、进度、总结和关联关系权威；
6. 带来源的历史文档：设计说明和历史资料；
7. AI 推断和建议：最低等级，必须标注可信度和验证方法。

发生冲突时不得静默选择。系统必须记录冲突来源、影响范围和推荐处理；只有方向性、破坏性或无法确定的冲突才提交用户决定。

## 5. 现状保留与重构边界

### 5.1 必须保留的已验证内核

以下能力增量演进，禁止推翻重写：

- ZIP 预检、哈希校验和安全提取；
- 安装、升级、恢复、原子回滚预检和包文件受控修复；
- 统一结构化状态、追加式事件链和可恢复事务；
- 任务、下一步、证据、总结和完成门禁；
- 会话租约、本机范围锁和乐观修订；
- Doctor、容量诊断、派生视图和权威历史校验；
- 通用项目识别、适配器、预算扫描和未知格式降级；
- 项目外维护工作区、完整回归和确定性重打包；
- 旧数据兼容、入口内容保留和用户文件保护。

### 5.2 需要重构的使用层

重点重构：

- 多命令人工流程改为单一自动编排入口；
- 最近历史恢复改为按当前目标和受影响对象检索；
- 分散 Markdown 与结构化状态建立稳定索引关系；
- 局部输出截断改为全局上下文硬预算；
- 手工节点总结改为自动触发；
- Git 检查、受保护成果和失败方案检查改为修改前自动门禁；
- 内部状态细节从普通用户交互中隐藏；
- 会话重复、孤儿会话和异常退出改为自动治理。

## 6. 目标架构

### 6.1 客户端薄入口层

Codex、Claude、Gemini、Copilot 等入口只负责：

- 加载受信任统一入口；
- 自动调用高层会话入口；
- 不复制业务规则；
- 检测本地运行能力和协议兼容性；
- 无本地 Python 时明确只读降级，不伪造状态写入。

### 6.2 自动编排层

新增面向 AI 的高层编排能力，日常只保留两个概念动作：

```text
进入项目并准备开发
结束本次工作并保存上下文
```

内部可实现为稳定命令或 API，但不得要求用户操作。进入动作必须完成健康检查、会话复用、意图分类、任务选择、历史检索、上下文预算和修改前门禁。结束动作必须完成差异检查、证据绑定、验收核对、总结、下一步、锁释放和安全 Git 检查点。

现有底层命令继续保留为诊断和高级接口，不作为日常主流程。

### 6.3 项目方向层

增加稳定的项目方向基线，至少记录：

- 最终目标；
- 当前优先级；
- 完成判定；
- 明确不做的范围；
- 不可破坏的成果；
- 已确认关键决策；
- 暂缓事项；
- 当前阶段；
- 最近方向调整及用户来源。

AI 每次开始任务和准备完成任务时都必须核对方向基线，禁止因局部便利偏离项目最终目标。

### 6.4 历史关联与检索层

建立以下稳定关联：

```text
用户意图 → 任务 → 文件/符号/模块 → 决策 → 失败方案
         → 验收条件 → 证据 → 总结 → Git/环境基线
```

历史检索优先级：

1. 相同文件或符号；
2. 相同模块、接口或数据模型；
3. 相同任务目标或验收条件；
4. 相同错误、测试失败或设备现象；
5. 已确认设计决策；
6. 已失败方案；
7. 已验证功能和保护项；
8. 最近相关修改；
9. 带依据的语义相似内容。

每条被选入上下文的历史必须携带：

- 稳定来源引用；
- 相关原因；
- 当前有效性；
- 证据状态；
- 对当前工作的约束；
- 可继续读取的命令或位置。

确定性位置和结构化关联优先于 AI 语义判断。语义检索只能辅助排序，不能创造事实。

### 6.5 修改保护层

AI 修改前自动检查：

- Git 工作区和用户已有改动；
- 当前分支、提交、worktree 和仓库身份；
- 相关项目决策；
- 相同或相似失败方案；
- 已验证功能和保护范围；
- 可能受影响的调用方、数据和测试；
- 是否需要设备、凭据或外部授权；
- 当前会话是否拥有有效任务上下文。

只靠文档无法从操作系统层面阻止 AI 修改文件，因此约束分为三层：

1. 受信任入口的行为约束；
2. 状态、证据和完成门禁的确定性强制；
3. 修改后的 Git 差异与受保护成果审计。

不得宣传为无法绕过的系统级沙箱。

### 6.6 Token 与上下文预算层

所有默认回执和上下文包必须经过统一预算器，不允许各命令自行决定输出规模。

建议默认硬边界：

- 普通会话上下文包保守估算不超过 4,000 Token；
- 普通单命令结构化回执保守估算不超过 2,000 Token；
- 同时设置 Unicode 字符、UTF-8 字节、对象数量和嵌套深度上限；
- 任一限制先到即停止继续展开；
- 输出必须保持合法 JSON，禁止直接截断序列化文本。

默认上下文预算建议分配：

| 内容 | 预算上限 |
|---|---:|
| 项目方向与当前用户意图 | 400 Token |
| 当前任务、进度与下一步 | 700 Token |
| 相关历史与决策 | 1,100 Token |
| 失败方案与受保护成果 | 600 Token |
| 当前任务规则 | 500 Token |
| 证据和环境摘要 | 400 Token |
| 分页、来源和继续查询信息 | 300 Token |

预算不足时优先保留：用户方向、当前任务、阻断、失败方案、受保护成果和下一步。低相关历史只返回数量、来源和分页游标。

所有分页结果必须返回：

- 实际字符数和字节数；
- 保守 Token 上界；
- 已返回项目数；
- 被省略项目数；
- `has_more`；
- 稳定游标；
- 下一条安全查询命令。

完整模式也必须分页。禁止单个 `--full` 绕过总预算；超量时返回预估、拒绝原因和分段读取方案。

Token 预算覆盖规则、历史、源码摘要、Git diff、工具输出和证据，不只覆盖状态 JSON。

### 6.7 生命周期自动化层

系统自动处理：

- 会话复用和孤儿会话恢复；
- 用户意图分类；
- 继续任务或建立任务；
- 验收条件生成与变更；
- 下一步生成；
- 修改前历史与保护检查；
- 失败尝试记录与去重；
- 重要节点检查点；
- 测试证据捕获；
- 阶段总结和完成总结；
- 未完成任务的交接；
- 会话结束、锁释放和视图更新。

用户输入变化必须区分补充、改向、扩范围、插入、取消和新任务。方向或验收变化需要保留前后关系，并使受影响证据和结论进入复核状态。

## 7. 数据模型调整

在现有状态模型上增量增加以下实体或等价结构。

### 7.1 项目方向 `project_direction`

关键字段：

- 稳定 ID 和修订；
- 最终目标；
- 优先级；
- 完成判定；
- 排除范围；
- 保护项；
- 用户确认来源；
- 生效时间；
- 被替代关系。

### 7.2 用户意图变化 `intent_change`

关键字段：

- 原始用户要求的受控引用或哈希；
- 归一化意图；
- 变化类型；
- 前后任务关系；
- 受影响验收、证据和总结；
- 是否需要用户决定。

不得在日志中保存密钥或不必要的完整敏感对话。

### 7.3 历史关联 `history_link`

关键字段：

- 来源实体；
- 目标文件、符号、模块或任务；
- 关系类型；
- 确定性依据；
- 相关分值；
- 有效性和失效原因；
- 来源 Git/环境基线。

### 7.4 上下文包 `context_capsule`

上下文包是派生结果，不是第二权威状态。必须记录：

- 当前方向和意图；
- 当前任务与下一步；
- 选中的历史和选择依据；
- 失败方案与保护项；
- 证据摘要；
- 未知项和用户决策；
- Token/字符/字节预算；
- 省略统计和继续查询游标；
- 来源状态修订和 Git 基线。

### 7.5 纠正记录 `correction`

错误事实、错误总结或过期结论不得静默覆盖。纠正记录必须保存：

- 被纠正对象；
- 纠正原因；
- 新事实或结论；
- 支撑证据；
- 影响范围；
- 相关任务和总结复核状态。

### 7.6 工作副本身份 `workspace_identity`

至少关联：

- 项目 ID；
- 仓库身份；
- 绝对路径的本地引用；
- 分支；
- 提交；
- worktree；
- 环境和工具链指纹。

路径移动、分支切换、rebase、cherry-pick 和仓库复制后必须能够识别身份变化，不能把不同工作副本错误当成同一现场。

## 8. 历史有效性与纠错

以下变化必须触发相关结论复核：

- 相关源码、构建配置或依赖变化；
- Git 基线、分支或工作副本变化；
- 工具链、设备、固件或运行环境变化；
- 用户方向或验收条件变化；
- 原始输入、证据或产物哈希变化；
- 新证据与旧结论冲突。

恢复结果必须区分：

- 已验证且当前有效；
- 以前验证但环境已经变化；
- 静态推断；
- AI 建议；
- 已失效；
- 数据不足无法判断。

用户可以纠正错误记录。系统保留旧记录、纠正关系和审计事件，并传播相关复核状态。

## 9. Git 与检查点策略

默认策略：

- 修改前记录 Git 基线和用户改动；
- 一个功能增量通过对应测试后，可创建仅包含当前任务文件的本地检查点；
- 不得自动 push；
- 不得夹带用户无关改动；
- 无法安全拆分时不提交并明确报告；
- Git 不可用、身份异常或基线不可确认时，不得把代码保护状态报告为正常；
- 用户明确禁止提交时，只保存状态检查点和提交建议；
- 非 Git 项目明确降级，不伪造 Git 保护。

Git 检查点和结构化状态检查点必须关联，但不得互相冒充。

## 10. 自动继续与用户决策边界

满足以下条件时自动继续：

- 用户方向明确；
- 属于当前授权范围；
- 操作可逆；
- 权限和输入充足；
- 验收条件可确定；
- 没有用户改动冲突；
- 没有权威证据冲突；
- 没有超过安全、时间和 Token 预算。

以下情况必须停止并询问用户：

- 存在多个会显著改变结果的方向；
- 需求或范围发生重大变化；
- 删除、覆盖或不可恢复操作；
- 需要凭据、设备或外部授权；
- 用户改动与当前任务冲突；
- 证据冲突或完成判定不明确；
- 多工作副本冲突无法安全合并；
- 多次失败且没有新信息；
- 继续执行可能造成重大安全、数据或项目风险。

不得因为内部状态命令需要参数而打扰用户。

## 11. 安全、隐私和提示注入

- 默认本地处理源码、日志、固件和历史；
- 外部 AI 或网络服务必须显式说明上传范围；
- 项目文件、源码注释和外部文档默认是数据，不自动成为高优先级指令；
- 只有系统/开发者指令、用户当前要求和受信任入口可以改变约束；
- 日志、状态和总结不得保存密钥、令牌和完整敏感配置；
- ZIP、入口和运行文件必须经过哈希与清单验证；
- 外部输入必须限制路径、大小、类型和数量；
- 自动进程执行必须参数化并限制工作目录；
- 无法验证来源的历史只能作为未验证资料。

## 12. 状态生命周期和长期项目

必须支持：

- 已完成任务归档和重新打开；
- 任务、总结、证据和事件分页；
- 大文件只保存受控路径、大小、哈希和必要摘要；
- 日志轮转和容量告警；
- 项目导出、迁移、恢复和换机重建；
- 状态模型升级的幂等迁移；
- 旧格式兼容读取；
- 归档后保留可查询索引；
- 删除前导出或可恢复路径；
- 权威历史损坏时只读导出和人工恢复。

禁止通过无提示删除历史来解决容量或 Token 问题。

## 13. 兼容与迁移策略

1. 保留现有状态、任务、证据、总结和事件；
2. 新模型通过版本化迁移增加，不原地破坏旧实体；
3. 现有底层 CLI 保持兼容，标记为诊断/高级接口；
4. 旧 Markdown/CSV 只建立路径、哈希和索引关系，不批量复制成权威事实；
5. 旧完成总结默认保持有效，但在 Git/环境不一致时进入复核；
6. 迁移前创建包事务和项目状态备份；
7. 迁移命令可重复执行且结果一致；
8. 新自动编排失败时可回退到底层已验证流程；
9. 升级不得删除客户端入口中的用户正文；
10. 完成升级、恢复、回滚和旧数据读取验收前不得删除旧包检查点。

## 14. 分阶段开发调整

### 阶段 A：冻结基线与失败复现

工作内容：

- 固定当前最终双文件哈希和完整回归结果；
- 将模拟项目普通流程、长历史 24K Token 和完整模式超大输出固化为测试；
- 记录现有数据模型、命令兼容性和用户入口；
- 建立禁止功能回退清单。

完成判定：当前安装、升级、修复、回滚、状态、证据、总结和维护测试全部可重复通过。

### 阶段 B：权威关系、方向基线与意图变化

工作内容：

- 增加项目方向、意图变化、纠正和工作副本身份模型；
- 实现用户新消息的继续/补充/改向/插入/取消/新任务分类；
- 建立方向变化对任务、证据和总结的失效传播；
- 增加旧状态迁移。

完成判定：用户改变方向后，系统能够解释变化、保留旧目标、重新计算受影响范围并只在必要时询问用户。

### 阶段 C：历史关联索引与相关性检索

工作内容：

- 建立任务、文件、符号、模块、决策、失败方案、证据和总结关联；
- 增量索引旧 Markdown 历史资料；
- 实现确定性相关性排序和选择依据；
- 实现结论有效性和环境漂移传播；
- 提供按文件、符号、任务、错误和决策分页查询。

完成判定：准备修改一个已有文件前，系统能够自动返回相关决策、失败方案、已验证功能和来源位置，不依赖全量历史读取。

### 阶段 D：统一上下文预算器

工作内容：

- 为所有高层回执建立统一字符、字节、对象和保守 Token 上限；
- 实现优先级裁剪、合法 JSON、分页游标和继续命令；
- 将完整模式改为分页模式；
- 限制输入文本、验收条件、数组和单实体大小；
- 提供输出预算统计和超量错误码。

完成判定：普通和压力测试中任何默认回执不超过预算；30 个超长活动任务仍能在预算内恢复关键状态；完整历史不能一次性输出超量内容。

### 阶段 E：自动编排入口

工作内容：

- 实现单一进入动作；
- 自动复用会话、恢复任务、分类意图、加载相关历史和生成上下文包；
- 自动生成任务、验收条件和下一步；
- 自动处理节点检查点、失败记录、证据关联和完成总结；
- 实现单一结束动作和异常退出恢复；
- 普通回执隐藏底层 ID 和修订。

完成判定：模拟使用者从首次接入到跨会话完成任务，全程不需要输入任何状态管理命令或内部 ID。

### 阶段 F：Git、保护项和非合规检测

工作内容：

- 修改前自动检查 Git、用户改动、失败方案和保护项；
- 建立文件差异与任务关联；
- 实现安全本地检查点策略；
- 检测绕过高层入口的状态和文件变化；
- 支持分支、worktree、路径移动和仓库复制；
- Git 异常时阻断错误的“正常”结论。

完成判定：用户改动不会被覆盖；已验证功能变化会触发回归；Git 不可用时不会伪称保护有效。

### 阶段 G：最终入口、跨客户端与交付

工作内容：

- 将最终使用文档压缩为首次接入和故障恢复说明；
- 各客户端薄入口统一调用自动编排；
- Windows、Linux、macOS 和主要客户端执行验收；
- 完成旧包升级、换机恢复、自维护和确定性双打包；
- 最终目录只保留新 Markdown 和 ZIP；
- 删除临时源码、模拟项目和测试产物；
- 创建单一可回退 Git 检查点，不自动 push。

完成判定：最终双文件独立完成全部验收，使用文档不包含开发过程和版本演进记录。

## 16. 量化完成标准

最终发布至少满足：

1. 用户首次只提供最终双文件和项目目标即可完成初始化；
2. 后续会话不要求用户输入内部状态命令；
3. 一次高层进入动作恢复项目、任务、相关历史和下一步；
4. 历史结果说明相关原因、来源和有效性；
5. 相同失败方案再次实施前能够被发现；
6. 修改受保护功能前自动触发影响和回归检查；
7. 普通上下文包保守估算不超过 4,000 Token；
8. 普通单命令回执保守估算不超过 2,000 Token；
9. 任何完整历史查询都不能绕过分页和总预算；
10. 用户无需管理会话、锁、修订、任务、证据和总结 ID；
11. Git 不可用或基线异常时不会报告为正常保护状态；
12. AI 结论明确区分事实、证据、推断和建议；
13. 崩溃后能恢复到最后已提交状态；
14. 旧任务、证据、总结和用户入口内容在升级后不丢失；
15. 自维护只能从受信任 ZIP、项目外工作区和完整回归生成新包；
16. 最终目录严格只包含使用 Markdown 和 ZIP；
17. 最终使用文档不包含开发过程、阶段记录或版本演进内容；
18. 自动化测试不能替代真实模拟项目和失败路径验收。

## 17. 明确非目标

- 不实现编译器、链接器或完整 IDE；
- 不替代 Git、Keil、IAR、CMake、Make 或厂商工具链；
- 不承诺只靠 Markdown 从操作系统层面绝对阻止 AI 修改文件；
- 不把所有项目资料永久塞入模型上下文；
- 不用删除历史解决 Token 问题；
- 不要求用户理解内部状态机；
- 不为某个样本项目写死规则；
- 不自动 push、不上传源码、不保存不必要敏感信息；
- 不把 AI 推断显示为已验证事实。

## 18. 开发执行原则

1. 先固化失败测试，再修改实现；
2. 优先扩展现有内核，不平行创建第二套状态系统；
3. 每阶段保持旧数据可读和底层诊断接口可用；
4. 每阶段先运行专项测试，再运行完整回归和模拟项目验收；
5. 一个功能增量一个 Git 检查点，不夹带用户无关改动；
6. 不以 Token 节省为理由降低证据、安全或兼容性；
7. 不以自动化为理由越过用户关键决策；
8. 不以重构为理由删除已有能力；
9. 阶段未达到量化完成标准时不得更新最终双文件；
10. 最终交付前必须再次从使用者角度执行完整流程。

## 19. 最终判定

重构完成后的系统必须达到：

> AI 自动知道项目历史、当前进度、下一步、失败方案和已有结论；在合理、可验证、受硬预算约束的范围内约束开发行为，尽量避免重复分析和重复失败。用户只把控项目完成方向和关键决策，不为每个项目或任务重复管理约束系统。

如果用户仍需要频繁执行状态命令、指定历史文件、管理内部 ID、提醒 AI 总结，或者长历史能够突破默认 Token 预算，则不能认定为最终完成。
