# 嵌入式产品项目目录框架

- 模板版本：V1.20
- 最后更新：2026-11-13
- 适用：嵌入式软硬件项目

本文件只管理项目目录与资料；普通代码、构建和调试任务不读取。目录任务统一按“AI快速执行摘要”执行，其余章节仅提供参数、分类和验收细节，不构成第二套流程。

## 使用方式

- 首次：让AI完整读取本文件，再指定 `NEW`、`ORGANIZE`或只读`AUDIT`；`ORGANIZE`可指定工程容器，默认`program/`。
- 后续：让AI核对Profile后执行；新增领域用`EXTEND`并给出具体分支，不补其他目录。

## AI 快速执行摘要

本节是目录任务的核心入口。首次使用、读取状态缺失、框架版本/SHA-256变化或修改本框架时完整读取全文；状态一致的后续目录任务按任务路由读取。普通代码、构建和调试任务不读取本框架，只读Profile和工程约束。

### 单次执行原则

- 本节定义唯一控制流程；后文的迁移六阶段、分类表和检查项只展开本流程，不得再次启动盘点、确认、迁移、构建或报告。
- 同一批次的清单、哈希、引用搜索、构建结果和Git状态只采集一次，后续章节直接复用证据；仅在源数据、范围或文件状态变化后重做受影响项。
- `ORGANIZE` 只请求一次批次确认；确认范围不变时不得按目录、阶段或检查项重复询问。

### 读取状态

1. 目录操作前先读 `.ai/PROJECT_PROFILE.md`；根目录首次出现框架、Profile不存在/缺少读取状态、版本或哈希不一致时，必须从第一行读到最后一行。
2. 全文读取后，`NEW`、`ORGANIZE`、`EXTEND` 将版本、SHA-256和日期写入Profile；严格 `AUDIT` 只报告，不写文件。
3. 版本、哈希和日期一致时按任务路由读取；用户要求全文审核或修改本框架时仍须全文读取。
4. 读取规则不授予删除、覆盖、移动、Git或外部系统操作权限。

### 模式与项目判定

| 模式 | 适用情况 | 默认行为 |
| --- | --- | --- |
| `NEW` | 除框架、版本控制元数据和占位说明外无实际资料 | 建立最小基线和当前使用分支 |
| `ORGANIZE` | 已有源码、工程、资料、测试或Git历史 | 盘点、映射、确认后迁移 |
| `EXTEND` | 已初始化项目新增一个领域 | 只创建当前分支 |
| `AUDIT` | 仅检查 | 保持只读 |

用户描述与实际内容不一致时报告并确认；无法判断模式时不默认整理。

### 核心边界

1. 已确认源码工程按顶层边界完整迁移，内部 `docs/tests/samples/tools/build` 和已有产物不拆分；只分类边界外资料。
2. 保留脏工作区和唯一工作主文件；冻结快照需清单及哈希。
3. 删除、覆盖、清理、生产配置和Git操作按授权表执行，不伪造任何业务资料。
4. 迁移按六阶段验证；最终复查根目录残留文件及目录，不以主要源码迁入作为整批完成依据；只创建真实需要的目录，不自动建 `.gitkeep`。

### 已有项目两轮闭环

`ORGANIZE` 默认两轮：

1. 第一轮只读盘点全部根目录项目，确认源码顶层边界，输出迁移映射、保持项、冲突、恢复保障、验证计划和最终根目录；只有不满足免备份条件时才建立独立备份。所有破坏性操作按精确路径合并请求一次确认。
2. 用户确认后，第二轮连续完成迁移、构建前哈希、引用更新、原有入口验证和最终审核；确认范围内不重复询问。

仅在出现新增破坏性操作、冲突/哈希不一致、源不可读、边界判断错误、用户改变范围或环境无法验证时暂停并重新确认。用户最初的整理指令不代替破坏性操作确认。

```text
[整理批次计划]
源码边界：<路径及证据>
迁移映射：<全部源→目标；保持/隔离/待确认项>
破坏性操作：<精确路径、影响；无则写无>
恢复保障：<源文件保留、Git恢复、独立备份或其它方式；说明是否满足免备份条件>
验证：<构建前数量/字节/哈希、引用、原有入口及产物>
```

### 任务路由

状态一致时按需读取：`NEW`→摘要+初始化；`ORGANIZE`→摘要+目录映射+六阶段；`EXTEND`→目录映射+通用约束；发布/生产→快照+大文件规则；`AUDIT`→摘要+映射+验收矩阵并保持只读。

### 首次启动与归位

1. 完整读取根目录框架并检查Git及 `.ai/`；目标不存在时归位并校验大小、SHA-256，已存在时不覆盖而报告冲突。
2. 生成或核对Profile、README、`.gitignore`和AI入口；失败时保留源文件并报告。

## 初始化与生成规范

### 新项目最小基线

确认是空白新项目后，只建立根文件和四个核心入口，不预建二级业务目录：

```text
项目根目录/
├─ AGENTS.md
├─ CLAUDE.md
├─ README.md
├─ .gitignore
├─ .ai/
│  ├─ 项目目录框架.md
│  ├─ PROJECT_PROFILE.md
│  └─ 工程规则/          # 有项目专属约束时
├─ program/
├─ 开发文档/
├─ 硬件原理图PCB/
└─ 测试/
```

空目录不创建 `.gitkeep`，除非用户明确要求Git保留。初始化前只确认：是否空白项目、当前立即开展的领域、仓库管理范围，以及是否有文件需要保留或迁移；非关键未知项写“待确认”。

### Profile最小模板

```markdown
# 项目档案
- 目录框架版本：V1.20
- 目录框架 SHA-256：{实际值}
- 目录框架完整读取日期：{YYYY-MM-DD或未读取}
- 生成/复核日期：{YYYY-MM-DD}

## 项目事实
- 名称/产品/范围/阶段：{实际值或待确认}
- 启用目录及用途：{清单}
- 构建入口及恢复方式：{实际值或待确认}
- 存储方案/工作主文件/冻结快照：{实际值或待确认}
- 项目例外与待确认：{真实清单或无}
```

花括号必须替换；已有Profile逐项更新，不整体覆盖用户事实。

### README、忽略规则和AI入口

README只写真实目录、入口和最小验证；`.gitignore`精确匹配并用 `git check-ignore` 验证；根AI入口不写凭据或本机配置，只合并下列机制：

```markdown
仅在目录初始化、创建、整理、迁移、扩展或审核时读取 .ai/项目目录框架.md。首次目录任务、读取状态缺失或版本/SHA-256变化时完整读取全文；状态一致时按任务路由读取。普通代码、构建和调试任务只读Profile及工程约束。读取不代表获得删除、覆盖、移动或Git授权。
```

## 全局不变量

1. `NEW` 只建立四个核心入口和当前需要的分支；其他模式也只创建有真实资料或明确用途的目录，不自动创建 `.gitkeep`。
2. 源码与构建路径优先使用英文；同一可编辑受控文件只保留一个工作主文件，受控冻结快照除外。
3. 未知内容先读标题和关键段落；不按扩展名批量归类，不确定时保持原位并列入同一批次确认。
4. AI只依据真实资料归类或生成空模板，不伪造参数、结果、批准、签名、认证、生产或发布记录。

## 安全确认与 Git 授权边界

| 操作 | 默认权限 | 执行要求 |
| --- | --- | --- |
| 只读盘点、搜索、状态检查 | 允许 | 不改变文件、Git索引或外部状态 |
| 创建当前任务所需的新目录/模板 | 允许 | 不覆盖已有内容，不生成虚假业务数据 |
| 移动或重命名已有文件 | 条件允许 | 先给出映射、检查引用和冲突；高影响或不确定时先确认 |
| 删除、覆盖、清空、清理旧目录 | 禁止自动执行 | 必须列出精确目标、恢复方式和影响，取得单独确认；是否需要独立备份按“迁移备份规则”判断 |
| 修改生产配置、证书、密钥流程 | 禁止自动执行 | 必须确认环境、权限和回滚方案；不得接触真实私钥 |
| `git add` / `git commit` | 仅在用户明确要求时允许 | 只暂存本次范围，提交前检查差异，不混入既有修改 |
| `git push`、强推、改写历史 | 禁止自动执行 | 普通推送也需明确授权；强推或历史改写需单独风险确认 |

用户要求“整理、修复、生成目录”不等于授权提交或推送。若工作区已有修改，AI 必须先识别并保持原状；无法隔离本次变更时停止并说明。

## 通用文件约束

- 文档优先Markdown；二进制资料记录来源、版本、负责人和时间。受控文件建议 `{产品或模块}_{资料名}_V{版本}_{YYYYMMDD}.{扩展名}`，草稿加 `_DRAFT`，正式版不覆盖；源码、脚本和配置用英文名。
- 不提交密码、Token、私钥、真实设备密钥或敏感 `.env`；公开证书/公钥注明用途和轮换方式。
- `.gitignore` 只精确匹配已确认输出，不用 `/program/**/Debug/` 等宽泛规则，也不全局忽略 `*.cmake`、Makefile、`*.lds`、库文件或 `cmake/`。
- 测试、生产、校准和发布资料可追溯到产品、软硬件版本、时间及执行人/设备；归属不明时保持原位并列入批次确认。

## 权威文件与冻结快照

- 专业目录保存唯一可编辑主文件；其他普通目录用索引或相对链接，不复制可编辑副本。
- `release/`、`manufacturing/`、`生产备份/` 可保存独立只读快照；清单记录来源/提交、型号、软硬件版本、时间、大小、SHA-256和批准状态，修订时新建版本且不得覆盖。

## 迁移备份规则

- 独立备份不是迁移的强制前置条件。迁移过程保留源文件，且完整映射、文件数量、总字节、逐文件 SHA-256、路径引用和原入口构建/功能验证全部通过后才清理源文件时，可以不另建备份。
- 已跟踪文件使用可恢复历史的 `git mv` 时，也可作为恢复保障；必须确认对象已进入 Git 历史、工作区原有修改未丢失，并完成同等完整性和功能验证。
- 存在目标覆盖或同名冲突、源文件不可重建、迁移过程中不能保留源、文件未受版本控制、元数据必须保真、校验无法完整执行或任一校验不通过时，必须先建立并验证独立备份，或继续保留源文件而不清理。
- “无需独立备份”只免除额外副本，不免除破坏性操作确认、迁移清单、逐文件校验、引用检查、构建/功能验证和最终根目录复查。

## 大文件与二进制资料存储

- Profile声明普通Git、Git LFS或外部存储。二进制达到10 MiB或频繁修改时评估LFS/外存；达到50 MiB不得直接进入普通Git历史。
- LFS提交 `.gitattributes` 并验证取得实际对象；外存保留受控位置、版本、大小和SHA-256。固件、发布包和备份必须能按清单恢复。
- 切换存储方式不得删除文件或改写历史，除非另获确认且已有可验证备份。

## 目录内容与约束

### 根文件

- `AGENTS.md`、`CLAUDE.md`：平台入口，只指向框架、Profile和工程规则。
- `README.md`：真实目录、构建入口和最小验证；`.gitignore`：仅精确忽略已确认的缓存、日志、本机环境和输出，并用 `git check-ignore` 防止误伤构建输入或正式产物。
- `.ai/PROJECT_PROFILE.md` 保存项目事实；本框架保存通用目录规则；`.ai/工程规则/` 保存编码、构建和调试约束。未知事实写“待确认”，不得混写。
- 默认一个仓库对应一个产品或共享基线系列；独立产品不得混用BOM、发布和生产归档，多型号必须标明适用范围。

### `program/` 固件与软件

源码边界以用户指定目录为准；未指定时按构建入口、工程文件、应用、驱动/中间件和链接配置确定共同顶层。只判断顶层边界，不识别或审计 IDE、编译器、许可证及工程内部文件；无法确认时保持原位并纳入一次性确认。

| 对象 | 唯一归属规则 |
| --- | --- |
| 已确认源码工程/SDK | 全部原样迁入唯一工程容器，保留相对路径及内部 `docs/tests/samples/tools/build`、工程配置和已有产物，不拆分、不清理 |
| 工程外参考程序 | `开发文档/参考资料/参考程序/` |
| 工程外技术、过程或协议资料 | `开发文档/技术文档/`、`开发文档/开发记录/` 或 `开发文档/通信协议/` |
| 协议草稿、备份稿和旧版本 | 按内容归入 `开发文档/通信协议/`，保留可辨识的原名及版本状态；归位不代表批准为权威版本，不覆盖现行版本 |
| 工程外构建错误、日志和测试结果 | `测试/测试报告/异常分析/` 或对应测试分支 |
| 工程外独立工具包 | 根级 `tools/` 整体保存；项目自行维护的测试辅助源码才进入 `测试/工具/` |

多个独立工程可在容器内按功能分目录。用户指定 `project/` 等例外时直接作为唯一容器并记录在Profile，避免再建 `program/` 或形成 `project/project/`。构建验证应进入工程容器作为工作目录，再执行其原有入口；仅从仓库根目录调用容器内脚本，不足以证明依赖相对路径的打包流程可用。本节只定义边界和归属；迁移、哈希、引用及原入口验证统一执行后文六阶段一次。

目录名称即归属语义并遵守通用约束。特殊边界：`开发文档/版本发布/`放发布文档、根级`release/`放产物；认证过程放硬件目录、生效原件放合规目录；`制造工程/`是转产开发、`manufacturing/`是当前现场资料、`生产备份/`是冻结归档；产品资料保留可编辑源和授权依赖。

## ORGANIZE 六阶段明细

本表是“两轮闭环”的阶段展开，不是额外流程：阶段1–2在第一轮各执行一次，阶段3–6在确认后的第二轮各执行一次。目标是内容不丢失、版本不混淆、引用不中断、结果可验证且可回滚。

| 阶段 | 单次动作与通过条件 |
| --- | --- |
| 1. 只读盘点 | 覆盖全部根目录一级项目和隐藏文件；清单记录源/目标相对路径、类型、大小、时间、SHA-256、文件/目录数、总字节、Git状态、重要属性、链接/联接/嵌套仓库、LFS/子模块/执行权限及有效引用。无法读取、名称冲突、非法路径或哈希失败的分支停止。文件系统专有元数据仅在属于交付要求时纳入。 |
| 2. 映射与确认 | 每个一级项目标记“迁移/保持/工程内部保持/仓库外隔离/待确认”；只建必要目录，不拆工程或混合型号/版本。目标同名先比哈希，不同则保留双方并待确认。一次列全冲突、精确破坏性路径、恢复保障、是否满足免备份条件、验证命令及最终根目录，合并请求一次确认。 |
| 3. 可回滚迁移 | 优先使用规范化字面量路径复制并保留源；已跟踪文件可按计划用 `git mv`，仍需校验。不满足免备份条件时，先建立并验证独立备份。禁止模糊通配、猜测盘符、未确认覆盖或提前清理；错误时停止并按清单恢复，不能带着部分成功继续。 |
| 4. 构建前完整性 | 在任何构建前一次比较相对映射、数量、大小、总字节和逐文件SHA-256，并检查零字节/额外文件、属性、链接、LFS实际对象、子模块提交和执行权限；二进制至少校验哈希，条件允许时打开检查。固定结果供后续复用，不能只凭退出码或目测通过。 |
| 5. 引用与功能 | 一次搜索旧路径并只更新当前有效引用，历史记录可保留旧路径；检查路径大小写和分隔符，确认参考程序未进入正式构建。使用原有入口普通构建/测试，不识别工具链且默认不 `Clean`、Rebuild或删除产物；记录命令及产物路径、大小、时间、SHA-256。无法运行则标记未验证。最后检查Git差异无计划外变化。 |
| 6. 清理与报告 | 仅在阶段4–5通过且精确清理路径已确认时清理源；范围变化须重新确认，否则保留源。按阶段1清单复查根目录每个原始项目及隐藏文件，逐项标明已迁移、按约束保留、仓库外隔离或待确认；剩余的单个文件和旧目录不能因主体迁移完成而遗漏。输出迁移报告和最终目录审核，失败项明确标记未完成。 |

阶段6报告格式：

```text
[迁移验证]
源文件数：<数量>，目标文件数：<数量>，结果：一致/不一致
源总字节：<字节数>，目标总字节：<字节数>，结果：一致/不一致
SHA-256：<通过数量>/<总数量>
路径引用检查：<结果>
构建/测试：<实际命令与结果>
冲突与未迁移项：<清单或无>
源文件状态：仍保留/已单独确认后清理
恢复保障：<无需独立备份及依据，或备份/恢复步骤>
```

任何必需项未通过时保留源数据并报告未完成，不使用“基本完成”代替失败状态。

## 最终验收矩阵

最终审核只读取并汇总本批次已有证据，不重复扫描、哈希或构建；证据缺失时标记未验证，仅补做缺失项。

| 验收面 | 复用证据检查 |
| --- | --- |
| 目录 | 所有根级项目已覆盖；新增目录有真实用途；无非预期空目录、同义重复目录或错误 `.gitkeep` |
| 边界 | 源码顶层完整、参考程序未入正式构建、根级 `tools/` 与 `测试/工具/` 未混用 |
| 完整性与可用性 | 六阶段报告已含数量、字节、逐文件哈希、引用、原入口结果、产物及源文件状态 |
| 资料与安全 | 受控资料可追溯且未伪造；无凭据、私钥、未脱敏数据、乱码、异常文件名或未处置的差异副本 |
| 当前入口 | README、Profile、AI入口、脚本和说明使用当前路径；旧路径仅存在于明确历史记录 |
