# 嵌入式项目目录与工程框架具体约束

- 框架来源：`项目目录框架_V1.20`
- 适用范围：嵌入式软硬件项目的目录初始化、整理、迁移、扩展、审核、归档和交付
- 强制边界：普通软件开发、硬件设计和测试执行不得为“顺便整理”而加载或改造整个目录框架

## 1. 模式与使用入口

目录任务必须先确定模式：

| 模式 | 适用情况 | 默认行为 |
|---|---|---|
| `NEW` | 除约束、版本控制元数据和占位说明外无实际资料 | 建立最小基线和当前需要分支 |
| `ORGANIZE` | 已有源码、工程、资料、测试或Git历史 | 盘点、映射、确认后迁移 |
| `EXTEND` | 已初始化项目新增一个专业领域 | 只创建当前分支 |
| `AUDIT` | 仅检查目录与资料 | 全程只读 |

无法判断模式、用户描述与实际内容冲突或工程边界不明时，不得默认整理。

## 2. 读取和状态规则

- 首次目录任务、Profile缺少读取状态、框架版本/SHA-256变化或修改本框架时，完整读取本文件及项目Profile。
- 后续目录任务在版本、哈希和日期一致时只读取命中章节，不重复盘点未变化范围。
- `NEW/ORGANIZE/EXTEND` 将框架版本、SHA-256和复核日期写入Profile；严格 `AUDIT` 不写文件。
- 读取框架不授予移动、覆盖、删除、Git或外部系统操作权限。

## 3. 新项目最小基线

确认是空白新项目后，只建立以下根结构：

```text
项目根目录/
├─ AGENTS.md
├─ CLAUDE.md
├─ README.md
├─ .gitignore
├─ .ai/
│  ├─ PROJECT_PROFILE.md
│  └─ 工程规则/
├─ program/
├─ 开发文档/
├─ 硬件原理图PCB/
└─ 测试/
```

- 只创建当前真实需要的目录，不预建全部二级目录，不自动创建 `.gitkeep`。
- `README.md`只写真实目录、入口和最小验证；`.gitignore`只精确忽略已确认缓存、日志和输出，并用 `git check-ignore` 验证。
- 源码与构建路径优先使用英文；花括号占位符必须替换，不能作为真实目录名保留。

## 4. 一级目录映射

| 一级目录 | 唯一职责 |
|---|---|
| `program/` | 完整正式源码工程/SDK，内部结构原样保留 |
| `tools/` | 正式源码边界外的独立工具包 |
| `开发文档/` | 需求、系统设计、通信协议、技术文档、开发记录、参考资料、发布文档 |
| `硬件原理图PCB/` | 当前原生设计、制造资料、器件资料、硬件版本、EMC与认证过程资料 |
| `测试/` | 计划、用例、自动化、HIL、产测、测试工具和报告 |
| `项目管理/` | 范围、计划、预算、风险、会议决策和状态报告 |
| `工业设计与结构/` | ID、结构、热、材料工艺、公差、模具和结构样机 |
| `阶段评审/` | 立项、EVT、DVT、PVT、MP和退市评审 |
| `质量与可靠性/` | 质量策划、FMEA、可靠性、失效分析和CAPA |
| `制造工程/` | DFM/DFA/DFT、工艺、工装、产线、试产和良率改善 |
| `供应链/` | 供应商、AVL、成本、采购、来料、替代料和停产风险 |
| `合规与法规/` | 标准、EMC、安规、无线、环保、市场准入和生效证书 |
| `配置与变更管理/` | 产品基线、整机BOM、兼容矩阵、追溯矩阵、ECO/ECN、偏差和变更验证 |
| `产品安全/` | 安全需求、威胁模型、安全架构、升级、密钥流程、SBOM和漏洞响应 |
| `生命周期与售后/` | 上市移交、RMA、维修备件、市场质量、维护升级、停产和召回 |
| `产品资料/` | 产品规格、说明书、标签、合格证、包装、宣传和售后资料 |
| `manufacturing/` | 当前现场固件、作业指导、工位配置和校准记录 |
| `生产备份/{产品代次}/` | 按代次冻结的源程序、硬件、文档、下载文件、结构、BOM和工艺快照 |
| `release/{型号}_V{版本}_{YYYYMMDD}/` | 正式产物、说明、兼容矩阵、验证报告、清单和SHA-256 |

根级同义目录不得自动并存或合并。`src/firmware/sdk/程序`、`docs/文档`、`test/tests`、`production/生产资料`、`releases/发布包`必须先比较内容、引用和职责，再纳入一次确认。项目确有 `project/`、`records/` 等例外时，在Profile登记唯一用途。

## 5. 正式源码工程边界

- 源码边界优先使用用户指定目录；未指定时依据构建入口、工程文件、应用、驱动/中间件和链接配置确定共同顶层。
- 已确认源码工程/SDK整体迁入唯一工程容器，保留内部 `docs/tests/samples/tools/build`、相对路径、工程配置和已有产物；禁止按文件类型拆散。
- 工程外参考程序归入 `开发文档/参考资料/参考程序/`；工程外协议归入 `开发文档/通信协议/`；工程外构建/测试日志归入 `测试/测试报告/`。
- 工程外独立工具包进入根级 `tools/`；项目维护的测试辅助源码才进入 `测试/工具/`。
- 无法确认某文件是否属于正式构建时保持原位并列入同一批次确认。

## 6. 文件、权威源与冻结快照

- 同一可编辑受控对象只保留一个工作主文件；其他普通目录使用索引或相对链接，不复制可编辑副本。
- `release/`、`manufacturing/`、`生产备份/`可以保存只读快照；清单必须记录来源提交、型号、软硬件版本、时间、大小、SHA-256和批准状态。
- 文档优先Markdown；二进制资料记录来源、版本、负责人和日期。
- 受控文件建议使用 `{产品或模块}_{资料名}_V{版本}_{YYYYMMDD}`；草稿增加 `_DRAFT`，正式版不得覆盖旧正式版。
- 不得提交密码、Token、私钥、真实设备密钥或敏感 `.env`。

## 7. 大文件与存储

- Profile声明普通Git、Git LFS或外部存储方案。
- 二进制达到10 MiB或频繁修改时评估LFS/外存；达到50 MiB不得直接进入普通Git历史。
- LFS必须提交 `.gitattributes` 并验证实际对象；外部存储必须记录受控位置、版本、大小和SHA-256。
- 切换存储方式不得删除文件或改写历史，除非另获明确授权并已有可验证备份。

## 8. ORGANIZE 两轮六阶段闭环

第一轮只读完成：

1. 全量盘点根目录一级对象、隐藏文件、Git状态、链接/联接、嵌套仓库、LFS和子模块。
2. 建立完整“源→目标”映射，将每项标为迁移、保持、工程内部保持、仓库外隔离或待确认。
3. 列出同名冲突、精确破坏性目标、恢复保障、验证命令和最终根目录，一次请求确认。

用户确认后第二轮连续完成：

4. 优先复制并保留源；已跟踪文件可按计划 `git mv`，禁止通配猜测和未确认覆盖。
5. 构建前比较相对映射、文件数量、总字节和逐文件SHA-256，检查额外/零字节、链接和LFS对象。
6. 更新有效路径引用，使用原有入口在新的正式工作目录完成构建/功能验证，再复查根目录残留和Git差异。

仅在新增破坏性操作、冲突/哈希不一致、源不可读、工程边界错误、用户改变范围或验证无法执行时暂停重新确认。

## 9. 备份、恢复与删除

- 迁移全程保留源文件，完成映射、数量、字节、逐文件哈希、引用和原入口验证后才允许讨论清理。
- 已跟踪文件使用可恢复历史的 `git mv` 可作为恢复保障，但必须确认对象已进入历史且用户原修改未丢失。
- 存在覆盖/同名冲突、源不可重建、无法保留源、未受版本控制、元数据必须保真或校验不完整时，必须先建立并验证独立备份。
- 删除、覆盖、清空和清理旧目录必须列出精确路径、影响和恢复方法，获得单独确认；“整理项目”不等于删除授权。
- 失败时停止当前分支并按映射恢复，禁止带着部分成功继续后续清理。

## 10. Git与目录任务验收

- `git add/commit/push`分别授权；目录整理不自动授权提交或推送。
- `.gitignore`不得宽泛忽略正式构建输入、链接脚本、库、Makefile、CMake或发布产物。
- 验收必须核对：所有源对象有归属、工程内部未被拆散、无未解释重复工作主文件、数量/字节/哈希一致、引用有效、原入口可用、根目录无遗漏、Git差异只含本批次。
- `AUDIT`全程只读；发现问题输出精确路径、当前归属、建议目标、风险和所需授权，不自动整改。
- 最终报告列出模式、框架版本/SHA-256、迁移映射、保持项、冲突、验证、未执行项、恢复方式和下一安全动作。
