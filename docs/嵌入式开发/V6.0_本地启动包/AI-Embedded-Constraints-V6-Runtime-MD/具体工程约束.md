# AI 嵌入式开发具体工程约束

> 本文件是直接约束 AI 实施嵌入式开发的统一具体规则。AI 不得把本文件当作建议清单；命中任务范围的“必须、禁止、PASS 条件和失败处理”均为执行门禁。项目专属芯片、引脚、地址、周期、阈值、命令和安全限值必须来自当前工程证据，不得从示例或经验复制。

## 1. 事实来源、任务开始与修改范围

### 1.1 参数来源优先级

项目参数只能按以下顺序取值：

1. 用户本次明确要求及批准的需求基线；
2. 当前作用域内的 `AGENTS.md`、项目约束和已确认 Profile；
3. 当前版本原理图、接口表、协议、数据手册、勘误和工程配置；
4. 当前源码、构建产物和同版本实测证据；
5. 适用版本的标准组织或厂商官方资料。

来源冲突必须标记 `CONFLICT`，同时保留各候选值、来源、影响动作和待确认人。缺少关键值标记 `UNKNOWN`；影响写入、构建目标、硬件控制、兼容性或安全时必须停止依赖动作。

### 1.2 修改前必须完成

- 确认项目根、目标板卡、硬件版本、软件基线、正式构建目标和用户要求。
- 检查 Git/文件状态，识别目标文件中已有的用户修改；不得回退、覆盖或格式化无关内容。
- 精确搜索现有实现、调用者、配置、所有者和测试；不得在已有驱动、状态机、协议栈或错误码之外另造第二套实现。
- 明确本次必须完成、明确不包含、受影响文件、接口、数据格式、设备行为、失败路径和回退方法。
- 只修改完成任务所需的最小文件集。生成代码、供应商 SDK、校准、身份和生产数据默认不得直接修改。

### 1.3 完成门禁

只有以下条件同时满足才可报告完成：当前 diff 与任务一致；正式目标构建或适用检查通过；正常、边界和失败路径已验证；资源与兼容影响已记录；证据绑定当前源码、产物、设备和配置；所有阻塞性 `UNKNOWN/CONFLICT` 已关闭。缺真实工具或设备时必须降低相应验证层级，不得用 mock 或旧日志替代。

## 2. 软件架构与接口合同

### 2.1 分层与平台隔离

- 应用层不得直接散落寄存器地址、Pin、DMA 通道、编译器属性、绝对路径或特定 RTOS API。
- 芯片、SDK、RTOS、工具链和板卡差异必须进入 BSP/HAL、适配器、配置或规则注册表。
- 公共头文件不得暴露内部可变状态；跨模块依赖必须能被替换、模拟或单元测试。
- 修改公共接口前必须列出全部调用者和兼容影响；旧接口需要迁移期时必须明确版本、废弃路径和删除条件。

### 2.2 每个接口必须定义

- 参数范围、单位、空指针、长度与容量关系；
- 输入、输出、别名、所有权和生命周期；
- 调用上下文、线程/ISR 安全、重入和同步方式；
- 单次超时、总时限、取消点和资源释放；
- 成功、参数错误、忙、超时、设备离线、资源不足、校验失败和内部故障；
- 失败后是否允许重试、是否幂等以及部分提交如何回退。

禁止忽略影响一致性或安全的返回值，禁止用一个模糊 `bool` 覆盖多类需要不同处置的失败。

## 3. RTOS、并发、中断与实时性

### 3.1 任务和事件

- 每个任务、线程、主循环步骤或事件消费者必须记录职责、优先级依据、周期 `T`、截止期 `D`、最坏执行时间 `C`、最大阻塞 `B`、最大抖动 `J`、栈、队列、启动和停止路径。
- 验收至少核对 `C + B + J <= D`；存在抢占时必须加入更高优先级执行单元的干扰。
- 高优先级上下文不得持锁等待 Flash、网络、文件系统或长总线事务。
- 周期任务不得用连续固定 sleep 累积漂移；时间比较必须正确处理 tick 回绕。

### 3.2 共享状态和锁

- 每个共享可变对象必须有唯一所有者，或明确使用互斥、临界区、原子、队列、事件或信号量。
- `volatile` 只处理可见性，不能替代原子性、内存顺序或互斥。
- 必须定义全局锁顺序、最长持锁时间和超时；禁止嵌套锁顺序不一致、持锁调用未知回调或无限等待。
- 模块停止、设备断开或任务取消时必须停止定时器/DMA、解绑回调、唤醒等待者并释放资源。

### 3.3 ISR 强制禁令

ISR 只允许读取和清除本中断源必要状态、保存最少数据、执行确定性握手并使用已证明 ISR-safe 的原语通知后续上下文。

ISR 中禁止：阻塞、sleep、普通互斥、堆分配/释放、格式化日志、Flash/NVM 写入、复杂协议解析、设备重连、无界循环及未经证明上下文安全的 API。

每个中断必须记录最大到达率 `f_i` 和 WCET `C_i`，计算 `U_isr = Σ(f_i × C_i)` 并与项目 CPU 预算比较。缺最大事件率、目标优化配置或测量方法时，实时性结论必须保持 `UNKNOWN/NOT_RUN`。

## 4. DMA、Cache、内存与缓冲

### 4.1 DMA 和 Cache

- DMA 缓冲必须定义地址、长度、对齐、内存属性、生命周期、生产者、消费者和传输期间所有权。
- 禁止 DMA 使用即将失效的栈对象；禁止传输中修改、释放或复用缓冲。
- 有 Cache/非一致总线时，必须按当前目标官方规则执行 clean、invalidate、屏障和描述符同步；不得用 `volatile` 掩盖一致性错误。
- 错误、取消或超时后必须停止正确通道、清除状态并恢复缓冲所有权，不得遗留活动 DMA。

### 4.2 缓冲和队列容量

接收缓冲至少满足：

`capacity >= ceil(R_peak × T_block) + F_max`

其中 `R_peak` 为峰值输入字节率，`T_block` 为消费者最长不可运行时间，`F_max` 为最大完整帧。DMA 分段、协议窗口或突发要求更大时取更严格值。

测试必须覆盖：容量 0/1、容量减 1、恰好填满、再多一项、回绕、多圈、消费者停顿、恢复顺序、溢出计数和关键数据丢失策略。

### 4.3 C/C++ 和数值安全

- 禁止无界字符串函数、可变长度数组、递归进入资源受限路径、依赖结构体填充的线格式和未定义行为。
- 指针、索引、长度、乘加、移位、符号转换、取负最小值和除零必须在使用前检查。
- 新增数组、任务栈、对象池和大结构体必须记录 Flash/RAM/栈增量及来源。
- 动态内存必须定义使用阶段、总上限、失败、释放、碎片控制和重复启停测试；ISR/硬实时路径禁止动态分配。
- 传感和协议量必须声明原始单位、工程单位、缩放、偏置、范围、精度、舍入和饱和策略。

## 5. UART、I²C、SPI 与 CAN

### 5.1 UART/RS-485

- 明确 TTL、RS-232 或 RS-485 电气层，不得只写“串口”。
- 按当前外设时钟和分频公式计算实际波特率：`error = |baud_actual - baud_target| / baud_target`；结合双方时钟容差和接收器采样结构核对最坏相对误差。
- 明确数据位、停止位、校验、流控、空闲定义、最大帧、超时、缓冲和错误恢复。
- RS-485 必须定义终端、偏置、DE 建立/保持时序、半双工仲裁和回声；发送完成以移位寄存器或硬件完成事件为准，不能只看软件 FIFO 空。
- 溢出、帧错或奇偶错误必须使受影响帧作废，保留计数，并在有界字节/时间内恢复到后续好帧。

### 5.2 I²C

上拉电阻必须满足：

- `R_min = (VDD - VOL_max) / IOL_max`
- `R_max = t_r_max / (0.8473 × C_bus)`

`C_bus` 必须包含器件引脚、PCB、连接器、线缆及测量探头。若 `R_min > R_max`，必须降低速率、减少负载或改变拓扑，禁止任选常用电阻。

必须处理 NACK、仲裁丢失、clock stretching、SDA/SCL 卡死和超时。只有器件资料允许时才能执行总线恢复：释放 SDA、产生最多 9 个受控 SCL 脉冲、检测 SDA、生成 STOP 或复位控制器；每一步必须有超时。

### 5.3 SPI

- 明确 Mode、位序、字宽、SCK、CS 极性、事务边界和多从机共享规则。
- 必须比较控制器、从设备、隔离器和电平转换链路的频率上限，并核对 `tCSS/tCSH/tSU/tH` 和字间间隔。
- 波形在接收端测量；一次成功读取 ID 不能证明最高速率、全部模式或连续事务通过。

### 5.4 CAN

- 明确 Classic/FD、时钟、预分频、时间量子、各时间段、采样点、实际标称/数据波特率、终端和拓扑。
- 帧合同必须记录标准/扩展 ID、DLC、端序、符号、缩放、单位、周期、超时和发送优先级。
- 必须处理 error active、error passive、bus-off、控制器复位和对端离线。
- 自动 Bus-Off 恢复只能按项目安全策略启用，并测试故障持续、故障解除和重复 Bus-Off。

## 6. 协议、网络与外部输入

- 帧表必须记录帧头、版本、类型、长度含义、序号、字段偏移、端序、符号、缩放、单位、完整性和兼容策略。
- 解析顺序必须为：同步/帧头→版本→声明长度与本地上限→完整帧→校验→命令和字段范围。每次读取字段前检查剩余长度。
- 禁止把外部字节流直接强转本地结构体；多字节值必须显式编解码。
- 流式接收必须处理半包、粘包、噪声、超长、坏校验、重复、乱序、迟到响应、超时和连续坏帧。
- CRC 必须明确多项式、初值、输入/输出反射、结果异或、覆盖范围和权威测试向量；“CRC16”不是完整定义。
- TCP 一次 `recv` 不等于一帧；UDP 不得假定可靠或有序；WebSocket 必须处理 fragment、ping/pong、关闭码和重连。
- 请求必须有事务 ID/序号、最大并发和迟到响应策略；超时重试不得重复执行非幂等命令。
- 所有外部输入设置长度、连接数、速率、内存和计算上限；达到上限时必须有明确拒绝、背压或丢弃策略。

## 7. GPIO、时钟、ADC、PWM 与看门狗

### 7.1 GPIO、Pinmux 和时钟

- 每个信号逐项核对当前原理图网络、Pin、复用、方向、电压域、有效电平、外部上下拉、上电默认和低功耗状态。
- 输出初始化按“预装载安全值→配置方向/复用→允许外设驱动”或器件规定顺序执行，禁止产生危险毛刺。
- 时钟必须核对源、容差、分频、锁定、切换、依赖和失败回退；修改时钟后重新计算通信、定时器、PWM、ADC、看门狗和 RTOS tick。

### 7.2 ADC/PWM/定时器

- ADC 必须明确参考、分辨率、采样时间、源阻抗、量程、单位、触发、校准、滤波和饱和。
- 未经范围和有效性检查的 ADC 原始值不得直接参与安全控制。
- PWM 必须明确频率、极性、分辨率、更新点和禁用安全电平；更新不得产生不可控窄脉冲或毛刺。
- 计数器、捕获和软件时间必须处理回绕；硬件时序不能仅用日志时间证明。

### 7.3 看门狗和复位

- 喂狗必须绑定规定关键周期的真实完成条件；禁止在空闲任务、无条件循环、死循环或恢复未完成时喂狗。
- 复位原因必须在覆盖前读取并保存，区分棕断、看门狗、软件和升级复位。
- 重复复位必须有次数/时间窗口、诊断和安全降级；整机复位不得作为普通外设错误的默认修复。

## 8. NVM、配置、Bootloader 与 OTA

### 8.1 NVM

- 持久化记录必须包含 magic/类型、schema 版本、长度、完整性和有效/提交状态；先验证元数据再读取字段。
- 未知版本不得按当前结构解释；格式变化必须提供兼容读取、确定性迁移或明确拒绝。
- 更新使用“写非活动记录→回读验证→原子提交标记→切换活动记录”或经过证明的等价方案。
- 必须对每个持久化写步骤注入掉电/中断，任一点失败都至少保留一个可识别的旧或新有效版本。
- 写入寿命计算：`预计写入次数 = 目标寿命秒数 / 最短写入间隔 × 最坏写放大`；采用磨损均衡时记录有效槽数、坏块和保留空间。

### 8.2 Bootloader/OTA

- 镜像必须关联产品、板卡/硬件范围、版本、长度、哈希和批准的认证方式；CRC 不能证明来源可信。
- 写入前验证目标分区、擦除粒度和边界，不得覆盖 Bootloader、校准、身份、密钥或非目标槽。
- 完整验证后才能标记候选启动；通过规定健康检查后才能永久确认。
- 更新断电、错误产品/硬件、损坏镜像、禁止降级、首启失败、确认前复位和回退必须测试。
- 失败后必须保留或恢复最近已验证可启动镜像；最后可启动路径可能丢失时禁止发布。

## 9. 硬件原理图与电源

### 9.1 器件和库

- 每个器件核对完整 MPN、制造商、数据手册版本、生命周期、温度等级、额定、降额、封装、Pin1/极性和引脚编号。
- 符号 Pin、封装 Pad 和数据手册引脚必须一致；禁止按封装名称相同推定可替换。
- 替代料必须分别验证参数、封装、引脚、固件、校准、认证和工艺兼容。

### 9.2 电源计算

- 每条电源轨计算 `I_rail,max = ΣI_load,max + I_dynamic + I_external`，未知负载不得按 0 计入。
- 线性稳压器至少计算 `P_loss = (V_in,max - V_out,min) × I_out,max + P_iq` 和 `T_j = T_a,max + P_loss × θ_effective`。
- 储能下界计算 `C_ideal >= I_step × Δt / ΔV_allow`，再按直流偏压、温度、容差、ESR/ESL修正有效电容。
- 必须核对稳态、峰值、启动、浪涌、短路、掉电、反灌、纹波、瞬态和最坏环境温度。
- `θJA` 只有在板层、铜面积、气流和安装条件适用时才能直接使用，否则必须采用适用模型或实测。

### 9.3 数字电平与保护

- 每个方向计算 `NMH = VOH_min - VIH_min`、`NML = VIL_max - VOL_max`，在最坏电源、温度和负载下均须满足项目要求。
- 正常额定和绝对最大值必须分开核对；不得把绝对最大值当连续工作点。
- 必须检查未上电 IO 注入、调试器/USB 反灌、三态、上拉域、方向冲突和掉电高阻。
- ESD/EFT/浪涌保护必须比较保护器件钳位、残压、功率和失效模式与被保护器件能力。

## 10. 模拟、传感与校准

- 建立从传感器到 ADC/算法的完整信号链，列出量程、共模、源阻抗、增益、偏置、参考、带宽、采样和保护。
- 误差预算必须包含器件初始误差、容差、温漂、噪声、参考、量化、非线性、布局寄生和校准残差，并说明最坏值或 RSS 方法。
- 每一级在全输入、全温度和故障条件下不得超出输入共模、输出摆幅、绝对最大值和注入电流。
- 校准必须绑定设备/通道身份、算法版本、标准器、环境、原始数据、系数、有效期和回退。
- 缺少原始测量或标准器溯源时，只能报告算法/流程验证，不能报告精度或校准 PASS。

## 11. PCB 设计与制造输出

### 11.1 数值规则合同

每条 PCB 数值规则必须记录：

`对象/网络 → 输入值及单位 → 来源版本/页码 → 公式或工具及版本 → 最坏结果 → 设计裕量 → EDA 写入值 → 验证证据`

缺层叠、铜厚、材料、板厂能力、电流、边沿、阻抗或安规条件时，相应规则保持 `UNKNOWN`，不得填写“常用 6/6 mil”等经验值。

### 11.2 布局与布线

- 先固定板框、孔、连接器、天线、传感器、隔离区和结构关键件，再放电源、时钟、处理器、存储、模拟和普通器件。
- 去耦必须对应具体电源脚并形成最小回路；开关电源高 `di/dt` 回路和 SW 节点必须受控。
- 高速/时钟/快速边沿信号必须有连续参考层；换层提供就近回流路径，禁止无依据跨平面分割。
- 电源路径必须从最坏电流、压降、温升、铜厚和环境推导，并检查线段、焊盘颈缩、过孔、连接器和开关器件全路径。
- 大电流过孔必须计算成品孔径/孔铜下的电阻、损耗、温升和电流分配；禁止简单使用“单孔能力×数量”放行。
- 差分对必须记录单端/差分阻抗、线宽、间距、参考层、铜厚、介质厚度/介电常数、允许偏差、偏斜和层换结构。
- 安规间距必须记录标准版本、工作/瞬态电压、材料组、污染等级、海拔、绝缘类别及涂覆/开槽条件。

### 11.3 DRC 与制造

- 必须运行当前原生工程和实际规则的 DRC，保存工具版本、规则、原始报告、坐标及 waiver。
- `0 DRC` 只证明已配置规则未报错，不能证明规则完整；必须独立检查未布线、短路、断网、板框、孔、丝印、阻焊和制造能力。
- 制造输出必须明确层映射、钻孔/槽、板框、阻焊、钢网、原点、单位、镜像、PnP、BOM和版本。
- 输出后必须用独立查看器或回读解析核对层、孔、槽、外形、极性、原点和坐标，并生成逐文件哈希清单。
- 只能报告实际达到的等级：`PLAN_ONLY / EDITABLE_LAYOUT / ROUTED / DRC_VERIFIED / FAB_FILES_CHECKED / PHYSICALLY_TESTED`。

## 12. 构建、测试、证据与交付

### 12.1 构建

- 使用当前工程原有正式入口、目标和工具链；不得用 GCC/CMake 等替代 Keil、IAR 或厂商工程后冒充正式构建。
- 构建前记录源码基线、目标、配置和工具版本；构建后记录工作目录、命令、退出码、警告、产物、时间和 SHA-256。
- 退出码为 0 但缺预期产物仍为 FAIL；旧 output、不同目标或不同哈希产物不得作为本次证据。
- 从同一正式目标的当前 MAP/ELF 记录 Flash/ROM、RAM/BSS/data、堆和任务栈；无当前产物时资源结论为 `UNKNOWN/NOT_RUN`。

### 12.2 测试矩阵

根据功能至少覆盖：正常、空、最小、最大、超限、坏格式、超时、资源耗尽、队列满、竞态、断开、复位、重复、乱序、取消、恢复和旧数据兼容。

修复缺陷必须保留首次失败、最小复现、期望、实际、根因或假设、针对性修改和回归证据。禁止删除失败测试、放宽断言、增加无限重试、关闭功能或整机复位来制造通过。

### 12.3 证据等级

- 静态源码/规则检查只能证明静态层。
- 主机单测或模拟器不能证明目标 ISR 时延、DMA/Cache、真实总线、电气、功耗或设备行为。
- 工具执行必须保存原始日志、退出码、输入和输出身份。
- 真实设备证据必须包含设备 ID、板卡版本、固件哈希、配置、工具版本、时间和原始日志/波形。
- 人工批准、生产放行和认证结论不得由 AI 自行填写。

### 12.4 Git、状态和交接

- 提交前检查状态和 diff，只暂存本任务文件；缓存、密钥、运行日志、下载物和无关构建产物不得提交。
- Git 提交不等于推送、标签、发布或生产授权。
- 长任务和会话结束时，按任务 ID 保存目标、基线、已修改文件、命令、结果、证据、失败、阻塞、下一安全动作和禁止重放事项。
- 恢复时重新核对 Git、关键输入和产物哈希；状态未知的烧录、生产写入、发布等非幂等动作不得自动重放。

## 13. AI 输出要求

AI 的最终交付必须明确：

1. 实际修改了什么以及为什么；
2. 用户输入、目标对象和适用版本；
3. 实际执行的构建、测试或检查命令；
4. PASS、FAIL、BLOCKED、NOT_RUN、UNAVAILABLE 和 UNKNOWN 的分别结果；
5. 原始证据和源码/设计位置；
6. 尚未验证的真实设备、电气、时序、制造或发布边界；
7. 回退方法、Git 检查点和下一安全动作。

禁止只回复“已优化、已修复、测试通过”而不提供当前证据、失败路径和适用边界。
