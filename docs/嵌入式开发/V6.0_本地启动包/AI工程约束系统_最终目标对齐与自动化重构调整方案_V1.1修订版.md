# AI 工程开发约束 Markdown 最终目标对齐与优化方案（纯 Markdown 版）

> **文档定位：** 本文是最终约束 Markdown 的开发调整方案，位于最终交付文件之外，不属于使用者最终文件。
>
> **方案状态：** 待按本文开发、模拟测试和使用者验收后，才能形成正式最终文件。
>
> **核心收敛：** 最终交付只需要一个通用 Markdown，不开发跨平台运行时、安装器或状态程序。项目状态文件由 AI 首次使用时自动生成并维护。

## 1. 最终目标

最终形成一个可放入不同项目、供不同 AI 读取的通用开发约束 Markdown，使 AI 在开发过程中自动做到：

1. 知道项目最终目标和当前方向；
2. 知道已经做到哪里、正在做什么；
3. 知道下一步应该做什么以及完成条件；
4. 自动回顾相关历史、已有结论和失败方案；
5. 避免重复分析、重复读取和重复执行没有条件变化的失败方案；
6. 修改前保护用户已有代码、Git 改动和已验证成果；
7. 修改后执行与风险匹配的测试并保留证据；
8. 自动生成节点总结和跨会话交接；
9. 用户改变方向时保留旧结论并重新计算影响；
10. 用户只把控目标、方向和真正需要决定的问题，不管理内部状态文档。

约束的目的，是让 AI 更有效、更可靠地开发，不是限制 AI 的分析深度、必要工具调用、测试范围或最终输出质量。

## 2. 最终交付形式

### 2.1 最终只交付一个文件

建议最终文件名：

```text
AI工程开发约束.md
```

最终不需要：

- ZIP；
- Python、PowerShell 或 Shell 运行时；
- Windows、Linux、macOS 可执行程序；
- 安装器和卸载器；
- 后台服务；
- SBOM、程序签名或多架构构建；
- 开发源码目录；
- 开发过程、版本演进和修改记录。

Markdown 本身与操作系统无关。需要验证的是 AI 是否能读取文件、修改项目、运行现有工具并遵守约束，而不是为每个操作系统开发一套程序。

### 2.2 项目状态文件由 AI 自动生成

为了实现跨会话连续开发，AI 首次接入项目时自动创建：

```text
.ai-work/PROJECT_STATE.md
```

该文件不是额外交付模板，而是由最终约束 Markdown 中内置的模板自动生成。用户不需要创建、填写或维护它。

AI 创建前必须先检查同名目录和文件。文件已经存在时只能读取和兼容更新，不得使用空模板覆盖。`.ai-work/` 是项目本地工作目录，不属于用户源码；Git 项目默认使用 `git rev-parse --git-path info/exclude` 定位本地排除文件，并根据 `git rev-parse --show-toplevel` 计算项目目录相对仓库根的位置：项目就是仓库根时使用 `/.ai-work/`，项目位于 monorepo 子目录时使用对应的精确锚定路径。在不覆盖原内容且不存在相同规则时追加，不得修改共享 `.gitignore`。无法安全写入本地排除文件时继续保存状态并简短说明一次，不得覆盖排除文件。非 Git 项目直接创建该目录。

AI 不得擅自暂存、提交或上传 `.ai-work/`。如果该目录在接入前已经被 Git 跟踪，保持项目现有策略，不得自动取消跟踪。用户明确要求团队共享或换机同步时，再说明隐私、冲突和体积边界并调整策略；普通使用不让状态文件持续污染 `git status`。

固定约束与动态状态必须分离：

- `AI工程开发约束.md`：所有项目共用，不积累项目历史；
- `.ai-work/PROJECT_STATE.md`：只记录当前项目的方向、进度、结论、失败方案、证据和下一步。

不得把项目历史追加到通用约束文件中，也不得在普通项目开发过程中擅自修改通用约束。

### 2.3 客户端自动加载边界

目前不存在所有 AI 客户端都会自动读取的统一 Markdown 文件名。最终方案提供以下两种接入方式：

1. 通用方式：用户首次明确要求 AI 读取 `AI工程开发约束.md`；
2. 客户端原生方式：首次初始化时，AI 在确认不会覆盖项目现有入口后，为当前客户端生成一个只包含“读取通用约束和项目状态”指向的轻量入口文件。

客户端入口不得复制整套规则，避免多份约束发生漂移；不得覆盖已有 `AGENTS.md`、`CLAUDE.md` 或其他用户入口正文。不能安全生成入口时继续使用通用方式，并如实说明后续新会话可能需要客户端配置或首次提示。

这些入口是 AI 按实际客户端生成的项目接入文件，不属于最终交付包。没有实际验证的客户端不得声称能够自动加载。

## 3. 真实使用方式

### 3.1 首次使用

用户把最终约束 Markdown 放入项目，只需告诉 AI：

```text
读取 AI工程开发约束.md，初始化项目状态，然后按照约束继续当前开发目标。
```

AI 自动完成：

1. 完整读取约束文件；
2. 检查是否已有 `.ai-work/PROJECT_STATE.md`；
3. 没有状态文件时，根据内置模板创建；
4. 检查项目目录、Git 状态和用户已有改动；
5. 只读取顶层结构、已有项目规则、主要构建/测试入口和与当前目标直接相关的文件，形成第一版项目事实；
6. 将用户目标转成当前任务和完成判定；
7. 给出简短的当前状态、准备执行内容和第一步；
8. 开始开发，不要求用户执行内部状态命令。

首次初始化采用快速路径：先建立足够支持当前任务的最小状态并开始工作，不为追求“完整理解项目”而全量扫描源码、历史、依赖或生成目录。未检查范围明确标记为未知，后续只有当前任务需要时才扩大读取。

### 3.2 后续会话

后续用户只需正常提出目标，例如：

```text
继续
修复当前问题
新增某项能力
先处理这个优先问题
原来的方向调整为……
```

AI 自动：

1. 读取约束文件，并先读取项目状态的元数据、当前目标、当前任务、关键结论、失败方案、保护项和下一步，再按当前工作定向读取其余历史；
2. 检查 Git、文件变化和状态修订；
3. 恢复当前任务、停止位置和下一步；
4. 判断用户要求是继续、补充、插入、改向、取消还是新任务；
5. 定向查找相关代码、历史结论和失败方案；
6. 继续开发并在节点完成后更新状态。

### 3.3 用户可见信息

普通情况下只向用户显示：

- 当前做到哪里；
- 本次准备做什么；
- 本次完成了什么；
- 测试和证据是否通过；
- 风险、未知项或阻断；
- 是否需要用户决定；
- 下一步是什么。

内部修订号、历史压缩、状态整理和引用维护由 AI 自动处理，不要求用户理解。

## 4. 约束能够做到与不能做到的边界

### 4.1 能够做到

只要 AI 能读取项目文件并愿意遵守约束，Markdown 可以统一它的工作流程、状态维护、历史回顾、修改保护、测试、总结和交接行为。

### 4.2 不能绝对保证

纯 Markdown 不能从操作系统层面强制阻止 AI：

- 忽略约束文件；
- 绕过修改前检查；
- 不更新状态；
- 直接产生超大工具输出；
- 多个 AI 同时修改同一文件；
- 在客户端未提供自动加载能力时自动读取自己不知道的文件。

因此最终文件必须诚实声明：这是对遵守约束的 AI 的工作规范，不是系统级沙箱、锁服务或强制执行程序。

### 4.3 AI 客户端兼容等级

不按操作系统划分兼容性，只按 AI 实际能力划分：

- `FULL`：能读取和修改文件、执行 Git/测试，并能更新项目状态；
- `PARTIAL`：能读写文件，但不能执行部分工具或测试；
- `READ_ONLY`：只能分析和建议，不能可靠修改或验证；
- `UNSUPPORTED`：无法读取约束或项目文件。

AI 必须根据当前实际能力说明降级边界，不能把“文档中要求执行”冒充“客户端已经自动执行”。

### 4.4 指令与事实优先级

发生冲突时按以下顺序处理：

1. 客户端/系统安全、权限和适用的高优先级指令；
2. 用户当前明确要求和最新纠正；
3. 当前项目已有的专用开发规则；
4. 通用 `AI工程开发约束.md`；
5. `.ai-work/PROJECT_STATE.md` 中仍然有效的历史状态；
6. 其他项目资料；
7. AI 推断和建议。

用户当前决定更新项目方向时，旧状态不能反向覆盖用户；必须保留旧方向和影响关系，再更新当前状态。通用约束不得削弱项目已有的安全、测试和兼容性要求。无法判断指令是否冲突时只询问真正影响方向或安全的关键问题。

## 5. 统一项目状态文件

### 5.1 固定结构

`.ai-work/PROJECT_STATE.md` 至少包含以下固定章节：

```markdown
# AI Project State

## 状态元数据
- 状态格式版本：
- 约束格式标识：
- 项目稳定标识：
- 状态修订：
- 最近成功写入修订：
- 最近更新时间：
- 最近 AI/客户端：
- 项目路径或仓库身份：
- Git 分支与提交：

## 项目最终目标

## 当前方向与完成判定

## 当前任务

## 当前进度

## 已完成且已验证

## 已有关键结论与决策

## 失败方案与允许重试条件

## 不可破坏成果与用户已有改动

## 测试、证据与来源

## 风险、未知项与阻断

## 下一步

## 最近节点总结

## 历史压缩摘要
```

### 5.2 状态记录规则

状态文件必须：

- 只记录能帮助后续开发继续工作的内容；
- 区分事实、验证结果、静态推断和 AI 建议；
- 重要结论记录源码路径、行号、命令、测试或原始证据；
- 未运行的测试不得写成已通过；
- 未完成内容不得写成完成；
- 用户纠正后保留纠正原因，不静默覆盖造成误解；
- 项目方向变化时保留前后关系和受影响结论；
- 不保存密钥、令牌、密码和完整敏感配置；
- 不把大段源码、完整日志或重复聊天内容直接复制进状态文件。

### 5.3 结构化记录

为保证不同 AI 能稳定检索，任务、决策、失败方案、证据和检查点使用固定记录块和稳定 ID。ID 由 AI 自动生成，用户不需要查看或管理。建议前缀：

- `TASK-*`：任务；
- `DECISION-*`：关键决策；
- `FAIL-*`：失败方案；
- `EVIDENCE-*`：测试或原始证据；
- `CHECKPOINT-*`：节点总结。

每条记录至少包含状态、目标/结论、作用范围、来源或证据、有效性条件和关联记录。示例：

```markdown
### FAIL-20261118-001
- 状态：有效
- 目标：
- 作用范围：文件、符号或模块
- 输入与环境：
- 方法：
- 失败现象：
- 证据：EVIDENCE-*
- 原因或未知项：
- 允许重试条件：
- 关联任务：TASK-*
```

同一对象必须优先更新原记录或建立替代关系，不能每轮生成语义重复的新记录。删除或压缩记录时保留仍被引用的 ID、结论和有效性。

### 5.4 失败方案记录

失败方案至少记录：

- 当时要解决的问题；
- 使用的方法；
- 涉及文件、符号或模块；
- 输入、环境或工具条件；
- 失败现象和证据；
- 已知原因或未知项；
- 什么条件发生变化后允许重试。

目标、输入、环境和失败条件均未变化时，不得再次执行相同失败方案。条件发生实质变化时可以重新验证，但必须说明变化和重试依据。

### 5.5 状态大小与压缩

文件大小不是完成目标，信息有效性才是。

- 通用约束 Markdown 建议保持在约 20～60 KB；
- 项目状态文件可以达到几十到几百 KB，不需要压缩成 ZIP；
- 日常恢复优先读取当前目标、当前任务、关键结论、失败方案、保护项和下一步；
- 已确认且长期不变的旧节点可以压缩成简洁摘要；
- 不得压缩掉仍会影响当前工作的失败方案、决策、保护项和关键证据引用；
- 状态过长时先合并重复内容，再压缩低相关旧记录；
- 压缩前后必须保证新的 AI 仍能正确恢复项目。

### 5.6 缺失、损坏、迁移与并发变化

- 状态文件缺失时，根据当前用户要求、Git、项目文档、源码和测试结果尽力重建，并明确哪些历史无法恢复；
- 状态文件结构损坏时先保留原文件或差异，再修复可确认部分，不得直接生成空状态覆盖；
- 状态格式版本低于约束要求时先保留迁移前副本，再执行可重复的增量迁移；迁移必须保留未知章节和已有记录，成功核对后再更新格式版本；
- 状态格式版本高于当前约束认识范围时进入只读恢复，不得用旧模板降级覆盖；
- 每次更新前重新读取状态修订和目标文件变化；
- 状态修订在本轮外发生变化时，重新核对并合并不冲突内容；无法确认时停止写入并说明真实冲突；
- 状态更新优先使用局部修改，不为更新一个字段重写整个文件；
- 引用源码结论时尽量同时记录 Git 提交、文件哈希或可重新定位的符号，防止行号变化后误用旧结论。

纯 Markdown 无法提供强并发锁，因此目标是发现变化并避免静默覆盖，而不是宣称多个 AI 可以无冲突同时写入。

## 6. AI 开发工作流程

### 6.1 开始任务前

AI 必须：

1. 读取当前目标、任务、进度和下一步；
2. 检查状态修订、Git 分支、提交和工作区变化；
3. 识别用户已有修改，不得把它们当成 AI 本轮修改；
4. 查找与当前文件、模块、错误或目标相关的历史；
5. 检查失败方案、关键决策和不可破坏成果；
6. 明确本轮完成判定和必要测试；
7. 只有遇到方向、授权、不可逆操作或真实冲突时才询问用户。

### 6.2 修改过程中

AI 必须：

- 优先增量修改，不为小改动重写整个文件；
- 不删除或覆盖无法确认归属的用户修改；
- 不使用整体回退工作区的方式解决局部问题；
- 修改范围扩大时重新检查影响和完成判定；
- 出现失败时记录证据和新的未知项；
- 用户插入新任务时保存当前停止位置，完成插入任务后能够恢复；
- 用户改变方向时停止继续扩大旧方向的修改；
- 长任务在重要节点及时更新状态，不能只依赖正常会话结束。

### 6.3 修改完成后

AI 必须：

1. 检查实际差异是否超出任务范围；
2. 执行与风险匹配的专项测试；
3. 必要时执行回归测试或真实使用流程；
4. 明确哪些测试通过、失败、未执行或环境不具备；
5. 更新已完成、已有结论、失败方案、证据、风险和下一步；
6. 生成简短用户回执；
7. 只有证据满足完成判定时才标记任务完成。

### 6.4 Git 保护规则

AI 必须：

- 修改前检查 `git status`；
- 区分工作区、暂存区和本轮修改；
- 不使用 `git add .` 或 `git add -A` 夹带无关改动；
- 不重置、覆盖或取消用户已有暂存内容；
- 无法安全拆分混合修改时不自动提交；
- 不自动 push；
- 用户未授权自动提交时只给出精确提交建议；
- 非 Git 项目明确说明没有 Git 恢复能力，并更加谨慎地修改。

约束 Markdown 不能提供真正的多进程锁。发现状态修订、Git 基线或目标文件在本轮外发生变化时，AI 必须重新读取并核对，不能直接覆盖。

## 7. 历史回顾与避免走弯路

### 7.1 定向回顾顺序

AI 不应每轮读取全部历史。按以下顺序查找：

1. 当前文件、符号和模块；
2. 当前错误、测试失败或设备现象；
3. 当前目标和验收条件；
4. 已确认设计决策；
5. 失败方案；
6. 已验证成果和保护项；
7. 最近相关修改；
8. 必要时才扩大范围。

### 7.2 历史选择要求

被用于当前开发的历史必须说明：

- 为什么相关；
- 来源在哪里；
- 当前是否仍有效；
- 对本轮工作有什么约束；
- 是否需要重新验证。

不得把较新等同于更正确，也不得把 AI 推断写成项目事实。

### 7.3 历史有效性

以下变化会使旧结论需要复核：

- 相关源码或配置变化；
- Git 分支、提交或工作副本变化；
- 工具链、依赖、设备或固件变化；
- 用户方向和完成判定变化；
- 原始证据变化；
- 新证据与旧结论冲突。

## 8. 节点总结与下一步

每次重要节点、暂停、任务切换和完成时，AI 自动记录：

- 本轮目标；
- 已完成；
- 未完成；
- 实际修改文件；
- 测试和证据；
- 失败方案；
- 已有结论；
- 风险和未知项；
- 当前停止位置；
- 下一步动作；
- 下一步完成判定。

“下一步”必须可以直接执行或验证，包含目标对象、预期结果和完成条件，禁止只写“继续完善”“后续优化”。

完成总结必须区分：

- 已验证完成；
- 部分完成；
- 已实现但未验证；
- 阻断；
- 数据不足无法判断。

## 9. Token 与上下文效率

### 9.1 最高原则

Token 管理只用于减少浪费，不能降低：

- 正确性；
- 分析深度；
- 安全检查；
- 必要测试；
- 关键证据；
- 用户最终答复质量。

纯 Markdown 无法精确控制模型计费 Token，不得宣传为全局硬预算系统。

### 9.2 应减少的内容

AI 应避免：

- 重复读取未变化的完整文件；
- 重复输出已经确认的背景；
- 每轮读取全部项目历史；
- 把完整编译日志、测试日志和源码粘贴进状态；
- 对同一失败方案进行无条件重复分析；
- 为简单任务生成过度复杂的流程说明。

工具执行时应在输出进入 AI 上下文前控制规模：

- 搜索先用精确关键词定位，再读取必要范围；
- 命令设置合理输出上限，只返回错误、摘要、关键片段和完成判断所需内容；
- 超长编译、测试和设备日志保存到 `.ai-work/evidence/`，AI 按错误、时间、用例或行范围定向读取；
- 保留命令、退出码、日志路径和必要哈希，不能因未读取完整日志而假定成功；
- 输出被截断时明确标记，并在完成判断需要时继续读取相关部分；
- 已读取且未变化的日志不重复完整输出。

`.ai-work/evidence/` 必须设置合理的单文件、总容量和保留边界，并避免保存密钥、令牌和完整敏感配置。AI 可以清理自己生成、能够重新执行且已经提取结论的临时成功日志；未解决失败、不可复现现场和仍被状态引用的唯一证据不得自动删除。该目录与状态目录一样不得自动提交或上传。

### 9.3 不得减少的内容

AI 不得为了节省 Token 跳过：

- 关键源码；
- 用户已有改动检查；
- 失败信息；
- 必要测试；
- 安全和兼容性检查；
- 能影响完成判断的历史；
- 用户需要的完整结论。

### 9.4 长任务处理

上下文不足或任务较长时，AI 应：

1. 更新项目状态文件；
2. 保存当前停止位置和下一步；
3. 保留关键证据引用；
4. 在客户端允许时继续下一阶段；
5. 客户端不能自动续接时，保证用户下一次只需说“继续”。

不得因为上下文不足而错误宣布完成，也不得机械截短用户最终答复。

## 10. 用户决策边界

AI 可以自动处理：

- 明确目标范围内的可逆开发工作；
- 状态维护和历史整理；
- 定向检索和增量修改；
- 与修改相关的测试；
- 节点总结和下一步；
- 不改变用户方向的低风险修复。

AI 必须停止并询问用户：

- 存在多个会显著改变结果的方向；
- 项目最终目标或范围发生重大变化；
- 删除、覆盖或不可恢复操作；
- 需要凭据、设备或外部授权；
- 用户改动与当前任务冲突且无法安全拆分；
- 证据冲突导致完成判定不明确；
- 多次失败且没有新信息；
- 继续可能造成重大安全、数据或项目风险。

不得因为状态文件格式、内部编号或文档维护问题打扰用户。

## 11. 约束文件自维护

普通项目开发过程中，AI 不得擅自修改 `AI工程开发约束.md`。

发现约束存在问题时，先在项目状态中记录“约束改进建议”。只有用户明确要求维护约束文件时，AI 才进入维护模式：

1. 检查约束文件和相关用户修改；
2. 明确问题、影响和修改目标；
3. 创建可回退 Git 检查点或备份；
4. 增量修改约束正文；
5. 使用模拟项目执行回归；
6. 确认没有降低输出质量或删除已有能力；
7. 只交付更新后的最终 Markdown，不把修改过程写入最终文件。

不需要保存或交付单独开发源码。约束 Markdown 本身就是可由 AI 继续维护的源文件和最终文件。

## 12. 开发调整阶段

### 阶段 A：目标收敛与旧方案清理

- 冻结“一个最终 Markdown + 一个 AI 自动生成状态文件”的边界；
- 冻结 `.ai-work/` 本地状态目录、Git 本地排除和不自动提交策略；
- 冻结指令与事实优先级；
- 删除运行时、ZIP、安装器、多操作系统构建、签名和后台服务要求；
- 保留用户最终目标、历史、失败方案、Git保护、总结和Token质量原则；
- 确认最终文件不包含开发过程和版本演进记录。

完成判定：方案不再把 Markdown 约束扩展成独立软件系统。

### 阶段 B：生成最终约束 Markdown

- 将强制规则放在前部；
- 内置带格式版本、稳定标识和结构化记录的项目状态模板；
- 写清首次、后续、修改前、修改后和结束流程；
- 写清快速初始化、旧状态迁移、损坏恢复和并发变化处理；
- 实现通用首次提示和不复制规则的客户端轻量入口策略；
- 写清 AI 能力边界和降级方式；
- 控制文档长度和重复内容。

完成判定：只依靠最终 Markdown，AI 能创建状态并开始开发。

### 阶段 C：跨会话与历史测试

- 测试新项目和中途接入项目；
- 测试当前进度、已有结论、失败方案和下一步恢复；
- 测试用户补充、插入、改向、暂停和取消；
- 测试长历史压缩后关键内容不丢失；
- 测试陌生 AI 只读取约束和状态后能否继续。

完成判定：用户不需要向新 AI 重新解释项目历史和停止位置。

### 阶段 D：修改保护与失败路径测试

- Git 干净、Git 有用户改动和非 Git 项目；
- 同一文件混合用户修改；
- 测试失败和环境无法测试；
- 状态文件缺失、过期、冲突和部分损坏；
- 两个 AI 先后修改导致状态修订变化；
- 相同失败方案重复出现。

完成判定：用户修改不丢失，失败不被写成成功，冲突时不会静默覆盖。

### 阶段 E：Token 与输出质量测试

- 小任务验证约束不会产生过重流程；
- 大任务验证按需读取而非全量历史；
- 超长日志验证只保留必要片段和引用；
- 验证工具输出在进入上下文前受限，完整证据能够从 `.ai-work/evidence/` 定向复核；
- 对比使用约束前后的缺陷发现、测试完整性和最终答复质量；
- 验证 Token 优化不减少必要分析和输出。

完成判定：约束减少重复和无关内容，但不降低开发结果。

### 阶段 F：使用者模拟验收

模拟用户只执行：

1. 放入最终 Markdown；
2. 提出项目目标；
3. 在需要时改变方向；
4. 查看开发结果。

用户不执行状态命令，不填写状态模板，不管理历史文件，不提醒 AI 总结。

### 阶段 G：最终交付

- 最终目录只保留一个约束 Markdown；
- 不包含 ZIP、源码目录、测试项目、运行日志和开发调整文档；
- 从空项目再次执行完整模拟；
- 创建只包含最终文件的 Git 检查点；
- 不自动 push。

## 13. 必测场景

至少覆盖：

1. 全新空项目；
2. 已开发一半的现有项目；
3. Git 干净项目；
4. Git 含用户未提交修改；
5. 非 Git 项目；
6. 第一次 AI 初始化；
7. 新 AI 跨会话续做；
8. 用户临时插入任务后恢复原任务；
9. 用户改变最终方向；
10. 已有失败方案再次出现；
11. 测试失败、缺工具或无法连接设备；
12. 状态文件缺失、过期、冲突或损坏；
13. 状态格式较旧、较新或包含未知章节时的兼容迁移和只读降级；
14. 长历史和超长日志；
15. 两个 AI 先后修改同一项目；
16. Git 本地排除文件已有内容、worktree 和非 Git 项目的状态目录创建；
17. 小任务，验证约束开销不过重；
18. 大任务，验证 Token 优化不降低输出质量；
19. Codex、Claude、Gemini、Copilot 中能够读取项目文件的实际客户端；
20. 项目已有 `AGENTS.md`、`CLAUDE.md` 或其他客户端入口时，不覆盖用户正文且不会生成冲突规则。

不同客户端没有实际测试时必须标记为未验证，不得把理论可读 Markdown 宣传为已经完整兼容。

## 14. 量化完成标准

最终文件至少满足：

1. 最终交付文件数量为 1；
2. 不需要 ZIP、运行时或安装程序；
3. 用户首次只提供最终 Markdown 和项目目标即可初始化；
4. `.ai-work/PROJECT_STATE.md` 由 AI 自动创建，Git 项目中不污染普通 `git status`；
5. 后续会话用户无需输入内部状态命令；
6. 新 AI 能正确说明项目目标、当前进度、已有结论、失败方案和下一步；
7. 下一步是可直接执行或验证的动作；
8. 相同条件下重复执行已失败方案的次数为 0；
9. 用户已有修改被覆盖或错误提交的次数为 0；
10. 未执行或失败的测试被写成通过的次数为 0；
11. 方向变化后旧结论不会被静默当成当前目标；
12. 状态文件过长时能够压缩且关键结论不丢失；
13. Token 优化不会减少必要源码读取、测试、证据和最终答复；
14. 小任务不会被迫执行无收益的重型流程；
15. 普通任务中用户管理状态、历史、内部 ID 和总结的次数为 0；
16. 约束不能强制实现的能力均已诚实说明；
17. 最终约束 Markdown 不包含开发过程、版本记录和本调整方案；
18. AI 能在用户明确授权后直接维护约束 Markdown，并通过模拟项目回归；
19. 客户端需要原生入口时只生成通用约束指向，不复制规则、不覆盖用户已有入口；无法自动加载时明确说明边界；
20. 状态具有格式版本和可重复迁移规则，旧状态、未知章节和失败记录不会被空模板覆盖；
21. 任务、决策、失败、证据和检查点使用稳定结构，陌生 AI 能用精确搜索恢复相关记录；
22. 首次接入在不全量扫描仓库的情况下先形成最小可用状态并开始当前任务；
23. 指令冲突按固定优先级处理，旧状态不会覆盖用户当前决定；
24. 超长工具输出不会无控制进入上下文，截断、退出码和完整证据位置均有明确记录。

## 15. 最终判定

最终完成效果必须是：

> 用户把一个通用 Markdown 放入项目并提出开发目标后，AI 自动维护项目状态，知道项目历史、当前进度、下一步、失败方案和已有结论；开发前保护用户成果，开发后验证和总结。Token 优化只减少重复和无关内容，不限制必要分析、测试和最终输出。用户只把控项目方向和完成结果，不为每个项目重新编写或管理约束。

如果仍需要用户填写状态、指定历史文件、维护内部编号、提醒 AI 总结，或者约束为了节省 Token 降低开发质量，则不能认定为完成。
