> **文档状态：** V1.1 修订建议稿，作为后续重构开发基线；完成阶段 A 的现状审计并冻结证据后，方可转为正式冻结基线。
>
> **修订原则：** 保留原 V1.0 的最终用户目标、权威来源、A～G 七阶段路线和最终双文件交付原则；补齐自动触发、无 Python 运行、全局 Token 预算、状态一致性、Git 用户改动保护、异常恢复和压力测试要求。
>
> **重要边界：** 本文定义的是目标与验收要求，不代表当前受信任最终双文件已经具备全部能力。实际基线文件名、包身份和 SHA-256 由阶段 A 审计记录冻结。任何能力必须以实际代码、可重复测试和真实运行证据判定，不得以文档描述代替实现。

> **基线关系：** 本修订版经用户确认后，取代 V1.0 成为后续开发、审计和验收的唯一目标文档。V1.0 仅作为历史参考，不再作为并行开发基线。V1.1 目标生效不代表其中能力已经实现，能力状态仍由阶段 A 审计确定。

## 1. 文档定位

本文是后续重构、测试和交付的开发基线，位于最终交付目录之外。最终交付给使用者的内容仍然只能是通用接入 Markdown 和自包含 ZIP，不得把本文、阶段报告、源码工作区或修改记录放入最终双文件。

后续实现发生冲突时，以本文定义的用户最终效果、权威来源、自动化边界、Token 硬预算和验收标准为准。不得因为现有命令、数据结构或测试已经存在，就降低最终目标。

本文作为开发基线，不等同于现状验收通过。正式冻结前必须完成阶段 A：对现有代码、命令、数据结构、测试和实际行为逐项审计；只有具备实现证据和可重复测试的能力才能标记为 VERIFIED。未完成审计的能力不得默认继承“已验证”状态。

## 2. 最终目标

最终系统是在项目后台自动工作的 AI 项目记忆、历史检索、开发约束、证据验证和任务连续性系统。

用户只负责：

- 提出和调整项目最终方向；
- 决定重大技术方案、范围变化和高风险操作；
- 判断最终成果是否符合预期。

用户不负责：

- 为每个项目重新编写约束；
- 手工创建任务、下一步、会话、锁或修订；
- 指定应该读取哪些历史文档；
- 管理证据 ID、总结 ID 或内部状态文件；
- 提醒 AI 保存失败方案、阶段总结或交接信息；
- 控制历史输出数量和 Token 分页。

每个项目只需一次接入同一套最终双文件。以后用户正常提出开发目标，AI 必须自动恢复项目、检索相关历史、保护已有成果、决定下一步、执行开发、验证结果并保存可恢复总结。

## 3. 最终用户体验

### 3.1 首次接入

用户把 Markdown 和 ZIP 放入项目后，只需告诉 AI：

```text
按照约束文档初始化，并继续完成这个项目。
```

AI 自动完成：

1. 确认唯一项目根和访问边界；
2. 校验 ZIP 身份与完整性；
3. 安全安装或升级运行系统；
4. 检查 Git、用户已有改动和项目事实；
5. 建立稳定项目身份与工作副本身份；
6. 识别已有工程、构建方式、规则和历史资料；
7. 建立项目方向基线、历史索引和统一状态；
8. 将用户目标转换为任务、验收条件和第一步；
9. 在没有真实阻断时继续实际开发。

### 3.2 后续会话

用户只需正常描述当前想完成的内容。AI 自动：

1. 运行单一高层会话入口；
2. 恢复当前任务和上次停止位置；
3. 判断用户输入是继续、补充、插入、改向、取消还是新任务；
4. 根据目标、文件、符号、模块和错误自动检索相关历史；
5. 生成受硬预算约束的当前上下文包；
6. 检查失败方案、已有决策、受保护成果和用户改动；
7. 给出简短的当前进度、风险和下一步；
8. 无需用户管理内部状态即可继续工作。

### 3.3 用户可见回执

普通情况下只向用户显示：

- 当前做到哪里；
- 本次准备做什么；
- 本次完成了什么；
- 使用了什么证据；
- 有什么风险、未知项或阻断；
- 是否需要用户决定；
- 下一步是什么以及理由。

内部会话 ID、锁 ID、实体修订、事件序号和证据 ID 默认不展示，只有诊断时才显示。

## 4. 权威来源和冲突优先级

系统不得把所有事实都归入一个状态文件。不同类型事实的权威来源如下：

1. 用户当前明确决定：项目方向和授权的最高权威；
2. 已确认的项目方向与决策：长期目标和范围权威；
3. 源码、Git、构建配置和真实设备状态：工程事实权威；
4. 测试产物、日志、设备数据和哈希：验证结果权威；
5. 结构化状态中心：任务、进度、总结和关联关系权威；
6. 带来源的历史文档：设计说明和历史资料；
7. AI 推断和建议：最低等级，必须标注可信度和验证方法。

上述权威来源适用于项目事实、方向和研发决策；法律、安全、隐私、数据保护、权限和工具授权边界属于不可突破的前置约束，不因用户项目方向或历史记录而被绕过。

在上述边界内，发生冲突时不得静默选择。系统必须记录冲突来源、影响范围和推荐处理；只有方向性、破坏性、授权变化或无法确定的冲突才提交用户决定。用户当前明确决定优先于旧项目方向，但必须保留旧方向、变更原因、来源和受影响任务的关联，不得静默覆盖历史。

## 5. 现状保留与重构边界

### 5.1 必须保留的已验证内核

以下能力作为优先保留对象，必须先进行代码、测试和实际行为三方审计；不得仅凭目录中存在脚本、命令或文档就认定已完成。审计后按以下状态标记：

- `VERIFIED`：实现存在，专项测试可重复通过，关键失败路径有证据；
- `PARTIAL`：已有部分实现，但能力范围或失败路径不完整；
- `UNVERIFIED`：发现实现或文档，但缺少充分测试证据；
- `PLANNED`：尚未实现。

只有 `VERIFIED` 能力可列入“已验证内核保护清单”；其他状态允许在不破坏兼容性的前提下修复和重构。以下能力优先增量演进，禁止在未完成影响分析前推翻重写：

- ZIP 预检、哈希校验和安全提取；
- 安装、升级、恢复、原子回滚预检和包文件受控修复；
- 统一结构化状态、追加式事件链和可恢复事务；
- 任务、下一步、证据、总结和完成门禁；
- 会话租约、本机范围锁和乐观修订；
- Doctor、容量诊断、派生视图和权威历史校验；
- 通用项目识别、适配器、预算扫描和未知格式降级；
- 项目外维护工作区、完整回归和确定性重打包；
- 旧数据兼容、入口内容保留和用户文件保护。

阶段 A 必须输出《现有内核能力审计表》，至少包含：能力名称、实际实现路径、入口/调用方式、数据格式或协议、对应测试、测试结果、失败路径、已知限制、状态等级、是否允许重构。审计表中的 `VERIFIED` 项形成禁止无证据回退清单；`PARTIAL`、`UNVERIFIED` 和 `PLANNED` 不得宣传为已完成。

### 5.2 需要重构的使用层

重点重构：

- 多命令人工流程改为单一自动编排入口；
- 最近历史恢复改为按当前目标和受影响对象检索；
- 分散 Markdown 与结构化状态建立稳定索引关系；
- 局部输出截断改为全局上下文硬预算；
- 手工节点总结改为自动触发；
- Git 检查、受保护成果和失败方案检查改为修改前自动门禁；
- 内部状态细节从普通用户交互中隐藏；
- 会话重复、孤儿会话和异常退出改为自动治理。

## 6. 目标架构

### 6.1 客户端薄入口层

Codex、Claude、Gemini、Copilot 等入口只负责：

- 加载受信任统一入口；
- 自动调用高层会话入口；
- 不复制业务规则；
- 检测本地运行能力、客户端协议兼容性和可用执行引擎；
- 权威状态、事务、锁、迁移和证据写入必须由同一套规范实现的单一权威运行内核完成，禁止 Python、PowerShell 和 POSIX Shell 分别实现可能产生不同结果的状态写入逻辑；
- 优先使用满足版本要求的系统 Python 启动权威内核；对于交付矩阵中宣称完整支持的平台，最终 ZIP 必须同时提供由同一权威内核构建、带清单和哈希、按平台实测的自包含运行时，使用户没有兼容 Python 时仍可使用完整能力；
- Windows PowerShell 和 Linux/macOS POSIX Shell 只负责安全提取、环境探测、能力报告和启动权威内核，不得独立写入权威状态；
- 自包含运行时必须与系统 Python 模式通过同一套状态契约、迁移、事务、锁、证据和确定性输出一致性测试；
- 系统 Python 和自包含运行时均不可用时，只允许不依赖状态写入的只读诊断，并明确报告缺失能力；不得伪造任务创建、状态保存、锁、检查点、证据登记或验收通过；
- 执行引擎必须通过统一接口暴露能力清单，记录实际选择的引擎、构建身份、版本、支持能力和降级原因；
- 不得未经用户授权自动下载、安装运行环境或修改系统级配置。

#### 6.1.1 自包含运行时交付矩阵

阶段 A 必须冻结计划支持的操作系统、CPU 架构、执行模式和能力等级矩阵。最终发布只允许宣称实际构建并通过完整验收的组合；未在矩阵中的组合必须标记为只读或不可用。对于宣称支持完整状态写入的平台，最终 ZIP 必须包含兼容的权威运行内核，不能使用“可以携带”代替交付要求。

最终仍只交付一个通用 Markdown 和一个 ZIP。ZIP 可以包含多个按平台/架构划分的自包含运行时，但必须满足：

- 每个运行时具有稳定构建身份、文件清单、SHA-256、依赖清单和构建来源；
- 记录源代码版本、构建工具版本、目标平台、目标架构和可重复构建条件；
- 提供最小 SBOM 或等价依赖清单；
- 不包含未经使用的调试符号、缓存、下载器或包管理器；
- 设置单文件和总包大小上限，具体值由阶段 A 使用真实构建结果冻结；
- Windows 验证执行策略、SmartScreen/杀毒误报和文件来源标记；
- macOS 验证可执行权限、隔离属性以及需要时的签名/公证边界；
- Linux 验证可执行权限、动态依赖和目标发行版兼容边界；
- 薄启动器只能选择和校验清单内运行时，不能从网络隐式下载替代品；
- 任一运行时校验失败时进入只读诊断，不得回退到未验证可执行文件。

如果单一 ZIP 无法在安全、体积和维护成本内覆盖计划平台，阶段 A 必须将其记录为阻断决策并提交用户选择，不能在阶段 G 临时改变“最终双文件”交付原则。

### 6.2 自动编排层

新增面向 AI 的高层编排能力，日常只保留两个概念动作：

```text
进入项目并准备开发
结束本次工作并保存上下文
```

内部可实现为稳定命令或 API，但不得要求用户操作。进入动作必须完成健康检查、会话复用、意图分类、任务选择、历史检索、上下文预算和修改前门禁。结束动作必须完成差异检查、证据绑定、验收核对、总结、下一步、锁释放和安全 Git 检查点。

现有底层命令继续保留为诊断和高级接口，不作为日常主流程。

#### 6.2.1 自动触发与执行边界

自动编排必须区分三种触发来源，并在内部审计记录中标记：

1. `CLIENT_HOOK`：由 AI 客户端真实支持的生命周期或工具事件自动触发；
2. `AGENT_INVOKED`：客户端不支持相应事件时，由 AI 按统一工作流主动调用；
3. `USER_INVOKED`：用户手动执行诊断或高级命令。

优先适配并验证以下事件：会话启动、任务进入、文件修改前、文件修改后、测试完成、阶段完成、上下文压缩前（客户端支持时）、会话正常结束。每种客户端必须单独验证事件是否真实触发、参数是否完整、失败时是否阻断或降级；不得把“AI 按文档记得执行”描述为客户端自动触发。

关键门禁（例如修改前保护检查、阶段验收和状态提交）必须返回明确执行结果。钩子执行失败时，按风险等级停止相应自动操作或进入受限模式，不得静默跳过并继续宣称检查通过。

系统不要求安装常驻后台守护进程，也不持续扫描整个项目。优先采用客户端事件、任务事件、文件修改后的增量检查和关键节点检查点。只有在用户明确启用且有明确收益时，才允许增加可关闭的后台监控能力。

#### 6.2.2 高层编排接口契约

“进入项目”和“结束工作”必须提供版本化、可测试的统一请求与响应契约，不允许各客户端自行拼接一套流程。请求至少包含：

- 协议版本和客户端身份；
- 触发来源与客户端能力；
- 项目根和工作副本身份；
- 用户当前意图的受控摘要、来源引用或哈希；
- 幂等键；
- 允许的操作范围和自动化策略；
- 当前 Token、时间和资源预算。

响应至少包含：

- 项目方向、当前任务和下一步；
- 相关历史、失败方案和保护项摘要；
- 健康、Git、权限和执行引擎状态；
- 是否允许继续写入；
- 需要用户决定的最小问题；
- 输出预算使用量、截断情况、稳定游标和继续命令；
- 结构化错误码、重试条件和降级原因。

同一幂等键重复调用不得重复创建会话、任务、证据、总结、检查点或 Git 提交。原始用户要求只有在确有追溯必要且完成脱敏时才允许保存；默认保存受控摘要、来源和哈希。

#### 6.2.3 客户端能力等级

每个客户端和平台组合必须独立声明并实测以下等级之一：

- `HOOK_SUPPORTED`：客户端提供真实、稳定且已验证的生命周期事件；
- `AGENT_INVOKED`：无对应钩子，由 AI 按受信任入口主动调用；
- `READ_ONLY`：只能读取入口和诊断，不能可靠写入状态；
- `UNAVAILABLE`：无法安全接入。

能力清单必须细分会话启动、修改前、修改后、测试完成、上下文压缩前和会话结束事件，不得用一个总状态掩盖部分缺失。客户端升级后必须重新验证协议和事件能力。

能力等级必须对应实际约束强度：

- `HOOK_SUPPORTED` 可以在已验证事件范围内执行修改前硬门禁；
- `AGENT_INVOKED` 依赖 AI 遵循受信任入口，只能声明为流程约束，并使用修改后差异审计发现绕过；
- `READ_ONLY` 只能恢复、检索和报告，不得执行受控状态写入或声称完成自动开发闭环；
- `UNAVAILABLE` 不得声称约束系统已经接入。

同一客户端可能对不同事件具有不同等级。缺少修改前钩子时，不得把修改后检测宣传为事前阻断；缺少测试完成钩子时，不得把 AI 自报测试结果宣传为自动证据捕获。

### 6.3 项目方向层

增加稳定的项目方向基线，至少记录：

- 最终目标；
- 当前优先级；
- 完成判定；
- 明确不做的范围；
- 不可破坏的成果；
- 已确认关键决策；
- 暂缓事项；
- 当前阶段；
- 最近方向调整及用户来源。

AI 每次开始任务和准备完成任务时都必须核对方向基线，禁止因局部便利偏离项目最终目标。

### 6.4 历史关联与检索层

建立以下稳定关联：

```text
用户意图 → 任务 → 文件/符号/模块 → 决策 → 失败方案
         → 验收条件 → 证据 → 总结 → Git/环境基线
```

历史检索优先级：

1. 相同文件或符号；
2. 相同模块、接口或数据模型；
3. 相同任务目标或验收条件；
4. 相同错误、测试失败或设备现象；
5. 已确认设计决策；
6. 已失败方案；
7. 已验证功能和保护项；
8. 最近相关修改；
9. 带依据的语义相似内容。

每条被选入上下文的历史必须携带：

- 稳定来源引用；
- 相关原因；
- 当前有效性；
- 证据状态；
- 对当前工作的约束；
- 可继续读取的命令或位置。

确定性位置和结构化关联优先于 AI 语义判断。语义检索只能辅助排序，不能创造事实。

#### 6.4.1 索引范围与更新策略

历史索引必须采用白名单/排除规则与增量更新，不得默认全量读取或索引整个工程。默认排除或仅保存元数据的内容包括：构建输出、缓存目录、第三方依赖、生成文件、大型二进制、固件镜像、密钥、令牌、凭据、个人敏感信息和未经授权的外部资料。

源码索引优先记录路径、文件哈希、语言、模块归属、符号位置和必要摘要；大型日志只保留受控路径、大小、哈希、时间范围及错误片段。文件或环境变化后，相关索引标记为待更新，不得继续把过期关联作为当前事实。

索引必须支持暂停、重建、校验和排除规则配置。无法可靠解析的格式标记为 `UNKNOWN_FORMAT`，保留文件元数据并降级处理，不得伪造符号级检索能力。

索引操作必须具备版本化资源预算，至少限制最大文件数、累计读取字节、单文件大小、执行时间、并发数、内存目标和索引磁盘配额。达到任一上限时返回合法的部分结果、停止原因、未扫描范围和可恢复游标。索引必须可取消、可续跑，组件卸载或会话结束后不得留下失控扫描任务。具体默认值由阶段 A 使用小型工程、monorepo、生成文件密集工程和大日志样本校准后冻结，未经评审不得取消上限。

### 6.5 修改保护层

AI 修改前自动检查：

- Git 工作区和用户已有改动；
- 当前分支、提交、worktree 和仓库身份；
- 相关项目决策；
- 相同或相似失败方案；
- 已验证功能和保护范围；
- 可能受影响的调用方、数据和测试；
- 是否需要设备、凭据或外部授权；
- 当前会话是否拥有有效任务上下文。

只靠文档无法从操作系统层面阻止 AI 修改文件，因此约束分为三层：

1. 受信任入口的行为约束；
2. 状态、证据和完成门禁的确定性强制；
3. 修改后的 Git 差异与受保护成果审计。

不得宣传为无法绕过的系统级沙箱。

#### 6.5.1 项目文件变更事务与非 Git 恢复

状态事务只能保护结构化状态，不能替代项目文件恢复。自动编排执行文件修改前必须建立 `change_set` 或等价的文件变更事务，至少记录计划范围、修改前路径与哈希、用户已有修改状态、恢复能力、实际修改结果、修改后哈希和对应任务。

Git 项目优先使用明确基线、精确差异和安全检查点恢复，但不得重置或覆盖用户改动。非 Git 项目执行自动写入前必须为将要修改的文件建立受限、项目外或专用恢复区中的修改前副本；恢复区必须有容量、文件数量、保留时间和路径边界，且不得备份密钥或未经授权的大文件。

出现进程中断、部分文件写入成功、状态提交失败或实际差异超出计划范围时，`change_set` 必须进入 `PARTIAL` 或 `RECOVERY_REQUIRED`，下次进入项目时优先报告并核对现场。无法建立可靠恢复点时，只允许低风险单文件修改或停止自动写入，不得执行批量、生成式覆盖或不可逆修改。

文件恢复不得自动覆盖中断后产生的新用户修改。恢复前重新比较当前哈希、修改前哈希和记录的修改后哈希；存在第三方变化时停止并提供可审阅的恢复方案。

### 6.6 Token 与上下文预算层

所有默认回执和上下文包必须经过统一预算器，不允许各命令自行决定输出规模。

硬预算的可执行范围必须如实声明：运行内核、高层编排器和受控适配器返回的内容可以强制执行硬预算；客户端提供可靠工具钩子或包装器时，可以将对应工具输出纳入累计账本。AI 绕过入口直接读取文件、执行 Shell、调用浏览器/MCP 或接收用户粘贴内容时，最终双文件不能天然截获全部 Token，只能依赖客户端能力、流程约束和事后差异审计。无法截获关键工具输出的客户端必须降低对应能力等级，不得宣称实现全局硬控制。

因此，“全局 Token 预算”指约束系统能够观察和管理的完整执行链预算。每份预算回执必须同时报告已纳入和未纳入核算的来源；存在未受控大输出时，应停止继续自动展开、提示上下文风险并优先生成检查点，而不是伪造剩余额度。

建议默认硬边界：

- 普通会话上下文包保守估算不超过 4,000 Token；
- 普通单命令结构化回执保守估算不超过 2,000 Token；
- 同时设置 Unicode 字符、UTF-8 字节、对象数量和嵌套深度上限；
- 任一限制先到即停止继续展开；
- 输出必须保持合法 JSON，禁止直接截断序列化文本。

默认上下文预算建议分配：

| 内容 | 预算上限 |
|---|---:|
| 项目方向与当前用户意图 | 400 Token |
| 当前任务、进度与下一步 | 700 Token |
| 相关历史与决策 | 1,100 Token |
| 失败方案与受保护成果 | 600 Token |
| 当前任务规则 | 500 Token |
| 证据和环境摘要 | 400 Token |
| 分页、来源和继续查询信息 | 300 Token |

预算不足时优先保留：用户方向、当前任务、阻断、失败方案、受保护成果和下一步。低相关历史只返回数量、来源和分页游标。

所有分页结果必须返回：

- 实际字符数和字节数；
- 保守 Token 上界；
- 已返回项目数；
- 被省略项目数；
- `has_more`；
- 稳定游标；
- 下一条安全查询命令。

稳定游标必须绑定查询类型、规范化参数哈希、排序规则、状态修订、索引版本、预算账本和上一页最后稳定键，并通过完整性校验。分页期间权威状态或索引发生影响结果集的变化时，返回 `CURSOR_STALE` 和重新查询建议，或者继续使用创建游标时的只读快照；不得静默跳项、重复或把不同修订结果拼成同一页序列。

完整模式也必须分页。禁止单个 `--full` 绕过总预算；超量时返回预估、拒绝原因和分段读取方案。

Token 预算覆盖规则、历史、源码摘要、Git diff、工具输出和证据，不只覆盖状态 JSON。

#### 6.6.1 全局累计预算

单条命令上限不能替代全局累计预算。系统必须同时控制单次回执、单轮工具输出、一次会话恢复和单任务历史读取，建议初始默认值如下；阶段 A/B 应使用真实样本校准，必要时可下调，不得未经评审取消上限：

“单轮”定义为一个高层请求幂等键对应的执行周期：从接收一次用户意图或系统恢复触发开始，到向用户产生一次最终回执或持久化暂停结果为止。周期内的所有内部命令、分页、重试和工具调用都属于同一轮；重复调用编排器、更换客户端或创建内部子步骤不得重置单轮预算。

| 预算维度 | 初始默认上限 | 说明 |
|---|---:|---|
| 普通上下文包 | 4,000 Token | 进入项目时的首轮恢复包 |
| 普通单次结构化回执 | 2,000 Token | 单个命令或工具响应 |
| 单轮累计工具输出 | 6,000 Token | 同一轮所有工具返回累计值 |
| 单次会话恢复的历史读取 | 8,000 Token | 包括分页读取的累计历史内容 |
| 单页历史/证据展开 | 2,000 Token | 超出必须继续分页 |
| 单任务单次执行周期累计历史读取 | 默认 16,000 Token，受控上限 32,000 Token | 扩大时记录原因、已用预算和剩余预算；不得取消硬上限 |

普通上下文包 4,000 Token 是启动摘要预算，不是复杂研发任务的全部专业资料上限。任务执行中可以按需分页加载相关规范、源码和证据，但每次展开仍受单页、单轮和任务累计预算控制。FULL 模式不得绕过预算，只能使用更高且有记录的任务预算分段读取。

当预算即将耗尽时，优先保留项目方向、当前任务、阻断、失败方案、受保护成果、关键证据和下一步；低相关内容只返回来源、数量和稳定游标。达到上限后必须停止继续展开并返回合法结构化结果，不得截断 JSON 或通过反复调用变相突破预算。

若可获得对应模型的准确 Tokenizer，应使用其估算；否则使用经过样本校准的保守估算，并同时记录字符数、UTF-8 字节数、估算方法和估算误差。字符数除以固定常数只能作为粗略估算，不得标记为真实 Token 计量。

#### 6.6.2 预算账本与重置规则

新增 `budget_ledger` 或等价的权威预算账本。预算扣减必须与高层请求幂等键、会话、任务、客户端和状态修订关联，并通过原子事务或等效机制更新。账本至少记录：

- 预算范围和预算版本；
- 默认上限、受控上限和当前有效上限；
- 已使用、已保留和剩余额度；
- 字符、字节、对象、工具输出和历史读取分类用量；
- Tokenizer 或保守估算器身份、版本和误差；
- 调用来源、幂等键、客户端、任务和会话；
- 扩容原因、授权来源和到期条件；
- 最近检查点和状态修订。

单次执行周期从高层“进入项目”开始，到成功生成持久化上下文检查点并结束或明确暂停为止。客户端重连、重复调用、切换客户端或分页读取不得静默重置预算。同一活动任务进入新执行周期时，应优先复用已持久化上下文包和引用，避免重复扣减相同历史；确需重新读取时记录原因。

普通风险任务可以由系统在硬上限内根据复杂度调整额度，但必须留下理由。超过受控上限必须停止展开并生成分阶段任务或请求真正影响方向的用户决定，不得通过创建无意义会话、重复分页或切换客户端规避预算。

### 6.7 生命周期自动化层

系统自动处理：

- 会话复用和孤儿会话恢复；
- 用户意图分类；
- 继续任务或建立任务；
- 验收条件生成与变更；
- 下一步生成；
- 修改前历史与保护检查；
- 失败尝试记录与去重；
- 重要节点检查点；
- 测试证据捕获；
- 阶段总结和完成总结；
- 未完成任务的交接；
- 会话结束、锁释放和视图更新；
- 文件修改前写入操作意图事件，修改后记录实际差异；
- 测试完成后立即登记结果、命令、环境和证据引用；
- 重要节点创建轻量检查点，避免只在会话结束时保存；
- 上下文压缩前保存当前状态（仅限客户端提供可靠事件时）；
- 异常退出后依据最后一次持久化状态、事件链和实际工作区差异恢复。

生命周期自动化应优先由客户端事件和显式任务事件驱动，不要求常驻服务。对于突然断电、进程被强制终止等无法捕获的事件，只能恢复到最后一次成功持久化的状态，并重新核对工作区；不得承诺恢复尚未写入磁盘的内存状态。

用户输入变化必须区分补充、改向、扩范围、插入、取消和新任务。方向或验收变化需要保留前后关系，并使受影响证据和结论进入复核状态。

## 7. 数据模型调整

在现有状态模型上增量增加以下实体或等价结构。

### 7.1 项目方向 `project_direction`

关键字段：

- 稳定 ID 和修订；
- 最终目标；
- 优先级；
- 完成判定；
- 排除范围；
- 保护项；
- 用户确认来源；
- 生效时间；
- 被替代关系。

### 7.2 用户意图变化 `intent_change`

关键字段：

- 原始用户要求的受控引用或哈希；
- 归一化意图；
- 变化类型；
- 前后任务关系；
- 受影响验收、证据和总结；
- 是否需要用户决定。

不得在日志中保存密钥或不必要的完整敏感对话。

### 7.3 历史关联 `history_link`

关键字段：

- 来源实体；
- 目标文件、符号、模块或任务；
- 关系类型；
- 确定性依据；
- 相关分值；
- 有效性和失效原因；
- 来源 Git/环境基线。

### 7.4 上下文包 `context_capsule`

上下文包是派生结果，不是第二权威状态。必须记录：

- 当前方向和意图；
- 当前任务与下一步；
- 选中的历史和选择依据；
- 失败方案与保护项；
- 证据摘要；
- 未知项和用户决策；
- Token/字符/字节预算；
- 省略统计和继续查询游标；
- 来源状态修订和 Git 基线。

### 7.5 纠正记录 `correction`

错误事实、错误总结或过期结论不得静默覆盖。纠正记录必须保存：

- 被纠正对象；
- 纠正原因；
- 新事实或结论；
- 支撑证据；
- 影响范围；
- 相关任务和总结复核状态。

### 7.6 工作副本身份 `workspace_identity`

至少关联：

- 项目 ID；
- 仓库身份；
- 绝对路径的本地引用；
- 分支；
- 提交；
- worktree；
- 环境和工具链指纹。

路径移动、分支切换、rebase、cherry-pick 和仓库复制后必须能够识别身份变化，不能把不同工作副本错误当成同一现场。

### 7.7 状态一致性、事务与幂等

所有结构化实体必须具备稳定 ID、Schema 版本、修订号、创建/更新时间和来源引用。状态写入必须具备幂等键，重复调用不得重复创建任务、证据、总结或事件。

事件链采用追加式记录，事件至少包含事件 ID、单调序号、实体引用、前后修订、触发来源、时间、操作类型和结果。权威状态快照必须能够与事件链校验；派生索引、上下文包和 Markdown 视图不得反向成为第二权威来源。

并发更新必须使用乐观修订检查或等效机制。发现修订冲突时不得覆盖后写入者，必须重新读取、合并或停止并报告。涉及多个实体的状态变更必须使用可恢复事务：先记录事务意图，再执行变更，最后提交；中断后能够识别未完成事务并安全恢复或回滚。

任何状态损坏或事件链不一致时，默认进入只读诊断和导出模式，不得通过重建空状态、删除历史或静默修补来掩盖损坏。

### 7.8 预算账本 `budget_ledger`

预算账本是累计输出和历史读取控制的权威记录，字段和重置规则遵循第 6.6.2 节。预算账本不得仅存在于进程内存；崩溃、客户端切换或会话恢复后必须能够继续核算。由预算生成的裁剪结果和上下文包仍是派生数据，不得反向修改权威任务事实。

### 7.9 自动化执行回执 `automation_receipt`

每次高层进入、结束和关键门禁必须记录轻量执行回执，至少包含：协议版本、触发来源、客户端能力等级、执行引擎、幂等键、允许的操作范围、检查结果、预算账本引用、状态修订和降级原因。该回执用于证明自动化实际发生，不得用文档要求代替执行回执。

### 7.10 文件变更事务 `change_set`

文件变更事务是项目文件修改和恢复的权威审计记录，至少包含：任务与会话、计划路径、修改前哈希、用户已有修改标记、恢复副本引用、实际路径、修改后哈希、未计划差异、事务状态、失败位置和恢复条件。状态至少区分 `PLANNED`、`APPLYING`、`APPLIED`、`PARTIAL`、`RECOVERY_REQUIRED`、`VERIFIED` 和 `ABORTED`。

恢复副本是受限恢复资源，不是第二源码仓库；不得无限保留或与用户项目混淆。Git 和非 Git 模式必须使用同一变更事务接口，但可以采用不同恢复后端。

## 8. 历史有效性与纠错

以下变化必须触发相关结论复核：

- 相关源码、构建配置或依赖变化；
- Git 基线、分支或工作副本变化；
- 工具链、设备、固件或运行环境变化；
- 用户方向或验收条件变化；
- 原始输入、证据或产物哈希变化；
- 新证据与旧结论冲突。

恢复结果必须区分：

- 已验证且当前有效；
- 以前验证但环境已经变化；
- 静态推断；
- AI 建议；
- 已失效；
- 数据不足无法判断。

用户可以纠正错误记录。系统保留旧记录、纠正关系和审计事件，并传播相关复核状态。

## 9. Git 与检查点策略

项目首次接入时必须确定一次本地 Git 检查点策略，并写入项目方向或项目策略；以后不因每个任务重复询问：

- `DISABLED`：不创建 Git 提交，只保存结构化状态检查点；
- `SUGGEST`：测试通过后给出精确提交建议，不自动提交；
- `AUTO_SAFE`：测试通过、文件归属明确且能与用户改动安全分离时创建本地提交。

默认使用 `SUGGEST`；只有用户明确授权或项目已有可信策略时才能进入 `AUTO_SAFE`。策略变更必须记录用户来源和生效范围。任何模式均禁止自动 push。

默认策略：

- 修改前记录 Git 基线和用户改动；
- 一个功能增量通过对应测试后，可创建仅包含当前任务文件的本地检查点；
- 不得自动 push；
- 不得夹带用户无关改动；
- 无法安全拆分时不提交并明确报告；
- 自动检查点前必须分别读取暂存区差异和工作区差异，不得将两者混为一体；
- 禁止使用 `git add .`、`git add -A` 或其他会把无关用户改动整体纳入的操作；
- 不得重置、覆盖或取消用户已有暂存内容；
- 文件在任务开始前已有用户改动，或同一文件混合了用户与 AI 修改且无法可靠分离时，不得自动提交该文件；
- 只有能够证明属于当前任务、且不会夹带用户改动的文件才可进入自动检查点；
- 自动检查点失败不得影响用户原有工作区和暂存区。
- Git 不可用、身份异常或基线不可确认时，不得把代码保护状态报告为正常；
- 用户明确禁止提交时，只保存状态检查点和提交建议；
- 非 Git 项目明确降级，不伪造 Git 保护。

Git 检查点和结构化状态检查点必须关联，但不得互相冒充。

本机会话锁和状态修订只协调同一工作副本，不是跨计算机或不同仓库副本的分布式强锁。跨计算机协作必须依赖 Git 远端、协作服务或其他外部协调机制发现冲突；合并、rebase、cherry-pick 或同步外部状态后，必须重新校验项目方向、工作副本身份、证据有效性和保护项，不得把本机锁状态直接沿用到另一副本。

## 10. 自动继续与用户决策边界

满足以下条件时自动继续：

- 用户方向明确；
- 属于当前授权范围；
- 操作可逆；
- 权限和输入充足；
- 验收条件可确定；
- 没有用户改动冲突；
- 没有权威证据冲突；
- 没有超过安全、时间和 Token 预算。

以下情况必须停止并询问用户：

- 存在多个会显著改变结果的方向；
- 需求或范围发生重大变化；
- 删除、覆盖或不可恢复操作；
- 需要凭据、设备或外部授权；
- 用户改动与当前任务冲突；
- 证据冲突或完成判定不明确；
- 多工作副本冲突无法安全合并；
- 多次失败且没有新信息；
- 继续执行可能造成重大安全、数据或项目风险。

不得因为内部状态命令需要参数而打扰用户。

意图分类必须记录分类结果、置信度、受影响任务和依据。高置信度、低风险且不改变项目最终方向的补充或任务排序调整，可以自动处理；低置信度、改变最终方向、扩大重大范围、改变验收标准或涉及不可逆操作时，必须保留原方向和原验收条件，并只询问真正影响决策的关键问题。不得将“暂时插入一个优先任务”误判为“取消或永久替换原任务”。

## 11. 安全、隐私和提示注入

- 默认本地处理源码、日志、固件和历史；
- 外部 AI 或网络服务必须显式说明上传范围；
- 项目文件、源码注释和外部文档默认是数据，不自动成为高优先级指令；
- 只有系统/开发者指令、用户当前要求和受信任入口可以改变约束；
- 日志、状态和总结不得保存密钥、令牌和完整敏感配置；
- ZIP、入口和运行文件必须经过哈希与清单验证；
- 外部输入必须限制路径、大小、类型和数量；
- 自动进程执行必须参数化并限制工作目录；
- 无法验证来源的历史只能作为未验证资料。

## 12. 状态生命周期和长期项目

必须支持：

- 已完成任务归档和重新打开；
- 任务、总结、证据和事件分页；
- 大文件只保存受控路径、大小、哈希和必要摘要；
- 日志轮转和容量告警；
- 项目导出、迁移、恢复和换机重建；
- 状态模型升级的幂等迁移；
- 旧格式兼容读取；
- 归档后保留可查询索引；
- 删除前导出或可恢复路径；
- 权威历史损坏时只读导出和人工恢复。

禁止通过无提示删除历史来解决容量或 Token 问题。

## 13. 兼容与迁移策略

1. 保留现有状态、任务、证据、总结和事件；
2. 新模型通过版本化迁移增加，不原地破坏旧实体；
3. 现有底层 CLI 保持兼容，标记为诊断/高级接口；
4. 旧 Markdown/CSV 只建立路径、哈希和索引关系，不批量复制成权威事实；
5. 旧完成总结默认保持有效，但在 Git/环境不一致时进入复核；
6. 迁移前创建包事务和项目状态备份；
7. 迁移命令可重复执行且结果一致；
8. 新自动编排失败时可回退到底层已验证流程；
9. 升级不得删除客户端入口中的用户正文；
10. 完成升级、恢复、回滚和旧数据读取验收前不得删除旧包检查点。

## 14. 分阶段开发调整

### 阶段 A：冻结基线与失败复现

工作内容：

- 固定当前最终双文件哈希和完整回归结果；
- 将模拟项目普通流程、长历史 24K Token 和完整模式超大输出固化为测试；
- 记录现有数据模型、命令兼容性和用户入口；
- 建立禁止功能回退清单；
- 输出《现有内核能力审计表》，逐项记录实现路径、调用方式、数据结构、专项测试、失败路径、状态等级和重构边界；
- 区分 VERIFIED、PARTIAL、UNVERIFIED、PLANNED，只有 VERIFIED 项进入已验证内核保护清单；
- 固定最终双文件的基线哈希、包清单、可重复构建方式和完整回归结果；
- 建立当前版本的 Token 输出基线，记录普通恢复、单命令、连续工具调用和长历史场景的实际输出规模。
- 冻结单一权威运行内核策略，明确系统 Python、自包含运行时和 PowerShell/POSIX 启动器的能力边界、构建来源和一致性测试要求。

完成判定：当前安装、升级、修复、回滚、状态、证据、总结和维护测试全部可重复通过；现有内核能力审计完成；所有保留能力均有明确状态和证据；未验证能力已列入待修复或待实现清单。

### 阶段 B：权威关系、方向基线与意图变化

工作内容：

- 增加项目方向、意图变化、纠正和工作副本身份模型；
- 实现用户新消息的继续/补充/改向/插入/取消/新任务分类；
- 建立方向变化对任务、证据和总结的失效传播；
- 增加旧状态迁移。

完成判定：用户改变方向后，系统能够解释变化、保留旧目标、重新计算受影响范围并只在必要时询问用户。

### 阶段 D：统一上下文预算器

工作内容：

- 为所有高层回执建立统一字符、字节、对象和保守 Token 上限；
- 实现优先级裁剪、合法 JSON、分页游标和继续命令；
- 将完整模式改为分页模式；
- 限制输入文本、验收条件、数组和单实体大小；
- 提供输出预算统计和超量错误码；
- 实现与高层请求幂等键、任务、会话、客户端和状态修订关联的持久化 `budget_ledger`，确保重试、分页和客户端切换不能重置累计预算；
- 实现绑定查询参数、状态修订、索引版本和预算账本的稳定游标，以及 `CURSOR_STALE` 或只读快照语义。

完成判定：普通和压力测试中任何默认回执不超过预算；30 个超长活动任务仍能在预算内恢复关键状态；完整历史不能一次性输出超量内容。

### 阶段 C：历史关联索引与相关性检索

工作内容：

- 建立任务、文件、符号、模块、决策、失败方案、证据和总结关联；
- 增量索引旧 Markdown 历史资料；
- 实现确定性相关性排序和选择依据；
- 实现结论有效性和环境漂移传播；
- 提供按文件、符号、任务、错误和决策分页查询。

完成判定：准备修改一个已有文件前，系统能够自动返回相关决策、失败方案、已验证功能和来源位置，不依赖全量历史读取。

### 阶段 F：Git、保护项和非合规检测

工作内容：

- 修改前自动检查 Git、用户改动、失败方案和保护项；
- 建立文件差异与任务关联；
- 实现安全本地检查点策略；
- 检测绕过高层入口的状态和文件变化；
- 支持分支、worktree、路径移动和仓库复制；
- 实现 Git 与非 Git 项目统一的 `change_set` 文件变更事务、受限恢复副本和部分修改恢复；
- Git 异常时阻断错误的“正常”结论。

完成判定：用户改动不会被覆盖；已验证功能变化会触发回归；Git 不可用时不会伪称保护有效；非 Git 项目中断后能够识别部分修改并提供不覆盖新用户改动的恢复方案。

### 阶段 E：自动编排入口

工作内容：

- 实现单一进入动作；
- 自动复用会话、恢复任务、分类意图、加载相关历史和生成上下文包；
- 自动生成任务、验收条件和下一步；
- 自动处理节点检查点、失败记录、证据关联和完成总结；
- 实现单一结束动作和异常退出恢复；
- 普通回执隐藏底层 ID 和修订。

完成判定：模拟使用者从首次接入到跨会话完成任务，全程不需要输入任何状态管理命令或内部 ID。

### 阶段 G：最终入口、跨客户端与交付

工作内容：

- 将最终使用文档压缩为首次接入和故障恢复说明；
- 各客户端薄入口统一调用自动编排；
- 构建并验证按平台需要提供的自包含权威运行时，以及只负责探测和启动的 PowerShell/POSIX 薄启动器；
- 使用同一套一致性测试验证系统 Python 与自包含运行时产生相同状态、事务、迁移、证据和错误语义；
- Windows、Linux、macOS 和主要客户端执行验收；
- 完成旧包升级、换机恢复、自维护和确定性双打包；
- 最终目录只保留新 Markdown 和 ZIP；
- 删除临时源码、模拟项目和测试产物；
- 创建单一可回退 Git 检查点，不自动 push。

完成判定：最终双文件独立完成全部验收，使用文档不包含开发过程和版本演进记录。

### 14.1 阶段门禁与回退规则

阶段章节已经按正式依赖顺序排列为 `A → B → D → C → F → E → G`。先建立统一预算器，再向正式入口暴露历史检索；先完成修改保护与 Git 门禁，再启用可写自动编排。前置阶段的必需交付物、专项测试、完整回归和失败路径验收未通过时，不得将依赖阶段标记为正式完成；允许进行不影响基线的探索性验证，但必须与正式实现隔离。

后续阶段可以提前进行内部原型验证，但不得向最终入口暴露未通过前置门禁的能力。自包含运行时和薄启动器可以提前试验，正式构建、签名/哈希、平台一致性和交付验收归入阶段 G。

每个阶段结束必须生成节点总结，记录输入基线、完成内容、未完成项、测试证据、风险、回滚方式和下一阶段准入结论。阶段结论只允许 `PASS`、`PASS_WITH_LIMITATIONS`、`BLOCKED`、`FAIL`。存在未解决的 P0 问题时不得进入依赖该能力的后续阶段。阶段回退必须保留原记录和原因，不得覆盖历史结论。

## 16. 量化完成标准

最终发布至少满足：

1. 用户首次只提供最终双文件和项目目标即可完成初始化；
2. 后续会话不要求用户输入内部状态命令；
3. 一次高层进入动作恢复项目、任务、相关历史和下一步；
4. 历史结果说明相关原因、来源和有效性；
5. 相同失败方案再次实施前能够被发现；
6. 修改受保护功能前自动触发影响和回归检查；
7. 普通上下文包保守估算不超过 4,000 Token；
8. 普通单命令回执保守估算不超过 2,000 Token；
9. 任何完整历史查询都不能绕过分页和总预算；
10. 用户无需管理会话、锁、修订、任务、证据和总结 ID；
11. Git 不可用或基线异常时不会报告为正常保护状态；
12. AI 结论明确区分事实、证据、推断和建议；
13. 崩溃后能恢复到最后已提交状态；
14. 旧任务、证据、总结和用户入口内容在升级后不丢失；
15. 自维护只能从受信任 ZIP、项目外工作区和完整回归生成新包；
16. 最终目录严格只包含使用 Markdown 和 ZIP；
17. 最终使用文档不包含开发过程、阶段记录或版本演进内容；
18. 自动化测试不能替代真实模拟项目和失败路径验收；
19. 已验证内核清单中的每一项均有实现路径、专项测试和可复现证据；未验证能力不得标记为 VERIFIED；
20. 自动触发必须有真实客户端事件证据；不支持钩子的客户端必须明确标记为 AGENT_INVOKED 或受限模式；
21. 无系统 Python 的受支持平台能够由薄启动器启动经过实测的自包含权威运行时，并与系统 Python 模式通过同一套一致性测试；无法提供自包含运行时的平台必须明确列出能力缺口并安全降级；
22. 单轮累计工具输出和一次会话恢复历史读取均受统一预算控制，连续多次调用不能绕过预算；
23. 状态写入具备幂等、修订冲突检测、事务恢复和事件链校验；
24. 用户已有暂存内容和无法分离的混合修改不会被自动 Git 检查点覆盖或夹带；
25. 重要节点检查点不依赖正常会话结束事件，异常恢复只能声称恢复到最后一次成功持久化状态；
26. 多客户端并发、历史污染和跨客户端恢复压力测试有真实结果记录。
27. 普通任务中用户输入内部状态命令的次数为 0，因约束系统内部参数产生的用户询问次数为 0；只有方向、授权、不可逆操作和真实冲突可以询问用户；
28. 客户端能力按事件逐项标记为 `HOOK_SUPPORTED`、`AGENT_INVOKED`、`READ_ONLY` 或 `UNAVAILABLE`，不存在用文档要求冒充真实自动触发的情况；
29. 单任务执行周期具有持久化预算账本、默认硬上限和受控上限，客户端切换、重复调用和分页不能重置或绕过预算；
30. 本机锁不被宣传为跨计算机强锁，跨副本同步后会重新校验工作副本、方向、证据和保护项。
31. Token 硬预算只对系统可观察的执行链作出保证；未受控工具输出会被明确标记并触发能力降级，不会伪造全局剩余额度；
32. 非 Git 项目自动修改前具有受限恢复点和 `change_set`，部分修改与第三方变化能够被发现且不会被自动覆盖；
33. 分页游标绑定查询参数、状态修订、索引版本和预算账本，数据变化时不会静默漏项或重复；
34. 最终 ZIP 的自包含运行时交付矩阵、平台/架构、总包大小、构建来源、依赖清单和安全边界已经冻结并通过对应平台实测；
35. V1.1 是后续开发和验收的唯一目标文档，V1.0 仅作为历史参考，不再产生并行实现。

## 17. 明确非目标

- 不实现编译器、链接器或完整 IDE；
- 不替代 Git、Keil、IAR、CMake、Make 或厂商工具链；
- 不承诺只靠 Markdown 从操作系统层面绝对阻止 AI 修改文件；
- 不把所有项目资料永久塞入模型上下文；
- 不用删除历史解决 Token 问题；
- 不要求用户理解内部状态机；
- 不为某个样本项目写死规则；
- 不自动 push、不上传源码、不保存不必要敏感信息；
- 不把 AI 推断显示为已验证事实；
- 不要求安装常驻后台守护进程才能实现基本生命周期自动化；
- 在已交付并实测自包含运行时的平台上，不要求用户预先安装 Python；未提供可用权威运行内核时必须如实降级；
- 不未经授权自动安装 Python、PowerShell 模块或其他系统级依赖；
- 不承诺客户端未提供的事件钩子可以被约束文档凭空实现。

## 18. 开发执行原则

1. 先固化失败测试，再修改实现；
2. 优先扩展现有内核，不平行创建第二套状态系统；
3. 每阶段保持旧数据可读和底层诊断接口可用；
4. 每阶段先运行专项测试，再运行完整回归和模拟项目验收；
5. 一个功能增量一个 Git 检查点，不夹带用户无关改动；
6. 不以 Token 节省为理由降低证据、安全或兼容性；
7. 不以自动化为理由越过用户关键决策；
8. 不以重构为理由删除已有能力；
9. 阶段未达到量化完成标准时不得更新最终双文件；
10. 最终交付前必须再次从使用者角度执行完整流程；
11. 阶段 A 未完成现有内核审计前，不得大规模重构或删除旧实现；
12. 每个自动化能力必须记录真实触发来源和执行引擎，不得将 AI 主动调用冒充客户端自动触发；
13. 每次状态写入、检查点和 Git 操作必须保护用户既有改动，并具备失败恢复路径；
14. 所有 Token 预算必须覆盖累计工具输出和历史分页，不能只限制单条命令；
15. 对平台、客户端和运行环境的兼容性必须按实际测试结果标记，不得以理论可移植性代替实测。

## 19. 最终判定

重构完成后的系统必须达到：

> AI 自动知道项目历史、当前进度、下一步、失败方案和已有结论；在合理、可验证、受硬预算约束的范围内约束开发行为，尽量避免重复分析和重复失败。用户只把控项目完成方向和关键决策，不为每个项目或任务重复管理约束系统。

如果用户仍需要频繁执行状态命令、指定历史文件、管理内部 ID、提醒 AI 总结，或者长历史能够突破默认 Token 预算，则不能认定为最终完成。
