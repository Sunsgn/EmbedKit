# AI 嵌入式全栈开发约束包最终目标对齐与重构方案

> 本文是开发调整方案，位于最终交付目录之外。最终交付文件不得包含开发过程、版本演进或修改记录。

## 1. 最终目标

交付一套可直接放入不同嵌入式项目、由 AI 自动执行和后续维护的 Markdown 约束包，使 AI 在开发中自动知道：

- 项目最终目标、当前方向和完成标准；
- 已完成内容、准确停止位置和唯一优先下一步；
- 已有结论、失败方案、允许重试条件和不可破坏成果；
- 当前任务需要加载的嵌入式专业规范、工作流、测试与证据要求；
- 何时总结、何时回顾历史、何时停止重复尝试以及何时请求用户决策。

用户只把控产品方向、关键取舍和最终验收，不负责维护状态文件、编号、历史摘要、加载清单或 Token 分页。

## 2. 产品边界

最终成果是无运行时依赖的 Markdown 文件集合，不附带 Python、安装器、后台服务、平台二进制或必须执行的初始化脚本。小体积目录直接交付，不强制压缩。

Markdown 可以规范遵守指令的 AI，但不能提供操作系统级权限隔离、强并发锁或保证所有 AI 客户端自动读取。因此交付必须同时提供：

1. 通用入口文档；
2. 可由支持项目指令的客户端使用的根级 `AGENTS.md` 接入文件；
3. 对不自动识别入口的客户端可直接粘贴的一句启动指令；
4. 明确的能力边界和并发变化检测规则。

## 3. 最终交付结构

```text
最终版/
├── AGENTS.md
└── AI嵌入式全栈开发约束/
    ├── 00-AI嵌入式全栈约束入口.md
    ├── 01-AI工作流与项目状态约束.md
    ├── 02-约束索引与任务路由.md
    ├── rules/
    ├── disciplines/
    ├── workflows/
    ├── profiles/
    ├── templates/
    ├── references/
    └── examples/
```

`AGENTS.md` 只负责接入，不复制规则正文。`00` 是职责、永久底线和每轮入口；`01` 负责统一项目状态、历史恢复、Git 保护、证据和 Token 效率；`02` 负责按任务路由专业文档。专业规范保留完整工程深度，不压缩为一份泛化清单。

## 4. 专业覆盖

最终约束包至少覆盖：

1. 系统工程与需求；
2. 电子硬件；
3. 原理图设计与审核；
4. PCB 设计与审核；
5. 嵌入式软件、驱动、RTOS、通信、存储、Bootloader 与构建；
6. 软硬件协同分析和板级 Bring-up；
7. 真实测试、故障注入、回归与交付证据；
8. 机械、热与可靠性；
9. 生产制造、工装与校准；
10. 安全、合规与发布；
11. 供应链、替代料、RMA 与现场维护；
12. Embedded Linux、设备树、内核驱动、rootfs、服务和系统镜像。

平台特定内容只能作为带适用条件的检查项或非规范示例。不得默认 STM32、FreeRTOS、Keil、GCC、特定 EDA 或固定目录结构。

## 5. 按需加载与 Token 策略

每轮只常驻入口、统一状态的相关章节和四份通用底线。根据任务信号加载一个主工作流和必要专业规范；跨专业任务按影响追加，不预读整个包。

Token 优化目标是减少重复读取、无关历史、大段日志和重复复述。不得为了节省 Token 跳过需求确认、影响分析、异常路径、测试、证据、兼容性、安全检查或最终结果说明。

项目状态超过合理长度时先保留当前任务、失败条件、保护项、有效决策、证据索引和下一步，再把已经完成且稳定的旧记录压缩为可检索摘要。原始证据不塞入状态正文。

## 6. 统一项目状态

项目运行记录统一位于：

```text
.ai-work/
├── PROJECT_STATE.md
├── evidence/
└── backup/
```

不再并行维护 `TASK_ANCHOR`、`STATUS`、`HANDOFF`、`STATE_HISTORY`、`DECISION_LEDGER` 等旧状态文件。独立专业报告只在确有交付或复用价值时生成，其路径和结论摘要回写统一状态。

状态至少包含目标、当前任务、进度与停止位置、下一步、保护项、风险和阻断、任务记录、关键决策、失败方案、证据、最近节点总结及历史压缩摘要。AI 自动创建、迁移、更新、备份和压缩；用户不需填写。

## 7. 历史回顾与节点总结

开始任务时按“下一步与当前任务 → 相关失败方案 → 有效决策 → 保护项 → 证据 → 压缩历史”的顺序定向回顾。只有范围、输入、环境和适用条件仍一致的旧结论才可复用。

阶段完成、复杂问题解决、问题关闭、一轮修改及回归完成、里程碑完成、会话即将结束、上下文接近上限或出现阻断时自动更新节点总结。总结必须包含实际完成、证据、失败路线、剩余风险、准确停止位置和唯一优先下一步。

## 8. 旧包复用与清理原则

保留旧包中成熟的专业规范、工作流、事实 Profile、报告模板和非规范示例。清除或重写：

- Python 工具、安装和版本文件依赖；
- 多套重复状态文件和脚本锁；
- 强制项目迁移到固定目录树的规则；
- 把示例平台当作默认平台的表述；
- 失效路径、重复规则和自相矛盾的加载要求。

模板不得成为日常必填负担，示例必须明确为非规范内容，目录框架只能是可选参考。

## 9. 开发与替换流程

1. 在 `work/` 中建立模块化候选包，不直接覆盖最终版。
2. 复用并审计旧包专业文档，建立入口、索引和路由。
3. 将旧认知链路统一映射到 `.ai-work/PROJECT_STATE.md`。
4. 检查失效引用、运行时依赖、平台偏置、重复权威规则和危险动作边界。
5. 运行静态检查和代表性模拟项目验收。
6. 只有候选通过后才替换 `out/最终版`，旧交付移动到历史归档，不直接销毁。
7. 检查 Git 差异，只提交本次方案和最终包相关文件，不夹带工作区其他改动。

## 10. 必测场景

- 新项目首次接入和状态初始化；
- 中断后的新会话恢复目标、停止位置和下一步；
- 裸机、事件驱动、一个主流 RTOS、一个非 FreeRTOS 系统和未知框架；
- 驱动开发、板级 Bring-up、原理图审核、PCB、生产校准和跨专业问题；
- 失败路线检索及条件变化后的允许重试；
- 用户已有改动、脏工作区和相关/无关文件拆分；
- 多会话状态变化检测，避免静默覆盖；
- 缺失、损坏、旧结构迁移及未知字段保留；
- 长历史和长日志下的上下文压缩；
- 不可执行实机测试时保持 `NOT_RUN`，不虚报通过；
- 示例中的 FreeRTOS、STM32、Keil 等内容不被当作默认；
- 约束包只读、项目状态和证据不回写到交付目录。

## 11. 量化完成标准

最终候选必须同时满足：

1. 交付目录只包含 Markdown 约束、模板、参考和示例，不包含脚本、运行日志、缓存和开发过程记录；
2. 入口、核心状态、路由、12 类专业规范和代表性工作流齐全；
3. 无 Python、旧多状态链路、失效内部路径或强制目录迁移依赖；
4. 所有示例均明确非规范，平台特定规则有适用条件；
5. AI 能自动恢复目标、当前进度、失败方案、已有结论和下一步；
6. 正常、异常、边界、证据、回退和 Git 保护形成闭环；
7. 按需加载可把普通任务上下文控制在入口、状态摘要、通用规则和少量专业文档内；
8. 模拟验收覆盖第 10 节场景且无高风险失败；
9. 最终 Git 检查点只包含本次相关文件。

## 12. 最终判定

最终成果不是“一个万能 Markdown”，也不是带运行时的约束系统，而是一套由短入口统一调度、由统一状态保持连续性、按任务加载专业深度的嵌入式全栈 Markdown 约束包。

只有在它能让 AI 少走弯路、保持专业输出质量、自动总结并继续工作，同时不把文档管理负担转给用户时，才可作为最终版交付。
