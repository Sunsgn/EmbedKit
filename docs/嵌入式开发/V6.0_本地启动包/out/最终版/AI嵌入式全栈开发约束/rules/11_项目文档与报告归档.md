# 项目文档与报告归档

## 1. 适用范围

本规则只在 AI 需要生成独立可交付文档、正式报告，或执行项目目录新建、整理、扩展和审核时读取。普通代码修改、构建、调试和日常会话总结不加载本规则，也不为这些任务预建完整目录树。

## 2. 状态、证据和正式文档必须分开

- 日常进度、最近节点总结、准确停止位置和唯一优先下一步只写入 `.ai-work/PROJECT_STATE.md`。
- 临时或原始测试日志、失败现场、命令输出和其他证据放入项目已有稳定证据目录，或 `.ai-work/evidence/<稳定对象ID>/`。
- 具有长期查阅、评审、交付或项目管理价值的独立报告必须进入项目业务文档目录，不得默认放在约束包、临时目录、工作区外部或隐藏的 `.ai-work` 中。
- `PROJECT_STATE.md` 只记录正式文档的项目相对路径、用途、状态、适用版本和必要证据索引，不复制报告全文。

聊天回复中的简短结果不自动生成文件。只有用户要求交付文档，或任务验收明确需要独立报告且内容已有真实证据时，才创建正式文档；普通小改动只更新统一状态，禁止制造重复过程报告。

## 3. 正式文档归属

项目已有职责等价的目录时沿用，不强制改名或迁移。没有合适目录时，只创建当前报告所需的最小分支，不预建兄弟目录。默认归属如下：

| 文档或报告类型 | 默认项目目录 |
|---|---|
| 需求、规格、系统设计、接口与通信协议 | `开发文档/需求规格/`、`开发文档/系统设计/`、`开发文档/通信协议/` |
| 可复用技术说明、分析结论、设计说明 | `开发文档/技术文档/` |
| 开发过程中的正式问题闭环、调试复盘、变更说明 | `开发文档/开发记录/` |
| 测试计划、测试用例和自动化测试定义 | `测试/测试计划/`、`测试/测试用例/`、`测试/自动化测试/` |
| 单元、集成、台架、HIL、实机、回归和异常分析报告 | `测试/测试报告/`；需要分类时在其下创建最小子目录 |
| 项目阶段状态和跨会话可交付总结 | `项目管理/项目状态报告/` |
| 计划、里程碑、风险、问题、会议和正式决策 | `项目管理/计划与里程碑/`、`项目管理/风险与问题/`、`项目管理/会议与决策/` |
| EVT、DVT、PVT、MP等阶段准入或评审报告 | `阶段评审/<对应阶段>/` |
| 原理图、PCB、制造输出及硬件版本报告 | `硬件原理图PCB/` 下与当前设计、制造资料或硬件版本对应的分支 |
| 可靠性、失效分析和整改闭环 | `质量与可靠性/` 下对应分支 |
| 生产、校准、产测、合规、安全、供应链或售后报告 | 对应的专业一级目录及最小必要分支 |
| 发布说明、兼容矩阵和发布验证文档 | `开发文档/版本发布/`；冻结发布产物及其清单进入对应 `release/<实际版本>/` |

目录名称与现有项目语言或惯例不一致时，复用职责相同的现有目录。归属不明、可能形成重复权威文档或需要移动已有资料时，保持原位并向用户说明冲突，不自行建立第二套目录。

## 4. 创建和更新规则

1. 创建前搜索同主题、同对象和同阶段文档，优先增量更新唯一权威文件；需要保留冻结版本时新建明确标识的快照，不覆盖历史基线。
2. 报告必须标识对象、范围、输入版本或提交、工具与配置、实际时间、验证状态、证据位置、未知项和适用边界；不得把计划、Mock、推断或未执行步骤写成通过。
3. 文件名使用项目既有规则；没有规则时采用可识别的主题名称，只有确需版本冻结时才加入实际版本或日期，禁止用“最终版”等无法持续维护的含糊名称覆盖旧文件。
4. 原始大日志和二进制证据不复制进 Markdown；报告使用项目相对路径和必要哈希引用。
5. 目录创建、移动、覆盖、清理和 Git 操作仍受项目权限、用户改动保护及变更管理规则约束；读取本规则不代表获得相应授权。

## 5. 完成检查

生成独立报告后必须确认：报告位于正确项目目录、引用对象和版本匹配、证据可回溯、失败与未测项未被隐藏、没有重复权威文件，并已在 `.ai-work/PROJECT_STATE.md` 写入相对路径和后续动作。仅有聊天结论或 `.ai-work` 内部状态不能替代任务要求的正式交付报告。
