# 项目目录创建与资料归属

## 1. 触发与加载

AI 在执行以下任一动作前必须读取本规则：初始化项目；新增一级目录或新的业务分类目录；移动、合并、整理或审核资料；判断新文件应归属何处；扩展软件、硬件、测试、生产、发布或其他专业分支。

在现有明确目录内新增普通源码、测试代码或配置文件，且不改变目录职责时，不必加载本规则。不得为普通代码修改重复读取全文。

目录任务分为：

- `NEW`：空白项目建立最小基线和当前立即需要的分支；
- `ORGANIZE`：已有项目盘点、映射、确认后整理；
- `EXTEND`：只增加当前任务需要的新领域分支；
- `AUDIT`：只读检查目录和资料归属，不做修改。

## 2. 创建原则

1. 先读取项目根、`.ai-work/PROJECT_STATE.md`、已有入口和目录，再判断现有目录职责；禁止看到名称不同就新建同义目录。
2. 只创建承载当前真实文件或已明确产物的最小目录，不预建完整目录树、不为目录美观创建空目录或 `.gitkeep`。
3. 项目已有职责等价的英文、中文或自定义目录时沿用，并在状态中记录映射；不得同时建立 `src/firmware/program/程序`、`docs/文档/开发文档`、`test/tests/测试` 等重复根目录。
4. 项目源码和构建路径优先使用英文；正式业务资料可以沿用项目已确定的语言和命名规则。
5. 创建、移动、覆盖、删除、清理和 Git 操作分别遵守用户授权、工作区保护和变更管理规则；读取本规则不代表获得破坏性操作权限。
6. 不确定归属时保持原位，记录候选目录、影响和待确认项；禁止按扩展名批量猜测资料职责。

## 3. 新项目最小基线

空白嵌入式项目首次只建立实际需要的入口：

```text
项目根/
├── AGENTS.md
├── AI嵌入式全栈开发约束/
├── .ai-work/
│   └── PROJECT_STATE.md
├── program/                 # 当前确有源码工程时
├── 开发文档/               # 当前确有开发资料时
├── 硬件原理图PCB/          # 当前涉及硬件设计时
├── 测试/                   # 当前已有测试资料或立即开展测试时
├── README.md               # 需要项目入口说明时
└── .gitignore              # 已确认忽略项后建立或更新
```

除 `AGENTS.md`、约束目录和运行状态外，其余业务目录都按实际任务创建。不得为了匹配示意图一次性生成所有目录。项目已有源码容器名称时沿用，不再创建 `program/`。

## 5. 源码、工具和资料边界

- 已确认的源码工程或 SDK 按共同构建入口和工程边界整体保留，不拆散其内部文档、测试、样例、工具、构建配置和已有产物。
- 工程外参考程序进入 `开发文档/参考资料/参考程序/`；不得混入正式构建，除非用户明确将其纳入产品源码并完成验证。
- 工程外技术、协议和过程资料分别进入 `开发文档/技术文档/`、`开发文档/通信协议/` 或 `开发文档/开发记录/`。
- 工程外构建错误、调试日志和测试结果进入 `测试/测试报告/` 的适当分支；原始临时证据也可放 `.ai-work/evidence/`，正式报告归属执行 `11_项目文档与报告归档.md`。
- 独立工具包进入根级 `tools/`；仅服务本项目测试且由项目维护的辅助源码进入 `测试/工具/`。
- `开发文档/版本发布/` 保存发布说明等可编辑文档；`release/` 保存对应版本的冻结交付产物及清单。
- `制造工程/` 保存转产开发资料；`manufacturing/` 保存当前现场执行资料；`生产备份/` 保存受控冻结归档，三者不得混用。

## 6. 文件、权威来源和大文件

1. 同一可编辑受控资料只保留一个权威主文件；其他位置使用索引或相对链接。`release/`、`manufacturing/` 和 `生产备份/` 可以保存带来源、版本、时间、大小及 SHA-256 的只读快照。
2. 文档优先使用 Markdown；二进制资料记录来源、适用产品、版本、负责人或生成工具和时间。不得伪造参数、签名、批准、认证、生产或测试记录。
3. 测试、生产、校准和发布资料必须可追溯到产品、软硬件版本、时间及实际执行人或设备；无法确认时标记未知。
4. 密码、Token、私钥、真实设备密钥和敏感环境文件不得进入资料目录或日志；必要记录必须脱敏。
5. 二进制文件达到 10 MiB 或频繁修改时评估 Git LFS 或受控外部存储；达到 50 MiB 不得直接加入普通 Git 历史。外部存储至少保留受控位置、版本、大小和 SHA-256。
6. `.gitignore` 只能精确忽略已确认的缓存、本机环境和生成输出，不得用宽泛规则误伤工程配置、链接脚本、库、固件或正式资料。

## 7. 已有项目整理

`ORGANIZE` 必须分两轮执行：

1. **只读盘点与计划**：识别全部根级对象、源码顶层边界、现有职责、Git状态和有效引用；给出每项“迁移、保持、工程内部保持、隔离或待确认”的精确映射，以及冲突、备份、回滚和验证方法。涉及移动、覆盖或删除时，在执行前取得针对精确路径的授权。
2. **迁移与验证**：先以可回滚方式复制或移动；构建前比较文件数量、总字节和必要哈希；更新当前有效引用；使用原有入口执行与风险匹配的构建或测试；检查无计划外差异。只有完整性和功能验证通过且清理另获授权时才能删除源文件。

同名目标必须先比较内容；不同内容保留双方并报告冲突。无法读取、哈希不一致、边界错误、引用无法恢复或验证失败时停止受影响分支并保留源数据，不得用“基本完成”代替失败。

## 8. 完成验收

目录任务结束前确认：

- 新目录确有当前用途，没有预建空树、同义根目录或错误占位文件；
- 源码边界完整，参考资料、独立工具、测试辅助和正式构建没有混放；
- 新增或移动的资料有唯一权威位置，旧引用已处理，用户原有资料未丢失；
- 报告、证据、发布产物、生产资料和冻结备份进入正确职责目录；
- 需要的数量、字节、哈希、构建、测试、打开验证和 Git 差异已实际检查，未执行项明确标记；
- `.ai-work/PROJECT_STATE.md` 已记录目录变化、权威路径、未解决冲突、验证结果和下一步。

最终向用户报告新增、移动、保持原位、未创建、验证结果、风险和需要额外授权的动作，不把内部目录维护转交给用户。
