# 规范效力与加载规则

## 1. 唯一规则源

`rules/`定义跨专业强制底线，`disciplines/`定义专业强制规则。一个要求只能在其权威文件中定义一次；其他文件只能引用标题或路径，不得转抄后形成第二版本。

## 2. 冲突优先级

在不突破安全、事实和证据底线的前提下，按以下顺序处理：

1. 用户对当前任务的明确要求与授权；
2. 目标路径内更具体且已存在的项目约束；
3. 项目源码、配置、测量、项目文档或统一状态中有来源、版本、状态的已确认项目事实；
4. 当前启用并命中的专业规范；
5. 通用工程规则；
6. 工作流和模板。

发现冲突必须列出双方内容、适用范围、风险和拟采用项。涉及安全、不可逆动作、接口兼容或验收口径时，在冲突解决前不得执行依赖该结论的动作。AI不得以项目习惯绕过安全和证据底线。

## 3. 按需加载

每个任务只加载`00`至`03`四份通用底线、当前专业强制Profile、命中的专业规范和一个主工作流；修改任务追加Git规则，涉及接口或持久化时追加数据兼容规则。跨专业交接、真实测试、合规或发布门禁可以追加必要工作流，但必须记录触发原因。不得为了“可能有用”预读全部规范。

## 4. 项目事实状态

- `CONFIRMED`：有文件、数据手册、配置、测量或用户确认等可定位来源，可用于决策。
- `ASSUMPTION`：为了继续分析暂定，必须显式标记，不能用于危险或不可逆操作。
- `UNKNOWN`：未知，不得替换成经验值。
- `CONFLICT`：来源冲突，解决前不得依赖。
- `NOT_APPLICABLE`：经说明确实不适用。

只补充当前任务所需事实。无关`UNKNOWN`不得阻塞工作；缺少信息会影响安全、接口、电气正确性、不可逆操作或结论有效性时才构成阻塞。

## 5. 专业启用

`profiles/`只提供事实采集检查表，不是需要用户填写的运行状态。AI 根据当前任务、影响传播和已有项目事实自动选择专业，并将必要事实及来源写入统一状态或项目已有权威文档。例如软件修改改变引脚、电压、时序或通信契约时，必须追加协同分析；纯软件重命名不因此加载硬件规范。不得因为某个 Profile 未填写而忽略明显命中的专业，也不得强迫用户一次补齐无关字段。

## 6. 状态词

所有专业和模板的最终状态只能使用`PASS`、`FAIL`、`BLOCKED`、`BLOCKED_BY_AUTH`、`NOT_RUN`、`UNAVAILABLE`或`NOT_APPLICABLE`。分类标签和阶段等级不得替代最终状态；`UNKNOWN`只表示项目事实未知。不得用“应该没问题”“基本通过”替代状态。
