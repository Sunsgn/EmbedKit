# AI 工作流与项目状态约束

## 1. 每轮运行顺序

1. 确认项目根和更具体的项目约束，检查工作区及用户已有改动。
2. 先读取 `.ai-work/PROJECT_STATE.md` 顶部不超过 4,000 字符的“会话恢复摘要”。
3. 只在摘要指向或当前任务需要时，按对象 ID、文件、符号或错误定向读取失败方案、有效决策和证据。
4. 用关键词在 `02-约束索引与任务路由.md` 定位所有实际受影响的专业，选择必要规则和专业章节，但只选择一个主工作流。
5. 明确本轮范围、实际输入、预期输出、失败路径、验收和权限后执行。
6. 修改后执行与风险匹配的定向测试、失败测试和必要回归，检查实际差异。
7. 更新状态并向用户报告结果、证据、风险、阻断和唯一优先下一步。

只读分析不得擅自变成实施；诊断不得擅自修复。用户消息改变目标时先更新方向和影响，不机械继续旧任务。

## 2. 统一状态位置

```text
.ai-work/
├── PROJECT_STATE.md
├── evidence/
└── backup/
```

`PROJECT_STATE.md` 是唯一运行状态中心。不得并行创建另一套任务锚点、状态、交接、决策或失败台账。原始日志、大文件和临时证据放入 `evidence/` 或项目已有证据目录；需要长期查阅、评审或交付的独立报告按 `rules/11_项目文档与报告归档.md` 进入项目业务文档目录。状态只保存摘要、结果、适用范围和相对路径索引。

若状态不存在、结构损坏、来自旧格式、发生并发变化或需要压缩，读取 `references/统一项目状态详细规则.md` 的对应章节后处理。不要在正常会话中加载整份详细规则。

## 3. 状态最小结构

文件顶部的“会话恢复摘要”必须在不超过 4,000 字符内回答：

- 项目最终目标、当前方向和完成判定是什么；
- 当前活动任务是什么，已经做到哪里，准确停在哪里；
- 唯一优先下一步是什么，为什么是它；
- 哪些成果和用户改动不可破坏；
- 哪些结论已经确认，依据和适用范围是什么；
- 哪些方案失败过，证据和允许重试条件是什么；
- 已执行哪些测试，结果、证据和未测项是什么；
- 当前风险、未知项、冲突和阻断是什么；
- 最近节点完成了什么，后续如何直接续接。

记录必须区分事实、推断、假设、未知和冲突。完成时间、源码/固件/硬件/工具版本及证据位置按任务风险记录；无证据不得把尝试写成已验证结论。

## 4. 历史回顾

按“当前任务和下一步 → 同对象失败方案 → 有效决策 → 保护项 → 相关证据 → 压缩历史”回顾。只复用任务范围、输入版本、环境和适用条件仍成立的结论；条件变化时说明变化并重新验证。

同一条件下不得重复已确认失败的路线。新证据推翻旧结论时保留失效原因和替代结论，不删除历史依据。历史只用于减少重复劳动，不能压过当前源码、实测、用户新要求或更具体规则。

## 5. 修改保护与 Git

- 修改前检查状态、分支、工作区、局部规则、现有入口、接口、数据和测试。
- 用户改动默认保留；不得整体回退、覆盖、顺手格式化或夹带无关文件。
- 优先精确检索、局部读取、增量修改和定向测试；复杂重构先建立保护基线。
- 提交前检查实际差异、暂存清单、敏感信息和测试结果，只包含当前目标相关文件。
- 推送、合并、打标签、发布、烧录、生产写入及其他高影响动作必须符合用户授权和安全规则。
- 不能安全拆分相关改动时报告原因，不擅自提交或把用户改动一起纳入。

## 6. 测试、证据与完成

测试必须与当前实现和输入匹配，并区分静态检查、编译、仿真、单元、集成、台架、目标板、环境及生产验证。工具返回成功不自动等于功能通过；日志不完整、证据过期或对象不匹配时不能记 `PASS`。

完成至少要求：范围内功能真实可用；正常、异常和关键边界经过与风险匹配的验证；失败可定位和恢复；持久化、兼容性、资源上限和回退已处理；差异无越界；状态、证据、剩余风险和下一步已更新。不能执行的项目明确标为 `NOT_RUN` 或 `UNAVAILABLE`，不得用计划、Mock 或推测冒充完成。

## 7. 节点总结与下一步

阶段完成、复杂问题解决、问题关闭、一轮修改及回归完成、里程碑完成、会话将结束、上下文接近上限或出现阻断时，自动更新“最近节点总结”。至少记录目标、实际完成、关键结论、变更、验证、失败路线、风险、准确停止位置和下一步。

节点总结默认只写入 `PROJECT_STATE.md`，不为每轮工作生成独立过程报告。用户要求正式文档，或验收明确需要可交付报告时，才按项目目录职责归档并把相对路径写回状态。

下一步必须具体、可执行、可验证，并说明目标对象和完成条件。若首选动作被阻断，先推进不依赖阻断的安全工作；确需用户决定时给出选项、影响和建议，不把内部状态维护转给用户。

## 8. Token 与上下文

Token 优化首先限制约束自身开销：日常只常驻短入口和恢复摘要；索引只读取命中行；专业文档先读标题和相关章节；详细状态、模板、案例和历史默认不加载。开发中继续先检索再读局部；已读且未变化的文件不重复读取；长日志只提取错误、上下文和退出状态；先定向测试再做必要回归；回复聚焦结果和边界。

不得因节省 Token 跳过需求、安全、兼容、影响分析、失败路径、测试或证据。状态变长时，当前任务、保护项、有效决策、失败条件、证据索引和下一步保留原文；已完成且稳定的旧记录压缩为可检索摘要。详细压缩和恢复规则见 `references/统一项目状态详细规则.md`。

## 9. 状态并发和损坏边界

Markdown 不提供强锁。写入前后检查状态修订、修改时间和内容是否变化；检测到其他会话或用户更新时先合并不同字段，冲突字段保留双方内容并请求决定，禁止静默覆盖。

状态缺失时基于项目事实重建并标记未知；状态损坏时先备份原文再恢复可识别内容；旧格式迁移必须保留未知字段和原始备份。详细步骤只在实际命中时读取 `references/统一项目状态详细规则.md`。

## 10. 约束维护边界

普通项目开发不得擅自修改本约束包。发现缺口时在项目状态记录改进建议；只有用户明确授权后才修改规则。修改必须保持跨项目通用性，检查入口、路由、交叉引用、平台偏置和代表性场景，不把项目临时参数固化为通用约束。

每轮结束前自检：目标未偏离、用户改动未覆盖、相关历史已检查、差异未越界、测试与证据足够、风险和下一步已更新、用户无需管理内部状态即可继续。
