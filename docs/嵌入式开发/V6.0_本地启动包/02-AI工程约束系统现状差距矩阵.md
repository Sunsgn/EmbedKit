本文档回答：现有约束包已经具备什么、距离最终目标还缺什么、哪些内容应保留、哪些内容必须重构，以及下一阶段应按什么依赖顺序推进。

## 2. 状态定义

| 状态 | 含义 |
|---|---|
| `VERIFIED` | 已使用真实工作流和有效证据完整满足目标 |
| `PARTIAL` | 存在可复用实现，但未形成完整闭环或缺少真实验收 |
| `NOT_STARTED` | 目标要求的核心能力不存在，只有文档、模板或无关局部能力 |
| `BLOCKED` | 已有实现存在阻断性缺陷，按自身规则不能合法继续 |
| `STALE` | 曾有实现或证据，但已不适用于当前版本 |

复合目标只有全部关键验收通过才能标记为 `VERIFIED`。本文档不使用总体百分比掩盖局部缺口。

## 5. 关键结构性问题

### 5.1 文档承担了本应由程序完成的安装职责

当前初始化指令要求 AI 自行完成 ZIP 预检、临时解压、迁移计划、备份、三方比较、增量合并、冲突阻断、恢复和报告。包内只有 `init_cognition.py`，没有负责整个接入事务的安装器。

结果是：不同 AI 可能选择不同命令和合并方式；中断后没有统一事务状态；文档测试只能证明文字存在，不能证明文件保护真实有效。

### 5.2 包校验在 Windows 上自我阻断

`.ai/tools/validate_package.py` 使用以下逻辑检查非法路径：

```python
if p.is_file() and '\\' in str(p.relative_to(ROOT)):
    errors.append(...)
```

Windows 的正常 `Path` 字符串使用反斜杠，因此所有包文件都被判为 `INVALID_PATH`。初始化指令明确规定包级验证失败不得安装，所以当前包在 Windows 上按自身规则必须停止。

### 5.3 状态由多个模板共同承担

任务创建会生成或依赖：

- `TASK_ANCHOR.md`
- `STATE_CARD.md`
- `STARTUP_RECEIPT.md`
- `PROJECT_DISCOVERY_REPORT.md`
- `INPUT_LOCK.md`
- `TASK_PLAN.md`
- `STATUS.md`
- `STATE_HISTORY.csv`
- `DECISIONS.md`
- `HANDOFF.md`
- `GIT_BASELINE.json`

这些文件具有局部校验，但没有统一状态修订号和单一读写入口。同一事实需要在多个文件中重复填写，无法可靠进行乐观并发校验、事件重放和派生视图同步。

### 5.4 局部锁不能解决多会话一致性

`task_lock.py` 的优点是原子创建、记录会话并拒绝非所有者释放；应保留这些原则。但它仍存在以下边界：

- 只有单个任务目录锁，没有项目、状态实体或文件范围锁。
- 没有租约、续租和受控接管。
- `inspect` 调用前会创建任务目录，不是完全只读。
- 不校验状态修订号和 Git/文件重叠范围。
- `generate_summary.py` 和 `checkpoint.py` 没有强制持锁。
- 总结索引和检查点索引采用追加写入，两个会话可能竞争。

### 5.5 总结工具只创建草稿，不生成可信总结

`generate_summary.py` 能验证任务身份并创建不可覆盖的记录 ID，这是可复用能力。但实际内容来自模板，工具最后明确提示由 AI 根据真实文件和证据填写。它没有：

- 读取统一当前状态。
- 聚合任务事件和证据。
- 判断哪些证据已过期。
- 根据研发节点触发。
- 去重或修订既有总结。
- 对索引更新提供事务保护。

因此当前属于“总结草稿生成器”，不是目标要求的研发节点总结服务。

### 5.6 项目识别不满足通用性

`discover_project.py` 只使用少量文件名模式：

- 任意 `Makefile` 会成为 Linux 候选证据。
- 任意 Eclipse `.project`/`.cproject` 会成为 STM32CubeIDE 候选证据。
- Vite/Web 项目的 `package.json` 和 `vite.config.ts` 不会产生技术栈候选。
- 排除目录是在匹配结果阶段判断，递归遍历仍可能进入大型目录。
- 结果最多保留 100 条，但扫描过程没有时间、文件数、取消或进度限制。

该工具可以保留为早期启发式样本，不能继续作为通用项目识别核心。

### 5.7 Git 门禁与首次安装流程没有衔接

`create_task.py` 要求 Git 工作区干净，任务记录目录除外；这是建立可信基线的合理原则。但用户刚把两个输入文件放入项目并完成安装后，ZIP、指令、根入口和 `.ai/` 都会使工作区变脏。初始化指令又禁止 AI 自动提交或删除输入文件。

系统缺少“安装事务完成—用户确认—初始化检查点—建立正式任务基线”的明确过渡，因此首次使用会在创建正式任务前停止。

### 5.8 测试更偏向局部结构，不足以证明最终目标

现有测试对任务 ID、路径穿越、基线身份、非法状态转换和负向拒绝有实际价值，应保留并迁移。但以下关键流程尚无真实自动化验收：

- 两文件到已有项目的完整事务安装。
- 三个根入口和已有 `.ai/` 的真实合并。
- Codex、Claude、Gemini、Copilot 的实际自动加载。
- 统一状态、并发修订冲突和崩溃恢复。
- 研发节点总结生成、过期和去重。
- 需求完成度追踪。
- 包内自维护、重新打包、升级和回滚。
- Windows、另一操作系统、特殊路径和大型仓库矩阵。

## 6. 应保留和迁移的现有资产

### 6.1 原则与规则资产

- 不覆盖项目已有文件和用户改动。
- 映射未确认时 fail-closed。
- Git 基线固定且不能用当前 HEAD 偷换。
- 输入锁绑定项目、任务、基线和路径。
- 已验证文件使用版本化快照，不覆盖旧基线。
- 检查点、总结和证据使用稳定 ID，不覆盖既有记录。
- 未知格式和未知项目明确降级，禁止猜测。
- 工具输出不替代工程事实和真实测试。

### 6.2 可迁移工具逻辑

| 现有工具 | 可保留部分 | 需要重构部分 |
|---|---|---|
| `storage_map.py` | 相对路径、项目边界和任务 ID 校验 | 接入统一配置、Schema、Junction/链接策略和迁移 |
| `lock_inputs.py` | 项目/任务/基线绑定、哈希校验 | 接入统一证据、容量限制、增量哈希和取消 |
| `detect_drift.py` | 固定 Git 基线和 NUL 安全路径处理 | 接入状态修订、证据过期和无 Git 降级 |
| `protect_verified.py` | 版本化文件哈希快照 | 接入统一证据 ID、保留策略和需求关联 |
| `validate_task.py` | 合法状态转换和完成门禁思想 | 状态迁入结构化中心，Markdown/CSV 改为视图 |
| `task_lock.py` | 原子抢占和所有者释放 | 增加租约、范围、修订、恢复和会话注册 |
| `checkpoint.py` | 不覆盖检查点和身份绑定 | 从状态事件生成、事务更新索引并校验恢复能力 |
| `generate_summary.py` | 总结类型、稳定记录 ID和任务身份绑定 | 从状态/事件/证据生成，增加触发、去重、过期和并发 |
| `validate_package.py` | 清单哈希、本地链接和文件集合检查 | 修复跨平台并加入 ZIP 预检、根入口、资源上限和重打包验证 |

### 6.3 可迁移模板内容

现有 Markdown/CSV 模板中的项目身份、目标、验收、输入、决策、状态历史、证据、下一步和交接字段具有参考价值。迁移时应建立字段映射，把它们变为：

- 结构化状态的初始化表单。
- 由结构化状态生成的人类可读视图。
- 旧项目导入兼容格式。
- 报告和归档输出。

不能继续让每个模板独立维护同一事实。

## 7. 必须重建的核心能力

以下部分不适合在现有脚本上继续零散打补丁：

1. 事务化安装、升级、卸载和恢复控制器。
2. 统一结构化状态中心、Schema、修订和事件模型。
3. 会话注册、多范围锁、租约和乐观并发控制。
4. 需求—任务—代码—证据—总结关联模型。
5. 研发节点触发、总结生成、索引、过期和去重服务。
6. 状态健康检查、事件重放、索引重建和损坏修复。
7. AI 客户端入口适配、能力声明和启动回执。
8. 包内维护、测试、版本、清单、重打包和回滚入口。
9. 通用项目识别适配器和大型仓库扫描引擎。

“重建”不等于删除现有规则和测试，而是让现有有效逻辑迁入统一内核，不再由互相独立的脚本和模板各自维护状态。

## 8. 重构依赖顺序

### 阶段 0：冻结和可追溯基线

目标：确保现有包、目标文档和差距评估均可回退。

完成条件：

- 固定当前 ZIP、SHA-256、版本和测试结果。
- 固定 15 个核心目标 ID。
- 记录所有现有工具、模板和迁移映射。
- 不再把当前 RC 描述为最终可用版本。

### 阶段 1：安全安装与包内统一入口

依赖目标：`GOAL-DELIVERY-001`、`GOAL-INSTALL-001`、`GOAL-SAFETY-001`、`GOAL-LOAD-001`。

主要工作：

- 修复跨平台包校验。
- 建立 ZIP 预检、dry-run、事务、备份、安装状态和回滚。
- 建立包拥有文件与项目拥有文件的边界。
- 建立 Codex、Claude、Gemini、Copilot 薄入口和加载验收。
- 解决首次安装与 Git 基线衔接。

阶段门禁：在 Windows 上通过新项目、已有项目、重复安装、冲突、中断恢复和恶意 ZIP 测试。

### 阶段 2：统一状态内核

依赖目标：`GOAL-STATE-001`、`GOAL-CONTINUITY-001`、`GOAL-TRACE-001`。

主要工作：

- 定义项目、需求、任务、下一步、会话、证据、决策、问题、检查点和总结 Schema。
- 建立当前快照、只追加事件、状态修订和原子事务。
- 建立 Markdown/CSV 字段迁移和视图生成。
