# AI 工程约束系统 7.1.0 自动完善执行方案

> 文档性质：开发控制基线，不属于最终用户交付文件。  
> 输入基线：`out/最终版/通用ai约束文档_7.0.0.zip`。  
> 最终交付仍然只能包含配套初始化执行指令 Markdown 和正式 ZIP 两个文件。  
> 目标：把 7.0.0 中依赖 AI 自觉遵守的关键约束，升级为运行时可验证、默认拒绝绕过、可恢复且可迁移的确定性机制。

## 1. 最终完成标准

7.1.0 必须同时实现以下结果，缺少任何一项不得标记正式完成：

1. 所有状态写入统一经过包完整性、权威历史、活动会话、会话租约、状态修订和范围锁门禁。
2. AI 即使漏读指令、使用伪造会话 ID、使用过期会话、不持有锁或跳过 Doctor，也不能写入受保护状态。
3. 每条验收条件具有稳定 ID，并逐条关联当前有效证据；不能使用一份无关 `PASS` 文件完成全部验收。
4. 证据保存执行命令或工具身份、退出码、工具版本、输入哈希、环境摘要、产物哈希、结果和局限；无法取得的信息明确为未知，不能伪造。
5. 总结核验时重新读取当前证据实体并复核产物哈希；证据、输入、Git 基线或环境漂移后，任务和总结自动传播为 `STALE`。
6. 新会话可以通过正式命令查询已完成、进行中、失败、暂停和阻断任务，并恢复“做到哪里、为什么、下一步是什么”。
7. 内部状态写锁和锁注册表在进程崩溃后能够通过 Doctor 识别并受控恢复，不允许永久锁死项目，也不允许未经核对直接删除。
8. 自维护测试报告绑定维护工作区确定性内容哈希；测试后任何受打包文件变化都会拒绝重打包。
9. 7.0.0 项目可以无损升级到 7.1.0，并可事务回滚到 7.0.0；状态、证据、总结、用户文件和旧入口均不丢失。
10. Windows、Linux、macOS 均提供可直接复制执行的安全单文件引导提取和初始化步骤，并完成实际 CI 或本机矩阵验证。
11. 长期状态具有容量诊断、分页查询、归档策略和性能基线，不能随任务数量无限退化。
12. 最终目录严格只有 `AI工程约束包通用接入与初始化执行指令_7.1.0.md` 和 `通用ai约束文档_7.1.0.zip`。

建议版本：

- `package_version=7.1.0`
- `runtime_api_version=1.1.0`
- `state_schema_version=1.1.0`
- `structure_version=16`

## 2. 自动执行总规则

执行 AI 按阶段顺序连续推进。每个阶段执行“读取基线 → 增加失败回归 → 最小实现 → 专项测试 → 完整回归 → 差异检查 → 独立 Git 检查点”，通过后自动进入下一阶段，不逐项等待确认。

只有以下情况必须停止并报告：

1. 需要覆盖或删除不能证明属于当前维护工作区的用户文件。
2. 需要改变本方案的最终目标、双文件交付形式或安全边界。
3. 7.0.0 状态无法无损迁移，且存在两个以上会造成不同用户结果的方案。
4. 连续三次遇到相同阻断且安全替代路径已经耗尽。
5. 需要网络发布、Git push、外部消息、凭据或新的系统权限。

不得停止的情况：实现困难、测试较慢、需要增加回归、发现可在维护工作区修复的缺陷、当前阶段存在多个内部实现选项。此类情况由 AI 选择改动最小、可测试、可回滚的方案继续执行。

每阶段必须只暂存当前阶段相关文件，不得夹带工作区原有删除、未跟踪文件、日志、缓存、临时 ZIP 或其他模块改动。

## 3. 阶段 0：建立 7.1.0 维护基线

### 修改内容

1. 使用 7.0.0 已安装 CLI 的 `maintenance prepare` 从正式 ZIP 建立项目外维护工作区。
2. 核对 ZIP SHA-256、195 个成员、清单和包版本。
3. 运行完整 `test_*.py`，保存基线报告和测试数量。
4. 为本方案每个缺陷先建立能够在 7.0.0 上失败的回归用例。
5. 新增 `RELEASE_7_1_ACCEPTANCE.md`，以本方案的最终完成标准作为发布门禁。

### 验收

- 原始 ZIP 不修改。
- 所有新增缺陷测试在修复前能够准确失败，不能因测试脚本本身错误失败。
- 维护工作区位于业务项目外。

### 检查点

`test(ai-constraints): establish 7.1 regression baseline`

## 4. 阶段 1：统一强制写入门禁

### 设计

新增唯一的 `WriteGuard` 或等价服务。除初始化和只读命令外，所有状态变更必须通过同一入口，禁止各 CLI 分支自行拼装部分检查。

门禁顺序固定为：

1. 安装状态和受管理运行时文件完整性；
2. `state verify` 的权威历史快速校验；
3. Doctor 是否要求只读；
4. 会话存在、状态为 `ACTIVE`、租约未过期；
5. 请求携带当前状态修订和实体修订；
6. 当前会话持有覆盖全部写入范围的有效锁；
7. 执行状态事务；
8. 写后快速校验。

必须覆盖：`task create/transition`、`next create/transition`、`evidence add/verify/invalidate`、`summary generate/verify`、`legacy import`、Doctor 修复和未来新增写命令。

`task create` 使用项目级最小锁，例如 `project:state` 或经过注册的 `path:.ai/state` 范围；不得继续绕过会话验证。锁作用域模型需要正式支持项目级作用域，不能用特殊字符串临时拼接。

### 必测失败路径

- 伪造但格式正确的 `SES-*`。
- 已结束会话。
- 已过期会话。
- 不持锁写入。
- 锁只覆盖另一个任务或相邻目录。
- 权威事件链损坏后直接执行写命令。
- 安装运行时文件被修改后直接写入。
- 写前校验通过、状态修订随后变化。

### 验收

- 所有失败均返回稳定错误码且零状态变化。
- 不存在绕过 `WriteGuard` 的公开写入路径。
- 通过静态测试枚举 CLI 写命令，未来新增写命令未声明门禁时测试失败。

### 检查点

`feat(ai-constraints): enforce unified write guard`

## 5. 阶段 2：锁与崩溃恢复

### 修改内容

1. 给 `state-write.lock` 和 `.registry.lock` 增加模式、令牌、PID、创建时间、主机/工作副本标识和最大存活时间。
2. Doctor 显式诊断内部互斥锁，不把内部互斥锁与用户范围锁混为一类。
3. 增加受控恢复计划：检查进程是否仍存活、锁年龄、未完成事务、HEAD、Git 和文件变化；生成备份和审计报告后才能恢复。
4. 进程仍存活、锁信息无效或状态不一致时拒绝自动恢复。
5. 会话过期后禁止新写入；原会话必须先受控恢复或启动新会话。
6. 会话心跳不隐式续租范围锁；范围锁续租仍需显式、可审计。

### 测试

- 在持有两个内部锁的不同时刻强制终止子进程。
- 事务写入前、事务封套写入后、事件追加后、HEAD 更新后分别模拟崩溃。
- 活进程锁、死进程锁、PID 重用、损坏锁文件、系统时间跳变。
- 恢复前后事件链、事务封套和用户文件不变。

### 验收

- 断电模拟后项目不会永久不可写。
- 不存在“看到锁过期便自动删除”的路径。
- 每次恢复均有备份、原因、执行者和时间记录。

### 检查点

`feat(ai-constraints): recover orphaned internal locks safely`

## 6. 阶段 3：可查询历史与确定性恢复

### 新增命令

至少实现：

```text
task list/show/search
next list/show
evidence list/show
summary list/show
history timeline
session resume
checkpoint create/show
```

所有查询支持 JSON，列表支持状态、任务、时间和数量过滤，并具有默认分页上限。不得要求 AI 直接读取 `.ai/state/entities/`。

`session resume` 必须返回：

- 项目身份和包版本；
- 最近活动任务；
- 最近完成任务；
- 阻断、失败方案和未知项；
- 当前有效与失效证据；
- 最近已验证总结；
- 可执行下一步；
- Git/环境漂移；
- 建议的唯一首要动作及依据。

没有活动任务时，不能只返回空数组；必须返回最近完成节点、未闭环事项或明确的“当前无未完成工作”。

### 测试

- 完成任务后新会话仍能查询完整历史。
- 数千任务分页稳定且顺序确定。
- 未知 ID、损坏派生索引和旧 7.0.0 状态安全降级。
- 查询命令严格只读。

### 检查点

`feat(ai-constraints): add resumable history queries`

## 7. 阶段 4：验收条件与证据模型 1.1

### 数据模型

将字符串验收条件迁移为稳定实体或稳定子记录：

```json
{
  "id": "ACPT-...",
  "text": "...",
  "required_evidence_types": ["TEST"],
  "status": "UNVERIFIED",
  "evidence_refs": [],
  "verified_at": null
}
```

证据至少增加：

- `acceptance_refs`
- `producer_kind`
- `command_argv` 或结构化工具操作
- `exit_code`
- `tool_name`、`tool_version`
- `working_directory`
- `input_manifest`（相对路径、哈希、大小、角色）
- `environment_fingerprint`
- `started_at`、`finished_at`
- `result_basis`
- `artifact_manifest`

命令必须保存参数数组，禁止保存拼接 Shell 字符串。敏感参数必须脱敏。人工检查证据需要明确 `producer_kind=MANUAL` 和核验人/局限，不能伪装成自动测试。

### 完成门禁

任务完成要求：

1. 每条验收条件均为已核验；
2. 每条验收条件至少有符合类型要求的当前有效证据；
3. 证据的输入、产物和环境未漂移；
4. 当前源码基线可确定，或明确获得允许的非 Git 基线清单；
5. 总结在最后一次证据或任务变化之后生成并核验；
6. 无活动下一步、剩余项和阻断项。

不得接受任意文本文件加 `PASS` 作为充分证据。保留“导入外部证据”能力，但必须标记来源、可信级别和人工核验状态。

### 漂移传播

- `summary verify` 必须重新加载证据实体并重新核验产物哈希。
- Doctor 发现证据、输入或 Git 漂移时生成明确的失效计划；安全确定时自动传播 `STALE`，不能只报告后继续允许完成。
- Git 比较同时考虑 commit、dirty 状态摘要和受任务影响路径。
- Git 不可用时生成受预算的项目输入清单，不能静默使用 `null` 基线完成高风险任务。

### 迁移

7.0.0 字符串验收条件迁移为稳定 ID，状态默认为 `UNVERIFIED`。旧有效证据保留但不自动声称满足具体条件，必须重新关联和核验。

### 检查点

`feat(ai-constraints): bind acceptance criteria to reproducible evidence`

## 8. 阶段 5：总结、失败方案和高层工作流

### 修改内容

1. 总结加入逐条验收结果、关键修改、证据依据、失败方案、未知项、风险、恢复条件和下一步理由。
2. 总结验证要求来源状态仍然适用；任务或证据变化后旧总结不能继续作为完成依据。
3. CLI 失败允许在当前会话审计流中自动登记结构化失败事件，但不得把用户输入错误直接当作工程失败方案。
4. 增加组合命令：

```text
workflow resume
workflow begin
workflow checkpoint
workflow finish
workflow close-session
```

组合命令内部仍调用相同领域服务和门禁，不能复制一套逻辑。

### 验收

- AI 日常流程不需要手工抄写多个修订号和实体 ID。
- 组合命令在并发变化时拒绝执行并返回重新恢复所需上下文。
- 底层命令继续保留，以支持诊断和高级操作。

### 检查点

`feat(ai-constraints): add deterministic workflow commands`

## 9. 阶段 6：自维护供应链门禁

### 修改内容

1. `maintenance test` 在测试前生成确定性的维护工作区清单哈希，排除测试报告、缓存和允许的临时文件。
2. 报告保存包版本、清单哈希、测试发现列表、测试数量、Python/平台版本和测试结果。
3. `maintenance repack` 重新计算当前工作区清单，必须与测试报告一致。
4. 修改任意打包成员、测试文件、清单或重打包工具后，旧报告立即失效。
5. 报告本身防止路径替换和跨工作区复用。
6. 正式重打包要求完整测试集合，且测试发现数量不能异常减少。

### 必测攻击场景

- 测试通过后修改运行时代码。
- 测试通过后删除失败测试。
- 使用另一个同路径重建工作区复用报告。
- 修改 `PACKAGE.json` 版本但不重新测试。
- 只运行一个匹配模式后伪造完整模式字段。

### 检查点

`fix(ai-constraints): bind maintenance reports to workspace content`

## 10. 阶段 7：正式升级与状态迁移框架

### 修改内容

1. 新增版本化迁移注册表，明确 `1.0.0 → 1.1.0` 的前置条件、迁移、验证和回滚。
2. 迁移先只读检查，再在项目外或事务备份目录生成计划；禁止就地无备份改写。
3. 入口受控块升级利用旧安装状态中的受信任块哈希：只有当前块等于已安装版本记录的哈希时，才能替换为新块。
4. 人工修改过的受控块仍然冲突停止；入口的非受控用户内容逐字节保留。
5. 升级事务同时覆盖运行时、入口和状态迁移；任一阶段失败可恢复或回滚。

### 升级矩阵

- 7.0.0 空状态 → 7.1.0 → 回滚。
- 7.0.0 活动任务、证据、总结和锁 → 7.1.0。
- 7.0.0 已完成任务 → 7.1.0 后历史查询。
- 7.0.0 人工修改入口非受控区 → 保留。
- 7.0.0 人工修改受控区 → 阻断。
- 迁移中断后续跑和回滚。

### 检查点

`feat(ai-constraints): add trusted 7.0 to 7.1 migration`

## 11. 阶段 8：项目识别、容量和跨平台

### 项目识别

1. 将源码扫描与构建产物扫描分开设置预算。
2. 不再一律忽略 `build/out/dist`；通过有限深度、扩展名白名单和大小预算识别 MAP、ELF、HEX、BIN、日志及工程配置。
3. 适配器结论记录规则 ID、命中路径、反证、覆盖率、可信度和未知项。
4. 同分结果不能静默选定平台，必须报告候选或未知。

### 容量与性能

1. 为事件、事务、会话、锁、缓存和派生视图定义容量诊断。
2. 增加只读归档计划，不删除权威历史；归档必须可验证和重新导入。
3. 查询必须分页，不在每次普通命令中遍历全部历史。
4. 建立 1 千、1 万任务以及 10 万事件的性能样本和上限。
5. 大证据使用清单和分片哈希，原始大文件可留在项目内或用户指定证据库，不复制进状态目录。

### 跨平台

1. 最终指令提供 Windows PowerShell 和平台无关 Python 的安全 `bootstrap.py` 单文件提取方式。
2. Linux/macOS 示例使用真实路径和权限，不只把反斜杠替换为斜杠。
3. CI 至少覆盖 Windows、Ubuntu、macOS 与 Python 3.10～当前受支持版本。
4. Windows 测试包括中文路径、空格、只读文件、重解析点和 Git `safe.directory` 异常。

### 检查点

`feat(ai-constraints): harden portability and long-term operation`

## 13. 自动执行状态记录

执行 AI 在本文件末尾只追加阶段结果，不改写上述目标。每阶段记录：

```text

状态：NOT_STARTED | IN_PROGRESS | PASSED | BLOCKED
修改：
专项测试：
完整回归：
升级/回滚：
剩余风险：
Git 检查点：
下一阶段：
```

初始状态：

```text
阶段：0
状态：NOT_STARTED
```
