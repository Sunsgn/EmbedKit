# 系统工程、需求与架构详细约束

## 适用范围与事实来源

适用于新品、需求分解、架构、资源预算、风险、阶段门禁、ECO/ECN 和跨专业变更。输入包括使用场景、利益相关方、产品边界、法规市场、平台、环境、寿命、制造和维护目标。来源不明的自然语言只能作为待确认需求，不能直接变成设计事实或数值。

## 需求基线具体规则

- 每项原子需求使用稳定 ID，只有一个可验证主语和行为；记录来源、版本、优先级、适用配置、理由、验收方法和责任方。
- 将功能、性能、接口、安全、可靠性、安规、环境、制造、诊断、升级和退役要求分别建模；禁止把“稳定、快速、低功耗、兼容”等形容词留作无阈值验收条件。
- 明确区分 `MUST/SHOULD/TARGET/ASSUMPTION/UNKNOWN`；派生需求写出推导链和单位。AI 不得自行把目标提升为强制或把冲突来源静默合并。
- 每项需求必须有正常、边界和适用失败场景；不可测试的需求须拆分或标记 `NEEDS_REVIEW`，不能用评审文字宣称满足。

## 场景、边界与运行模式

- 建立参与者、前置条件、触发、主流程、异常流程、结束状态和可观察结果；覆盖首次启动、正常运行、维护、升级、断电、降级、恢复和退役。
- 明确系统边界、外部依赖、信任边界、能量/数据/控制流及第三方责任；不把云端、设备、工装或操作员能力当作系统内部保证。
- 运行模式及切换用状态图/表定义，列出允许命令、输出安全状态、超时和恢复；禁止多个专业分别维护互相冲突的隐式模式。

## 架构分解与接口合同

- 组件说明职责、拥有的数据/硬件、输入输出、启动停止、并发、故障域和替代实现；一个资源只能有明确所有者。
- 接口合同包含方向、数据类型、单位、范围、精度、端序、时序、频率、超时、错误、版本、兼容、权限和数据生命周期。
- 控制面、数据面、安全保护和诊断路径分离；单个非关键服务故障不得阻塞本地安全功能。
- 架构决策记录候选、约束、可量化权衡、被否决理由、适用版本和回退条件；禁止以代码行数、页面或文件存在作为架构完成。

## 预算与余量

- 对 CPU、Flash/ROM、RAM、堆、栈、总线带宽、端到端延迟、启动时间、存储寿命、功耗、热、精度和成本建立预算表。
- 每个预算值记录最坏条件、公式、单位、输入来源、设计余量、分配对象和验证方法；通用包不提供默认百分比，缺项目阈值保持 `UNKNOWN`。
- 子系统预算总和必须包括协议开销、调度/中断、对齐、温漂、老化、容差和升级预留等适用项；平均值不能替代峰值/最坏值。
- 超预算必须提出削减、重新分配或需求变更，并重新验证受影响项；不得隐式挪用安全或升级余量。

## 安全、可靠性与风险

- 从场景识别危害/故障、原因、后果、严重度、可能性、可检测性、预防、检测、控制、安全状态和残余风险；评分方法只能来自项目批准规则。
- 分析单点故障、共因、级联、错误配置、错误操作、通信丢失、电源异常和软件失控。独立保护不能与被保护功能共享未分析的单点资源。
- 风险缓解必须追踪到实现和验证；“通过设计避免”仍需证据。高残余风险没有责任人批准时禁止门禁放行。

## 需求追踪与变更影响

- 建立需求→架构→接口→硬件/软件/机械/工艺→测试→证据双向追踪；每个 PASS 需求至少关联当前版本实现和验证。
- 变更前建立基线和差异，分析代码、原理图、PCB、结构、工装、标定、认证、物料、库存、生产、升级和现场版本。
- 接口变更必须有版本、兼容窗口、混合版本行为、迁移/回退及旧数据处置；禁止只修改一端后假定系统兼容。
- 已删除需求不得直接从矩阵消失，记录废弃理由、批准和受影响测试/现场功能。

## 评审与阶段门禁

- 门禁清单明确进入条件、必需输出、批准角色和允许遗留问题等级；AI 可以汇总证据，不能代替法定/组织责任人签署。
- 评审意见使用 ID、严重度、对象、责任人、计划、关闭证据和重新打开条件；仅回复“已处理”不能关闭。
- 原型、工程样机、设计验证、生产验证和正式发布的证据等级分开；前一阶段通过不能自动证明后一阶段。

## 验收、证据与失败门禁

必需证据：需求基线、场景/模式、系统边界、架构与接口、资源预算、风险表、追踪矩阵、决策记录、变更影响和门禁状态。需求不可验证、接口冲突、关键预算未知、高风险未闭环或当前实现/测试无追踪时保持 `NEEDS_REVIEW/BLOCKED`；可继续无依赖分解，禁止宣传系统完成。
