# 系统工程、需求与架构具体约束

## 适用范围与输入

适用于新品、跨模块变更、系统架构、需求分解、资源预算、风险、阶段门禁和版本变更。输入包括用户目标、使用场景、利益相关方、产品边界、法规市场、已有平台、硬件/软件/制造/维护限制及验收方式。来源不明的目标不得直接转成设计事实。

## 需求与追踪动作

1. 将自然语言拆分为稳定 ID 的功能、性能、接口、安全、可靠性、制造、维护和约束需求；每项标记来源、优先级、适用版本和可验证条件。
2. 区分“必须”“目标”“假设”“候选”和“未知”；冲突需求列出来源、影响和待决责任人，不由 AI 静默取舍。
3. 建立需求→架构组件→接口→软硬件实现→测试→发布证据的双向追踪；派生需求说明推导依据。
4. 需求变更执行影响分析，覆盖代码、原理图、PCB、工装、标定、生产、认证、库存和现场版本。

## 架构与预算

- 划分组件职责、数据/控制流、状态、并发、故障域和信任边界；接口必须有所有权、单位、时序、错误和版本语义。
- 对 CPU、Flash、RAM、栈、带宽、延迟、功耗、热、精度、启动时间和存储寿命建立预算。每个数值记录来源、计算、裕量和验证方法；缺项为 UNKNOWN。
- 架构决策记录候选方案、权衡、被否决理由、适用条件和回退路径；不得用代码数量或页面存在代替架构完成。
- 安全和高影响功能明确独立保护、单点故障、降级、安全状态、监测覆盖和人工责任。

## 风险、门禁与变更

风险记录危害/故障、原因、后果、严重度、可能性、可检测性、缓解、验证和残余风险。评分方法必须来自项目批准规则，通用包不伪造阈值。高风险缓解未验证时禁止相应阶段放行。

阶段门禁只汇总可核验证据：需求基线、设计评审、构建/EDA/测试、兼容矩阵、未决问题和批准。AI 不得自行签署正式门禁。变更必须有基线、差异、受影响对象、验证、回退和现场/生产处置。

## 验收、证据与失败处理

必需证据：需求清单、追踪矩阵、架构/接口、预算、风险表、决策记录和门禁状态。每个“已满足”需求至少关联一个当前版本的实现位置和验证证据；仅有设计文字不能证明运行能力。

需求不可验证、架构接口冲突、关键预算缺数据、残余高风险未接受或门禁证据不完整时保持 `NEEDS_REVIEW/BLOCKED`。允许继续不依赖该缺口的分析和隔离实现，禁止把局部完成宣传为系统完成。
