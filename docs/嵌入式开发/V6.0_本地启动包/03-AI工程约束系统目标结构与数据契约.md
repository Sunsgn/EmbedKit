## 1. 设计目标

本设计用于把现有分散的规则、Markdown/CSV 模板和独立脚本收敛为一个自包含、可由 AI 直接维护的最终约束包。目标不是重新发明项目管理平台，而是提供支持 AI 连续开发所需的最小确定性内核：

1. 安全、事务化、可恢复地接入新项目和已有项目。
2. 使用统一结构化状态中心保存项目事实、需求、任务、下一步、会话、证据和总结。
3. 让 Markdown/CSV 成为可读视图和兼容输入，不再形成多套事实源。
4. 支持多会话冲突检测、乐观并发、范围锁和异常恢复。
5. 根据真实状态和证据生成研发节点总结。
6. 让 AI 能直接维护最终包，同时保留测试、版本、迁移和回滚门禁。

## 2. 设计原则

### 2.1 唯一事实源

- 结构化状态是项目连续性数据的唯一权威源。
- 源码、Git、构建、测试、设备和文件原始证据是工程事实源，状态中心记录其引用与有效性，不能取代它们。
- Markdown/CSV 是视图、报告、导入格式或历史兼容层。
- AI 不得绕过统一状态接口直接把任意文档当作当前状态。

### 2.2 最终文件即维护对象

- ZIP 内的 Python、Markdown、JSON、Schema、模板和测试就是正式最终文件。
- 不设置用户必须维护的 `src/`、构建仓库或第二份规则源。
- AI 修改最终文件时仍必须经过问题复现、回归测试、版本更新、清单再生、新包验证和用户确认。

### 2.3 事实、状态和视图分离

- 通用规则与运行工具由包拥有。
- 项目事实和本地配置由项目拥有。
- 当前状态、事件和证据由状态中心拥有。
- Markdown/CSV 由视图生成器拥有，但允许受控导入人工修改。
- 项目专属扩展不能直接污染通用核心。

### 2.4 默认安全停止

身份不明、Schema 不兼容、状态损坏、修订冲突、路径逃逸、权限不足或证据不完整时，停止受影响写入并提供诊断；不通过删除历史、重置状态或降低规则强度继续执行。

## 3. 两文件交付和首次执行边界

正式交付仍为：

```text
AI工程约束包通用接入与初始化执行指令.md
通用ai约束文档.zip
```

首次执行分为两个信任阶段：

1. AI 读取外部初始化指令，计算 ZIP SHA-256 并与指令记录的预期值比较。
2. 哈希匹配后，在项目外对 ZIP 进行不执行包内代码的最小安全预检。
3. 安全解压到唯一临时目录后，先按内部清单逐文件校验，再运行包内 `bootstrap.py inspect` 和 `bootstrap.py plan`。
4. 用户或已有授权确认迁移计划后，运行 `bootstrap.py apply`。
5. 安装提交后，项目内统一入口由 `.ai/system/aic.py` 提供。

`bootstrap.py` 不得在 ZIP 安全预检之前直接从包内执行。系统找不到兼容 Python 时，只允许完成只读盘点并报告 `TOOL_UNAVAILABLE`，不得退化为无备份的手工覆盖安装。

## 4. ZIP 内目标结构

ZIP 是最终维护包，建议结构如下：

```text
PACKAGE.json
PACKAGE_MANIFEST.json
bootstrap.py

entrypoints/
├─ AGENTS.md
├─ CLAUDE.md
├─ GEMINI.md
└─ copilot-instructions.md

.ai-system/
├─ aic.py
├─ core/
│  ├─ ids.py
│  ├─ io.py
│  ├─ paths.py
│  ├─ result.py
│  ├─ transactions.py
│  └─ versions.py
├─ install/
├─ state/
├─ concurrency/
├─ evidence/
├─ summaries/
├─ policies/
├─ adapters/
│  ├─ clients/
│  ├─ projects/
│  └─ vcs/
├─ maintenance/
├─ schemas/
├─ templates/
├─ migrations/
├─ tests/
├─ fixtures/
└─ docs/
```

说明：

- `.ai-system/` 是 ZIP 内的包目录名，安装后复制为项目 `.ai/system/`。
- 目录内文件全部是最终可运行和可维护文件，不是需要另行编译的开发源。
- `PACKAGE_MANIFEST.json` 覆盖除清单自身外的所有 ZIP 成员，包括根入口模板、`bootstrap.py` 和 `PACKAGE.json`。外部初始化指令记录预期 ZIP SHA-256，用于核对包含清单自身在内的完整归档；内部清单用于解压后逐文件核对。两者都只证明完整性，不单独证明发布者身份。
- 历史测试报告不默认进入运行时核心，可放在 `docs/history/` 或归档包中，避免运行目录噪声。

### 4.1 包身份契约

`PACKAGE.json` 至少包含：

```json
{
  "schema": "aic.package",
  "schema_version": "1.0.0",
  "package_id": "ai-engineering-constraints",
  "package_version": "x.y.z",
  "structure_version": 1,
  "runtime_api_version": "1.0.0",
  "state_schema_version": "1.0.0",
  "minimum_python": "3.10",
  "supported_platforms": ["windows", "linux", "macos"],
  "manifest": "PACKAGE_MANIFEST.json",
  "entrypoints": {},
  "capabilities": [],
  "created_at": "2026-11-17T00:00:00Z"
}
```

`PACKAGE.json` 不写入构建机器绝对路径、临时目录或项目特例。`PACKAGE_MANIFEST.json` 记录成员相对路径、SHA-256、大小、类型、归属和安装策略，并拒绝未列出成员与陈旧清单项。

## 5. 安装后项目结构与文件归属

```text
项目根目录/
├─ AGENTS.md                         # 已有则使用受控块增量合并
├─ CLAUDE.md                         # 已有则使用受控块增量合并
├─ GEMINI.md                         # 已有则使用受控块增量合并
├─ .github/
│  └─ copilot-instructions.md        # 已有则使用受控块增量合并
└─ .ai/
   ├─ INSTALL_STATE.json
   ├─ system/                        # 包拥有；通用运行时
   ├─ project/                       # 项目拥有；项目事实与配置
   ├─ state/                         # 可持久化状态记录面
   ├─ run/                           # 本机临时会话、锁和事务控制面
   ├─ tasks/                         # 任务实体及任务级引用
   ├─ evidence/                      # 原始或索引化证据
   ├─ summaries/                     # 结构化总结及不可覆盖版本
   ├─ views/                         # 生成的 Markdown/CSV
   ├─ extensions/                    # 版本化项目扩展
   ├─ local/                         # 不进入通用包的项目本地覆盖
   ├─ audit/                         # 事务、迁移、冲突和修复报告
   └─ legacy/                        # 旧版导入清单与只读快照
```

### 5.1 包拥有文件

范围：`.ai/system/` 和四个入口文件中的受控块。

规则：

- 只通过安装、升级、回滚或维护命令修改。
- 文件路径和哈希记录在安装清单中。
- 项目需要改变通用行为时优先使用 `extensions/` 或 `local/`，不直接修改 `system/`。
- AI 修复通用核心后必须升级包版本并生成新 ZIP，不能继续沿用旧清单。

### 5.2 项目拥有文件

范围：`.ai/project/`、`.ai/extensions/`、`.ai/local/` 以及项目已有资料。

规则：

- 包升级不得覆盖。
- 所有结构化文件带 Schema 版本。
- 项目事实不因项目类型适配器改变而被静默改写。

### 5.3 状态中心拥有文件

范围：`.ai/state/`、`.ai/run/`、`.ai/tasks/`、`.ai/evidence/` 和 `.ai/summaries/`。

规则：

- 只能通过统一状态、证据、总结和维护接口写入。
- AI 不直接编辑当前快照、事件或锁文件。
- 不直接写入安装状态、迁移审计和生成视图。

### 5.4 安装与维护工具拥有文件

范围：`.ai/INSTALL_STATE.json`、`.ai/audit/` 和 `.ai/legacy/` 中的安装、升级、迁移、修复与旧版导入记录。

规则：

- 只能由安装、维护、迁移和修复事务更新。
- 包身份与项目运行状态分开校验，项目状态变化不能导致包完整性误报。
- 审计记录使用不可覆盖 ID；修复或回滚生成新记录，不改写旧记录。

### 5.5 视图生成器拥有文件

范围：`.ai/views/`。

规则：

- 视图从明确的状态修订生成，并记录来源修订、模板版本和内容哈希。
- 人工修改生成视图不会自动成为权威状态，必须通过导入命令处理。
- 重新生成前检测人工修改，禁止静默覆盖。

### 5.6 项目配置最小结构

```text
.ai/project/
├─ PROJECT.json                      # 稳定项目身份和已确认事实
├─ CONFIG.json                       # 流程等级、保留、扫描和 Git 策略
├─ CAPABILITIES.json                 # 已验证工具与客户端能力
├─ ADAPTERS.json                     # 启用适配器及识别证据
└─ POLICY_OVERRIDES.json             # 有范围和依据的项目规则覆盖
```

项目识别产生的候选事实不得直接写入 `PROJECT.json`；需要证据或用户确认后通过状态事务提升为已确认事实。规则覆盖必须引用稳定规则 ID、说明原因、适用范围、有效期和批准记录，不能通过复制整份通用规则实现。

## 6. 受控入口合并契约

四种 AI 客户端入口只包含最小加载逻辑。新增内容使用稳定标记：

```markdown
<!-- AI-CONSTRAINTS:BEGIN managed version=1 -->
开始任务前读取 `.ai/system/ENTRYPOINT.md`，执行状态校准并输出启动回执。
<!-- AI-CONSTRAINTS:END managed -->
```

合并规则：

1. 文件不存在时，从入口模板创建。
2. 文件存在且无受控块时，备份后追加受控块，不改写原内容。
3. 文件存在且受控块版本较旧时，只替换受控块。
4. 受控块被人工修改时，记录冲突并停止该文件更新。
5. 卸载只删除可证明由系统管理且未被修改的受控块。
6. 根入口文件的安装前哈希、安装后哈希和受控块哈希进入事务记录。

## 7. 统一状态中心结构

```text
.ai/state/
├─ CURRENT.json                      # 可重建当前快照
├─ HEAD.json                         # 当前修订和事件链头
├─ events/
│  └─ YYYY-MM.jsonl                 # 只追加事件分片
├─ checkpoints/
│  └─ <CHECKPOINT_ID>/
├─ indexes/
│  ├─ entities.json
│  ├─ relationships.json
│  └─ active.json
└─ committed-transactions/
   └─ <TXN_ID>.json

.ai/run/
├─ sessions/
│  └─ <SESSION_ID>.json
├─ locks/
│  └─ <LOCK_ID>.json
├─ transactions/
│  └─ <TXN_ID>.json
├─ health/
│  └─ latest.json
└─ cache/
```

权威关系：

- 事件和已提交事务是状态变化的权威历史。
- `HEAD.json` 是当前事件链位置和修订号。
- `CURRENT.json` 与索引是可从事件和检查点重建的派生快照。
- 原始证据文件是证据内容权威源，证据实体保存身份、哈希、范围和有效性。
- Markdown/CSV 视图不参与状态修订竞争。

### 7.1 持久记录面与本机控制面

- `.ai/state/`、`.ai/tasks/`、`.ai/summaries/` 和必要证据元数据属于可移植持久记录，可以随项目归档，并可按项目策略纳入 Git。
- `.ai/run/` 保存会话心跳、锁、未完成事务和缓存，默认不纳入 Git，不进入正式归档；异常恢复后按审计规则清理。
- `.ai/evidence/` 中的小型证据可直接归档；大型、敏感或设备原始数据只保存受控引用、哈希和恢复说明。
- Git 偏离检查必须把产品文件、可持久化研发记录和本机运行控制数据分开报告，不能让心跳或缓存污染产品源码差异。
- 本机文件锁和租约只能协调同一工作副本中的进程。不同计算机或不同仓库副本之间不能宣称拥有共享强锁，只能通过 Git/状态修订冲突、远端协作机制或明确人工协调发现和解决冲突。

## 8. 通用数据信封

所有结构化实体使用共同字段：

```json
{
  "schema": "aic.task",
  "schema_version": "1.0.0",
  "id": "TASK-01H...",
  "project_id": "PRJ-01H...",
  "revision": 7,
  "status": "EXECUTING",
  "created_at": "2026-11-17T08:00:00Z",
  "updated_at": "2026-11-17T09:00:00Z",
  "created_by": "SES-01H...",
  "updated_by": "SES-01H...",
  "extensions": {}
}
```

约束：

- `schema` 和 `schema_version` 必填。
- `id` 创建后不可改变，不依赖显示名称和文件路径。
- `revision` 是实体级单调递增整数。
- 时间统一存 UTC RFC 3339，显示时可转换本地时区；时间不决定并发覆盖顺序。
- 未知扩展字段放入命名空间化 `extensions`，核心字段不能被扩展重定义。
- JSON 使用 UTF-8、稳定键排序和末尾换行；哈希以规范化字节计算。

## 9. 稳定 ID 契约

| 实体 | 前缀 | 示例 |
|---|---|---|
| 项目 | `PRJ-` | `PRJ-01HXYZ...` |
| 需求 | `REQ-` | `REQ-01HXYZ...` |
| 任务 | `TASK-` | `TASK-01HXYZ...` |
| 下一步 | `NEXT-` | `NEXT-01HXYZ...` |
| 会话 | `SES-` | `SES-01HXYZ...` |
| 锁 | `LOCK-` | `LOCK-01HXYZ...` |
| 事件 | `EVT-` | `EVT-01HXYZ...` |
| 事务 | `TXN-` | `TXN-01HXYZ...` |
| 证据 | `EVD-` | `EVD-01HXYZ...` |
| 检查点 | `CP-` | `CP-01HXYZ...` |
| 总结 | `SUM-` | `SUM-01HXYZ...` |
| 决策 | `DEC-` | `DEC-01HXYZ...` |
| 问题 | `ISS-` | `ISS-01HXYZ...` |
| 风险 | `RSK-` | `RSK-01HXYZ...` |
| 规则 | `RULE-` | `RULE-GIT-SAFETY-001` |
| 关联 | `REL-` | `REL-01HXYZ...` |

ID 使用类型前缀加时间可排序随机标识；生成不依赖网络和系统显示名称。导入旧 TASK_ID 时保留 `legacy_ids`，不能用旧 ID 覆盖新主键。

### 9.1 关联契约

跨对象关系使用结构化关联，不只在 Markdown 中写名称：

```json
{
  "id": "REL-01H...",
  "type": "VERIFIES",
  "source_id": "EVD-01H...",
  "target_id": "REQ-01H...",
  "status": "ACTIVE",
  "created_by": "SES-01H...",
  "created_at": "2026-11-17T09:00:00Z",
  "metadata": {}
}
```

核心关系类型至少包括：`IMPLEMENTS`、`VERIFIES`、`DEPENDS_ON`、`BLOCKS`、`AFFECTS`、`INVALIDATES`、`SUMMARIZES`、`DERIVED_FROM`、`SUPERSEDES` 和 `GENERATED_FROM`。关系两端必须存在或明确指向外部受控对象；删除、合并和迁移实体前执行引用完整性检查。任务依赖和规则继承等不允许形成环的关系必须检测循环。

## 10. 事件契约

事件是状态变更历史，不允许原地修改：

```json
{
  "schema": "aic.event",
  "schema_version": "1.0.0",
  "event_id": "EVT-01H...",
  "project_id": "PRJ-01H...",
  "sequence": 42,
  "previous_sequence": 41,
  "previous_event_hash": "sha256:...",
  "event_type": "task.status.changed",
  "entity_type": "task",
  "entity_id": "TASK-01H...",
  "expected_entity_revision": 6,
  "new_entity_revision": 7,
  "session_id": "SES-01H...",
  "transaction_id": "TXN-01H...",
  "occurred_at": "2026-11-17T09:00:00Z",
  "payload": {},
  "references": ["EVD-01H..."],
  "event_hash": "sha256:..."
}
```

规则：

- `sequence` 在项目内单调递增，是提交顺序依据。
- `expected_entity_revision` 不等于当前修订时返回 `STATE_REVISION_CONFLICT`。
- 事件哈希链用于发现截断、重排和意外修改，不宣称提供数字签名级真实性。
- 一个事务可以包含多个待提交事件；只有事务提交后才进入权威历史。
- 事件分片达到配置上限后创建新分片，旧分片不可覆盖。

```json
  "package_version": "x.y.z",
  "project_profile_revision": 3,
  "active_tasks": ["TASK-01H..."],
  "ready_next_actions": ["NEXT-01H..."],
  "active_sessions": ["SES-01H..."],
  "active_locks": ["LOCK-01H..."],
  "open_blockers": ["ISS-01H..."],
  "latest_checkpoint_id": "CP-01H...",
  "latest_summary_ids": ["SUM-01H..."],
  "health": "HEALTHY",
  "updated_at": "2026-11-17T09:00:00Z"
}
```

`CURRENT.json` 不保存全部历史和大型证据；只保存恢复当前工作所需索引。损坏时从最近检查点和后续事件重建。

## 13. 任务生命周期契约

任务状态：

```text
NEW
DISCOVERING
PLANNED
READY
EXECUTING
VERIFYING
PAUSED
BLOCKED
FAILED
COMPLETED
CANCELLED
STALE
REOPENED
```

任务实体至少包含：

- 用户原始目标和规范化目标。
- LIGHT/STANDARD/FULL 等级及判定原因。
- 作用域、允许修改范围和排除范围。
- 父任务、子任务、依赖和关联需求。
- 验收条件、测试计划和证据要求。
- 当前阶段、已完成工作、未完成工作和阻断。
- 计划修改文件、实际修改文件和影响对象。
- Git/文件基线和输入锁引用。
- 下一步、检查点、总结和决策引用。

规则：

- 状态转换由注册表校验，不把合法转换写死在多个脚本中。
- 暂停必须有恢复条件和下一步；阻断必须有解除条件。
- 取消保留全部历史；完成后证据过期可进入 `STALE` 并创建 `REOPENED` 事件。
- `COMPLETED` 需要所有强制验收项具有有效证据和总结。

状态枚举：`PLANNED`、`READY`、`IN_PROGRESS`、`BLOCKED`、`DONE`、`CANCELLED`、`STALE`。

## 15. 会话与并发契约

### 15.1 会话实体

```json
{
  "id": "SES-01H...",
  "client": "codex",
  "client_version": "unknown",
  "host_id": "local-hash",
  "status": "ACTIVE",
  "started_at": "2026-11-17T08:00:00Z",
  "last_heartbeat_at": "2026-11-17T09:00:00Z",
  "read_state_revision": 42,
  "task_ids": [],
  "declared_write_scopes": [],
  "loaded_rule_ids": [],
  "capabilities": {},
  "limitations": []
}
```

会话状态：`ACTIVE`、`IDLE`、`PAUSED`、`ENDED`、`CRASHED`、`NEEDS_REVIEW`。

### 15.2 锁实体

锁至少包含：

- 所有者会话 ID。
- 锁范围类型：项目、任务、状态实体、文件集合、安装或维护。
- 规范化范围值。
- 获取时状态修订号。
- 获取时间、最后续租时间和租约截止时间。
- 锁状态和冲突对象。

锁通过独占创建或等价原子操作获取。租约截止只表示需要检查，不能自动授权其他会话接管。接管前必须核对会话、事务、事件、Git 和文件变化，并按风险请求用户确认。

### 15.3 写入协议

1. 启动会话并读取当前状态修订号。
2. 声明任务和预计写入范围。
3. 检查现有锁和范围重叠。
4. 获取所需锁。
5. 执行外部文件修改和验证。
6. 以 `expected_state_revision` 提交状态事务。
7. 修订冲突时不覆盖，重新读取并生成冲突报告。
8. 提交成功后更新视图、索引和心跳。
9. 结束会话并释放锁；异常退出保留恢复记录。

## 16. 证据契约

证据类型至少包括：

- Git 基线和差异。
- 输入锁和文件哈希。
- 命令执行、退出码、标准输出和标准错误。
- 测试报告。
- 构建产物和工具版本。
- 设备、通信、日志和测量记录。
- 静态分析与源码位置。
- 用户确认和授权。

证据实体至少记录：

```json
{
  "id": "EVD-01H...",
  "type": "test-execution",
  "status": "VALID",
  "producer": "tool-or-session",
  "captured_at": "2026-11-17T09:00:00Z",
  "project_revision": 42,
  "git_commit": "full-sha-or-null",
  "input_refs": [],
  "artifact_path": ".ai/evidence/...",
  "sha256": "...",
  "size": 1234,
  "result": "PASS",
  "limitations": [],
  "invalidated_by": []
}
```

证据状态：`VALID`、`FAILED`、`INFERRED`、`UNKNOWN`、`STALE`、`CORRUPT`、`UNAVAILABLE`。

文件、环境、工具、设备或任务范围变化时，根据依赖关系把相关证据标记为 `STALE`，不能删除旧证据或把旧通过结果继续作为当前完成依据。

## 17. 研发节点总结契约

总结实体至少包含：

- 总结 ID、类型、任务、会话、状态修订和 Git 基线。
- 触发节点及触发原因。
- 目标、输入范围、完成和未完成内容。
- 修改文件和影响范围。
- 证据、结论、未知项和过期项。
- 决策、失败方案、风险、问题和恢复方法。
- 按优先级排列的下一步。
- `DRAFT`、`VERIFIED` 或 `STALE` 状态。

总结类型：

```text
INITIALIZATION
STAGE
TECHNICAL
ISSUE_CLOSURE
CHANGE
MILESTONE
RETROSPECTIVE
HANDOFF
RECOVERY
MAINTENANCE
```

触发器只创建结构化候选总结。总结服务从状态、事件和证据填充确定性字段，AI 只补充需要判断的解释，并明确区分事实与推断。相同状态修订、任务和节点类型不得重复生成等价总结。

## 18. 事务契约

事务用于安装、升级、卸载、迁移、状态提交、修复和重打包：

```json
{
  "id": "TXN-01H...",
  "type": "INSTALL",
  "status": "PREPARED",
  "project_id": "PRJ-01H...",
  "session_id": "SES-01H...",
  "expected_state_revision": 0,
  "operations": [],
  "backups": [],
  "events": [],
  "started_at": "...",
  "updated_at": "...",
  "error": null
}
```

状态：

```text
PLANNED
PREPARED
APPLYING
COMMITTING
COMMITTED
ROLLING_BACK
ROLLED_BACK
FAILED
NEEDS_REVIEW
```

规则：

- `PREPARED` 前完成路径、权限、容量、冲突和备份可用性检查。
- 文件写入先写同目录临时文件、刷新并原子替换；不支持原子替换时明确降级并增加恢复记录。
- 每项操作记录写入前后哈希。
- 状态事件只有事务提交后才进入权威事件链。
- 中断重启时根据事务状态继续提交、回滚或进入人工检查，禁止从头无条件重放。
- 备份不能放入被替换目录；备份清理必须确认事务提交、保留期限和引用状态。

状态事务采用可恢复提交协议：

1. 在 `.ai/run/transactions/` 写入并刷新完整待提交事务，包含预期修订、实体变更和候选事件。
2. 获取项目状态写锁，重新核对 HEAD、实体修订和文件前置哈希。
3. 将不可变事务封套写入 `.ai/state/committed-transactions/`。
4. 在事件日志追加一个引用事务封套哈希的提交事件，并刷新日志。
5. 原子更新 `HEAD.json`；只有 HEAD 指向该提交后，事务才进入权威状态历史。
6. 更新 `CURRENT.json`、索引和视图；这些派生更新失败时标记 `DEGRADED`，可从 HEAD 和事务封套重建，不回写或删除已提交历史。
7. 崩溃恢复时，HEAD 之后的尾部记录、没有提交事件的事务封套和本机待提交事务均进入诊断，不自动当作已提交状态。

## 19. 安装状态契约

安装计划在写入前以结构化文件固化，至少记录：

- 计划 ID、目标项目根目录、包身份和输入文件哈希。
- 项目标志、Git 状态、已发现入口、已有 `.ai/` 和旧版身份。
- 每项文件操作的源、目标、归属、前置哈希、预期结果和回滚动作。
- 操作类型：创建、受控块合并、保持、迁移、替换包拥有文件、冲突或阻断。
- 项目边界、符号链接/Junction、容量、权限和磁盘空间检查结果。
- 需要用户确认的冲突、风险和选择。
- 计划生成时目标文件快照；应用前必须重新核对，变化后计划失效。

安装计划本身不授予超出用户原始请求的权限。`apply` 只能执行计划中已确认且前置条件仍成立的操作。

`.ai/INSTALL_STATE.json` 至少记录：

- 安装 Schema、包版本、结构版本和包 SHA-256。
- 安装事务 ID、安装时间和安装工具版本。
- 包拥有文件路径和安装后哈希。
- 四个入口文件的受控块版本与哈希。
- 项目拥有和状态拥有目录边界。
- 已执行迁移和兼容版本。
- 当前安装状态：`INSTALLED`、`PARTIAL`、`UPGRADING`、`ROLLING_BACK`、`NEEDS_REVIEW`。
- 最近成功验证时间和验证结果引用。

安装状态不能把项目运行数据纳入包文件哈希，也不能因项目状态变化误报通用包损坏。

## 20. Markdown/CSV 兼容迁移

### 20.1 迁移原则

1. 旧文件先计算哈希并登记到 `.ai/legacy/IMPORT_MANIFEST.json`。
2. 解析成功的字段写入候选导入事务，不直接覆盖当前状态。
3. 无法解析、重复或冲突字段保留原始文件并生成冲突记录。
4. 导入提交后，旧文件保持只读兼容或原位置保留，不自动删除。
5. 新视图写入 `.ai/views/`，包含来源状态修订号、生成时间和“受控生成”标记。

### 20.2 主要旧文件映射

| 旧文件/模板 | 新结构化目标 | 新视图 |
|---|---|---|
| `PROJECT_PROFILE.md` | `project/profile.json` | `views/PROJECT_PROFILE.md` |
| `PROJECT_FACTS.md` | 项目事实实体 | `views/PROJECT_FACTS.md` |
| `ENVIRONMENT_BASELINE.md` | 环境证据和项目事实 | `views/ENVIRONMENT_BASELINE.md` |
| `COGNITION_STORAGE_MAP.json` | 项目配置和旧路径导入映射 | `views/STORAGE_LAYOUT.md` |
| `TASK_ANCHOR.md` | 任务、需求、作用域和基线引用 | `views/tasks/<id>/TASK_ANCHOR.md` |
| `STATE_CARD.md`、`STATUS.md` | 任务状态和当前状态 | `views/tasks/<id>/STATUS.md` |
| `STATE_HISTORY.csv` | 状态事件 | `views/tasks/<id>/STATE_HISTORY.csv` |
| `STARTUP_RECEIPT.md` | 会话实体和已加载规则 | `views/sessions/<id>.md` |
| `PROJECT_DISCOVERY_REPORT.md` | 发现证据和项目事实候选 | `views/PROJECT_DISCOVERY_REPORT.md` |
| `INPUT_LOCK.md`、输入清单 | 输入锁证据 | `views/tasks/<id>/INPUT_LOCK.md` |

| `HANDOFF.md` | HANDOFF 总结实体 | `views/tasks/<id>/HANDOFF.md` |
| `GIT_BASELINE.json` | Git 基线证据 | 保留 JSON 兼容导出 |
| `CONTEXT_CHECKPOINTS/` | 检查点实体和快照 | `views/checkpoints/` |
| 各类知识总结 Markdown | 总结实体 | `views/summaries/` |

### 20.3 人工编辑视图

生成视图记录内容哈希。发现人工修改时：

- 默认停止覆盖并报告 `VIEW_MODIFIED`。
- 用户选择导入后，解析为候选变更，显示与当前状态的字段差异。
- 用户确认后通过正常状态事务提交。
- 无法安全解析的内容保留为附件或项目本地文档，不强行写入核心字段。

## 21. 规则注册契约

正式规则使用稳定 ID 和结构化元数据：

```json
{
  "id": "RULE-GIT-SAFETY-001",
  "version": "1.0.0",
  "title": "禁止破坏用户工作区",
  "severity": "MANDATORY",
  "scopes": ["MODIFY", "REFACTOR"],
  "triggers": [],
  "validator": "git-safety",
  "exceptions": {
    "allowed": true,
    "requires_user_approval": true
  },
  "document": "policies/git.md#RULE-GIT-SAFETY-001",
```

规则正文继续使用 Markdown，但机器路由依赖注册表，不依赖搜索关键词。任务启动回执记录实际命中的规则 ID、版本、命中原因、未加载项和冲突。

## 22. 客户端适配契约

每个客户端适配声明：

- 标准自动发现入口。
- 是否能运行本地工具。
- 是否支持持久会话 ID。
- 权限和沙箱边界。
- 上下文与文件读取限制。
- 并发模型。
- 必须由用户显式触发的步骤。
- 安全降级方式。

薄入口只要求客户端读取 `.ai/system/ENTRYPOINT.md`，启动本地会话，执行 `status reconcile` 并输出回执。不能运行本地工具时，客户端只读展示状态并明确 `LOCAL_RUNTIME_UNAVAILABLE`，不得直接编辑状态文件模拟成功。

## 23. 项目识别适配契约

项目识别结果必须按证据输出候选，不直接修改项目事实：

```json
{
  "adapter_id": "project.cmake",
  "candidate": "CMake",
  "confidence": 0.8,
  "evidence": [],
  "negative_evidence": [],
  "limitations": [],
  "status": "CANDIDATE"
}
```

单个通用文件名不能直接证明平台，例如仅有 `Makefile` 不能确认 Linux，仅有 `.project` 不能确认 STM32CubeIDE。发现引擎必须支持目录剪枝、最大文件数、最大深度、超时、取消、进度和缓存失效。

## 25. 统一结果和错误契约

成功或失败均返回结构化结果：

```json
{
  "ok": false,
  "code": "STATE_REVISION_CONFLICT",
  "message": "expected revision 41, actual revision 42",
  "retryable": true,
  "requires_user_action": false,
  "details": {},
  "evidence_refs": []
}
```

错误码至少分组：

- `INPUT_*`：输入和参数。
- `PATH_*`：路径和边界。
- `PACKAGE_*`：包身份和完整性。
- `INSTALL_*`：安装和升级事务。
- `STATE_*`：Schema、修订、损坏和迁移。
- `LOCK_*`：锁、租约和并发冲突。
- `GIT_*`：Git 基线和漂移。
- `EVIDENCE_*`：证据缺失、过期或损坏。
- `TOOL_*`：工具缺失、不兼容或执行失败。
- `PERMISSION_*`：授权和权限。
- `USER_DECISION_REQUIRED`：需要人工决策。

退出码保持稳定分类；详细错误通过 JSON 提供，不能让 AI 依赖中文或英文句子判断状态。

## 26. 原子写入与恢复协议

所有核心 JSON 写入：

1. 读取并校验当前 Schema、修订和哈希。
2. 在同目录创建唯一临时文件。
3. 写入 UTF-8 规范化内容并刷新文件。
4. 必要时刷新父目录。
5. 使用原子替换提交。
6. 更新事件、HEAD、快照和索引必须由一个可恢复事务协调。
7. 任何步骤失败都保留事务日志，不删除原始有效文件。

事件 JSONL 追加需要项目状态写锁；不能直接依赖多个进程同时追加的操作系统行为。索引和视图失败不回滚已提交事实事件，但必须把系统标记为 `DEGRADED` 并允许从事件重建。

## 27. 版本与迁移契约

独立管理：

- `package_version`：最终包版本。
- `runtime_api_version`：运行工具和扩展接口版本。
- `state_schema_version`：状态模型版本。
- `view_schema_version`：视图格式版本。
- `policy_registry_version`：规则注册版本。

迁移文件声明来源版本、目标版本、前置条件、是否可逆、备份要求、验证器和回滚方式。跨多个版本升级时按注册迁移链执行，不允许客户端直接把旧文件当新格式读取后写回。

## 28. 资源和保留契约

项目配置至少支持：

- 单证据文件和总证据大小。
- 单日志大小和轮转数量。
- 事件分片大小。
- 活跃与归档任务数量。
- 检查点数量、最短保留期和受引用保护。
- 总结去重窗口和归档规则。
- 扫描文件数、深度、时间和缓存大小。
- 命令超时和并发会话上限。

超过预算返回明确错误或降级计划，不自动删除仍被当前状态、需求、任务、总结或证据引用的数据。

## 30. 测试契约

### 30.1 单元测试

- ID、Schema、状态转换、路径、哈希和错误码。
- 事件哈希链、修订冲突和事务恢复。
- 锁范围、租约和所有者校验。
- 证据过期传播、总结去重和规则路由。

### 30.2 集成测试

- 安装、重复安装、升级、卸载、回滚。
- 旧模板导入和视图人工修改冲突。
- Git 与无 Git 项目。
- 多会话并发、异常退出和孤立锁恢复。
- 状态损坏、事件重放和索引重建。

### 30.3 端到端测试

逐项覆盖目标基线第 14 章，并将测试结果绑定 15 个 `GOAL-*`。至少使用：

- 已有嵌入式 Git 项目。
- Web 或桌面项目。
- 未知格式或无 Git 项目。
- 中文、空格、长路径和链接边界样本。
- 大型目录和 Monorepo 样本。
- 恶意 ZIP 和损坏状态样本。

### 30.4 测试真实性

- 关键词和文件存在测试只能作为静态一致性检查。
- 正向和负向测试必须检查退出码、结构化错误和文件系统最终状态。
- 故障注入必须验证中断点前后能恢复或安全停止。
- 跳过测试必须使对应能力保持未验证，不能计入通过总数。

## 31. 本设计明确不做的事

- 不要求用户维护独立源码仓库。
- 不把所有项目强制迁入同一种业务目录。
- 不把 Markdown 全部删除；它继续作为人类可读视图和规则正文。
- 不允许 AI 直接编辑事件、当前快照、锁或包清单伪造状态。
- 不在第一阶段实现所有项目类型适配器；未知项目先安全降级。
- 不把哈希链描述为数字签名或绝对防篡改。
- 不用统一状态中心替代 Git、测试系统、设备工具或原始证据。

## 32. 设计验收门禁

进入实现前必须确认：

1. 五类文件归属边界无重叠：包、项目、状态、安装维护记录、生成视图。
2. 事件、快照、事务、锁和修订之间没有循环权威关系。
3. 15 个核心目标均能映射到数据实体、命令和测试。
4. 旧 Markdown/CSV 的有效字段有明确迁移目标。
5. 任何写操作都有预期修订、事务或明确的单文件原子边界。
6. 多会话冲突不会依赖最后写入覆盖。
7. 包升级不会覆盖项目数据和本地扩展。
8. 最终文件仍可由 AI 直接读取、测试、维护和重新打包。
9. 用户最终仍只需保存和分发两个输入文件。
10. 无法满足前置能力时能够安全降级或阻断，而不是伪造完成。

## 33. 实现起点

设计通过后，第一实现增量只建设“安全安装与包身份基础”，不同时重写全部状态工具：

1. 建立新 ZIP 目标骨架、`PACKAGE.json` 和覆盖完整包的清单格式。
2. 实现独立 ZIP 安全预检。
3. 修复 Windows 路径和 UTF-8 输出。
4. 实现 `bootstrap.py inspect/plan/apply/resume/rollback` 最小事务闭环。
5. 实现四类入口受控块合并和真实加载检查条件。
6. 使用新项目、已有项目、重复安装、冲突和中断恢复样本验收。

该增量通过前，不迁移现有任务、总结和认知工具，避免安装边界与状态模型同时变化导致问题无法定位。
