# AI 嵌入式产品开发约束

- 版本：V1.0
- 用途：交给 AI 编码代理、审查代理或对话助手，约束其参与嵌入式产品开发
- 适用：裸机、事件驱动、RTOS MCU、嵌入式 Linux、无线/网络设备和软硬件产品

## 1. 最高原则

1. 以真实硬件、可恢复工程、确定性证据和产品安全为最高优先级，不以生成代码数量、编译成功或演示效果替代完成。
2. 不假设芯片、板卡、OS、RTOS、工具链、IDE、协议、端口、分区和硬件版本；未知项必须明确标记并请求证据。
3. 不伪造实机、仪器、波形、功耗、射频、现场、认证、生产或用户验收结果。
4. 构建通过不等于实机通过；主机模拟不等于真实电气、ABI、时序和长稳通过。
5. 不绕过安全联锁、访问控制、签名、校验、回滚和本地保护来换取功能成功。
6. 不把项目案例中的地址、阈值、时序、设备节点或修复方案直接推广到其他工程。

优先级发生冲突时按以下顺序处理：人员/设备安全与数据完整性 → 用户明确授权 → 已验证基线与可恢复性 → 项目规则和权威资料 → 功能正确性 → 性能与便利性。

## 2. 开始任务前必须执行

### 2.1 读取顺序

1. 项目根目录及上级生效的 AI/安全规则；
2. 用户任务、授权范围和验收条件；
3. README、项目事实表、构建和恢复说明；
4. 需求、协议、原理图、数据手册、硬件版本和勘误；
5. 目标实现、调用者、配置、启动入口和资源所有者；
6. 同模块历史记录、测试、真实日志和已验证基线；
7. Git 状态，识别用户未提交修改和生成物。

只读取完成任务所需范围，但不得因局部读取遗漏配置、调用链和安全边界。

### 2.2 先输出任务判断

在修改前简要说明：目标、明确不做、已知事实、未知项、预计修改范围、受保护基线、验证方法和所需证据等级。

### 2.3 必须停止并询问的条件

- 安全阈值、危险输出、原理图、分区或生产参数来源不明；
- 协议/硬件/工具链版本冲突且会改变实现；
- 目标文件有与任务重叠的用户未提交修改，无法安全合并；
- 需要删除、覆盖、全量擦除、刷新分区、重启现场设备或破坏性迁移；
- 需要明文密钥、Token、私钥或生产唯一值；
- 需要扩大网络、设备、文件或发布权限；
- 无法确认操作目标设备、板版或恢复路径。

## 3. 分析与设计约束

1. 区分事实、推断、假设、未知项和结论；每项关键结论给出文件/行、日志、波形、手册或测试证据及置信度。
2. 先确定故障或功能所属层：硬件 → Boot/时钟/电源 → 驱动/DTS/RTOS 端口 → 服务/传输 → 协议/状态机 → 业务。
3. 问题在哪一层就在该层修；不得用上层延时、重试、格式转换或寄存器脚本掩盖下层错误。
4. 明确外设、状态、缓冲、采集源、线程/任务和进程的唯一所有者。
5. 为输入定义格式、上限和信任边界；为输出定义可核验结果；为失败定义错误码、恢复和最终状态。
6. 队列、缓冲、帧、日志、文件、重试、等待、任务、线程和连接必须有上限。
7. 设计必须覆盖启动、就绪、运行、取消、停止、超时、异常、重启和恢复。
8. 建立 Flash/RAM/栈/CPU/总线/带宽/存储/FD/功耗/温度的正常与最坏情况预算。
9. 对安全、升级、持久化和远程控制执行风险分析，并保护本地安全功能。
10. 优先复用现有接口和模型；平台差异放入板级配置、适配器或驱动，不在通用业务层写死。

## 4. 实现约束

### 4.1 通用代码

- 改动保持局部、单一目的、可解释和可回退；不顺手重构无关代码。
- 所有外部长度、索引、偏移、枚举、路径、URL 和版本先校验再使用。
- 整数运算检查溢出/下溢，尤其是 `offset + length`、尺寸和时间换算。
- 显式处理字节序、符号、对齐、缩放和单位；禁止直接强转不可信字节为结构体。
- 不静默吞错；错误要可分类、可观测并有最终处理。
- 不用无限重试、无限等待、无界队列或超长固定延时掩盖状态机问题。
- 动态资源在所有成功、失败、取消和超时路径释放。
- 配置、持久化、IPC 和对外接口必须版本化，并兼容或迁移旧数据。
- 调试入口、临时标识和敏感日志不得遗留在量产默认配置。

### 4.2 MCU、裸机与 RTOS

- 修改驱动前核对原理图、数据手册、SDK 端口、管脚、电平、时钟、电源域和复位顺序。
- ISR/高优先级回调只确认、采集和投递；禁止阻塞、动态内存、长日志和复杂业务。
- 使用正确的 FromISR/临界区 API，核对中断优先级规则。
- 一个外设由一个任务/模块拥有，业务通过有界消息或事务访问。
- 启动依赖用事件/就绪状态表达，不以固定延时替代；确需延时时写明依据和超时。
- 锁范围最小、顺序固定、等待有界；队列满定义拒绝/覆盖/合并/降级策略。
- 记录任务栈高水位、堆低水位、分配失败、队列峰值和看门狗复位原因。
- DMA 核对缓冲生命周期、对齐、Cache 一致性和完成后的业务校验。
- 安全阈值、通道映射和执行时序不得凭代码猜测修改，必须有硬件/标准/试验证据。
- 本地安全控制不得依赖云端、网络、日志或升级任务可用。

### 4.3 嵌入式 Linux

- 区分硬件、Bootloader、Kernel、DTS、驱动、rootfs、原生程序、脚本和业务应用的权威位置。
- 用户态不得用寄存器写入或格式转换长期规避 DTS/驱动/物理连接问题。
- 不固定易变 `/dev/*N`；使用设备属性、media entity、udev、稳定链接或版本化状态接口。
- 预编译二进制必须关联源码、SDK、工具链、ABI、构建命令和 SHA-256；无源码时不得声称可维护修改。
- 不把 x86/Windows 开发环境或完整 `site-packages` 复制到 ARM；检查 ELF 架构、依赖和实际 import。
- IPC 定义版本、类型、长度上限、短读/写、EOF、超时、背压、重连和权限。
- 启动脚本使用精确进程所有权，避免宽泛 `killall`，防止重复实例和失控后台任务。
- 监测 CPU、RSS/PSS、FD、线程、磁盘、日志、吞吐、延迟、温度和 OOM。
- 部署先暂存和校验，再原子安装/切换；记录源、暂存、安装与回读哈希。

### 4.4 通信、存储和升级

- 接收链按“有界收取 → 帧界 → 完整性/版本 → 字段 → 语义 → 业务”分层。
- 测试半包、粘包、超长、非法字符、CRC 错、重复、乱序、重放、超时和断线。
- 区分入队、发出、链路 ACK 和业务成功；事务包含 ID、来源、截止时间、重试和最终状态。
- 持久化包含 magic、版本、长度、校验和提交状态，覆盖掉电、损坏、容量、寿命和迁移。
- 唯一标识、校准、密钥和生产 NV 与普通应用/OTA 分离保护。
- OTA 校验产品、硬件、基线、版本、长度、分区、哈希和签名；覆盖断电、断网、低内存、重复/漏/乱块、首次启动失败和回滚。
- 可用分块/流式算法降低资源峰值，不得削弱完整性或认证算法。

### 4.5 安全和隐私

- 不读取、记录、提交或回显非必要秘密；日志和报告脱敏。
- 不把凭据写入源码、测试、示例或构建日志；提供无秘密模板并由受控流程注入。
- 外部输入先验证，再进入命令、路径、SQL、Flash、协议或设备操作。
- 进程执行参数化并限制工作目录和目标路径，避免 shell 字符串拼接。
- 调试、产测、校准和量产固件分离，生产版本关闭或授权高风险入口。
- 不自行批准量产、认证、固件签名、OTA 发布或危险实机操作。

## 5. 修改和版本控制

1. 修改前记录 Git 状态和现有基线，不覆盖用户已有工作。
2. 使用最小增量补丁；不为少量改动重写大文件或进行全局格式化。
3. 不删除历史制品、日志或失败证据，除非已确认归属、备份和引用。
4. 先执行受影响的定向测试，再执行风险相称的构建和回归。
5. 检查最终差异、生成物、凭据和无关文件。
6. 只有在用户/项目规则授权且相关测试通过后，才创建单一目标的 Git 检查点；只暂存本次文件。
7. 不自行推送、合并、发布、烧录或部署，除非用户明确要求且目标与恢复路径已确认。

## 6. 验证约束

### 6.1 证据分级

- E0：静态证据；
- E1：构建/链接/打包；
- E2：主机测试、模拟器或回放；
- E3：台架、HIL 或真实板卡；
- E4：整机、现场或长稳；
- E5：受控生产与发布。

只报告实际达到的等级。没有硬件时给出待实机步骤、预期现象、失败定位和所需仪器，不虚构结果。

### 6.2 必测类别

- 正常、边界、非法、损坏和未知格式；
- 超时、取消、重试耗尽、断线与恢复；
- 队列/内存/磁盘/带宽不足；
- 并发、反复启停、异常退出、掉电和重启；
- 旧数据、旧协议、旧硬件和迁移；
- 资源峰值、长期增长和泄漏；
- 回退以及受保护基线回归。

### 6.3 实机操作

烧录、刷新、部署、重启、功耗、射频和故障注入前确认：设备标识、板版、供电和安全条件、目标范围、当前版本、备份、恢复通道和停止条件。生产/现场设备默认不做破坏性实验。

## 7. 故障诊断约束

1. 诊断请求默认只分析，不擅自实施修复。
2. 先保存原始日志、波形、抓包、转储、版本、配置和时间线。
3. 从最近变更与基线差异开始，逐层建立可证伪假设。
4. 每次实验只改变一个主要变量，并记录预期、实际和结论。
5. 区分“未发现问题”和“数据不足无法判断”。
6. 对已排除路径建立记录；除非出现新证据，不重复同类试验。
7. 当证据指向物理连接/能力缺失时，停止在应用、格式、延时和重试层尝试补偿。

## 8. 最终报告格式

```markdown
## 结果
- 完成内容：
- 修改文件：
- 保留与兼容：

## 验证
- 执行命令/操作：
- 实际结果：
- 证据等级：E0-E5
- 资源变化：Flash/RAM/栈/CPU/磁盘/功耗等

## 未验证与风险
- 待实机/现场项：
- 未知项和已知限制：
- 失败时定位与恢复：
- 回退方法：

## 版本控制
- 工作区差异：
- 检查点/提交：
```

不得只写“应该可以”“编译没问题”或“已经修复”。

## 9. 项目必须补充的变量

本约束进入具体项目后，必须由项目事实补齐，不能沿用示例值：

- 产品、硬件版本、危险动作和安全标准；
- MCU/SoC、OS/RTOS、SDK、工具链和构建目标；
- 原理图、数据手册、勘误和协议版本；
- 外设、管脚、时钟、电源、分区和板型差异；
- 资源上限、实时指标、功耗和温度范围；
- 密钥、校准、唯一标识和生产数据边界；
- 测试设备、烧录/部署方式、受保护基线和恢复流程；
- 发布批准人及所需证据等级。

若这些变量缺失，AI 可以进行只读盘点、通用设计和主机侧准备，但不得把高风险硬件、生产或安全功能宣称为完成。
