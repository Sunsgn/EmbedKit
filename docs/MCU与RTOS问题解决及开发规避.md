# MCU 与 RTOS 问题解决及开发规避

- 文档版本：V1.0
- 适用范围：裸机、事件驱动和多种 RTOS 的 MCU 产品
- 内容性质：从真实工程现象匿名提炼的问题解决方法，不保留产品名、项目代号、芯片型号或商业参数

## 1. 使用方式

本文不描述某个项目“做了什么”，而是回答三个问题：

1. 出现问题后，怎样用原始证据逐层缩小范围；
2. 根因确认后，怎样修复、回退和复测；
3. 在设计与编码阶段，怎样避免同类问题再次出现。

所有队列长度、任务优先级、超时、阈值、存储地址和重试次数都必须由目标产品重新测量，不能从案例直接复制。

## 2. 多链路通信互相阻塞或状态错乱

### 典型现象

- 联网、无线或串口单独运行正常，同时活动时出现丢包、乱序或假掉线；
- 业务任务直接等待 AT/协议响应，导致采集、安全判断或界面更新停顿；
- 断线重连后重复发送旧状态，或最新控制意图丢失；
- 半包、粘包和异步事件被同步命令处理器误判。

### 定位证据

- 保存带时间戳的原始 RX/TX 字节、命令序号、状态迁移和超时原因；
- 记录发送者、接收者、队列深度、高水位和丢弃策略；
- 区分“命令已写入”“模组已确认”“业务端已确认”三个完成层级；
- 用录制数据回放分包、粘包、延迟、重复响应、乱序事件和断线。

### 解决方式

1. 为每条物理链路设置唯一所有者任务或事件循环；
2. 业务层只提交版本化事务，不直接读写串口或等待模组；
3. 事务包含序号、期望响应、截止时间、有限重试和最终结果；
4. 接收端先增量组帧，再区分命令响应与异步事件；
5. 对“状态同步”只保留最新期望值，对“不可丢事件”使用有界持久队列；
6. 重连后按业务语义恢复，不盲目重放所有历史命令。

### 开发时规避

- 禁止多个任务直接拥有同一 UART、SPI 或通信模组；
- 禁止无限重试、无限队列和无截止时间等待；
- 协议解析器必须覆盖分包、粘包、错误编码和未知响应；
- 在接入第二条链路前先建立第一条链路的回放测试和资源基线。

## 3. RTOS 启动失败、随机复位或运行一段时间后卡死

### 典型现象

- 创建后续任务失败，但系统只表现为“没有继续运行”；
- 栈溢出、堆耗尽或中断优先级错误表现为随机 HardFault；
- 调试版本正常，优化或增加日志后故障；
- 看门狗复位掩盖了最初失败位置。

### 定位证据

- 为启动阶段、每次任务创建、队列/互斥量创建和堆申请记录结果；
- 周期采集任务栈高水位、堆剩余/最小值和对象数量；
- HardFault 保存寄存器、异常栈、固件哈希和 MAP/ELF 关联；
- 复位前将首个失败原因写入有界、掉电安全的诊断区。

### 解决方式

1. 先恢复“第一个失败点”，不要从最终复位现象倒推；
2. 对照链接结果确认静态 RAM、堆、任务栈和中断栈预算；
3. 修正 FromISR API、中断优先级和临界区边界；
4. 移除任务或 ISR 中不受控的同步等待；
5. 用压力场景测量高水位后再调整资源，不凭经验随意放大。

### 开发时规避

- 所有 RTOS 对象创建都必须检查返回值；
- 任务函数禁止意外返回，资源释放路径必须明确；
- 发布构建保留低成本资源遥测和故障快照；
- 新功能合入前比较 MAP、最小堆余量和任务栈余量。

## 4. 中断中延时或任务间竞争导致实时性失效

### 典型现象

- 某外设活动时其他中断延迟明显增加；
- 偶发漏采样、丢边沿或通信超时；
- 在 ISR 中加入日志后故障概率大幅变化；
- 同一状态同时被 ISR、定时器和多个任务修改。

### 解决方式

1. 用 GPIO 翻转、周期计数器或跟踪事件测量 ISR 实际占用；
2. ISR 只采集必要状态、清标志并投递事件；
3. 将延时、协议处理、日志和复杂计算移到任务上下文；
4. 为共享状态定义单写者，其他上下文通过消息或原子快照读取；
5. 对事件满载、队列满和优先级反转建立失败路径。

### 开发时规避

- ISR 中禁止阻塞延时、动态分配和无界循环；
- 不用 `volatile` 代替原子性、内存顺序或临界区设计；
- 明确每个共享变量的所有者、更新频率和一致性要求；
- 用最坏中断频率而不是平均频率计算 CPU 预算。

## 5. 掉电缓存重复、丢失或损坏

### 解决方式

- 记录格式包含版本、长度、序号和校验；
- 使用双槽、日志式提交或“写数据后写提交标志”的原子更新；
- 启动时扫描并选择最后一个完整记录，不静默接受半写数据；
- 业务确认后再回收，删除与覆盖前保留可恢复状态；
- 通过写入次数预算、磨损均衡和容量上限控制寿命。

### 开发时规避

- 不把 RAM 结构体直接作为永久格式；
- 不在收到链路 ACK 前删除待上报数据；
- 必须测试任意字节写入点断电、校验错误、版本升级和容量耗尽；
- 未知旧版本保留原始数据并安全降级。

## 6. 低功耗后无法唤醒或通信异常

### 解决方式

1. 将睡眠资格写成可观测条件集合，而不是一个模糊布尔值；
2. 进入前确认事务、DMA、Flash 写入和外设时钟状态；
3. 记录唤醒源、睡眠时长、恢复阶段和失败原因；
4. 按“时钟 → GPIO/中断 → 定时基准 → 总线 → 通信状态机”恢复；
5. 用电流波形和真实唤醒事件验证，不以函数返回代表成功。

### 开发时规避

- 关键事务使用有所有者和超时的低功耗锁；
- 所有锁必须有释放路径和超时诊断；
- 睡眠/唤醒与通信重连分别测试，再测试组合场景；
- 频繁睡眠场景必须评估启动电流、网络注册和 Flash 寿命。

## 7. 安全控制逻辑修改风险

### 解决方式

- 将确定性安全状态机与联网、日志、AI 建议隔离；
- 每个阈值、通道映射和延时关联硬件版本、需求和试验记录；
- 对传感器开路、短路、越界、冻结、抖动和互相矛盾输入做故障注入；
- 输出报告区分静态推断、台架验证和真实产品验证；
- 修改失败时可恢复到已验证固件与配置基线。

### 开发时规避

- 禁止仅凭代码命名或通用经验修改安全参数；
- 通道映射不得依赖可变数组顺序或显示名称；
- 通信和云端失败不得阻断本地安全动作；
- 未验证建议不得显示为已经确认的安全结论。

## 8. 推荐复测矩阵

| 问题域 | 正常路径 | 失败注入 | 必留证据 |
| --- | --- | --- | --- |
| 通信事务 | 请求、响应、异步事件 | 半包、超时、断线、重复响应 | 原始字节、事务序号、状态迁移 |
| RTOS 资源 | 典型负载 | 堆不足、栈逼近、队列满 | MAP、堆/栈高水位、首错位置 |
| 中断实时性 | 额定频率 | 突发最高频率、嵌套中断 | ISR 时长、漏事件计数 |
| 持久化 | 写入与恢复 | 任意阶段断电、损坏记录 | 原始记录、版本、校验、恢复选择 |
| 低功耗 | 进入和唤醒 | 锁未释放、通信活动、异常唤醒 | 电流、唤醒源、恢复阶段 |
| 安全控制 | 额定输入 | 断线、短路、越界、冲突输入 | 输入原值、状态迁移、输出与时间 |

## 9. 完成判定

问题只有在以下条件同时满足时才算解决：根因有原始证据；修复不依赖单一样例；失败路径可定位；资源上限明确；具有回退方案；复测覆盖正常、异常和长稳；报告能够关联源码/固件版本及测试配置。
