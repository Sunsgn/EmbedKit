# EmbedKit 本地工具箱与工程入口实施方案

## 1. 阶段定位

EmbedKit 当前阶段收敛为“本地嵌入式工具箱与工程入口管理器”。它不替代 Keil、IAR、VS Code、编译器、烧录器或通用 AI，而是把分散的工程、开发软件、官方资料、通信调试和确定性文件工具放在统一入口中。

已有工程分析、集成测试、学习中心和 AI 助手继续保留并可独立进入，但降为按需能力，不作为其他模块的前置条件。协议识别属于工具箱中的协议工具，不再作为产品中心。

## 2. 用户工作流

### 2.1 工程与环境

- 输入：用户选择的本地工程目录、程序功能说明和环境要求。
- 操作：有界扫描工程，识别已有 IDE、构建系统、工具链和产物；检测本机软件版本。
- 输出：可持久化工程档案、相对路径证据、缺失或不兼容环境清单，以及受控安装入口。
- 失败处理：Agent 离线、目录权限失效、未知工程或工具版本无法识别时保留档案并显示明确降级状态。

### 2.2 资料查询

- 输入：芯片完整型号、器件类别或开发主题。
- 操作：先查本地目录，再导航到带来源、适用范围和验证日期的官方资料。
- 输出：可打开、收藏或记录到工程资料索引的来源链接。
- 失败处理：离线或没有结果时保留搜索条件，不使用不可靠聚合内容冒充官方参数。

### 2.3 通信与确定性工具

- 输入：真实串口/网络数据、固件、HEX、BIN、ELF、MAP、DBC、SVD 或计算参数。
- 操作：用户直接进入独立工具；需要本机权限时仅依赖 Local Agent。
- 输出：原始数据、严格校验结果、错误位置，以及可复制或导出的证据文件。
- 失败处理：损坏格式、超限输入、Agent 离线和设备断开必须分别报告，纯浏览器工具继续可用。

### 2.4 与 AI 协作

- AI 不是平台依赖。EmbedKit 不负责与通用 AI 竞争文档理解、代码生成和开放式诊断。
- 本地工具负责确定性解析、计算、边界检查和证据导出；用户可以把导出结果交给任意 AI、同事或现有流程。
- 本地 AI 页面作为可选入口保留，未安装模型不得影响工程、资料、通信和工具箱。

## 3. 信息架构

第一层日常入口：

1. 工程中心与开发环境；
2. 资料中心与学习中心；
3. 通信调试与嵌入式工具箱；
4. 数据管理与可选 AI 协作。

第二层按需能力：工程分析、集成测试、本地助手和其他高级工具。所有现有路由继续兼容，旧数据不迁移或删除。

## 4. 实施顺序

### P0：入口收敛

- 重组首页和侧边导航；
- 首页明确 AI、Agent 和项目均不是通用工具的前置条件；
- 保留所有既有入口和路由。

### P1：软件与工程联动

- 在工程档案中统一展示环境满足情况；
- 从检测结果打开已验证的软件安装目录或可执行程序；
- 启动能力必须使用固定适配器和参数化进程接口，禁止网页传入任意命令。

### P2：资料索引联动

- 工程档案可记录芯片、手册和教程来源；
- 资料中心支持将可靠来源添加到工程，但工程不是资料查询前置条件。

### P3：结果交接

- 各确定性工具采用统一的复制、JSON/CSV/HTML 导出约定；
- 导出记录工具版本、输入摘要、时间和能力边界；
- 提供“适合交给 AI 的最小证据包”，但不自动上传任何本地数据。

## 5. 完成判定

- 新用户能从首页直接进入工程、环境、资料、通信和工具箱；
- Agent 离线时导航、资料缓存、工程档案和纯浏览器工具正常工作；
- AI 未配置时不出现阻塞；
- 高级模块仍可从按需入口独立进入；
- 首页和导航回归测试、类型检查、代码检查及 GitHub Pages 隔离构建通过；
- 后续功能以减少软件切换、环境恢复时间或重复操作为验收指标，不再以模块数量为完成标准。
