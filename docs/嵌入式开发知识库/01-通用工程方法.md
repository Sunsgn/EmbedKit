# 通用工程方法

## 1. 完成闭环

嵌入式开发不是“写完代码并编译”，而是以下闭环：

```text
需求与约束
  → 事实盘点与基线
  → 风险、架构和资源设计
  → 小步实现
  → 静态/构建/模拟/实机/系统验证
  → 制品、报告和发布
  → 现场反馈与知识回流
```

每一步必须能追溯到输入、决策、代码、配置、制品和证据。

## 2. 项目事实优先于假设

开始工作前建立事实表，至少包括：

- 产品型号、硬件版本、软件版本和生命周期阶段；
- MCU/SoC、内存、时钟、启动方式和关键外设；
- OS/RTOS、SDK、编译器、构建工具及版本；
- 权威源码、工程配置、构建命令、产物和清理方式；
- 原理图、数据手册、协议、分区和生产参数版本；
- 设备接口、电气约束、资源所有者和实时要求；
- 当前成功基线、已知失败、测试入口和恢复方法；
- Git 状态、未提交修改和受保护文件。

未知项写“未知/待确认”，不要用常见平台经验补空白。推断必须带依据和置信度。

## 3. 先保护基线

可运行基线至少记录：

- 源码提交或文件清单；
- 硬件、板卡和设备标识；
- 工具链、SDK、配置和完整构建命令；
- 固件/应用/模型/配置的大小和 SHA-256；
- 烧录或部署目标范围；
- 已通过与未通过的验证；
- 回退或有线恢复路径。

新增功能不得无关修改已验证链路。若必须触碰，应先设计最小变更、回归项和回退点。

## 4. 需求转换为可验收条目

自然语言需求应拆成：

- 正常路径：触发、前置状态、输入、状态变化、输出和完成条件；
- 边界：长度、数值、频率、并发、容量和持续时间；
- 失败：超时、断线、掉电、CRC 错、队列满、低内存和设备缺失；
- 兼容：旧硬件、旧固件、旧协议、旧数据和未知字段；
- 安全：危险动作、本地保护、权限、凭据和回滚；
- 可观测：状态、错误码、事务号、计数器和原始证据；
- 资源：Flash、RAM、栈、CPU、总线、存储、功耗、温度和带宽；
- 验证：需要达到的证据等级及验收人。

对安全、升级、存储和远程控制使用 FMEA 或等价风险分析。

## 5. 分层和所有权

通用分层可表述为：

```text
硬件/物理连接
  → 芯片支持、Boot、时钟、电源和管脚
  → 驱动与内核/RTOS端口
  → 设备服务与资源所有者
  → 协议、状态机和领域服务
  → 产品业务、UI、云端和测试接口
```

关键原则：

- 一个物理接口、采集源或可变状态有一个明确所有者；
- 上层通过稳定接口消费能力，不跨层写寄存器或依赖枚举编号；
- ISR/回调只采集、确认和投递，复杂业务由任务/线程处理；
- 队列、缓冲、重试和等待都有上限；
- 启动、停止、取消、超时、异常退出和重启都有状态；
- 高风险本地保护不依赖网络、日志、升级或云端可用。

## 6. 资源预算先于实现

设计阶段为正常和最坏情况建立预算：

| 类别 | 典型项目 |
| --- | --- |
| 存储 | 固件、分区、升级包、日志、模型、数据库和寿命 |
| 内存 | 静态 RAM、堆峰值、任务栈、DMA/媒体/协议缓冲 |
| 计算 | 中断占用、最坏执行时间、CPU、推理和编码负载 |
| 通信 | 总线占用、吞吐、并发、重传、弱网和峰值带宽 |
| 能源 | 平均/峰值电流、唤醒、无线发射和热约束 |
| 生命周期 | 任务、线程、进程、FD、句柄、定时器和锁 |

“平均可用”不代表最坏情况安全。功能关闭时应明确是否释放任务、外设、内存和电源锁。

## 7. 小步实现和受控变更

推荐顺序：

1. 补充数据结构、常量、纯函数和接口；
2. 为纯逻辑建立测试向量；
3. 接入有界队列、事务和状态机；
4. 接入驱动、启动和产品配置；
5. 每一步验证并记录资源变化；
6. 清理临时诊断入口，但保留有价值的可观测性。

不要为了套目录模板移动成熟 SDK；先补入口、索引和 manifest。大文件拆分前先建立行为测试，每次只拆一个职责。

## 8. 可恢复工程

一个可交付工程至少有：

- 清晰 README 和项目事实表；
- 唯一或明确分级的构建入口；
- 固定工具链来源、版本和离线恢复说明；
- 源码、生成物、发布制品、日志和测试证据的边界；
- 精确忽略规则，不把凭据、缓存和普通中间产物提交；
- 旧数据、配置和接口的版本化与迁移；
- 可执行的构建、测试、部署、回读和回退流程。

编译、传输、安装、回读和功能验证是不同里程碑，不能互相替代。
