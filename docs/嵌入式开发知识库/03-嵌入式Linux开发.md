# 嵌入式 Linux 开发

## 1. 分层定位

Linux 项目先区分故障和变更所属层：

```text
硬件连接与电气
  → Bootloader / 启动配置
  → Kernel / DTS / pinctrl / regulator / clock
  → 驱动与内核子系统
  → rootfs / Buildroot / 包和系统服务
  → 原生媒体或高吞吐进程
  → Python/其他控制与业务进程
  → 启动编排、部署和云端
```

问题在哪一层就在哪一层修。用户态不能通过 `/dev/mem`、shell 写寄存器或格式转换长期掩盖 DTS、驱动或物理连接错误。

## 2. 稳定设备接口

`/dev/videoN`、`/dev/ttyUSBn`、网卡名等可能随枚举变化。应用应使用：

- udev 规则或稳定符号链接；
- media entity、设备属性、序列号或总线拓扑；
- 由系统层发布的版本化状态文件/能力接口；
- 明确的设备缺失、未就绪和降级状态。

“节点存在、驱动绑定、可以启动流、有 DMA 数据、数据有效、达到性能、可长稳”是不同证据。

## 3. DTS 和驱动

修改前核对原理图与 SoC 手册：引脚位域、总线宽度、时钟、极性、endpoint、lane、供电和复位。物理线未连接到控制器可采样位时，软件 `data-shift`、像素格式或后处理不能恢复不存在的数据。

驱动/DTS 变更应：

- 在标准 SDK 权威位置维护；
- 固定 SDK commit、BoardConfig、defconfig 和工具链；
- 生成最小补丁并保护已验证设备；
- 分别验证 DTB/KO 构建、加载、拓扑、数据有效性和长稳；
- 保存构建产物与板端回读哈希。

## 4. 语言和进程职责

- C/C++：高吞吐、低延迟、硬件媒体、推理和严格资源路径；
- Python：控制、编排、网络业务和低频事件；
- shell：有限启动探针、环境准备和服务编排；
- systemd/BusyBox init/监督器：进程生命周期与重启策略。

语言不是绝对边界，选择需由性能测量、依赖、维护和恢复要求决定。预编译程序必须能追溯源码、SDK、构建命令、ABI、版本和哈希；没有源码的二进制不能作为可持续修改对象。

## 5. 进程与 IPC

FIFO、Unix socket、共享内存和消息总线都要定义：

- 协议版本、消息类型、长度和字节序；
- 最大消息/帧、队列和并发消费者；
- 短读、短写、EOF、断开、超时和重连；
- 背压与慢消费者策略；
- 启停握手、取消和资源释放；
- 身份、权限和不可信输入校验。

单一采集源由一个进程拥有，再通过有界分发向多个消费者提供数据，避免多个进程争夺设备。

## 6. 启动和进程管理

启动脚本必须：

- 明确依赖、就绪条件、超时和失败降级；
- 使用 PID 文件、cgroup、服务管理器或精确命令匹配；
- 避免 `killall python` 一类宽泛终止；
- 防止重复实例，支持停止、重启和异常恢复；
- 不在探针中无限等待或生成失控后台任务；
- 将运行状态放在 `/run` 等临时状态位置，不与配置混淆。

## 7. 依赖和 ABI

不要把开发机完整 Python `site-packages` 或主机二进制复制到目标板。发布前检查：

- ELF 架构、ABI、动态解释器和 `NEEDED` 库；
- Python 版本、扩展模块架构和实际 import 白名单；
- rootfs、SDK/sysroot、模型运行时和驱动 ABI；
- 包版本、许可证、哈希和离线来源；
- 空间、启动时间和升级影响。

优先用 Buildroot/Yocto 包、交叉构建或确定性的目标 wheel/overlay 生成目标依赖。

## 8. 部署与刷新

安全部署流程：

```text
本地构建并生成 manifest
  → 传到板端暂存目录
  → 校验大小、架构和哈希
  → 原子安装或可回退切换
  → 权限/属主校验
  → 受控重启服务
  → 回读哈希与健康检查
  → 功能和长稳验证
```

Kernel、Boot、rootfs、应用、模型和配置需作为兼容的产品版本管理。刷新分区、覆盖运行文件或重启设备前应确认目标、恢复通道和影响范围。

## 9. Linux 资源与可观测性

监测 CPU、RSS/PSS、FD、线程、队列、磁盘、日志增长、网络吞吐、帧率、延迟、温度和 OOM。日志、RAW/JPEG、core dump 和暂存制品必须有容量上限、轮转和清理策略。
