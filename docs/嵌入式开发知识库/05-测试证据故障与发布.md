# 测试、证据、故障与发布

## 1. 证据等级

| 等级 | 证据 | 能证明 | 不能证明 |
| --- | --- | --- | --- |
| E0 | 静态分析 | 结构、引用、配置和明显边界 | 可构建、可运行 |
| E1 | 构建/链接/打包 | 指定配置产生制品 | 外设、时序和业务正确 |
| E2 | 主机/模拟/回放 | 纯逻辑、协议和状态机样例 | 真实电气、ABI、射频和性能 |
| E3 | 台架/HIL/实机 | 真实板卡关键和故障路径 | 长期、批量和现场环境 |
| E4 | 系统/现场/长稳 | 整机、网络和持续运行 | 生产良率和所有未来环境 |
| E5 | 生产/发布 | 受控制品、工装、追溯和批准 | 未覆盖的新变更 |

报告只声明实际达到的等级，并列出未验证项。旧日志和留存构建产物要标注时间与来源，不能冒充本次验证。

## 2. 测试矩阵

每个关键功能至少覆盖：

- Golden Path；
- 最小/最大/零值和越界；
- 非法格式、损坏、重复和乱序；
- 超时、取消、重试耗尽和断线重连；
- 队列满、低内存、磁盘满和带宽不足；
- 反复启动、异常退出、掉电和看门狗；
- 旧数据、旧协议、旧硬件和降级；
- 多模块并发和资源峰值；
- 回退和恢复。

测试金字塔为静态/单元 → 构建 → 模拟/回放 → 集成 → HIL/实机 → 系统/长稳 → 生产。代码覆盖率不能替代状态、故障和硬件覆盖。

## 3. 故障诊断方法

### 3.1 冻结证据

保存设备、硬件、固件、应用、配置、时间、复现步骤、原始日志、波形、抓包、转储和最近变更。不要用新实验覆盖唯一证据。

### 3.2 建立时间线和层级

区分观察事实、推断假设和已验证结论。沿硬件 → 驱动 → 传输 → 协议 → 状态机 → 业务逐层定位。最先检查最近变化和已验证基线的差异。

### 3.3 最小实验

每个实验记录：假设、唯一主要变量、预期、实际、原始证据和结论。实验应能证伪，不只是重复产生同一现象。

### 3.4 停止无效路径

当证据证明故障位于物理连接或下层能力边界时，停止在上层尝试格式、延时和重试补偿。维护“已排除路径”及重新开启它所需的新证据。

## 4. 资源和性能验证

同时记录修改前、预计、实际、上限和余量：

- MCU：Flash、RAM、堆、栈、队列、CPU、ISR、总线、功耗；
- Linux：镜像、磁盘、RSS/PSS、CPU、FD、线程、吞吐、延迟、温度；
- 通信：帧率、丢包、重试、弱网和并发；
- 存储：写频率、增长、轮转、寿命和恢复时间。

峰值和长期趋势都要验证。

## 5. 发布 manifest

发布记录至少包含：

- 产品、硬件、软件和协议版本；
- Git commit、dirty 状态、SDK、工具链和构建目标；
- 固件、DTB、KO、rootfs、应用、模型、库和配置的目标路径；
- 每个制品的类型、长度和 SHA-256；
- 分区/烧录/安装范围；
- 数据 schema、IPC 和 Agent/API 版本；
- 测试证据、等级、已知问题和适用范围；
- 回滚条件、恢复步骤和批准记录；
- 生产参数与普通制品的隔离边界。

## 6. 发布门禁

- 需求、协议、硬件和工具链版本已冻结；
- 默认及关键功能配置构建通过；
- 静态、单元、集成、实机和长稳达到约定等级；
- 资源满足最坏情况余量；
- 掉电、断网、低内存、损坏和看门狗路径已覆盖；
- 升级、回滚和配置迁移已验证；
- 密钥、校准、唯一标识和生产 NV 不会被覆盖；
- 调试入口和敏感日志已关闭或受控；
- 制品哈希、已知问题、恢复方法和批准完整。

AI 可以整理和检查门禁，但不能代替责任人批准发布。
