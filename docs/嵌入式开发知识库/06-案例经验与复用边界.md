# 问题复盘与复用边界

## 1. 复盘目的

复盘不保留项目名、产品名、客户名、芯片型号或偶然参数。它只沉淀：

- 可观察的故障现象；
- 能够回到原始位置的证据；
- 排除错误方向的判断过程；
- 已验证的根因与解决步骤；
- 失败回退、复测方法和资源边界；
- 在设计、编码、测试和发布阶段应提前规避的做法。

## 2. MCU 与 RTOS 问题复盘

### 可迁移解决方法

- 通信链路采用单一所有者、版本化事务、有限重试和异步结果；
- RTOS 启动阶段、对象创建、分配失败、栈溢出和资源高水位保持可观测；
- ISR 只完成采集、清标志和事件投递，延时与复杂处理移到任务；
- 掉电数据使用版本、序号、校验和原子提交，启动时安全恢复；
- 低功耗按进入条件、外设状态、唤醒源和恢复阶段逐项验证；
- 安全阈值、通道映射和延时关联硬件版本、需求和试验记录。

### 开发规避

- 不允许多个任务直接拥有同一外设或通信模组；
- 不使用无限队列、无限重试或无截止时间等待；
- 不在 ISR 中阻塞、动态分配或执行无界循环；
- 不把 RAM 结构体直接当作永久存储格式；
- 不凭代码命名或单次现象调整安全参数；
- 不在缺少回放和故障注入测试时拆分大型状态机。

### 不可照搬

任务优先级、栈深度、堆大小、超时、阈值、队列长度、重试次数、端口、存储地址和低功耗条件都属于目标工程配置，必须重新测量。

## 3. 嵌入式 Linux 问题复盘

### 可迁移解决方法

- 明确 SDK/构建机、应用仓库和目标设备之间的权威关系；
- 按硬件、DTS/驱动、系统接口、原生服务、脚本和业务应用分层定位；
- 应用通过稳定设备标识或状态接口访问设备，不固定易变节点编号；
- “驱动加载、节点存在、DMA 有数据、业务数据有效、性能和长稳”分级验收；
- DMA 数据异常时先核对物理位集合与控制器采样位集合，再检查上层格式；
- FIFO/Socket 处理最大帧、短读、EOF、超时、背压、取消和重连；
- 二进制必须关联源码、工具链、sysroot、依赖和哈希；
- 进程停止只作用于本服务拥有且身份匹配的实例。

### 开发规避

- 不用 Python 或 shell 长期绕过 DTS、驱动或构建问题；
- 不把节点存在或采集启动成功宣传为数据有效；
- 不固定 `/dev/*N` 等可变编号；
- 不把开发机依赖目录整体复制到目标机；
- 不使用宽泛进程名终止其他任务；
- 不让日志、原始帧和临时部署目录无限增长。

### 不可照搬

SDK 路径、设备节点、GPIO、总线位序、帧上限、进程接口、依赖版本和部署目录都必须依据目标 SoC、板卡、内核和 rootfs 重新确认。

## 4. 跨平台共同规律

| 规律 | MCU/RTOS 表现 | Linux 表现 |
| --- | --- | --- |
| 单一所有者 | 外设/通信任务 | 设备服务/采集进程 |
| 稳定接口 | 队列、事件、事务 | Socket、FIFO、状态文件、稳定链接 |
| 资源有界 | 栈、堆、队列、重试 | RSS、FD、磁盘、帧、重连 |
| 分层定位 | 时钟→驱动→调度→业务 | 硬件→DTS/驱动→系统→应用 |
| 保护基线 | 可运行固件与安全链路 | Boot/Kernel/设备主链路 |
| 证据分级 | 构建不等于实机 | 节点/数据不等于有效业务 |
| 可追溯发布 | 固件/MAP/配置/测试 | 镜像/DTB/模块/应用/manifest |

## 5. 经验转规则的方法

1. 先删除项目身份和偶然参数，保留故障机制；
2. 区分平台规律、子系统规律和目标工程配置；
3. 标明证据等级：静态推断、主机测试、台架、实机、现场；
4. 写明适用前提、反例、未知项和验证方法；
5. 把“如何解决”和“如何提前规避”分别列出；
6. 只有跨平台成立且涉及安全、数据完整性或可恢复性的内容，才提升为强制规则。
