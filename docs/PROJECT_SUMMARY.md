# EmbedKit 项目定位与开发方案总结

更新日期：2026-10-13

## 1. 一句话定义

EmbedKit 是一个 Web 优先、本地助手增强的通用嵌入式开发工作台，目标是把工程理解、底层驱动、板级调试、I²C/SPI/UART/CAN、网络协议、固件诊断、自动化测试、资料和学习工具整合到统一系统中，帮助嵌入式工程师减少重复工作并提高问题定位效率。

它不替代 Keil、IAR、CMake、编译器、烧录器、J-Link、OpenOCD、逻辑分析仪或芯片厂商 IDE，而是消费这些工具已有的工程配置、构建产物、设备数据和日志，将分散的调试过程连接成可复现、可验证、可导出的工程闭环。

## 2. 项目要解决的问题

嵌入式开发通常需要频繁切换：

- IDE、编译器和烧录工具；
- 串口、网络、CAN、I²C 和 SPI 调试软件；
- 示波器、逻辑分析仪和调试探针；
- 数据手册、SVD、寄存器头文件和协议文档；
- MAP、ELF、HEX、BIN、SREC 和故障日志；
- 临时 Python/C 脚本、Excel、计算器和抓包软件；
- 测试记录、问题报告和版本对比。

这些工具通常互不关联，导致以下问题：

1. 陌生工程难以快速确定启动流程、任务、中断和关键数据流；
2. 驱动代码写出来后，缺少寄存器、总线交易和真实设备证据验证；
3. I²C/SPI/UART/CAN 问题需要在多个工具间手工复制数据；
4. 协议文档、解析代码、实际抓包和测试用例长期不一致；
5. MAP、ELF、HardFault 和源码位置不能形成统一调查链；
6. 测试结果只显示成功或失败，无法回到具体步骤和原始数据；
7. AI 可以生成代码和解释原理，但不能独立连接硬件、稳定复现和长期维护工程证据。

EmbedKit 的价值是把这些环节组合起来，而不是简单增加更多页面。

## 3. 产品核心目标

### 3.1 看懂工程

- 自动识别 Keil、IAR、CMake、Make、Ninja 和通用 C/C++ 工程；
- 区分裸机、事件驱动、多种 RTOS 和未知框架；
- 恢复启动、初始化、主循环、任务、中断、回调和状态机流程；
- 结论带文件、行号、证据、覆盖率和置信度；
- 结合 MAP、ELF 和运行日志验证静态分析；
- 给出有依据、可验证的内存、性能、可靠性和可维护性建议。

### 3.2 调通底层硬件

- 协助编写和审查时钟、GPIO、中断、DMA 和外设驱动；
- 导入数据手册、SVD、芯片头文件和板级参数；
- 比较初始化期望、源码配置、寄存器实测和总线交易；
- 连接调试探针读取关键寄存器、内存和运行日志；
- 形成板级 Bring-up 检查、错误恢复和回归测试流程。

### 3.3 调试常用总线

- UART：多会话、分屏、快捷指令、周期/文件发送、日志和协议联动；
- I²C：扫描、读写、重复起始、寄存器轮询、ACK/NACK 和交易日志；
- SPI：Mode 0–3、频率、位序、字宽、CS、多段传输和逻辑分析日志；
- CAN/CAN FD：收发、过滤、周期、DBC、信号、负载和错误统计；
- 后续通过适配器扩展 LIN、1-Wire、RS-485、USB、SDIO 等接口。

### 3.4 调试网络和协议

- TCP Client/Server、UDP 和 WebSocket；
- PCAP/PCAPNG 导入、连接筛选和 TCP 流重组；
- HTTP、MQTT、CoAP、Modbus TCP 和厂家私有协议；
- AI 从厂家文档生成协议草案；
- 确定性引擎负责拆包、校验、编解码、超时和测试判定；
- 协议绑定真实通信会话并生成测试流程。

### 3.5 分析固件和故障

- MAP：容量、模块、节区、符号和双版本增长证据；
- ELF/AXF：地址、符号、DWARF 和调用栈定位；
- HardFault：真实日志寄存器提取、SCB 解释和源码联动；
- HEX/SREC/BIN：校验、统一地址段、空洞、冲突、合并和发布清单；
- SVD：寄存器、字段、复位值、权限和快照差异；
- 日志：事件时间轴、状态转换和通信关联。

### 3.6 自动化测试和工程沉淀

- 多步骤流程支持发送、等待、断言、变量、条件、循环和人工检查；
- 流程支持串口、I²C、SPI、CAN、TCP、UDP 和 WebSocket；
- 默认继承第一个通信步骤的通道，高级模式允许覆盖；
- 用例支持增加、删除、复制、排序、版本和导入导出；
- 失败定位到具体步骤、帧、字段和原始数据；
- 可选关联设备、板卡、硬件版本、固件、协议和工程版本；
- 生成可复现、可审计的测试报告。

## 4. AI 的正确定位

AI 不是产品的最终执行层，而是工程辅助层。

### AI 适合完成

- 阅读数据手册、协议文档和陌生源码；
- 生成驱动、协议、测试和修复草案；
- 提取寄存器、字段、命令、枚举和时序描述；
- 解释 HardFault、MAP、日志和抓包结果；
- 汇总版本差异和优化方向；
- 根据已经验证的证据生成易读报告。

### EmbedKit 确定性代码必须完成

- 寄存器、位域、时钟、端序、CRC 和时序计算；
- I²C、SPI、UART、CAN 和网络真实操作；
- 文件、日志、抓包和连续字节流解析；
- 超时、取消、资源锁、错误恢复和测试判定；
- 原始位置、设备、固件、版本和结果证据；
- 批量执行、回归验证、导入导出和长期迁移。

AI 生成内容必须标明来源、适用范围、假设、未确认项和验证状态。AI 不能直接取得硬件写权限，也不能把缺少证据的推断显示为确定结论。

## 5. 实用性完成标准

所有功能统一使用以下验收模型：

```text
真实输入/硬件
→ 可控操作
→ 正常与失败路径
→ 原始位置和确定性证据
→ 导出或跨工具联动
→ 可重复执行和恢复
```

每项功能完成前必须明确：

1. 用户真实拿到的输入或设备是什么；
2. 用户具体需要执行什么操作；
3. 输出如何核验、复制、导出或进入下一流程；
4. 错误能否定位到页码、源码行、地址、日志行、帧或字段；
5. 文件大小、日志长度、帧数、时间和硬件资源上限；
6. Agent 离线、设备断开、权限不足和格式未知时如何降级；
7. 是否有领域测试、界面测试和真实设备验收；
8. 是否保持已有入口、数据和功能兼容。

只有入口、静态说明、Mock 数据、硬编码样例、一次性 AI 内容或无法带走的结果不能认定为完成。

## 6. 系统架构

### 6.1 GitHub Pages 前端

负责：

- 工具目录和独立工作区；
- 浏览器可完成的解析、计算、比较和报告；
- 项目、设备、协议、测试和证据展示；
- 本地持久化、数据迁移和能力检测；
- Web Serial、WebSocket 等浏览器允许的能力。

生产目标：

```text
https://sunsgn.github.io/EmbedKit/
```

### 6.2 Local Agent

只负责浏览器受限的本地能力：

- 系统串口后台会话；
- 原始 TCP/UDP 和 Server；
- CAN、I²C、SPI 硬件 Provider；
- SWD/JTAG、RTT/SWO 调试探针 Provider；
- 用户授权的本地文件、目录和大文件；
- 受控的本地工具链、OCR 和文档转换。

Agent 必须只监听回环地址，校验网页来源和协议版本，不提供任意命令执行。缺少某项 Provider 时只影响对应功能。

### 6.3 领域引擎

领域逻辑不依赖 React、操作系统或某个硬件厂商，包括：

- 源码和程序结构分析；
- MAP、ELF、固件、SVD 和故障解析；
- 总线交易、协议、校验和字段编解码；
- 测试流程、证据和报告；
- 数据格式、版本和迁移。

### 6.4 Provider 与 Adapter

- Provider 负责真实硬件或系统能力；
- Adapter 负责芯片、工具链、总线、协议和文件格式差异；
- 公共数据模型不得包含单一工程或单一厂家特例；
- 每个扩展声明版本、能力、依赖、安全边界、测试样本和降级行为。

## 7. 顶层功能结构

```text
工作台
设备项目
工程分析
通信调试
集成测试
嵌入式工具箱
AI 助手
资料中心
学习中心
数据管理
本地助手
```

模块可以独立使用，也可以通过公共模型形成可选闭环。嵌入式工具箱首页只展示目录、分类、搜索和说明，选择工具后才加载具体功能。

工具分类：

- 板级与驱动：时钟、GPIO、寄存器、中断/DMA、SVD；
- 总线调试：I²C、SPI、UART、CAN；
- 网络协议：TCP/UDP/WebSocket、PCAP、Modbus、DBC、自定义协议；
- 固件诊断：HEX/SREC/BIN、MAP、ELF、HardFault；
- 工程计算：定时器/PWM、ADC、CRC、字节序、位域、吞吐；
- 测试辅助：日志、测试向量、版本差异和报告。

复杂工作区采用步骤导航、互斥面板和证据抽屉，避免多个功能同时展开造成界面混乱。

## 8. 当前已经具备的能力

### 8.1 通信调试

- 浏览器直连串口和 Local Agent 可选增强；
- 多会话、分屏、周期发送、快捷指令、文件发送和日志导出；
- TCP Client/Server、UDP、WebSocket；
- 统一 `HH:mm:ss.SSS` 时间戳、RX/TX/SYS 方向、搜索、HEX 和统计；
- 暂停界面显示时继续接收和统计；
- Agent 离线只降级受影响功能。

### 8.2 工程和程序分析

- 多种工程入口和工具链识别；
- 裸机、FreeRTOS、非 FreeRTOS 和未知框架的降级分析；
- 启动流程、任务、回调、状态机、共享资源和执行轨迹；
- 源码位置、覆盖率、置信度和未知项；
- MAP、ELF 和构建产物关联基础。

### 8.3 集成测试

- 测试用例和多步骤流程；
- 共享通信通道继承；
- 流程步骤删除、排序和清理阶段；
- 虚拟设备和真实通信的基础执行；
- 测试证据、报告和设备项目关联基础。

### 8.4 已实用化的工具

- Modbus：厂家寄存器表、列映射、工程值和 CSV；
- CRC：命名/自定义模型、校验范围、批量帧和 C 参考实现；
- 自定义协议：连续流拆包、噪声、粘包、坏帧和 CSV；
- CAN DBC：单帧、candump/CSV 批量日志、筛选、异常统计和导出；
- HardFault：真实日志提取、原始行证据、冲突和 ELF 联动；
- MAP：双版本比较、模块/节区/符号下钻和证据导出；
- 固件：BIN/HEX/SREC 统一地址段、空洞、冲突和发布清单；
- Intel HEX、SREC、SVD、ELF、BIN、CAN、Timer/PWM、ADC 等独立工具。

### 8.5 产品工程能力

- GitHub Pages 子路径生产构建；
- Local Agent 集中状态和正式安装方案；
- 工作区备份、数据版本和隐私边界；
- 自动化领域测试、组件测试、Agent 测试、lint 和构建验证；
- 每个稳定增量独立 Git 检查点。

## 9. 当前主要缺口

| 领域 | 当前缺口 | 判定 |

| CAN | 批量 DBC 已有，真实 CAN Provider、CAN FD 和负载仍缺失 | P1 |
| 网络 | TCP/UDP/WebSocket 已有，PCAP 和 TCP 流重组尚未实现 | P1 |
| 协议工程 | 独立工具已有，统一协议模型、AI 草案和实时绑定尚未实现 | P1 |
| 固件诊断 | 单工具较完整，跨构建/设备/报告关联仍需加强 | P1 |
| 真实验收 | 自动测试较完整，但 I²C/SPI/探针等真实硬件矩阵未建立 | 持续任务 |

这些能力不得通过静态演示页面或 Mock 数据伪装成已完成。

## 10. 后续开发路线

### 阶段 P0：真实硬件底座

1. 建立 Hardware Provider、Hardware Session 和 Captured Event；
2. Local Agent 增加能力发现、资源锁、超时、取消和会话释放；
3. 建立虚拟 I²C/SPI Provider 用于自动化回归；
4. 保持现有串口和网络功能兼容；
5. 完善驱动缺失、权限和设备占用提示。

### 阶段 P0-A：I²C 工作台

- 适配至少一种系统接口和一种 USB/桥接方案；
- 扫描、读写、Repeated Start、寄存器轮询和脚本；
- ACK/NACK、超时、错误恢复和时间证据；
- 导入逻辑分析 CSV/VCD；
- 寄存器表解析和驱动测试向量。

真实验收：传感器 ID → 配置 → 数据轮询 → 错误注入 → 报告。

### 阶段 P0-B：SPI 工作台

- Mode 0–3、频率、位序、字宽、CS 和多段交易；
- 全双工 TX/RX、掩码断言和重复测试；
- 逻辑分析日志和不同模式重解释；
- SPI Flash/传感器命令模板；
- 真实交易保存为驱动回归向量。

真实验收：读取设备 ID → 状态 → 模式错误对比 → 报告。

### 阶段 P0-C：驱动与寄存器验证

- SVD/头文件统一寄存器模型；
- 寄存器快照和初始化期望比较；
- 调试探针只读 Provider；
- 时钟、GPIO、中断和 DMA 规则；
- 驱动代码草案与可执行验证清单。

### 阶段 P1：网络与协议

- PCAP/PCAPNG 和 TCP 流重组；
- 统一协议模型和 AI 文档草案；
- 厂家样例、真实日志和设备验证等级；
- 协议绑定通信会话并生成测试；
- 协议版本差异和经过测试向量验证的代码导出。

### 阶段 P1-A：诊断与发布闭环

- HardFault 地址批量符号化；
- MAP、ELF、固件关联同一构建；
- 完整固件镜像比较和分区校验；
- 设备、固件、会话、测试和报告追溯；
- 工作区迁移、脱敏和长期运行验证。

### 阶段 P2：生态扩展

根据真实需求增加 CAN FD、LIN、1-Wire、USB、RTT/SWO、功耗日志、逻辑分析仪和更多探针/适配器。每项扩展必须有真实设备、失败路径、测试和导出，不能以工具数量作为目标。

## 11. 关键端到端验收

### I²C 传感器驱动

```text
数据手册/SVD
→ 驱动初始化草案
→ 寄存器和值域检查
→ I²C 扫描和读取 ID
→ 初始化并轮询数据
→ 驱动日志与总线交易比较
→ 自动回归和报告
```

### SPI Flash Bring-up

```text
配置 Mode/频率/CS
→ 读取 JEDEC ID 和状态
→ 导入逻辑分析交易
→ 对比 CPOL/CPHA 和驱动序列
→ 保存测试向量和报告
```

### 联网模组

```text
导入 AT/协议手册
→ AI 草案和确定性验证
→ 串口连接真实模组
→ 执行联网流程
→ TCP/UDP 和业务协议解析
→ 失败定位和归档
```

### 固件异常

```text
HardFault 日志
→ 寄存器提取
→ ELF 源码定位
→ MAP 版本变化
→ SVD 故障状态
→ 修复后回归和证据比较
```

## 12. 项目开发纪律

- 不回退已经完成的通信、工具、测试和数据能力；
- 串口主界面非必要不大幅调整；
- 新能力优先领域模型和适配器，不把业务逻辑写入页面；
- 浏览器工具保持独立，Local Agent 只增强本地权限；
- 外部输入有大小、条数、超时和取消上限；
- 未知格式安全降级并保留原始证据；
- 每次先运行专项测试，里程碑再运行全量测试、lint、生产构建和 Pages 校验；
- 验证通过后只提交相关文件，及时创建可回退 Git 检查点；
- 不提交日志、缓存、抓取页面、临时文件和无关构建产物；
- 节省 Token 不能成为跳过安全、兼容性、测试和备份的理由。

## 14. 当前最终结论

EmbedKit 不应发展成单纯的 AI 助手、协议解析器或网页计算器集合。正确方向是：

> 以真实嵌入式工程任务为中心，用网页统一工作流，用 Local Agent 连接本地硬件，用确定性引擎执行和验证，用 AI 加速理解和生成，用证据模型连接源码、设备、通信、测试和报告。

近期最值得投入的能力不是继续增加孤立工具，而是完成：

```text
硬件 Provider 基础
→ I²C 真实工作台
→ SPI 真实工作台
→ SVD/驱动/寄存器验证
→ 网络抓包和协议工程
→ 多通道自动化测试闭环
```

当开发者能够从数据手册和源码出发，直接完成驱动草案、真实总线验证、问题定位、自动回归和报告归档时，EmbedKit 才真正实现“帮助嵌入式开发并提升开发效率”的目标。
