# EmbedKit 项目定位与开发方案总结

更新日期：2026-10-13

最终产品目标以 [EmbedKit 最终产品目标](./PRODUCT_GOAL.md) 为唯一最高约束；本文只总结当前能力、缺口和近期路线，不重新定义产品方向。

## 1. 一句话定义

EmbedKit 是一个 Web 优先、本地助手增强的通用嵌入式开发工作台，目标是把工程理解、底层驱动、板级调试、I²C/SPI/UART/CAN、网络协议、固件诊断、自动化测试、资料和学习工具整合到统一系统中，帮助嵌入式工程师减少重复工作并提高问题定位效率。

它不替代 Keil、IAR、CMake、编译器、烧录器、J-Link、OpenOCD、逻辑分析仪或芯片厂商 IDE，而是消费这些工具已有的工程配置、构建产物、设备数据和日志，将分散的调试过程连接成可复现、可验证、可导出的工程闭环。

## 2. 项目要解决的问题

嵌入式开发通常需要频繁切换：

- IDE、编译器和烧录工具；
- 串口、网络、CAN、I²C 和 SPI 调试软件；
- 示波器、逻辑分析仪和调试探针；
- 数据手册、SVD、寄存器头文件和协议文档；
- MAP、ELF、HEX、BIN、SREC 和故障日志；
- 临时 Python/C 脚本、Excel、计算器和抓包软件；
- 测试记录、问题报告和版本对比。

这些工具通常互不关联，导致以下问题：

1. 陌生工程难以快速确定启动流程、任务、中断和关键数据流；
2. 驱动代码写出来后，缺少寄存器、总线交易和真实设备证据验证；
3. I²C/SPI/UART/CAN 问题需要在多个工具间手工复制数据；
4. 协议文档、解析代码、实际抓包和测试用例长期不一致；
5. MAP、ELF、HardFault 和源码位置不能形成统一调查链；
6. 测试结果只显示成功或失败，无法回到具体步骤和原始数据；
7. 无论用户是否使用能够调用本地工具的 AI，工程版本、设备身份、真实输入、执行结果和失败证据仍需要统一保存、复现、比较和交付。

EmbedKit 的价值是把这些环节组合起来，而不是简单增加更多页面。

## 3. 产品核心目标

### 3.1 看懂工程

- 自动识别 Keil、IAR、CMake、Make、Ninja 和通用 C/C++ 工程；
- 区分裸机、事件驱动、多种 RTOS 和未知框架；
- 恢复启动、初始化、主循环、任务、中断、回调和状态机流程；
- 结论带文件、行号、证据、覆盖率和置信度；
- 结合 MAP、ELF 和运行日志验证静态分析；
- 给出有依据、可验证的内存、性能、可靠性和可维护性建议。

### 3.2 调通底层硬件

- 协助编写和审查时钟、GPIO、中断、DMA 和外设驱动；
- 导入数据手册、SVD、芯片头文件和板级参数；
- 比较初始化期望、源码配置、寄存器实测和总线交易；
- 连接调试探针读取关键寄存器、内存和运行日志；
- 形成板级 Bring-up 检查、错误恢复和回归测试流程。

### 3.3 调试常用总线

- UART：多会话、分屏、快捷指令、周期/文件发送、日志和协议联动；
- I²C：扫描、读写、重复起始、寄存器轮询、ACK/NACK 和交易日志；
- SPI：Mode 0–3、频率、位序、字宽、CS、多段传输和逻辑分析日志；
- CAN/CAN FD：收发、过滤、周期、DBC、信号、负载和错误统计；
- 后续通过适配器扩展 LIN、1-Wire、RS-485、USB、SDIO 等接口。

### 3.4 调试网络和协议

- TCP Client/Server、UDP 和 WebSocket；
- PCAP/PCAPNG 导入、连接筛选和 TCP 流重组；
- HTTP、MQTT、CoAP、Modbus TCP 和厂家私有协议；
- AI 从厂家文档生成协议草案；
- 确定性引擎负责拆包、校验、编解码、超时和测试判定；
- 协议绑定真实通信会话并生成测试流程。

### 3.5 分析固件和故障

- MAP：容量、模块、节区、符号和双版本增长证据；
- ELF/AXF：地址、符号、DWARF 和调用栈定位；
- HardFault：真实日志寄存器提取、SCB 解释和源码联动；
- HEX/SREC/BIN：校验、统一地址段、空洞、冲突、合并和发布清单；
- SVD：寄存器、字段、复位值、权限和快照差异；
- 日志：事件时间轴、状态转换和通信关联。

### 3.6 自动化测试和工程沉淀

- 多步骤流程支持发送、等待、断言、变量、条件、循环和人工检查；
- 流程支持串口、I²C、SPI、CAN、TCP、UDP 和 WebSocket；
- 默认继承第一个通信步骤的通道，高级模式允许覆盖；
- 用例支持增加、删除、复制、排序、版本和导入导出；
- 失败定位到具体步骤、帧、字段和原始数据；
- 可选关联设备、板卡、硬件版本、固件、协议和工程版本；
- 生成可复现、可审计的测试报告。

## 4. AI 的正确定位

AI 是可选外部工程辅助，不是产品依赖。未配置 AI 时全部确定性能力必须正常工作。

### AI 适合完成

- 阅读数据手册、协议文档和陌生源码；
- 生成驱动、协议、测试和修复草案；
- 提取寄存器、字段、命令、枚举和时序描述；
- 解释 HardFault、MAP、日志和抓包结果；
- 汇总版本差异和优化方向；
- 根据已经验证的证据生成易读报告。

### EmbedKit 确定性代码必须完成

- 寄存器、位域、时钟、端序、CRC 和时序计算；
- I²C、SPI、UART、CAN 和网络真实操作；
- 文件、日志、抓包和连续字节流解析；
- 超时、取消、资源锁、错误恢复和测试判定；
- 原始位置、设备、固件、版本和结果证据；
- 批量执行、回归验证、导入导出和长期迁移。

AI 生成内容必须标明来源、适用范围、假设、未确认项和验证状态。AI 不能直接取得硬件写权限，也不能把缺少证据的推断显示为确定结论。

## 5. 实用性完成标准

所有功能统一使用以下验收模型：

```text
真实输入/硬件
→ 可控操作
→ 正常与失败路径
→ 原始位置和确定性证据
→ 导出或跨工具联动
→ 可重复执行和恢复
```

每项功能完成前必须明确：

1. 用户真实拿到的输入或设备是什么；
2. 用户具体需要执行什么操作；
3. 输出如何核验、复制、导出或进入下一流程；
4. 错误能否定位到页码、源码行、地址、日志行、帧或字段；
5. 文件大小、日志长度、帧数、时间和硬件资源上限；
6. Agent 离线、设备断开、权限不足和格式未知时如何降级；
7. 是否有领域测试、界面测试和真实设备验收；
8. 是否保持已有入口、数据和功能兼容。

只有入口、静态说明、Mock 数据、硬编码样例、一次性 AI 内容或无法带走的结果不能认定为完成。

## 6. 系统架构

### 6.1 GitHub Pages 前端

负责：

- 工具目录和独立工作区；
- 浏览器可完成的解析、计算、比较和报告；
- 项目、设备、协议、测试和证据展示；
- 本地持久化、数据迁移和能力检测；
- Web Serial、WebSocket 等浏览器允许的能力。

生产目标：

```text
https://sunsgn.github.io/EmbedKit/
```

### 6.2 Local Agent

只负责浏览器受限的本地能力：

- 系统串口后台会话；
- 原始 TCP/UDP 和 Server；
- CAN、I²C、SPI 硬件 Provider；
- SWD/JTAG、RTT/SWO 调试探针 Provider；
- 用户授权的本地文件、目录和大文件；
- 受控的本地工具链、OCR 和文档转换。

Agent 必须只监听回环地址，校验网页来源和协议版本，不提供任意命令执行。缺少某项 Provider 时只影响对应功能。

### 6.3 领域引擎

领域逻辑不依赖 React、操作系统或某个硬件厂商，包括：

- 源码和程序结构分析；
- MAP、ELF、固件、SVD 和故障解析；
- 总线交易、协议、校验和字段编解码；
- 测试流程、证据和报告；
- 数据格式、版本和迁移。

### 6.4 Provider 与 Adapter

- Provider 负责真实硬件或系统能力；
- Adapter 负责芯片、工具链、总线、协议和文件格式差异；
- 公共数据模型不得包含单一工程或单一厂家特例；
- 每个扩展声明版本、能力、依赖、安全边界、测试样本和降级行为。

## 7. 顶层功能结构

```text
工作台
设备项目
工程分析
通信调试
集成测试
嵌入式工具箱
AI 助手
资料中心
学习中心
数据管理
本地助手
```

模块可以独立使用，也可以通过公共模型形成可选闭环。嵌入式工具箱首页只展示目录、分类、搜索和说明，选择工具后才加载具体功能。

工具分类：

- 板级与驱动：时钟、GPIO、寄存器、中断/DMA、SVD；
- 总线调试：I²C、SPI、UART、CAN；
- 网络协议：TCP/UDP/WebSocket、PCAP、Modbus、DBC、自定义协议；
- 固件诊断：HEX/SREC/BIN、MAP、ELF、HardFault；
- 工程计算：定时器/PWM、ADC、CRC、字节序、位域、吞吐；
- 测试辅助：日志、测试向量、版本差异和报告。

复杂工作区采用步骤导航、互斥面板和证据抽屉，避免多个功能同时展开造成界面混乱。

### 8.1 通信调试

- 浏览器直连串口和 Local Agent 可选增强；

- 裸机、FreeRTOS、非 FreeRTOS 和未知框架的降级分析；
- 启动流程、任务、回调、状态机、共享资源和执行轨迹；
- 源码位置、覆盖率、置信度和未知项；

### 8.3 集成测试

- 测试用例和多步骤流程；
- 共享通信通道继承；
- 流程步骤删除、排序和清理阶段；
- 虚拟设备和真实通信的基础执行；
- 测试证据、报告和设备项目关联基础。

- Modbus：厂家寄存器表、列映射、工程值和 CSV；

- MAP：双版本比较、模块/节区/符号下钻和证据导出；
- 固件：BIN/HEX/SREC 统一地址段、空洞、冲突和发布清单；

### 8.5 产品工程能力

- GitHub Pages 子路径生产构建；
- Local Agent 集中状态和正式安装方案；
- 工作区备份、数据版本和隐私边界；

## 10. 后续开发路线

### 阶段 P0：公共模型与兼容迁移

1. 定义工程版本、构建产物、设备、固件、会话、测试运行、证据引用、结论和知识条目；
2. 所有公共数据带 Schema 版本、稳定 ID、迁移和未知版本降级；
3. 保持现有设备项目、通信、测试、工具偏好和工作区备份兼容；
4. 区分确定性事实、推导、启发式风险、人工观察和外部 AI 建议；
5. 建立统一的大小、条数、时间、取消和脱敏规则。

### 阶段 P0-A：真实设备验证闭环

- 不创建项目即可直接使用串口、TCP、UDP 和 WebSocket；
- 可选关联设备、固件指纹、工程版本和测试套件；
- 记录准备、执行、清理、失败步骤和原始收发证据；
- 与历史基线比较新增失败、已修复和持续失败；
- 导出可复现的 JSON、HTML、JUnit 和 CSV 报告。

真实验收：确认设备和固件 → 执行正常步骤 → 注入一次失败 → 定位原始证据 → 修复复测 → 比较并导出报告。

### 阶段 P0-B：故障调查闭环

- 将 HardFault、ELF/DWARF、MAP、SVD、固件和通信日志关联为一次调查；
- 支持多个异常地址、冲突证据、未知项和结论状态；
- 所有地址和结论可回到原始日志、符号、源码或构建产物；
- 修复结论关联真实复测运行；
- 导出脱敏调查包和报告。

### 阶段 P0-C：陌生工程分析闭环

- 导入真实目录、工程配置和已有构建产物；
- 覆盖裸机、事件驱动、主流 RTOS、非 FreeRTOS 和未知格式；
- 展示启动、任务、中断、回调、状态机和关键调用关系；
- 结论显示源码位置、覆盖率、可信度、多定义和未知项；
- 关联运行轨迹、ELF、MAP 和可验证优化结果。

### 阶段 P1：知识、资料与经验沉淀

- 建立官方资料、通用经验和项目私有笔记的分层模型；
- 支持 Pack、SVD、SDK、头文件、启动文件、链接脚本和本地 PDF 的来源索引；
- 从真实故障调查生成带证据的经验条目；
- 记录症状、上下文、原因、诊断、解决、回退、复测和适用边界；
- 支持版本、失效状态、搜索、导入导出和本地隐私。

### 阶段 P1-A：适配器与协议工程

- 定义芯片、RTOS、工具链、MAP、协议、资料来源、探针和仪器的版本化适配器合同；
- 协议支持手工建模和导入，AI 草案仅为可选入口；
- 增加 PCAP/PCAPNG、TCP 流重组和协议版本比较；
- 适配器故障隔离，不影响独立工具和其他扩展；
- 每个适配器提供测试样本、能力边界和安全降级。

### 阶段 P2：需求驱动的硬件生态

根据真实用户、可获得硬件和验收样本增加 CAN/CAN FD、I²C、SPI、LIN、1-Wire、USB、RTT/SWO、功耗日志、逻辑分析仪和探针。每项扩展必须说明它验证的是主机侧、目标固件侧还是物理波形，具备真实设备、失败路径、资源限制、报告和独立入口，不能以工具数量作为目标。

```text
→ ELF 源码定位
→ MAP 版本变化
→ SVD 故障状态
→ 修复后回归和证据比较
```

## 12. 项目开发纪律

- 不回退已经完成的通信、工具、测试和数据能力；
- 串口主界面非必要不大幅调整；
- 新能力优先领域模型和适配器，不把业务逻辑写入页面；
- 浏览器工具保持独立，Local Agent 只增强本地权限；
- 外部输入有大小、条数、超时和取消上限；
- 未知格式安全降级并保留原始证据；
- 每次先运行专项测试，里程碑再运行全量测试、lint、生产构建和 Pages 校验；
- 验证通过后只提交相关文件，及时创建可回退 Git 检查点；
- 不提交日志、缓存、抓取页面、临时文件和无关构建产物；
- 节省 Token 不能成为跳过安全、兼容性、测试和备份的理由。

## 14. 当前最终结论

EmbedKit 不应发展成单纯的 AI 助手、协议解析器或网页计算器集合。正确方向是：

> 以真实嵌入式工程任务为中心，用网页提供独立工具和可选工作流，用 Local Agent 连接本地硬件，用确定性引擎执行和验证，用证据模型连接源码、设备、通信、测试、知识和报告；AI 仅作为可选外部增强。

近期最值得投入的能力不是继续增加孤立工具，而是完成：

```text
硬件 Provider 基础
→ I²C 真实工作台
→ SPI 真实工作台
→ SVD/驱动/寄存器验证
→ 网络抓包和协议工程
→ 多通道自动化测试闭环
```

当开发者能够从数据手册和源码出发，直接完成驱动草案、真实总线验证、问题定位、自动回归和报告归档时，EmbedKit 才真正实现“帮助嵌入式开发并提升开发效率”的目标。
